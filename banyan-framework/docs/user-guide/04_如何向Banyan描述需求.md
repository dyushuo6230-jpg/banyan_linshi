# 如何向 Banyan 描述需求

> 关键术语：Adapter（适配器：把编辑器请求转换为统一格式）；Preflight（执行前预检：动作前检查权限、风险、前置条件和证据）。

## 这篇解决什么问题

把一句模糊的“帮我改一下”变成范围清楚、可以检查且不会误改的请求。

## 什么时候需要看

新功能、Bug、排查、文档更新或只读审查开始前都适用。

## 核心概念

高质量请求至少包含：目标、范围、已有材料、约束、期望输出、是否允许修改。Scope（范围：允许处理的对象和边界）越明确，越容易区分事实、假设和需要人的 Decision（决策：对选项及影响作出的有效选择）。

## 推荐操作方式

按下面顺序描述：

1. 目标：完成后用户能看到什么变化。
2. 范围：允许读写哪些模块、目录或页面。
3. 已有材料：PRD、UI_SPEC、日志、截图、复现步骤、相关 Decision。
4. 约束：禁止项、兼容性、安全和时间要求。
5. 期望输出：分析、计划、代码、验证结果、文档或 commit plan。
6. 是否允许修改：只读、先规划再确认，或在明确范围内施工。

不确定的地方可以写 `UNKNOWN` 或 TBD（To Be Determined，待确定），不要让默认猜测悄悄变成事实。

## 自然语言示例

> 目标：修复登录失败后提示消失的问题。范围：只读检查登录页面、状态管理和相关测试；暂不修改。材料：复现步骤如下……约束：不改接口和权限。输出：原因、证据、候选方案、风险与测试计划。

> 我确认方案二。允许修改计划列出的三个文件，不允许改数据库、路由或 Git 配置。完成后运行相关测试并列出 leftovers。

## 当前实现状态

Banyan Framework 没有实现完整自然语言需求 parser / router。清晰请求是一种使用约定；受限 Adapter action、Preflight 和 Runtime permission evaluation 是已实现部分。

## 常见误区

- “顺便优化”会制造不受控范围，应拆成新请求。
- “可以改”应绑定目标和约束，不能当作无限授权。
- 给出截图不等于批准 UI_SPEC，也不等于后端需求事实。
