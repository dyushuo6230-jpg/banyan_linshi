# 多人研发与变更稿协作

> 关键术语：Decision（决策：对选项作出的明确选择）；Canonical Apply（正式真相应用：把批准变更应用到权威来源的治理过程）；Permission（权限判定：Runtime 根据 Policy 给出的结论）。

## 这篇解决什么问题

在多人同时开发时隔离草稿、对齐最新事实、收口决策，并避免多人修改同一 Canonical source 造成静默覆盖。

## 什么时候需要看

多人按模块、目录、独立需求或 Change 并行工作时。

## 核心概念

推荐按模块隔离、按目录隔离、按独立需求隔离或按 Change 隔离。Documentation Collaboration Role（文档协作角色：用于说明团队职责，不是 Runtime enum）包括：

- Implementation Owner（主要施工负责人）：协调实现和交付证据。
- Draft Contributor（变更稿贡献者）：在隔离范围贡献草稿。
- Reviewer（评审者）：检查提议、影响、证据和边界。
- Human Project Authority（人工项目权威决策方）：处理需要项目权威的治理决定；它是治理概念，不是 Runtime role enum。

`Role != Permission != Git Identity != Authentication`。

## 推荐操作方式

遵循治理流程：

`Draft Change Package → Pull Latest → Reconcile → Review → Human Decision → Canonical Apply → Archive Draft`

1. 每位贡献者在隔离的范围或 Change 中工作。
2. Draft Change Package 记录稳定 ID、来源、影响、Evidence 和未知项。
3. Pull Latest 后做 Reconcile（重新对账：把草稿与最新正式来源逐项比较）。
4. Reviewer 标记冲突、过期来源和缺少证据。
5. 由合适的 Human Authority 处理真正的取舍。
6. Canonical Apply 作为受治理步骤执行；当前没有一键 executable API。
7. 验证和对账完成后再 Archive Draft。

## 自然语言示例

> 我是这项工作的 Draft Contributor。只盘点我的 Draft 与最新 Canonical source 的差异，列出冲突和需 Reviewer 检查的项，不执行 Canonical Apply。

## 当前实现状态

协作角色是 Documentation Collaboration / Governance 概念，不是当前 Runtime role enum。Change、Draft promotion、Reconcile 与 Canonical Apply 主要是 frozen contracts；自动多人协作 executor 未实现。

## 常见误区

- Reviewer 身份不自动授予 Apply 权限。
- Pull Latest 不等于对账完成。
- 多人都能编辑文件不等于可以建立多份可写 Canonical truth。
- Git author 不能证明治理 Authority。
