# 总览相关文档编写方案

这是「给人看的白话说明」里 **总览** 这一夹的编写方案，不是需求真源。

总览是开会第一入口：15 分钟能讲清「两个产品线、五端、主链、钱、本期边界」。没有总览、直接丢模块或页面树，听的人会对不上。

落地目录（尚未写正文）：

```
docs/project/plain-document/doc-desc/总览/
```

---

## 1. 原先五篇够不够

原先建议是：

1. 项目总说明
2. 五端与角色
3. 主流程怎么走
4. 钱和券怎么算
5. 本期做什么和不做什么

这五篇方向对，但开会里还有两件反复撞车的事，五篇里都只顺口提一句：

- **名词**：众享营销 vs 众享源品、本地生活 vs 在线商城、业态 vs 类目、店铺池 vs 商城池。名称一混，后面所有模块都听岔。
- **怎么读这套说明**：总览 / 功能需求 / 分端页面 / 技术设计 / 架构图各看什么。不先说清，会把分端当成需求真源。

所以总览改为 **7 篇**：原五篇保留并收紧，再加「怎么读」和「名词对照」。不加第八篇「文档地图」——地图已经单独放在 `plain-document/doc-map.md`。

---

## 2. 必须遵守的编写规则

1. **单向同步。** 总览只摘已确认口径。新口径先进正式文档。
2. **总览不写细则。** 抽佣公式点到「看哪」就指向功能需求；菜单树指向分端；端口只指向技术设计里的部署篇。
3. **正文零编号。**
4. **每篇尽量一页，最多两页。** 总览一长，开会没人读。
5. **两个产品线贯穿每篇。** 不要写成「一个商城、一个后台」。
6. **待配置不编造指标。** GMV、转化率资料没给就不写。

---

## 3. 文件清单（7 篇）

```
docs/project/plain-document/doc-desc/总览/
├── 怎么读这套说明.md
├── 项目总说明.md
├── 名词对照.md
├── 五端与角色.md
├── 主流程怎么走.md
├── 钱和券怎么算.md
└── 本期做什么和不做什么.md
```

建议开会顺序就是上表顺序：先知道这套文档是投影 → 项目是什么 → 别叫错名字 → 五端 → 主链 → 钱 → 本期边界。然后再按需要进功能需求或分端。

---

## 4. 各篇写什么

### 4.1 `怎么读这套说明.md`（新增）

目的：防止把白话说明当成第二套需求。

要写：

- 这套是正式文档的可读投影，给人开会、交接、看全局。
- 改规则：先改正式文档，再刷白话。禁止只在说明里改口径。
- 四部分怎么选：

| 你想知道 | 去哪 |
|---|---|
| 项目是干什么的、本期做不做 | 总览 |
| 规则怎么转（审不审、抽谁的佣） | 功能需求 |
| 打开哪一页、表单填什么 | 分端页面 |
| 系统怎么拆、怎么部署、怎么测 | 技术设计 |
| 结构图、泳道图 | 架构图夹（后做） |
| 有哪些文件 | `doc-map.md` |

- 正文看不到需求编号是故意的。
- 未定项会写成「未定」，不要在会上当成已拍板。

不写：治理流程、阶段门禁、开发批次名单。

### 4.2 `项目总说明.md`

目的：一页讲清「这是什么项目」。

要写：

- 多租户、四业态（可增本地根），不是单店系统，也不是单用户系统。
- 两条产品线：到店的「众享营销 - 本地生活」；平台货架的「众享源品 - 在线商城」。
- 租户入驻后按业态进同一套租户后台。
- 平台不自己开自营店。
- 本期要把现有以餐饮为主的系统，扩成「本地生活可增根 + 在线商城」，并且登录安全一次过关。
- 不写端口、不写仓库目录名（那是技术）。

### 4.3 `名词对照.md`（新增）

目的：开会第一张「别叫错」表。比堆进总说明更不容易被略过。

建议用对照表，每行：口头容易说的 → 应该怎么叫 → 一句话。

至少覆盖：

| 别和这个混 | 应该怎么叫 | 一句话 |
|---|---|---|
| 本地生活 / 到店 / 店内小程序 | 众享营销 - 本地生活 | 某店自己的小程序，钱进该店账户 |
| 大厅 / 优选 / 商城 App / 共益优选 | 在线商城的顾客端（产品全称：众享源品 - 在线商城） | 多供应商货架，平台收款 |
| 四个 App | 四个业态根 + 一套后台 | 餐饮/美发/商超/在线商城是业态，不是四个后台 |
| 经营类目 | 业态树 / 入驻选的根 | 入驻选谁、本地抽佣看谁 |
| 平台类目 | 商品分类树 | 商城发品挂叶子，计佣看一级 |
| 店铺池 / 商城池 | 两个用户池 | 同一手机可以是三个号 |
| 商家端、商家 App（禁止再写） | 租户后台，或本地生活小程序的店员页 | 不是同一个入口，也不是两个产品 |
| 附近 | 店内周边 vs 众享源品附近 | 筛选规则不同 |

写完应能让人自己检查：刚才说的「商城」到底是哪一端。

### 4.4 `五端与角色.md`

目的：谁用哪一端，不要五端和角色各写一张对不上的表。

五端：

1. 平台后台
2. 租户后台（一套，四套菜单）
3. 租户入驻 H5
4. 众享营销 - 本地生活
5. 众享源品 - 在线商城（多端同一套）

角色至少：平台运营、入驻申请人、餐饮/美发/商超租户、在线商城供应商、本地生活消费者、众享源品用户、推广员（现状、本期不改造）、租户子账号（仅本地生活）。

要点：

- 在线商城供应商无独立小程序。
- 店员出餐/核销在本地生活小程序里，不是另一套独立 App。
- 同一手机三账号。

### 4.5 `主流程怎么走.md`

目的：一条主链，从入驻到钱。分支用短列表，不在总览里展开核销天数。

建议结构：

```text
入驻选业态
  → 平台审核
  → 套该业态菜单
  → 本地生活：店内发品（不审）→ 扫桌或核销 → 付到店
  → 在线商城：挂类目送审 → 众享源品可售 → 付给平台 → 按一级抽佣结算
```

再补三句分流：

- 餐饮扫桌；美发/商超核销。
- 本地店内券；众享源品平台券。
- 登录分池；认店只约束本地生活。

细则指向功能需求对应篇。

### 4.6 `钱和券怎么算.md`

目的：抽佣和券是最容易在模块里被讲散的，总览必须有专页。但只写「看哪、空怎么办」，不写死费率。

要写：

- 本地收到店账户；商城平台收款后再结给供应商。
- 抽佣看节点：本地看业态根，商城看商品一级类目。
- 下单时快照。空或 0 = 该新单不抽佣。未挂一级不是「按 0 抽」，而是不可售。
- 给人看用元。
- 券：店内券 vs 平台券，供应商不发店券。
- 本轮众享源品不真扣款，不等于没有订单和结算链路。

不写：通道商户号、手续费死数字。

### 4.7 `本期做什么和不做什么.md`

目的：验收线和「敬请期待」不要散落在各模块才第一次出现。

要写 **做**：

- 业态可入驻、一套后台按模板工作。
- 本地生活履约闭合（扫桌/核销，能闭口就闭口）。
- 入驻、平台后台、租户后台其余功能开发完成并闭口。
- 众享源品：前端接口先做到可打包、够申请支付；登录和「我的」登录态；不强制绑微信。
- 登录安全五条。

要写 **明确不做**：

- 外卖。
- 在线商城拼团秒杀。
- 众享源品 AI / 发现对接（页面可留）。
- 真扣款（本轮）、部分退、退货物流。
- 新地址表、类目正式名单、根费率死数字。
- 平台自营店。
- 推广员/小魔推改造必验。

要写 **页面还在但不验收**：附近/AI/发现默认 Tab 可不露出；资产类敬请期待。

量化运营指标：资料未给，写未定，不要编 KPI。

---

## 5. 优化时故意砍掉的

这些不要塞进总览：

- 每个模块的优先级表（那是正式需求目录的事，白话里用「先闭口主链」即可）
- 开发批次列表、未合主分支进度
- 菜单点名全表（分端）
- 部署域名全表（技术设计部署篇）
- 「阅读说明」和「怎么读」不要拆成两篇 —— 只保留 `怎么读这套说明.md`

---

## 6. 建议首批

总览 7 篇可以一次写完，因为短、且后面所有模块都依赖它们。建议顺序：

1. 怎么读这套说明
2. 项目总说明
3. 名词对照
4. 本期做什么和不做什么
5. 五端与角色
6. 主流程怎么走
7. 钱和券怎么算

先立边界和名词，再写流程和钱，避免主流程里夹带未定费率。

---

## 7. 写完后的自检

- 7 篇都能在会上单独投影，不依赖读者先读过决策单。
- 「众享营销」和「众享源品」在总览里一次都没有用反。
- 端口、表名、需求编号为零。
- 《本期做什么》和功能需求、分端里的「敬请期待」没有互相打架。
- 《钱和券》没有写死未配置的费率。
- 《怎么读》明确说了：说明不能当开工依据。
