# plain-document 文档地图编写说明

对应落地文件：`docs/project/plain-document/doc-map.md`（尚未按本文落盘）。

本文说明地图**怎么写、写什么、和总览《怎么读这套说明》怎么分工**。文件清单以同目录编写方案为准；不要各改各的。总树以 `白话文档总体编写规划.md` 为准。

---

## 1. 地图干什么

`doc-map.md` 是给人看的**目录 + 用法**，不是第二份需求，也不是第二份「怎么读」。

| 文件 | 管什么 |
|---|---|
| `doc-map.md` | 有哪些文件、怎么挑夹、统计多少、目录长什么样 |
| 总览 → `怎么读这套说明.md` | 这是投影、不能当需求改；改规则走正式文档 |
| `architecture-diagram/图怎么读.md` | 静态图 / 泳道 / 时序怎么看，不替代地图 |

地图顶部只留一张「你手里的问题 → 先打开」。不要在地图里再写一篇治理说明，否则和《怎么读》抢篇幅。

---

## 2. 必须遵守

1. **正文零编号。** 不写需求号、决策号、变更号。用目录和中文文件名。
2. **统计用目录和中文名。** 数量随正文落地改「计划中 / 已同步」，不写开发批次、不写未合主分支。
3. **每篇、每张图只一行职责。** 细则分别在各编写方案里。地图一变厚，没人当目录用。
4. **单向同步。** 清单改了：先改编写方案和总体规划，再改地图，再改 `doc-desc` / `architecture-diagram`。不要只改地图。
5. **架构图按完整清单登记。** 不再写「后做、0 张」。未画的标「计划中」，不要编造指导文档里本期没有的图（积分、退货物流、真扣款成功）。
6. **待配置不编造。** 未写正文的篇标「计划中」，不要写成已发布。

---

## 3. 固定结构

地图正文按这个顺序：

1. **这套是什么** + 问题选夹表  
2. **文档架构**（完整目录树 + 五部分怎么分工）  
3. **统计表**  
4. **各夹文件一览**（文字说明每篇一行；架构图每张一行）  
5. **三种读法**

后面可接：这里没有的、同步约定。不要再加模块细则、表单字段、端口列表、泳道步骤。

# 文档地图

这套说明放在 `docs/project/plain-document/`，给人开会、交接、看全局。

它是正式需求和技术文档的可读译本，不是第二套需求。改规则先改正式文档，再按批同步到这里。正文用业务语言：哪一端、哪个菜单、订单变成什么。

| 你手里的问题 | 先打开 |
|---|---|
| 这套说明能不能当需求改？怎么选夹？ | 总览 → 怎么读这套说明 |
| 项目是干什么的、两个名字别叫混 | 总览（其余六篇） |
| 审不审、抽谁的佣、订单变成什么 | 功能需求 |
| 打开哪一端、哪一页、表单填什么 | 分端页面 |
| 系统怎么拆、怎么部署、怎么测 | 技术设计 |
| 投屏看边界、谁在哪一步、会不会串 | 架构图 → 图怎么读 |
| 一共有哪些文件 | 本文 |

## 1. 文档架构

```
docs/project/plain-document/
├── doc-map.md                          本文：用法 + 目录 + 统计
├── doc-desc/                           全部文字说明（中文文件名）
│   ├── 总览/                           15 分钟看懂项目
│   ├── 功能需求/                       按业务怎么转
│   ├── 分端页面/                       按端、按菜单、按页面
│   └── 技术设计/                       按系统怎么落地
│       ├── 横切/                       拆分、账号、钱、部署、测试
│       └── 能力怎么落地/               业态、商品、履约、拼团、订单
└── architecture-diagram/               架构图（静态 + 场景泳道/时序）
    ├── 图怎么读.md
    ├── 静态架构/                       上下文、应用、数据、部署
    └── 场景流程/                       按业务场景分夹，不按用户/租户/平台三大夹切
```

五部分不重复写同一件事：

| 夹 | 切法 | 适合 |
|---|---|---|
| 总览 | 项目级 | 开会开场、对名词、对边界 |
| 功能需求 | 一条业务能力 | 对口径、对流程 |
| 分端页面 | 端 → 菜单 → 页面 | 对着屏幕走功能 |
| 技术设计 | 进程、隔离、部署、测试 | 开发、测试、运维交接 |
| 架构图 | 结构 + 场景 | 投屏看边界和泳道；时序只看会串的调用顺序 |

规则只在功能需求写全。分端点到规则时一句话指向功能需求。端口和域名只写在技术设计的《部署与环境》和架构图《部署架构》。图是说明的配图，不另起一套需求。

## 8. 三种读法

**开一场 15 分钟的会**  
总览七篇按顺序。需要投屏时打开静态《系统上下文》或主链一张泳道。不够再点一篇功能需求或一端子文档。

**对着产品走菜单**  
先看《五端与角色》，再打开对应分端文档。规则疑问跳功能需求，不要在分端里改口径。流程对不上时看对应场景泳道。

**开发和测试交接**  
技术设计：系统怎么拆 → 两套 C 端 → 部署与环境 → 测试怎么做。图看《部署架构》和《两套登录隔离-时序》《两种支付回调-时序》。域名和端口只认部署那一篇文字和那一张图。

## 9. 这里没有的

正式需求、决策、变更单、接口说明书、数据字典、工作日志、待确认问题——那些在正式文档夹。本夹不翻译成「白话决策单」。

仓库里还在、本期不验收的页面（例如在线商城的顾客端 AI/发现、部分资产入口），分端会写「页面在、不必验」，总览《本期做什么和不做什么》会点名，避免会上当成已上线。

`docs/temp/文档计划/` 里的编写方案不是开会包，不进本夹。

---

## 10. 同步约定（给人看的版本）

- 只同步已经确认、并且本批已经碰到的模块、页面和图。
- 未定就写未定，不编费率、不编菜单、不编没有的流程。
- 开发告一段落，以当时已落地的页面和菜单为准刷说明和图；若和正式口径不一致，先改正式文档，再改这里。
