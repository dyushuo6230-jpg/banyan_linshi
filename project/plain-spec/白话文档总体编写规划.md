# 白话文档总体编写规划

对应落地根目录：`docs/project/plain-document/`（规划已定，目录和正文尚未按此落盘）。

本文是总规划：这套白话说明是什么、完整树长什么样、怎么分工、怎么同步、按什么批次写。各夹怎么写正文，分别看同目录这几份，**三处不要各改各的**：

| 文件 | 管什么 |
|---|---|
| 本文 | 总树、分工、批次、总规则 |
| `总览相关文档编写方案.md` | 总览 7 篇写什么 |
| `功能需求相关文档编写方案.md` | 功能需求 14 篇写什么 |
| `分端页面相关文档编写方案.md` | 分端 6 本标题树和细度 |
| `技术设计相关文档编写方案.md` | 技术设计 14 篇写什么 |
| `架构图相关文档编写方案.md` | 架构图 29 份画什么、先画哪批 |
| `plain-document文档地图编写说明.md` | `doc-map.md` 怎么写 |

改清单：先改对应编写方案 → 再改本文的树和统计 → 再改 `doc-map.md` → 最后改 `doc-desc` / `architecture-diagram` 文件。

## 1. 这套文档是什么

给人开会、交接、看全局的可读译本。正式口径仍在 `docs/project/prd/`、`baseline/`、`changes/`、`architecture/`、`design/`。

| 项 | 约定 |
|---|---|
| 是 | 已确认规则 + 当时已落地事实的投影 |
| 不是 | 第二套需求、开工依据、决策单、接口说明书 |
| 读者 | 老板、业务、测试、开发交接 |
| 语言 | 中文文件名；哪一端、哪个菜单、订单变成什么 |
| 编号 | 正文零编号。编号只留在真源 |

四块文字 + 一套图：

| 夹 | 切法 | 回答 |
|---|---|---|
| 总览 | 项目级 | 干什么、名词、五端、主链、钱、本期边界 |
| 功能需求 | 业务怎么转 | 审不审、抽谁的佣、订单变成什么 |
| 分端页面 | 端 → 菜单 → 页面 | 打开哪一页、表单填什么 |
| 技术设计 | 系统怎么落地 | 怎么拆、怎么隔离、怎么部署、怎么测 |
| 架构图 | 结构 + 场景 | 投屏看边界和泳道 |

同一件事不两处写全：规则只在功能需求写全；分端点到即指向功能需求；端口只在技术设计《部署与环境》和架构图《部署架构》。

## 2. 必须遵守

1. **单向同步。** 会上新口径先改进正式文档，再刷白话。禁止「说明里改了规则、代码按说明做」。
2. **按批同步，禁止整夹重生。** 只改本批碰到的总览段落、模块、页面和图。
3. **正文零编号。**
4. **待配置不编造。** 未定写未定。费率死数字、类目正式名单、支付字段清单不编。
5. **以落地事实校正页面和部署。** 规则跟已确认口径；Tab 露出几个、哪张是现用页、本机接哪套，跟当时已落地。
6. **两条产品线贯穿。** 众享营销 - 本地生活 vs 众享源品 - 在线商城。不要收成一个用户、一个租户、一个商城。
7. **隐藏菜单不是安全边界。** 分端写「看不见」；技术设计必须写直访仍要拦。
8. **本轮事实和目标态分开。** 众享源品不真扣款用「按钮保留 / 虚线留口」，不写成已经扣成功。
9. **3.1 维护。** 同步提示写进 3.1：只同步已确认规则、不编造待配置、不把说明升格成 PRD。真源对照留在 3.1，不进开会包。
10. **架构图密度。** 流程图和泳道每个框必须是完整业务话（谁、变成什么、钱或权限落到哪、无此路径），禁止空标题框。时序用人话、不写接口参数。静态图框和箭头必须有人话含义。

## 6. 各夹写法要点（细则看分册）

**总览**  
每篇一页、最多两篇。先《怎么读》和《名词对照》，再主链和钱。不写端口、不写菜单全表。

**功能需求**  
每篇 1～3 页，固定：干什么、谁用、主路径、关键规则、变成什么、不做/未定、和谁交接。  
抽佣只在《业态经营类目与抽佣》写全。附近两边规则只在《周边与到店服务》写全。  
《平台运营与现码保留》保持薄，避免把未定写成已定。

**分端页面**  
每一级标题下都有说明；重要细点单独成四级标题。  
租户后台：本地生活一本 + 对照表，禁止餐饮/美发/商超三份全文；在线商城单独一本。  
店员出餐/核销写在《众享营销-本地生活》，不写进租户 Web。  
现码复制菜单占位「有、沿用」；P0 页才写到字段级。

**技术设计**  
横切讲隔离和部署；能力五篇不超过两页，不重写功能规则、不译正式设计成带表结构的白话。  
端口只出现在《部署与环境》。

**架构图**  
静态 4 张全局唯一。泳道按场景夹，不按用户/租户/平台三大夹切。  
登录、发品、支付都按两条产品线拆。时序不写参数。  
众享源品支付用虚线留口。指导文档里的积分、退货物流、统一扣款成功不画。

## 7. 建议批次（先闭口，不一次写 71 份）

骨架可以一次定齐（空目录或空标题），正文和图按批填。

**第零批：能开张地图**

- 建 `plain-document/` 目录树（可先空文件）
- `doc-map.md`（按地图编写说明第 5 节落盘，状态列「计划中」）

**第一批：能开会**

- 总览 7 篇（短，一次写完）
- 功能需求主链：业态抽佣、入驻审核、商品审核、本地履约、订单支付结算、众享源品逛买、用户池、登录
- 分端：入驻、平台审店/审品相关页、本地生活履约页、众享源品首页/详情/下单/我的、登录
- 技术设计：系统怎么拆、两套 C 端、部署与环境、账号登录、支付资金、测试怎么做
- 架构图：图怎么读、静态 4 张、入驻泳道、两套登录 + 隔离时序、商品两张泳道、扫桌/核销、在线商城的顾客端下未付单与关单、付到店、两种回调时序、两套结算、商城发货确认收货

**第二批：补齐规则和差异**

- 功能需求：优惠券、周边与到店服务、售后与退款、拼团与秒杀、租户后台与菜单、平台运营薄说明
- 分端：两本租户后台其余菜单占位加厚、平台其余侧栏
- 技术设计：数据快照、权限菜单、安全边界、能力落地五篇
- 架构图：整单退款、真评价、拼团、优惠券、周边 CPS；时序补入驻套菜单、商城审品、核销

**不进本期白话必做**

- 把每个决策翻译成一篇
- 接口全文、数据字典、工作日志
- AI/发现对接流程、外卖、商城拼团、真扣款成功路径、部分退/退货物流细图
- 为完整而写未落地的页面和未点名菜单

## 8. 和正式文档、3.1 的关系

```
正式文档（prd / baseline / changes / architecture / design）
        │  单向摘译
        ▼
plain-document（总览 / 功能需求 / 分端 / 技术设计 / 架构图）
        │
        ✕  禁止反写
        ─  会上新口径不得只改这里
```

开发批次结束、已确认改动已进正式需求之后：只刷本批碰到的白话篇和图。  
3.1 加「从真源生成/同步对外说明」：只同步已确认、不编造待配置、说明不得升格成 PRD。

## 10. 落盘后的自检

- 树与本文第 3 节、`doc-map.md`、各编写方案清单一致。
- 没有文档编号出现在 `plain-document` 正文和图上。
- 抽佣、附近/CPS、两类券没有在多篇里各写一套互相打架。
- 餐饮/美发/商超没有复制成三套功能需求或三套租户后台全文。
- 端口只出现在部署文字和部署图。
- 「计划中」没有被写成已上线；未合主分支没有写成生产已如此。
- 改规则的路径仍是：正式文档 → 功能需求白话 → 分端/图，而不是反过来。
