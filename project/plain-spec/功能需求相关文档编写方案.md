# 功能需求相关文档编写方案

这是「给人看的白话说明」里 **功能需求** 这一夹的编写方案，不是需求真源。

它按 **业务怎么转** 切：谁抽佣、谁审核、订单变成什么。开会问「规则」时看这里；问「打开哪一页」时看分端页面。

落地目录（尚未写正文）：

```
docs/project/plain-document/doc-desc/功能需求/
```

---

## 1. 这套文档干什么

| 项 | 约定 |
|---|---|
| 回答什么 | 这个能力干什么、谁用、主路径怎么走、关键规则、会变成什么、明确不做 |
| 不回答什么 | 侧栏第几项、按钮文案、表单逐字段（分端页面）；类名、端口、表结构（技术设计） |
| 切法 | 对齐现有正式需求模块，用中文名，不带模块号 |
| 读者 | 对口径、对流程、对验收边界的人 |

和分端页面的分工：同一件事两处都写全一定会漂。规则写在本夹；页面里只留一句 + 指向本夹对应文档。

---

## 2. 必须遵守的编写规则

1. **单向同步。** 只从已确认产品口径摘译。会上新口径先进正式文档，再刷本夹。
2. **按批同步。** 只改本批碰到的篇，禁止 14 篇整夹重生。
3. **正文零编号。** 编号留在真源。本方案为方便编写可对照正式模块，正文禁止出现。
4. **待配置不编造。** 未定就写「未定」。
5. **每篇 1～3 页。** 写到 5 页说明在抄正式需求，应删或拆。
6. **不搬逐条验收。** Given/When/Then、需求清单留在真源。
7. **跨模块的规则只在一处写全。** 另一处一句话指向，避免抽佣在三篇里各说一遍。

---

## 3. 每篇固定骨架

```markdown
# 中文标题
三句话：这个模块干什么。

## 谁用、在哪一端
角色 + 端 + 菜单/页面（点到为止，细节留给分端）。

## 主路径怎么走
步骤。最好能配以后的泳道图。

## 关键规则
人话。不拿字段名当规则。

## 会变成什么
订单状态、可售/不可售、是不是同一个人。

## 明确不做 / 未定

## 和谁交接
例如商品 → 订单，入驻 → 菜单。

## 落在哪一端
一小节。不展开类名、表名。
```

## 4. 文件清单（14 篇）

原先按正式需求 12 个模块对成 10 本专册 + 1 本薄说明，会漏三块开会必问、且跨多模块的规则：券、周边/CPS、售后。这三块若只塞进「订单」或「平台运营」，不是太肥就是太薄。

故定为 **11 本专册 + 3 本补册**，不把平台运营/推广员写成和入驻同等厚度。

## 5. 各篇写什么

### 5.1 `业态经营类目与抽佣.md`

- 种子四根 + 本地根可增；拷贝源只有餐饮（扫桌）或美发/商超（核销）；不发明第四种履约。
- 「入驻可选」控制能不能被申请人选到。
- 老店无业态默认餐饮。
- 抽佣权威在节点：本地看业态根，在线商城看商品所属平台类目一级。
- 在线商城发品必须挂叶子，计佣仍向上取一级。经营类目不再挂子节点。
- 空或 0 = 新单不抽佣。未挂一级不可售、不可下单。停用后已上架不可再售，已下单不改快照。
- 入驻多选一级只表示可售范围，不把费率平均到店铺。
- 费率死数字、类目正式名单：未定，不编造。

指向：入驻、商品、订单都不要重写抽佣全文。

### 5.2 `租户入驻与审核.md`

- 全业态同一套入驻 H5。
- 执照沿用现页；在线商城强制 1～3 个启用中的一级；本地不选下级。
- 无「是否自营」。
- 待审/已通过同手机不能再提；驳回只能提新单。
- 存量待审不猜业态，通过前补选。
- 通过后按业态套菜单。

### 5.3 `租户后台与菜单.md`

- 一套后台，不是四个产品。
- 四套模板同一配置页；新本地根克隆页签。
- 「无」= 删行；隐藏只用于小魔推，不是安全边界。
- 在线商城有店铺资料、无员工/角色；无装修、无拼团秒杀。
- 对照表用文字说清，细菜单树留给分端。

### 5.4 `商品类目与审核.md`

- 本地：店内分类，上架即可本店可售，平台不审。
- 在线商城：平台类目叶子 + 送审，通过后众享源品可售。
- 品牌可选不强制。
- 审核台不拆，只办理在线商城。
- 编辑后是否重审：未定则写未定。

### 5.5 `本地生活怎么履约.md`

- 有独立小程序。一套首页，模块按「首页模块归属」。
- 履约跟拷贝源：餐饮扫桌；美发/商超核销。
- 出餐或核销成功 → 已完成，跳过待评价。
- 整单一次核销；无天数、无过期自动退。
- 全额退后核销码作废、不补第二张主码。
- 不做外卖。
- 周边/CPS 本篇只点到，细则在《周边与到店服务》。

### 5.6 `拼团与秒杀.md`

- 仅本地生活。租户自发布，平台不审、不建场次。
- 在线商城菜单没有这能力。
- 待审历史改未上架。停用后不可新参，已下单不自动退。
- 拼团不另出核销码。餐饮拼团仍扫桌。

### 5.7 `众享源品怎么逛买.md`

- 货源来自在线商城业态租户。无独立小程序。
- 平台统一收款（本轮不真扣款，按钮保留）。
- 页面前端接口先做到可打包、可申请支付；后台与其余功能能闭口就闭口。
- 推荐双轨、地址复用、协议分业态。
- 真评价；购物/加购本轮可敬请期待。
- AI/发现：页面可留，不对接、不必验。
- 底部栏现码只露购物、我的——页面事实写一句，细则在分端。

### 5.8 `用户账号与用户池.md`

- 同一手机：店 A 小程序、店 B 小程序、众享源品 = 三个号。
- 认店只约束本地生活。
- 存量用户一律店铺池。
- 平台用户列表是否拆两个菜单：未定。

### 5.9 `登录会话与口令.md`

- 验收五条：忙不踢、闲必踢、退出/改密立刻作废、不能串店、库无明文密码。
- 网页 Cookie+CSRF；小程序 Header。
- 众享源品：短信或账密，不强制绑微信。
- 本期不做：短信二次验证、设备列表、异地提示、加密 JWT、C 端 30 分钟闲置等。

### 5.10 `订单支付与结算.md`

- 本地：付到该店账户。
- 商城：付给平台，再按一级类目快照抽佣结算。
- 订单主状态：无 40；确认收货即完成。
- 未付超时：打开列表/详情或去支付立刻关单；定时仍留。未付页要有倒计时。
- 本地佣金只对账，禁止假入账。
- 金额给人看用元，库内仍为分——点到即可，技术细节在技术设计。
- 售后细则指向《售后与退款》，本篇只写支付与主状态。

### 5.11 `优惠券.md`（补）

单独成篇的原因：店内券和平台券是两类生意，写进订单或商品都会被读漏。

- 本地生活各店发店铺券，仅本店用。
- 众享源品只用平台券。
- 供应商不发店铺券，租户后台无该菜单。
- 不把两类券互相当可用。
- 门槛、叠加、过期等未点名沿用现页，不编造。

### 5.12 `周边与到店服务.md`（补）

单独成篇的原因：两边都有「附近/CPS」，规则相反，最容易写串。

- 本地生活：按**本店已勾本地业态**展示周边；CPS 引用平台目录且本店上架。
- 众享源品附近：筛**当前全部本地业态根**（平台级），与某供应商勾选无关；CPS 不传某供应商。
- 平台维护一份 CPS 目录；无行=下架；平台下架则两端都不出。
- 无周边分类管理。
- 在线商城供应商无独立小程序、无周边菜单。
- 跳转第三方小程序：平台填 appid+path；店内 extraData 带店铺信息；商城侧只带来源标记。

### 5.13 `售后与退款.md`（补）

单独成篇的原因：订单篇已经要讲支付、状态、倒计时、结算；售后还有「平台不介入、部分退不做」。

- 售后仅已确认的办理范围。
- 平台售后只读，无「平台介入中」、无仲裁办理。
- 部分退、退货物流本期不做。
- 全额退后：本地核销码不可再核。
- C 端申请入口：本地现用订单页；众享源品订单/售后页。

### 5.14 `平台运营与现码保留.md`（薄）

不要写成和入驻同等厚度。只写：

- 平台轮播菜单保留，众享源品首页读取；没数据不轮。
- 两套协议分开维护。
- 首页模块归属（点到，细则在本地生活履约）。
- 推广员、小魔推：现码保留，本期不改造、不纳入必验。
- 参数配置里支付/商城字段清单未定。
- 其余待配置运营能力不编造成功能。

---

## 6. 不写进本夹的

- 决策单、变更单的白话版
- 接口、表、类名
- 每个页面的按钮树（分端）
- 工作日志、看板、待确认问题清单（开会一念就变已定）

## 8. 写完后的自检

- 没有文档编号。
- 抽佣只在《业态经营类目与抽佣》写全。
- 附近/CPS 两边规则没有写串。
- 券没有写成「全场通用一张券」。
- 平台运营没有把推广员写成必验。
- 每篇都能用「谁、哪一端、怎么走、变成什么」讲完，不依赖菜单截图也能听懂。
