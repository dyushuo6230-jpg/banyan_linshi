本文件是 G8 **Approved**（ADR-031）。已 **Baselined**（TECH_BASELINE=v0.1.5）。不能当作已开工。不改业务代码。不创建 `app/mall-online`。REST 路径与表结构以日后 `api/`、`database/` 为唯一真源；本文只给逻辑模型。G6 架构已 Approved（ADR-040），仅引用。`tree.md` 已 Approved，只读引用，不改树口径。待配置保持 TBD，批准后也不得编造。

## 1. 范围

| 项 | 口径 |
|---|---|
| 职责 | 全业态同一入驻 H5；按业态采集；平台审店；过审绑定业态；在线商城还绑定可售一级；无业态老店迁餐饮 |
| 非职责 | 不拥有树与节点费率（`tree`）；不配置四套菜单模板（merchant 暴露面）；不签发/作废入驻票（`auth-session`）；不拥有推广员（`promotion` 只注入）；不发品（`goods`）；不写下单快照（`trade`） |
| 暴露面 | 申请：入驻 H5（静态页 + mall 现码入驻接口所在进程，路径不改产品）。审店：仅 admin |
| 稳定 ID | `onboarding`（ADR-017） |

业态代码与 `tree` 一致：`catering` / `hair` / `supermarket` / `online-mall`。禁止「到店」当业态。禁止把 `is_self` 当身份。

## 2. 组件

| 组件 | 位置（逻辑） | 职责 |
|---|---|---|
| ApplyCommand | 入驻提交所在进程 | 校验入驻票、读树、落申请；拒绝自营问项；拒绝写树 |
| ApplyQuery | H5 / admin | 申请人看本单；平台看待审列表与详情 |
| AuditCommand | admin | 通过 / 驳回；通过则开户、绑业态/一级、触发套菜单 |
| BindingStore | 共库 | 店铺业态与可售一级的权威 |
| LegacyMigrate | 实施一次性 | 无业态老店写成餐饮；`is_self=1` 仍迁餐饮 |
| TicketGate | 提交前 | 向 `auth-session` 校验入驻资格；本模块不发票 |

进程间无同步 RPC。推广员 `sales_id` 由 `promotion` 现码注入申请行，本模块不改推广规则、不改审核状态机给推广员开后门。

## 3. 调用流程

### 3.1 申请（同一套 H5）

1. 申请人持入驻票打开同一入驻 H5（REQ-010）。票无效/过期：不能提交，须按现码重新获取资格（REQ-083）。票面无手机号由 `auth-session` 保证；本模块只拒绝无效票。
2. ApplyCommand 只读 `tree`：列出四根。选业态必填。
3. 餐饮 / 美发 / 商超：不展示经营类目下级多选。即使树上误挂了子节点，本模块忽略。
4. 在线商城：列出该根下 **enabled** 的一级。必须选 **1～3 个**（DEC-032）。多选只表示可售范围，**不**平均费率到店（DEC-001）。
5. 不采集「是否自营」。众享源品 - 在线商城侧若仍出现该问，同样去掉（REQ-012、DEC-006）。
6. 资质：沿用当前 mall 入驻页营业执照采集（DEC-032）。不新编分业态证件清单。不把身份证/行业许可证升格必填。
7. 提交失败保留已填项（REQ-003）。待审/已通过同手机不能再提；驳回后只能提新申请（DEC-043）。网络失败：现码已有幂等则沿用。
8. 提交成功 → 待审。记录业态与（若有）一级 ID。不再把 `merchant_category` 当入驻主数据。

### 3.2 平台审核

1. admin 待审列表 / 详情：展示业态；在线商城展示已选一级。无自营问项。
2. 通过：同一事务内（本进程本库）生成/启用一户租户、写下绑定、触发按业态套菜单。结果仍是一户；重复点通过不得生成第二套店。现码若已有「一申请一店」则保留；资料未写的双开细则 **TBD**，不得另发明规则。
3. 驳回：写原因；申请人不能当已入驻租户用后台。旧申请带自营答案：不作为身份，也不据此改业态。
4. 模板未配置：不得假装套成功（REQ-014）。套哪套模板写入审计。菜单模板内容不在本模块维护。
5. 开户主账号口令：只亮一次、不落明文，属 `auth-session`（REQ-080）。本模块触发开户，不设计口令存储。

### 3.3 过审后的绑定（给只读方）

| 只读方 | 读什么 | 本模块不做什么 |
|---|---|---|
| merchant 菜单 | 店铺业态代码 → 套对应模板 | 不编辑四套模板 |
| `goods` | 在线商城店的可售一级 ID 列表 | 不审品、不拦截未挂一级商品（DEC-013 在 `goods`/`trade`） |
| `trade` | 店铺业态根（本地生活计佣用树节点费率时，业态身份从本绑定读） | 不写订单快照 |
| `tree` | 无写 | 本模块永不写树 |

供应商不能自改可售一级。平台可改绑定。改完后不在新绑定内的货按 DEC-035：不可再售、不改商品行、不自动迁货（DEC-044）。

节点停用后：绑定留下、不静默删。该一级不能发新品；已上架不可再售（DEC-035）。再启用后绑定还在（DEC-044）。

### 3.4 无业态老店迁移（DEC-011）

上线迁移：没有业态的老店业态写成 `catering`，套餐饮模板。`is_self=1` **不**迁成在线商城。本模块写店铺绑定；餐饮根须已存在（`tree` 种子）。改业态操作细则、核销补偿 **TBD**，本文不写。

## 4. 状态机

申请（沿用现码，PRD 不重定义枚举名）：

```text
pending  →  approved
pending  →  rejected
```

现码：`0` 待审 / `1` 通过 / `2` 驳回。无独立持久化草稿则提交即 `pending`，H5 未提交内容可留在客户端，不发明第四态。

通过后店铺可经营。驳回后不能经营。不允许：待审经营、把驳回当通过、把自营勾选写成业态。

## 5. 逻辑数据（不冻结 DDL）

现码：`merchant_apply.merchant_category_id` 指向扁平 `merchant_category`；无业态列；`sales_id` 推广员；`status` 待审/通过/驳回。`merchant` 无业态，有 `commission_rate`、`is_self`。

目标逻辑：

| 实体（逻辑） | 权威 | 关键字段（逻辑） | 备注 |
|---|---|---|---|
| Apply | 本模块 | 业态代码；在线商城已选一级 ID 列表；sales_id（注入）；联系人；status；驳回原因；通过后 merchant_id | `merchant_category_id` 不再作主数据 |
| MerchantBinding | 本模块 | merchant_id；业态代码；可售一级 ID 列表（本地生活为空） | 过审或迁移后的店铺身份 |
| 资质快照 | 本模块 | 提交时采集副本 | 字段清单 TBD，不把现码执照列写成已确认必填 |

不在本模块存：树节点费率、菜单模板 JSON、入驻票私钥、商品挂点、订单快照。新单抽佣不以店铺 `commission_rate` 为权威。新单不写有业务含义的 `is_self=1`；列可留默认 0。

| 通过 | 平台 | 同一申请只开一户 |
| 驳回 | 平台 | 是 |
| 读店铺业态与可售一级 | `goods` / `trade` / 菜单套用 | 是 |
| 无业态老店迁餐饮 | 实施 | 已是餐饮则跳过 |

不在本文写具体 URL。网页后台 Cookie+CSRF（DEC-005）。入驻 H5 票校验走 Header/现码入驻通道，细节属 `auth-session`。

## 7. 事务、并发、一致性

| 场景 | 口径 |
|---|---|
| 通过 | 开户 + 写绑定 + 记套用模板 同一本地事务。失败全回滚，申请仍待审 |
| 套菜单 | 模板缺失则整笔失败。不跨进程分布式事务 |
| 并发双击通过 | 以申请 ID 互斥或状态条件更新；第二下看到已通过，不建第二户 |
| 与树 | **无**写树。提交时读到的一级 ID 写入申请；之后树改名不影响已记录 ID |
| 与推广 | 只存 `sales_id`。`promotion` 不得改 status |
| 补偿 | 无消息队列要求（ADR-005）。口令亮一次失败不在本模块用队列重发明文 |

## 8. 权限、安全、审计、异常

| 项 | 口径 |
|---|---|
| 提交 | 有效未过期入驻票。无票或废票失败 |
| 审核 | 仅平台运营。租户不可审自己。菜单隐藏不是安全边界 |
| 读绑定 | 后台按店；C 端不暴露未通过申请 |
| 审计 | 提交：业态、一级、时间。审核：人、时间、结果、套用了哪套模板。迁移：哪些店写成餐饮 |
| 拒绝 | 第五业态；自营问项；本地生活提交下级类目作为必选；租户写树 |
| 隐私 | 日志不出现完整入驻票（REQ-083）。口令不回读 |
| 重试 | 读可重试。审核冲突返回已处理结果 |

## 9. 性能、灰度、回滚、测试

| 项 | 口径 |
|---|---|
| 性能 | 申请量远小于订单。无特殊缓存要求。量化 SLA **TBD** |
| 灰度 | 新申请只认树根 + 本绑定。旧 `merchant_category` 可留兼容只读，不作新申请主数据 |
| 回滚 | 回退本模块代码。已通过的绑定保留。不把 `merchant_category` 恢复成新申请权威 |
| 测试 | 四业态同一 H5；本地生活无下级必选；在线商城可记录多个一级且不平均费率；无自营问项；通过套对应模板；无业态老店迁餐饮且 `is_self=1` 不迁在线商城；重复通过仍一户；无效票不能提交 |

Given/When/Then（设计级）：

- Given 美发申请人打开入驻；When 开始申请；Then 同一套 H5，不要求选经营类目下级。
- Given 在线商城申请人多选一级；When 提交；Then 申请记录这些一级，不写店铺平均费率。
- Given 打开入驻表；When 填写；Then 无是否自营。
- Given 待审申请；When 运营通过；Then 一户 + 该业态菜单；When 再点通过；Then 仍是该户。
- Given 无业态老店迁移；When 完成；Then 业态餐饮、菜单餐饮模板。

## 10. 迁移

| 步骤 | 谁执行 | 口径 |
|---|---|---|
| 新申请停用 `merchant_category` 主数据 | 本模块 | 改存业态代码 + 可选一级 ID |
| 无业态老店 | 本模块 | 绑定 `catering`；套餐饮模板 |
| `is_self=1` 老店 | 本模块 | 仍餐饮；新单不写 `is_self=1` |
| 存量待审申请只有旧类目 ID | 实施 | 不猜业态（DEC-044）。测试可清库。留下的旧单：审核时补选业态；在线商城再补 1～3 个一级；补不了驳回走新 H5 |
| 推广 `sales_id` | 保留现码列 | 不改造推广（ADR-015、REQ-120） |

不批准生产清库。本期测试清库不在本模块单开规则。
