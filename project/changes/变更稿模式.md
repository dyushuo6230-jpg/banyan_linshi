---

## 1. 要解决什么

两人改同一条分支：一边梳理需求，一边写代码。两边都去改已经定稿的正式文档，会互相覆盖。

需求先写进 **不提交的临时袋**。同事的代码拉回来之后，再把袋子倒进正式文档。倒的时候和现稿对比，对不上的问人，不擅自合并。

一个人从头做到底，直接写正式 `CR-xxx.md` 即可，不必用本模式。

---

## 2. 三条口令

1. **初始化变更稿模式**（第 39A 节）：每个文档根铺一次。写出本说明书、变更夹 README 分流、gitignore 忽略临时袋。不写草稿。
2. **进入变更稿模式**（第 39B 节）：往临时袋里写。不改正式文档、不写业务代码。可多次进入（换窗口续写）。说明书没有时，先做第 1 步再进入。
3. **变更稿纳入正式文档**（第 39C 节）：对照现稿迁入。全部迁完且用户回复「纳入完成」后才删袋内文件。

还在投资料、还在写第一版需求时，直接写正式文档，不要用袋。

---

## 3. 目录

临时袋路径：`{{DOC_ROOT}}/changes_temp/`（本仓库即 `docs/project/changes_temp/`）。

**禁止提交到共享分支。** 仓库 `.gitignore` 必须包含该目录。有 ignore 就加一行，没有就建。

进入第 39B 节时才建袋内文件。第 39A 节和空项目初始化（G0）都 **不** 建袋。

```text
{{DOC_ROOT}}/changes_temp/
  INDEX.md                 总表
  BAG.md                   模式开着、开始日期；不改写 PROJECT_STAGE
  DRAFT-CR.md              将来合成一张正式 CR 的草稿骨架
  items/DRAFT-*.md         一条决策或一条口径
  patches/                 锚点补丁（改哪份正式文的哪一节）
```

不要复制整棵正式决策树。袋子只保留将打到正式文上的补丁。

备份用私人拷贝或网盘，不要 `git add` 进共享功能分支。

---

## 4. INDEX 一行

草稿 ID、标题、状态（已确认 / 未确认）、迁入目标（文件 + 标题）、是否入库（规则 vs 纯实现）、冲突（未知 / 无 / 待决策）。

---

## 5. 每条草稿必有迁入头

```text
草稿ID：DRAFT-…
状态：已确认应用 / 未确认
方案：…
迁入目标文件：能指出则指出；拉完同事再改路径
迁入目标标题：…
文档类型：DEC补丁 / PRD补丁 / CR正文 / 不入库（实现）
正式编号：待 git pull 后分配（禁止先写下一号正式 CR/DEC）
知情决策证据：会话日期、是否已回复确认应用
```

下面才是与正式 CR 模板同结构的正文：变更原因、影响范围、业务规则、兼容/迁移/回滚、关联已有决策。袋内写功能（人能碰到的行为，或系统办完后人在某页能看见的结果）按使用说明第 2A 节人话 6 问。

未二次确认的条目必须标未确认。纳入时不得写成已拍板。

纯实现（按钮、SQL 文件编号、接口字段名、不冻结的示例数据）标「不入库」，迁 PRD 时丢掉。

---

## 6. 锚点补丁

只写：在某某文件某某节，把哪句改成哪句或增哪段。纳入时打开现稿对照。同事若已改过同一节，标冲突，走知情决策，禁止默并。

---

## 7. 编号

袋内只用 `DRAFT-*`。纳入时看 `changes/` 与 baseline 当前最大号往后编。空项目从 `CR-001` 起。禁止在会话里预占正式下一号。

---

## 8. 纳入

按当前 PRD 状态走使用说明第 40 / 41 / 42 节，不是第四条变更管道。

先出对照表，用户确认后再写入。未迁完或冲突未确认，不得删袋。用户文字回复「纳入完成」后，删除 `changes_temp` 内文件，保留 gitignore 规则和本说明书。

知情决策仍在会话窗口用正文问，禁止弹框。袋里「已确认」必须来自某次确认应用。

---

## 9. 和开工、交接

临时袋未纳入前，不得把袋内口径当成已基线需求去发开工写代码口令。

临时袋被 gitignore：Git 工作区干净也可能有未入库决策。交接须检查袋子，必要时拷走。
