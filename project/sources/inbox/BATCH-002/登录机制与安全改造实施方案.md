# 登录机制与安全改造实施方案

> 文档位置：`docs/temp/TypesBusines/登录机制与安全改造实施方案.md`  
> 日期：2026-09-03  
> 状态：方案稿（现码盘点 + 落地步骤）。未改代码前以本文为施工口径。  
> 适用范围：`nunu-go-api`（admin / merchant / mall）+ 平台/商家 Vue 后台 + `go-uni-app`（餐饮 C 端、入驻 H5）。

**权威顺序：** 本文（登录会话与口令相关）> 现码 > `docs/temp/SaaS多商户改造方案.md`（租户/通道，与本文正交）> `nunu-go-api/docs` 历史接口说明。

**一句话：** HTTPS 下登录 JSON 带明文密码是常见做法；更急的是库里的明文口令、默认 `123456`、日志抄密码。JWT 能解开看到 `merchant_id` 不是漏洞。要改的是：三端密钥分开、商家能踢人、闲置才掉线、入驻票不印手机号、C 端短票+长票。

## 0. 现码结论（先读这个）

### 0.1 已经做对的

| 项 | 现码 | 含义 |
|---|---|---|
| 登录校验落库 | `password` 列走 **bcrypt**（`HashPassword` / `CheckPassword`） | 不是把传输密码原样当库密码。**不是缺项。** |
| 传输 | 登录/改密 JSON 里密码是原文；无前端 RSA | 线上 **HTTPS** 时整包加密，可接受 |
| 商家后台认店 | JWT 内 `merchant_id`，接口 `GetMerchantID()` | 正确；不要改成信前端再传店 ID |
| 平台会话闸 | Redis **白名单**（当前这一张票） | 退出/换票可立刻作废 |
| 启动校验 | `jwt.secret` 为空拒启动 | 好；生产勿留 `CHANGE_ME` |

「登录校验用的是 bcrypt」= 设密时原文变成不可逆哈希写入 `password`，登录时用原文和哈希比对。拖库也拿不到能直接登录的原文（**前提是没有另一列明文**）。

### 0.2 明确的缺口

| 优先级 | 问题 | 现码 |
|---|---|---|
| 高 | 商家账号另存明文口令 | `merchant_user.text_password`；列表/重置/C 端店铺详情会带出 |
| 高 | 默认弱口令 | 登录页/种子/演示店 `admin` 或 `merchant1` / `123456` |
| 高 | 商家 JWT 无法踢下线 | 只验签，无 Redis 白名单；退出后旧票仍有效至过期 |
| 中 | 会话是「登录起倒计时」 | 平台/商家 `expire: 7200`（整 2 小时）；C 端 `604800`（整 7 天）；无 refresh、无闲置 |
| 中 | 入驻 JWT 印手机号 | `scope=apply` + `Mobile` 在载荷里，可解开看见 |
| 中 | C 端 JWT 印 `openid` | 隐私；7 天窗口大 |
| 中 | 日志可能抄敏感字段 | 应用默认未必 dump body，网关/排错/响应里的 `text_password` 仍会进日志 |
| 基线 | 三端密钥可能相同 | 模板都是 `CHANGE_ME`；同一 secret 时跨端 `uid` 可能撞号 |
| 后期 | Token 在 `localStorage` | XSS 可被脚本读走；HttpOnly Cookie 单独立项 |
| 后期 | 网页改 Cookie | 要动 CSRF/跨域，不挡下面步骤 |

### 0.3 不要改错方向

- 不要给 JWT 载荷再套一层「加密」当主方案。  
- 不要从商家票里拿掉 `merchant_id`。  
- 不要只把 `expire` 从 2 小时改成 7 天（那不是刷新机制）。  
- 不要三端共用一把 `jwt.secret`。  
- `text_password` 与会话改造可并行，但不要混成一个 PR 里理不清。

## 1. 口令：比「传输明文」更值得管的三项

传输：平台/商家登录均为 `POST /api/v1/login`，body 带 `password` 原文。输入框小圆点不加密网络包。HTTPS 下这是行业常态。  
下面三项 HTTPS **管不了**。

### 1.1 库里的 `text_password`（最高优）

**现状：** 登录校验用 bcrypt 的 `password`；入驻通过、平台重置主账号、商家建/改子账号又把**同一份原文**写入 `text_password`。注释是「便于告知商家」。  
平台商户账号列表会带出该字段；重置接口返回 `{ "password": "新明文" }` 并回写该列；mall 店铺详情 `ShopDetail.password` 取自主账号明文。

**风险：** 拖库、调列表/店铺详情、工单截图，拿到的是**现在就能登录商家后台**的密码，不必破 bcrypt。改密若同步更新该列，库里永远是当前真实密码。

**改法：**

1. 停写、停读：新入驻/重置/子账号不再写该列；列表与详情不再返回。  
2. 告知改成「只亮一次」：随机密码 → 短信或弹窗当场复制 → 只把 bcrypt 写入 `password`。刷新后永远看不到原文。  
3. 历史：`UPDATE merchant_user SET text_password=''`；已发出的初始密码视为泄露，强制首次登录改密。  
4. C 端店铺接口禁止带后台账号密码。  
5. 重置后旧 JWT 必须作废（与第 3 章商家白名单一起做）。

### 1.2 登录页与种子 `123456`

**现状：** 平台登录可预填 `admin` / `123456`；种子超管、演示商户 `merchant1 / 123456` 并写入 `text_password`。

**风险：** 字典第一页；测试映射公网或生产误用种子即可直接试。验证码和失败锁定只能拖慢扫号，挡不住「密码已经填好」。

**改法：** 生产登录页留空；演示账号切换仅开发包；生产首次部署交互设超管或发现默认哈希则拒启动；演示店不进生产库；上线检查改超管、删演示店；禁止文档写统一初始密码。

### 1.3 日志把密码/Token 抄下来

**现状：** HTTPS 保护路上。解密后若网关记 POST body、APM dump、`fmt.Printf` 整个 LoginReq、前端 `console.log` 表单，密码会进 ELK/文件。账号列表响应里的 `text_password` 若被记访问日志，效果相同。Gin 默认往往只打 path/status，**不等于整条链路都没记 body**。

**改法：** 默认不记 body；脱敏 `password` / `old_password` / `new_password` / `text_password` / `mini_secret` / Token / `Authorization`；登录日志只记用户名、IP、UA、成败；历史日志按策略删或脱敏。

### 1.4 和传输明文怎么排

| 优先级 | 问题 | 为何更急 |
|---|---|---|
| 高 | `text_password` + 接口带出原文 | 永久可登录，一次拖库/一次调接口 |
| 高 | 生产仍是 `123456` / 登录预填 | 不用拖库，打开网页就能试 |
| 中 | 日志记录密码或完整 Token | 泄露面变成所有能看日志的人 |
| 基线 | HTTPS | 路上防窃听；上面三件管不了 |

口令落地顺序：**停明文列和返回密码的接口 → 生产去掉默认口令 → 日志脱敏。** 登录 JSON 走 HTTPS 明文可以先不动。

## 2. JWT：能解析出来算不算隐患

### 2.1 JWT 是透明工牌，不是保险箱

形态：`头.载荷.签名`。中间是 **Base64，不是加密**。任何人拿到整串，到 jwt.io 就能看到 JSON，**不需要密钥**。密钥只保护签名：能看、改不了。改 `merchant_id` 再交上去会验签失败。

| | 没有密钥 | 有密钥或偷到整张票 |
|---|---|---|
| 读字段 | 可以 | 可以 |
| 伪造商家 ID / 超管 | 不行 | 能伪造任意票（密钥泄露才是灾难） |
| 冒充调接口 | 不行 | 可以，直到过期或被作废 |

### 2.2 三端票面（现码）

共用 `pkg/jwt.Claims`，HS256，过期写在票上（登录时刻 + `jwt.expire`）。

| 端 | 载荷 | 配置模板过期 | 作废方式 |
|---|---|---|---|
| 平台 | `uid`、用户名、角色、`is_super` | 2 小时 | Redis **白名单** |
| 商家 | `uid`、用户名、**`merchant_id`**、是否主账号 | 2 小时 | **无**白名单，到期才废 |
| C 端登录 | `uid`、**`openid`** | 7 天 | 退出才进**黑名单** |
| 入驻 H5 | `scp=apply` + **明文手机号**（无 uid） | 跟 mall 过期 | 同上 |

商家认店 = 票内 `merchant_id`（再查店是否营业）。C 端票 **没有** 店 ID，店靠小程序 appid 等解析。

### 2.3 `merchant_id` 能被解开？

**单独拿「能看见商家 ID」当漏洞，过了。** 店 ID 本就出现在附近列表、订单、URL。知道 `merchant_id=18` 不能当老板，除非还有签过名的整票。

真危险：

1. **整票泄露**（XSS、贴群、日志、截图）→ 拿商家票就能改菜看钱。  
2. **密钥泄露或三端同一 `jwt.secret`** → 用户表 id 都从 1 起，商家 `uid=5` 的票拿到 mall 可能被当成 C 端 5 号。mall 的 `merchant_secret` 就是为了跨端验商家票时用另一把钥匙。  
3. **入驻票手机号、C 端 `openid`**：不是权限开关，是隐私。

平台 `is_super`：改不成假超管；偷到超管票就是超管。白名单清掉则立刻失效。商家没有这一步。

**结论：** 解析出商家 ID ≠ 被攻破。隐患在丢票窗口、不能吊销、票面印 PII、密钥共用。

## 3. 会话机制：固定过期为什么不够

### 3.1 现在

签发时过期 = **登录时刻 + 秒数**。一直操作，到点照样掉；一直挂机，没到点仍算登录。  
无换票接口。后台模板里的 `refreshToken` 是演示壳，业务登录只发一张 JWT。

### 3.2 目标（两套钟）

1. **闲置钟：** 有操作就续命；连续没请求满 N 才掉线。  
2. **寿命钟：** 就算一直点，同一段登录最多 8～12 小时强制再登（防偷票的人一直刷接口续命）。

「Refresh Token」是换票零件，**不等于**闲置踢人。只把 refresh 做成 7 天随时能换，人走 6 天回来还能登，仍不是闲置。

### 3.3 和现栈对齐的做法

后台（平台 + 商家）已有/将有 Redis 花名册，**不必先上完整 OAuth**：

- 短 JWT（30 分钟～2 小时）当印刷有效期。  
- Redis：一账号一票；每次鉴权成功刷新 **idle TTL**（如 30 分钟）。  
- 快过期且花名册还在 → 发新票给前端换上。  
- 闲置到点 / 寿命到点 / 退出改密重置禁用 → 撕花名册。

C 端要免登：

- **access** 短票调业务（1～2 小时）。  
- **refresh** 只能换短票（7～30 天），Redis 记最后活动；退出/封号作废。  
- 闲置按「天」计，不要做成后台那种 30 分钟，否则顾客关一天小程序就要重新授权。

前端：axios 401 时有 refresh/新票则换完重试，不要整页踢登录。「操作」以调了业务接口为准。

## 4. 最终落地形态

### 4.1 用户侧

| 谁 | 一直在点 | 停手不管 | 改密 / 退出 / 禁用 | 票被抄走 |
|---|---|---|---|---|
| 平台、商家 | 不无故踢（隔不到闲置就有请求） | 如 **30 分钟** 无请求 → 重登 | **立刻** 作废 | 最多活「闲置这么久」 |
| 小程序 | 打开即用、换票无感 | 如 **7 天完全不用** 才重新微信登 | 退出/注销拉黑 | 短票窗口小；长票可废 |
| 入驻 H5 | 填到一半会话还在 | 会话过期重新验短信 | — | 解开票 **无手机号** |

### 4.2 技术侧

```
平台 / 商家
  登录 → 短 JWT + Redis「这人当前这一张」
  每次接口 → 验签 + 对花名册 + 拨满闲置 TTL
  短票快到期且人还在 → 发新票
  闲置 / 寿命 / 退出改密重置 → 撕花名册

C 端
  access 调业务；refresh 只换 access
  打开小程序或 401 → refresh 换票
  退出、封号 → 作废这对票

入驻
  票面：scp=apply + 随机 jti
  Redis：jti → 手机号（与票同过期）
```

- 密钥：admin / merchant / mall 三套 `jwt.secret`；mall 验商家票用 `merchant_secret`（与商家 secret 配对）。  
- 载荷：商家继续放 `merchant_id`；C 端可不放 `openid`（用 `uid` 查库）；入驻不放手机号。  
- 日志脱敏。HttpOnly Cookie **网页后台后期单独立项**；小程序继续 Header。

### 4.3 建议配置（可写入 yml，勿写死）

| 项 | 平台/商家 | C 端 |
|---|---|---|
| 短票（access / JWT） | 30～120 分钟 | 1～2 小时 |
| 闲置 | 30 分钟无请求 | refresh 按「天」无活动作废 |
| 绝对登录寿命 | 8～12 小时 | 与 refresh 上限一致即可 |
| refresh | 后台可不单独发，用换短票即可 | 7～30 天 |

数字上线前和产品拍板；上表是方案默认。

## 5. 要改什么（按端）

**可以不动：** 登录仍账号+验证码；密码 JSON + HTTPS；商家 `GetMerchantID()` 只信票。

| 范围 | 改动 |
|---|---|
| 配置 | 三份 prod `jwt.secret` 互异且长；mall `merchant_secret` 与商家配对；闲置/寿命/短票/refresh 配进化 |
| 平台 | 已有白名单。加：请求刷新 idle TTL；快过期发新票；寿命上限；核对退出/改密/禁用都清白名单 |
| 商家 | 中间件改为验签+对 Redis；登录写入；退出、改密、平台重置主账号、禁用子账号删除；同样闲置+换票 |
| 前端后台 | 存新票；401 先换票再跳登录 |
| mall + 小程序 | 登录发 access+refresh；Redis 管 refresh；401 换票；入驻改 jti |
| 入驻 H5 | 流程可不变，只是票面无手机号 |
| 口令（并行） | 停 `text_password`；清空历史；接口不再返回密码；生产去 `123456` |
| 日志 | 应用+网关脱敏 |
| 不做（本期） | 加密 JWT、拿掉 `merchant_id`、网页 Cookie、把 C 端做成 30 分钟闲置 |

## 6. 实施步骤

依赖顺序：密钥 → 商家能踢人 → 入驻去手机号 → 后台闲置换票 → C 端双票 → 日志（Cookie 另立项）。口令明文列可与 1～2 步并行。

### 第 0 步 — 当天：密钥（不改业务）

生产三端 `jwt.secret` 分开、足够长；`merchant_secret` 与商家密钥配对。  
旧票全部失效，选低峰，通知重新登录。  
**本步没有闲置续期**，只防跨端撞号。

### 第 1 步 — 商家 Redis 白名单（补最大洞）

对齐平台：一账号一票（先不做多端同时在线）。  
登录写入；每次请求核对；**退出 / 商家改密 / 平台重置 / 禁用** 删除。  
验收：重置密码后旧商家后台立刻 401。  
此时仍是「登录起 2 小时倒计时」，但丢票、离职能拉闸。

**并行建议：** 停写停读 `text_password`，C 端店铺详情去掉密码；生产登录去预填、改超管密码。

### 第 2 步 — 入驻票去掉手机号

Claims 只留 `scope=apply` + `jti`；Redis 存手机；入驻接口从 Redis 取。  
旧入驻票失效，重新验短信即可。

### 第 3 步 — 后台闲置 + 换短票（体验）

平台、商家同一套规则（见 §4.3）。  
前端拦截器认新票。  
验收：连续操作超过原 2 小时仍在；停过闲置再点 401；改密旧票立刻废。

### 第 4 步 — C 端 access + refresh（和产品定数字）

先拍板免登几天、几天不用作废。  
再改 mall 签发/换票/作废；小程序存两票、401 换票。  
refresh 必须能作废；只缩短成 2 小时一张票会伤体验。

### 第 5 步 — 日志脱敏；Cookie 单独立项

先日志与网关。Cookie 等 HTTPS/跨域稳了再做。

## 7. 验收（靠谱的三条 + 口令）

会话：

1. **忙：** 平台/商家连续操作超过原 2 小时，保存成功，不用重登。  
2. **闲：** 停过闲置时间，再点接口 401。  
3. **闸：** 重置商家密码或退出，旧 Token 立刻废；解开入驻新票看不到手机号。

口令（若已做并行项）：

4. 库中 `text_password` 为空；店铺详情/账号列表无明文密码。  
5. 生产登录页无预填 `123456`；演示账号无法登录生产。  
6. 日志检索 `password=`、完整 Bearer 无命中（或已打码）。

密钥：三端 secret 不同；用商家票调 mall 普通用户接口验签失败（小魔推走 `merchant_secret` 的除外）。

## 8. 与先前五条对照

| 原条目 | 落在哪一步 | 还要叠什么 |
|---|---|---|
| 生产三端密钥分开、足够长 | 第 0 步 | 商家 secret 与 mall `merchant_secret` 配对 |
| 商家 Redis 白名单 + 退出/改密/重置作废 | 第 1 步 | 第 3 步在同一本花名册上加 idle TTL，不要另造一套 |
| 入驻票去掉手机号 | 第 2 步 | 用 `jti`，不要把手机号加密后仍放票面 |
| C 端缩短过期或 access+refresh | 第 4 步 | refresh 也能作废；闲置按天 |
| 日志脱敏、能上 HttpOnly Cookie 再上 | 第 5 步 | 日志先做；Cookie 不挡 0～4 |

后台会话：**白名单 + 闲置 TTL + 换短票**，不必强上 refresh。  
C 端才用 access/refresh。

## 9. 明确不做（本期）

- 加密 JWT 载荷、从商家票删除 `merchant_id`。  
- 只改 `expire` 当刷新机制。  
- 三端共用 secret。  
- C 端 30 分钟闲置。  
- 为上 Cookie 阻塞第 0～4 步。  
- 把 `text_password`、会话、Cookie 搅在同一个「大爆炸」提交里。
