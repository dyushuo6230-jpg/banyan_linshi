- 主题：什么叫功能已落地；哪一块可以先做到申请支付够用；众享源品 - 在线商城打哪些端、多端怎么写
- 选择：仅众享源品 - 在线商城页面的前端接口先做打包/申请支付够用；必打端含 iOS / 安卓 / H5 / 微信小程序；其余功能开发完成，能闭口就闭口；多端差异用同一套代码条件编译。**v1.3.0：第 1 条限缩废止。**
- 限制条件：不编造支付申请材料清单、商户号、小程序 appid；不把后台/本地生活做成半成品；不编造各端差异清单；真扣款仍 DEC-050
- 被拒方案：把众享源品 - 在线商城整包前端当半成品；用「等页面」把其他模块留到下次；为某一端复制第二套工程；把鸿蒙写成必打
- 知情决策证据：用户要求加微信小程序必打 + 条件编译 → 评判合理后 APPLY；v1.3.0 袋内 BAG-D1=A 二次确认后第 39C 纳入

## 已确认规则

1. **源品 C 端现用页必须闭口或按已确认表藏掉。** 众享源品 - 在线商城 C 端（`go-uni-app-online`）现用页上已经出现的能力，必须接到 mall-online 并能办完（可以没货、空态，不能只 toast）。图上多出来、与已拍板打架的入口，按 DEC-053 v1.1 及后续 CR 藏或改跳，不得长期「敬请期待」当闭口——AI 整页假页是已点名例外（REQ-063）。**废止 v1.2.0 第 1 条「仅页面前端接口先做到打包/申请支付够用、不要求撑起完整逛买」。** 真扣款仍不要求（DEC-050）。
2. **其余所有功能必须开发完成；能闭口就闭口。** 包括但不限于：平台后台、租户后台、众享营销 - 本地生活、入驻 H5、以及对应后端；在线商城供应商发品/送审/接单/发货/结算/店铺资料；平台审品、统一收款配置、抽佣、平台券。已有现码同样按「能上线闭口」收口，不是「页面在、接口在」。
3. **不得**用已废止的第 1 条当借口：租户/平台/本地生活/入驻、或众享源品 - 在线商城的后台与业务接口，一律本期做完。
4. **本期必打端：** iOS、安卓、H5、**微信小程序**（众享源品 - 在线商城 C 端，工程 `go-uni-app-online`；不是众享营销 - 本地生活）。**鸿蒙仍非本期必打包。**
5. **多端同一套代码，有差异必须条件编译。** 在同一套代码中编写针对不同平台的差异化逻辑；编译时只保留对应平台的代码，避免为多端复制冗余实现。无差异处不要硬套条件编译。禁止为某一端再复制一套工程或整页拷贝双份逻辑。细则见 `docs/project/standards/CODING_STANDARDS.md` 第 7 节。
6. 不降低登录五条（DEC-005）。mall-online 进程仍 ADR-001，目录仍等对应批次。DEC-008 仍有效（视觉收窄见 v1.1）。
