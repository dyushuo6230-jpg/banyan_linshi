# 怎么读这套说明

这套说明放在 `docs/project/plain-document/`，给人开会、交接、看全局。它是正式需求和技术文档的**可读投影**，不是第二套需求，也不是开工依据。

改规则：先改正式文档，再按批刷到这里。禁止只在说明里改口径，再让代码按说明做。

正文用业务语言：哪一端、哪个菜单、订单变成什么。看不到需求编号、决策号是故意的——编号留在正式文档。未定会写成「未定」，会上不要当成已经拍板。

## 你想知道什么，打开哪一夹

| 你想知道 | 去哪 |
|---|---|
| 项目是干什么的、两个名字别叫混、本期做不做 | 总览（本夹其余六篇） |
| 规则怎么转：审不审、抽谁的佣、订单变成什么 | 功能需求 |
| 打开哪一端、哪一页、表单填什么 | 分端页面 |
| 系统怎么拆、怎么部署、怎么测、仓库文件夹对应哪一端 | 技术设计（《系统怎么拆》含目录对照；端口只认《部署与环境》） |
| 投屏看边界、谁在哪一步、会不会串 | 架构图 → 图怎么读 |
| 一共有哪些文件 | `doc-map.md` |

同一件事不两处写全。规则只在功能需求写全；分端点到规则时一句话指过去。端口和域名只出现在技术设计《部署与环境》和架构图《部署架构》。

## 三种读法

- **开一场 15 分钟的会**：按总览七篇顺序读。不够再点一篇功能需求或一端子文档。
- **对着产品走菜单**：先看《五端与角色》，再打开对应分端。规则疑问跳功能需求，不要在分端里改口径。
- **开发和测试交接**：技术设计横切（怎么拆、两套 C 端、部署、测试、权限、数据快照、安全）加能力落地五篇。域名和端口只认部署那一篇。仓库里哪棵树对应哪一端，只认《系统怎么拆》里的目录对照。

架构图已齐。开会先看《图怎么读》和静态四张，再打开对应场景泳道或隔离时序。不要把图当成第二套需求。
