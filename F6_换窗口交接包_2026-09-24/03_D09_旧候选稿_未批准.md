# F6-D09 — UI Conformance Validation × Design Drift × Interaction Regression

```text
Status = HUMAN_REVIEW
Architecture Freeze = NOT_YET
Implementation = NOT_AUTHORIZED
```

## 1. D09 的正式职责

F6-D09 负责：

```text
Target Resolution
→ Validation Scope Resolution
→ Actual Observation
→ Conformance Comparison
→ Drift Classification
→ Regression Detection
→ Validation Evidence
→ Validation Result
```

D09 回答的是：

```text
现在应该符合什么？
实际是什么？
两者是否一致？
差异属于什么？
差异是否被允许？
是否发生已有能力回归？
证据是否足够形成结论？
```

D09 **不负责直接拥有 Repair Mutation**。

因此：

```text
Validation != Repair
Drift Detection != Mutation Authorization
Regression Detection != Business Logic Rewrite
```

真正的：

```text
Repair Governance
Allowed Mutation Execution
Design-Code Synchronization
Repair Loop Control
```

进入 F6-D10。

# 3. UI Conformance Session

## VV-01 — UI Conformance Session 是正式顶层能力

正式名称：

```text
UI Conformance Session
UI 一致性校准会话
```

它是一个：

```text
scope-bounded
target-aware
evidence-based
provider-neutral
task-scoped
derived runtime session
```

不是新的 Canonical Truth。

---

## VV-02 — Visual Repair Loop 不再是 Core 顶层概念

Legacy：

```text
Visual Repair Loop
```

映射为：

```text
UI Conformance Session
mode = VISUAL
action = REPAIR
```

它只作为：

```text
Compatibility Profile / Alias
```

不得形成第二套 Core Conformance Architecture。

---

## VV-03 — Conformance Session 默认不属于固定开发阶段

默认：

```text
OFF
ON_DEMAND
NON_BLOCKING
```

因此它：

```text
不自动启动
不修改 PROJECT_STAGE
不占主开发进度分母
不默认阻塞其它合法开发工作
```

只有明确的：

```text
Project Policy
Acceptance Policy
Release Policy
```

才能把某个 Conformance Result 升级成 Gate。

Capability 本身不是 Gate。

# 4. Validation Scope

## VV-04 — Validation 必须 Scope-aware

Validation Scope 可以按：

```text
Application
Page
Region
Component
State
Interaction
```

组合限定。

例如：

```text
application = tenant-admin
page = /material
component = UploadProgressPanel
state = UPLOADING
```

Validation 不得默认扩张到整个应用。

---

## VV-05 — Scope 外区域默认不参加当前结论

当前 Session 未覆盖的对象必须保持：

```text
OUT_OF_SCOPE
UNKNOWN
NOT_EVALUATED
```

之一。

不得把：

```text
未检查
```

写成：

```text
PASS
```

---

## VV-06 — Validation Coverage 必须显式

Validation Result 必须能说明：

```text
Target Coverage
State Coverage
Interaction Coverage
Viewport / Device Coverage
Data Scenario Coverage
Evidence Coverage
```

Partial Validation 合法。

因此：

```text
Partial PASS
!=
Whole Page PASS
```

# 5. Conformance Target Resolution

## VV-07 — 每个 Session 必须解析 Conformance Target Bundle

正式对象：

```text
Conformance Target Bundle
```

表示：

```text
在给定 Scope
+ Authority
+ Version
+ Context
+ Applicability

下解析出的当前校准目标集合。
```

它是 Derived Runtime Context。

不是新的 Canonical Artifact。

---

## VV-08 — Target Resolution 必须服从 Authority，而不是 latest

优先判断：

```text
Authority
Current Effective
Applicability
Scope
Version
Freshness
```

不能使用：

```text
latest file wins
newest image wins
closest screenshot wins
AI confidence wins
```

---

## VV-09 — Current Effective UI_SPEC 是首选批准目标

存在：

```text
Current Effective UI_SPEC
```

时，它拥有：

```text
Approved UI Construction Target
```

Design Package、PNG、Figma、墨刀、Prototype 等可以作为 supporting evidence。

它们不能静默覆盖 Current Effective UI_SPEC。

---

## VV-10 — Governed Design Package 可以成为有效 Target

不存在适用 UI_SPEC，但存在：

```text
Current Governed Design Package
```

时，可针对其 Coverage 进行：

```text
Structural Conformance
Visual Semantic Conformance
State Conformance
Responsive Conformance
Data Presentation Conformance
```

结果必须明确：

```text
Target Authority = Design Package
```

不能伪称：

```text
Approved UI_SPEC Conformance
```

---

## VV-11 — 用户明确点名 Design Source 可以形成 Session Target

当没有适用 UI_SPEC / Governed Design Package，而用户明确指定：

```text
PNG
Figma
墨刀
Prototype
其它 Design Source
```

时，可以形成：

```text
User-Designated Source Target
```

但结论只能描述为：

```text
Matched Against Design Source
```

不能自动升级为正式 UI Construction Truth。

---

## VV-12 — PRD 不能直接充当视觉校准目标

```text
PRD
!=
Visual Target
```

只有 PRD 时：

```text
REPAIR_NOT_READY
```

应进入：

```text
PRD
→ Design Formation
→ Design Package
→ optional UI Governance
→ UI_SPEC
→ Conformance
```

D09 不允许从 PRD 自行发明视觉 Target。

---

# 6. Existing UI 与 Baseline

## VV-13 — Existing UI 默认是 Current Reality Evidence

已有页面、已有组件、已有代码默认表达：

```text
Current Implementation Reality
```

而不是：

```text
Design Truth
```

因此：

```text
Existing != Correct
Existing != Target
Existing != Approved
```

---

## VV-14 — Existing UI 可被明确指定为 Protected Baseline

当要求：

```text
只修改某一区域
其它区域保持不变
```

时，其它区域可以成为：

```text
Protected Baseline
```

其作用是：

```text
防止无关漂移
防止扩大修改影响面
支持 Regression Detection
```

但 Protected Baseline 不因此升级为 Design Truth。

---

## VV-15 — Protected Functional Baseline 是独立保护维度

UI Conformance 必须能够引用：

```text
Protected Functional Baseline
```

例如：

```text
API Integration
Routing
Permission
Business Logic
Business State
Data Contract
Persistence
Upload Logic
Delete Logic
Pagination
Query Behavior
Validated Callback
Accepted Interaction
```

这些属于 Regression Protection Target。

不是 Visual Target。

# 7. Actual Observation

## VV-16 — Actual 必须来自可追踪 Evidence

Actual Observation 可以来自：

```text
Rendered UI
Screenshot
DOM / Layout Observation
Browser Runtime
Interaction Trace
Automated Test Result
Manual Validation Evidence
Computed Geometry
Accessibility Observation
```

Provider 可以替换。

但必须保留：

```text
Source
Scope
Environment
Timestamp / Revision Context
Applicable State
Trace
```

---

## VV-17 — Observation 不得自动升级为语义事实

例如：

```text
按钮实际宽度 = 132px
```

只能首先说明：

```text
Observed Geometry = 132px
```

不能直接推出：

```text
Design requires width:132px
```

同样：

```text
Observed DOM
!=
Required DOM

Observed CSS
!=
Approved Implementation Strategy
```

# 8. Drift Model

## VV-18 — Difference 与 Drift 必须分开

```text
Difference
```

表示 Target 与 Actual 存在差异。

只有经过：

```text
Target
Scope
Applicability
Tolerance
Alternative
Exception
Deviation
```

解析后，才可以分类为：

```text
DRIFT
ACCEPTABLE_DIFFERENCE
LEGAL_ALTERNATIVE
EXPECTED_VARIATION
UNKNOWN
```

---

## VV-19 — Drift 分类必须可扩展

Core 不把所有 Drift 永久写死。

当前至少支持：

```text
VISUAL_DRIFT
STRUCTURAL_DRIFT
LAYOUT_DRIFT
STATE_DRIFT
INTERACTION_DRIFT
RESPONSIVE_DRIFT
DATA_PRESENTATION_DRIFT
ACCESSIBILITY_DRIFT
```

未来可增加新的 Drift Class，而无需改变核心 Session 模型。

---

## VV-20 — Visual Drift 不能退化成 Pixel Equality

```text
Pixel Diff
!=
Visual Correctness
```

允许考虑：

```text
Rendering Engine
Font Rasterization
Device Pixel Ratio
Anti-aliasing
Browser Difference
Legal Responsive Adaptation
Dynamic Content
Token Resolution
Platform Rendering
```

因此 Pixel Diff 是 Evidence。

不是最终 Authority。

---

## VV-21 — Structural / Layout Drift 判断语义关系，不只判断坐标

布局验证重点包括：

```text
Containment
Alignment
Ordering
Spacing Relationship
Sizing Relationship
Overflow
Anchoring
Layering
Responsive Transformation
```

而不是要求：

```text
所有坐标完全复制截图
```

继续遵守：

```text
Layout Relationship > Screenshot Coordinate Copy
```

---

## VV-22 — State / Interaction Drift 不得脑补未定义行为

Static Target 没有定义：

```text
Hover
Loading
Drag
Error
Responsive
Business Action
```

时，Validation 不得自行产生：

```text
EXPECTED_STATE
EXPECTED_BEHAVIOR
```

正确结果应允许：

```text
UNKNOWN
NOT_SPECIFIED
TARGET_COVERAGE_GAP
```

---

## VV-23 — Data Drift 与 Business Data Error 必须分开

UI Conformance 可以检查：

```text
Data Slot presence
Formatter
Fallback
Overflow
Demo Fixture rendering
Data Scenario presentation
```

但不能因此判断：

```text
API Contract is wrong
Database Schema is wrong
Business Value is wrong
```

除非对应 Authority / Evidence 明确支持。

---

# 9. Legal Alternative / Deviation

## VV-24 — Legal Alternative 不是 Drift

如果 Implementation Guidance / IR / Rule 明确允许多个合法实现：

```text
Alternative A
Alternative B
```

Actual 落入任一合法实现时：

```text
LEGAL_ALTERNATIVE
```

不得仅因为“不是推荐的那一个”就报告 Drift。

---

## VV-25 — Approved Deviation 不应重复报告为普通 Drift

如果存在已治理：

```text
Deviation
Expected
Actual
Reason
Scope
Approval
Validity
```

则 Validation 必须识别它。

有效 Deviation 应分类为：

```text
APPROVED_DEVIATION
```

而不是反复产生同一错误。

---

# 10. Baseline Freshness

## VV-26 — Validation Target 必须有 Freshness

Target 可能出现：

```text
CURRENT
STALE
REVIEW_REQUIRED
SUPERSEDED
UNKNOWN
```

如果 UI_SPEC、Design Package、PRD Link、Foundation、Token、Behavior Model 等发生相关变化，Validation Baseline 必须进入 Impact / Freshness 判断。

---

## VV-27 — Stale Baseline 不能产生伪 PASS

若关键 Target 已：

```text
STALE
UNRESOLVED
CONFLICTED
```

则不能简单输出：

```text
PASS
```

应输出：

```text
VALIDATION_NOT_READY
TARGET_RECONCILIATION_REQUIRED
PARTIAL_RESULT
```

等明确状态。

---

# 11. Regression Model

## VV-28 — UI Conformance 必须同时支持 Regression Detection

Conformance 不能只问：

```text
看起来更像 Target 了吗？
```

还必须问：

```text
原本应保护的能力是否退化？
```

特别是在 Repair 后，必须支持：

```text
UI Revalidation
+
Protected Functional Regression Check
```

Regression Result 与 Visual Result 分开记录。

---

## VV-29 — Regression Scope 必须由 Impact 决定

不是每次都全量回归。

建议：

```text
Changed Scope
→ Dependency / Impact Resolution
→ Minimum Sufficient Regression Scope
```

从而实现：

```text
快速
精准
可验证
```

但不得为了速度跳过：

```text
Authority-sensitive
Security-sensitive
Business-critical
Explicitly Protected
Impacted
```

范围。

---

Validation Result 至少能够表达：


```text

Target Version / Freshness
Scope
Coverage
Actual Evidence Refs
Findings

Regression Findings
Unresolved Items

```

但：

```text
Validation Result
!=
UI_SPEC

Validation Result
!=
Design Package

Validation Result
!=
PRD

Validation Result
!=
Canonical Product Truth
```

Validation Evidence 可以挑战现有 Target：

```text
Evidence
→ Gap / Conflict / Freshness Review
→ Governance
```

但不能：

```text
Validation Result
→ Silent Canonical Rewrite
```

# 13. INSPECT / REPAIR / AUDIT 边界

UI Conformance Session 支持：

```text
INSPECT
REPAIR
AUDIT
```

D09 主要拥有：

```text
INSPECT semantics
Validation semantics
Diff / Drift semantics
Regression semantics
Result semantics
```

REPAIR Action 可以调用 D09 Validation 能力形成：

```text
Inspect
→ Diff
→ ...
→ Revalidate
```

但其中：

```text
Mutation Authorization
Repair Planning
Mutation Execution
Repair Iteration Governance
Design-Code Synchronization
```

归 F6-D10。

因此：

```text
D09 = Judge / Evidence / Classification
D10 = Governed Correction / Synchronization
```

# 14. Allowed Mutation Scope 在 D09 中的定位

D09 可以消费：

```text
Allowed Mutation Scope
```

但只用于：

```text
判断某次修改是否越界
辅助 Regression Detection
辅助 Repair Result Validation
```

D09 不拥有：

```text
Mutation Permission
Repair Write Authorization
Business Change Authorization
```

Allowed Mutation Scope 的生成、修改与执行治理进入 D10。

---

# 15. Protected Functional Baseline 在 D09 中的定位

D09 使用：

```text
Protected Functional Baseline
```

作为 Regression Validation Target。

例如：

```text
UI Target Conformance = PASS
```

但：

```text
Upload API broken = true
```

最终不能认为该 Repair 成功。

逻辑上：

```text
Conformance Success
=
Target Conformance Satisfied
AND
Required Protected Regression Checks Satisfied
```

具体 Acceptance Policy 可决定最终 Gate 规则。

# 19. Bounded Autonomy

以下工作可以自动完成：

```text
采集确定性 Observation
计算 Diff
执行已明确的 Validation Rule
识别已登记 Deviation
产生 Drift Candidate
计算 Impact Scope
执行已授权的自动化 Regression Check
生成 Validation Report
```

但以下情况必须进入治理：

```text
Target Authority Conflict
Current Effective 不明确
Business Semantics Conflict
Protected Functional Regression
High-impact ambiguity
Required evidence missing
Approved sources conflict
```
