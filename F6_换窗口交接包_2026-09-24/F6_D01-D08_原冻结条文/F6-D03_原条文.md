# F6-D03 — Design Source × Scene × Semantic Tree × Design Truth

## 一、D03 的目标

D03 不解决：

> “页面最终怎么写代码。”

也不解决：

> “哪些设计规则适用。”

这些前面 D02 已经处理。

D03 专门解决：

> **Banyan 如何把各种设计相关物资，可靠地解释成结构化设计证据，再进一步形成当前设计目标的结构化事实。**

完整目标链：

```text
Unified Material Intake
        ↓
Registered Material
        ↓
Design-Relevant Classification
        ↓
Design Source Registration
        ↓
Evidence Extraction / Provider Interpretation
        ↓
Raw Scene
        ↓
Normalized Scene
        ↓
Semantic Interpretation
        ↓
Semantic Tree
        ↓
Design Reconciliation
        ↓
Resolved Design Facts / Decisions
        ↓
Design Truth Model
        ↓
Design Package
        ↓
UI Governance
        ↓
UI_SPEC
```

注意：

```text
Raw Scene
Normalized Scene
Semantic Tree
```

都不是新的 Canonical UI Truth。


作为永久唯一集合。

应该是：

```text
Material

Design Relevance

Source Type
↓
Provider Capability
```

未来新增：

```text
Sketch

新的 AI Design Tool

```

不改 D03 Core Semantic。

# 四、Registered Material 和 Design Source 要区分

不是所有 Material 都是 Design Source。

例如一批资料中可能包含：

```text
PRD
UI 图
会议纪要
CSS 规范
产品说明
Figma
测试记录
```

D01 登记后：

```text
Registered Material
```

D03 再判断：

```text
哪些具有 Design Relevance？
```

符合的才形成逻辑：

```text
Design Source Registration
```

所以：

```text
Material
≠ Design Source
```

而是：

```text
Material
→ classified as design-relevant
→ Design Source
```

# 五、Design Source 的正式定义

我建议：

> **Design Source = 已登记 Material 中，被确认可以为某个 Design Scope 提供设计证据的来源。**

它至少要能回答：

```text
Source 是什么？
来源哪里？
针对什么 Scope？
什么时间/版本？
目标还是现状？
是否完整？
可以证明什么？
不能证明什么？
```

---

# 六、Design Source 只拥有 Evidence Authority

这是硬规则。

例如：

```text
target-category.png
```

可以证明：

> “这张图里看到了某个视觉效果。”

不能直接证明：

```text
这是当前批准的产品需求
这是当前 UI_SPEC
这是项目 Shared Foundation
这是当前项目必须执行的 Rule
```

所以：

```text
Design Source Authority
= Evidence Authority
```

而不是：

```text
Product Authority
Approval Authority
Canonical Apply Authority
```

---

# 七、Source Intent 必须区分

同样一张截图，意义可能完全不同。

例如：

### A

用户说：

> “这是目标设计图。”

它是：

```text
Target Design Evidence
```

### B

用户说：

> “这是现在代码实现出来的效果。”

它是：

```text
Current Reality Evidence
```

### C

用户说：

> “参考一下这个网站的风格。”

它是：

```text
Reference Evidence
```

所以：

```text
same image format
≠ same semantic role
```

---

# 八、Original Source 和 Raw Scene 必须严格分开

例如：

```text
category.png
```

是 Original Source。

AnyDesign 解析得到：

```text
source-scene.json
```

不是 Original Source。

所以：

```text
Original Source
= 原始证据

Raw Scene
= Provider 对证据的一次机器解析结果
```

原始 Source 必须保留。

Raw Scene 可以重建。

---

# 九、Raw Scene 的正式定位

定义：

> **Raw Scene = 某个 Design Provider 对某个 Design Source 进行解析后产生的、尽量低损失的 Provider-specific machine representation。**

可能包含：

```text
原始 layer
provider node id
bounds
文字
颜色
图片引用
visibility
component metadata
provider-specific fields
```

Legacy UI Design Pack 本来就有这个思路：`source-scene.json` 保存 AnyDesign / Figma /视觉解析器的原始字段，而 `normalized-scene.json` 再转为统一 Schema。fileciteturn108file17L61-L105

这个价值继续保留。

---

# 十、Raw Scene 允许 Provider-specific

例如：

```text
AnyDesign Raw Scene
```

可能有：

```text
anydesignNodeType
```

Figma 可能有：

```text
figmaComponentId
```

墨刀可能有自己的字段。

没关系。

因为 Raw Scene 就是：

> Provider 边界内的低损失表达。

---

# 十一、Raw Scene 没有设计真相 Authority

例如 OCR 识别：

```text
“删除”
→ “刪阴”
```

Raw Scene 里出现错误，不代表：

```text
Design Truth = “刪阴”
```

因此：

```text
Raw Scene
= Derived Evidence Projection
```

---

# 十二、同一个 Source 可以产生多个 Raw Scene

例如：

```text
target.png
├── AnyDesign interpretation
├── Vision Provider interpretation
└── Future Provider interpretation
```

这是允许的。

目的不是：

> “多个 AI 投票”。

而是：

> 可以比较不同 Provider 的解析质量。

---

# 十三、Provider 数量不形成 Authority

禁止：

```text
3 个 Provider 说 A
1 个 Provider 说 B

→ A 一定是真相
```

这是：

```text
majority
```

不是 Authority。

最终仍要：

```text
Evidence
Scope
Source Intent
Confidence
Human Constraint
Foundation
Decision
```

综合对账。

---

# 十四、Normalized Scene 的正式定位

定义：

> **Normalized Scene = Banyan 将不同 Provider 的 Raw Scene 归一化后形成的 Provider-neutral structural observation model。**

核心目的：

```text
AnyDesign
Figma
墨刀
Vision Model
...
      ↓
统一进入
      ↓
Normalized Scene
```

这样 Banyan 后面的 Core 不认识具体工具。

---

# 十五、Normalized Scene 主要描述“观察到什么”

例如：

```text
Node
Parent
Children
Bounds
Visibility
Text
Asset
Observed Color
Observed Geometry
Observed Alignment
Source Ref
```

而不是：

```text
display:flex
grid-template-columns
position:absolute
React component
Vue component
Ant Design prop
```

后者属于 Implementation。

---

# 十六、Core 不能被 Provider 字段污染

例如不应该要求：

```text
NormalizedNode {
   figma_id
   modao_id
   anydesign_type
}
```

作为核心必需语义。

应该：

```text
Core normalized fields
+
provider metadata extension
```

Provider 变化：

> 不改核心 Schema 语义。

---

# 十七、Layer Tree 只表达结构关系

Legacy 已经把：

```text
layer-tree
```

用于表达父子层级。fileciteturn108file17L97-L105

继续保留。

但明确：

```text
Layer Parent
≠ Semantic Owner
```

例如：

```text
Dropdown popup
```

结构上可能挂在 Page Root。

语义上属于：

```text
Select
```

不能通过 Layer Parent 自动推断业务/设计所属关系。

---

# 十八、Geometry 是观察结果，不是 CSS

Legacy 已经明确：

> geometry 保存设计 viewport 下的 x/y/width/height/distance/alignment 测量结果；geometry 是测量结果，不是 CSS 施工指令。fileciteturn108file17L97-L112

所以：

```text
Observed width = 280
```

只能先表示：

```text
renderedGeometry.width = 280
```

不能：

```css
width: 280px;
```

# 十九、Geometry 必须附带 Observation Context

例如：

```text
viewport:
1440 × 900

node:
width 280
```

没有 viewport：

```text
280
```

意义并不完整。

因此 Geometry 在逻辑上需要保留：

```text

State
Device

```

精确字段后面 Implementation Freeze 再定。

# 二十、Scene 不自动推断 Sizing Strategy

例如观察到：

```text

```

不能直接决定：


可能实际应该：

```text
CSS Grid

fill
intrinsic

```

Scene 描述：

> 结果。

Implementation 后面决定：

> 如何重建这种关系。

# 二十一、Semantic Interpretation 是独立层

但设计真正需要：

```text
Semantic Interpreter
```

把结构 Observation 转为设计语义。

# 二十二、Semantic Tree 的正式定位

定义：

> **Semantic Tree = 对 Scene / Design Evidence 中结构的设计语义解释。**

例如：

```text

↓
PrimaryCategoryNavigation

node-203
↓
SecondaryCategoryNavigation

node-304
↓
TertiaryCategoryItem
```

Legacy 已经有类似 Semantic 层，用来把 Node 转成 Sidebar、MainContent、Toolbar、ResourceGrid、ResourceCard，并保留 `sourceNodes / status / confidence`。fileciteturn108file17L113-L127

# 二十三、Semantic Tree 默认是 Inference

现有 Stage 09 已确定：

```text
Semantic = Inference
```

所以：

```text
AI 判断这是 Sidebar
```

不能自动标：

```text
FACT
```

除非有更强 Evidence。

# 二十四、Source 本身的命名也不一定是事实

例如 Figma Layer 叫：

```text
Button
```

但实际可能只是设计师随手命名。

所以：

```text
Layer Name = Button
```

可以提高 Evidence，但不能自动：

```text
Semantic Fact = Button
```

仍要结合结构、视觉和上下文。

# 二十五、Confidence 和 Authority 必须分离

例如：

```text
confidence = 0.98
```

只能表示：

> 解析器很有把握。

不能表示：

```text
Human Confirmed
Approved
Current Effective
Authority
```

所以必须冻结：

```text
Confidence
≠ Authority

Confidence
≠ Approval

Confidence
≠ Current Effective
```

# 二十六、Evidence State 必须贯穿链路

建议整个 D03 都遵守：

```text
FACT
INFERENCE
RECOMMENDATION
UNKNOWN
```

但精确 enum 后面再定。

核心要求是：

> 不能因为一个数据经过了很多处理步骤，就从 INFERENCE 自动变 FACT。

例如：

```text
Raw Scene
↓
Normalized Scene
↓
Semantic Tree
```

经过三层之后：

```text
Sidebar inference
```

依然是 inference。

---

# 二十七、UNKNOWN 不能因为“设计需要完整”被消掉

例如静态图没有：

```text
hover
loading
animation
keyboard
drag
```

则：

```text
UNKNOWN
```

不能：

> “通常按钮都有 hover，所以我补一个。”

如果后来 UI Design Rules 给出建议：

```text
Hover SHOULD...
```

那也只是：

```text
Rule-derived Design Decision
```

不是：

```text
Observed Evidence
```

# 二十八、Behavior Evidence 只在有证据时产生

D03 本轮不展开完整 Behavior Model。

但要先冻结边界。

可以提供 Behavior Evidence 的 Source 例如：

```text
interactive prototype

screen recording

```

单张静态 PNG 通常不能证明：

```text

gesture
hover behavior
drag behavior
animation duration
```

# 二十九、Design Source 的 Scope 必须结构化

一个 Source 至少逻辑上需要知道：

不要求每项都一定知道。


# 三十二、Latest Source 不能自动获胜

例如：


不能：

```text

```

必须知道：

# 三十三、多数 Source 不能自动获胜

例如：

```text

1 张正式批准新图 = 红色
```

不能：

```text
3 > 1
所以蓝色
```

Authority/Version/Intent 比数量重要。

# 三十四、真正的 Design Conflict

只有在类似这种情况下才成立：

```text
same project
same app
same page
same state
same viewport/device
same target version
same semantic fact
```

而两个有效来源给出不可兼容值：

```text
radius = 8
vs
radius = 20
```

才进入：

```text
DESIGN_CONFLICT
```

---

# 三十五、Conflict 不由 Provider 或 AI Guess 决定

如果：

```text
Source A
vs
Source B
```

无法通过 Authority / Version / Scope 解决：

```text
Conflict
```

进入既有：

```text
Reconciliation / Decision
```

不能：

> “AI 觉得 12px 比较现代，所以选 A。”

# 三十六、Existing UI 的地位

现有页面也是 Design Material。

但默认属于：

```text
Current Reality Evidence
```

不是：

```text
Desired Target
```

例如现有页面：

```text
一级分类没有选中三角
```

而目标图：

```text
有三角
```

不能因为代码已经落地：

> “代码现在这样，所以目标也应该这样。”

---

# 三十七、Existing UI 什么时候可以参与 Target

如果用户明确：

> “沿用现有后台视觉风格。”

那么 Existing UI 可以成为：

```text
Baseline Design Evidence
```

用于帮助形成：

```text
Shared Foundation / Design Decision
```

但仍需要保留来源角色。

---

# 三十八、Reference Design 也不能自动成为 Target

例如用户：

> “参考这个苹果官网。”

则：

```text
Reference Source
```

只能支持：

```text
style inspiration
layout idea
interaction recommendation
```

不能：

> 直接复制成当前项目事实。

# 三十九、UDC 不通过 Scene Pipeline

例如用户说：

> “一级、二级、三级共用底板。”

D01 可以登记这句话。

经过语义治理：

```text
→ UDC
```

它不需要：


才能进入 Design Formation。

# 四十、Shared Foundation 也不通过 Scene Pipeline

Foundation 已经是治理后的项目设计事实。

它直接参与：

```text
Design Reconciliation
```

而不是重新被 AI 从图里“识别一次”。

---

# 四十一、UI Design Rules 同样不是 Scene Evidence

例如：

> “选中状态应明显。”

是 Design Rule。

不是：

```text

```

它只能参与：

```text
Design Decision Formation
```

# 四十二、无图设计必须是一等公民

```text
↓

↓
```

# 四十三、无图设计禁止伪造 Scene

不能为了“链路完整”生成：

没有 Scene Source：

```text

```

而不是：

```text

```

# 四十四、Partial Design 必须一等支持

例如：

```text
只有 Header + Category Area 设计图
```

则：

```text

```

后续 Content 可以：

```text
Human decision

Autonomous design
```

形成。

但不能：

```text
全部变成 SOURCE_EVIDENCE
```

# 四十五、Design Truth Model 的核心定义

这是 D03 最重要的一项。

建议正式定义：

> **Design Truth Model = 当前具体 Design Target 中，经过来源对账、语义解析和治理决策后，被认定为当前设计目标组成部分的结构化设计事实模型。**

它回答：

```text
这个页面最终应该是什么？
```

---

# 四十六、Design Truth 允许多个 Origin

例如：

```text
一级分类左侧
origin = HUMAN_CONSTRAINT
```

```text
品牌主色
origin = FOUNDATION_INHERITANCE
```

```text
二级标签是胶囊形
origin = SOURCE_EVIDENCE
```

```text
未给 hover 状态，按项目 Rule 形成 hover
origin = RULE_DERIVED
```

```text
某低风险间距由系统授权自动选择
origin = AUTONOMOUS_DESIGN_DECISION
```

所以：

> Design Truth 是当前 Target Truth。

但：

> Origin 仍然必须诚实。

---

# 四十七、Target Truth 和 Evidence Fact 要区别

例如：

```text
最终设计：
padding = 24
```

可能是真的当前设计目标。

但来源可能是：

```text
AUTONOMOUS_DESIGN_DECISION
```

而不是：

```text
SOURCE_EVIDENCE
```

所以：

```text
Target Truth
≠ Observed Fact
```
