好，进入 **F6-D02-04**。

这一轮解决的是你以后真正“喂前端规则物资”时最关键的一刀：

# F6-D02-04 — Material → Rule Entry Extraction & Reconciliation
## 前端规则物资 → 一笔一笔规则条目的提取、归纳与对账机制

当前仍是：

```text
Status = HUMAN_REVIEW
Implementation = NOT_AUTHORIZED
```

先给结论：

> **Banyan 不能把一份规范里的每句话、每个标题、每个代码示例都生成一条 Rule Entry（规则条目）。**
>
> 正确方式应该是：**先完整盘点物资 → 提取有价值知识片段 → 判断“这是不是规则” → 语义聚类和压缩 → 与已有规则对账 → 最后才形成少量、完整、可复用的一笔一笔 Rule Entry。**

这样才能防止你以后投一个 100 页文档，系统给你制造 500 条垃圾规则。

---

## 一、四源对账先确认方向

v3.1 原来已经要求一批资料进来后先登记来源、检查完整性和重复、摘要新增/修改/保留/废弃、识别冲突风险和缺口，再形成批次摘要，而不是拿到材料就直接生成最终产物。fileciteturn95file3L1047-L1067

F5 又进一步冻结：AI 可以对输入做 `extract / normalize / split / merge / dedup / structure Candidate`，也就是提取、归一、拆分、合并、去重和结构化候选；但 Source Material（来源物资）本身不等于正式语义对象。fileciteturn94file26L1-L25

同时 v3.1 原本已经坚持 `standards/` 是工程规范单点真源，其他设计或模块文档只能引用，不能再复制一套规范正文。fileciteturn95file4L1393-L1404

所以 D02-04 可以沿着这个方向继续，而不是重新发明一套“文档摘要器”。

---

# 二、最重要的第一条：一句话不等于一条规则

比如物资里写了：

> 卡片列表适合使用 Grid。

下一段：

> Grid 可以很好地保持多个卡片对齐。

然后又有代码：

```css
display: grid;
grid-template-columns: repeat(4, 1fr);
gap: 16px;
```

不能生成：

```text
RULE-001：卡片列表适合 Grid
RULE-002：Grid 可以保持对齐
RULE-003：使用 display:grid
RULE-004：使用 repeat(4,1fr)
RULE-005：gap 使用 16px
```

这明显是垃圾规则爆炸。

正确应该先判断：

> 这些内容是不是在讲同一个工程原则？

最终可能只形成一条：

```text
规则：
对于规则性的二维重复内容，
优先根据真实布局关系考虑 Grid，
而不是依赖子项固定坐标和手工换行。
```

而：

```text
为什么：
Grid 更适合二维轨道约束。

代码：
repeat(4, 1fr)
```

都只是这条规则的：

```text
Rationale
理由

Example
示例
```

不是新的规则。

---

# 三、所以第一步不是“抽 Rule”，而是先抽 Knowledge Fragment
## 知识片段

一份物资读完以后，AI 先把有价值内容识别出来。

例如一份文档可能包含：

```text
规则原则
解释说明
代码示例
错误案例
适用条件
例外条件
版本说明
术语定义
历史背景
废弃说明
性能提示
兼容限制
```

这些都可能有价值。

但：

> **有价值 ≠ 都是 Rule Entry。**

所以建议逻辑上先存在：

`Knowledge Fragment（知识片段）`

这只是物资盘点工作区里的内部分类，不需要因此再造一个新的 Framework 顶层 Artifact。

---

# 四、知识片段至少要先分成几种性质

具体最终枚举名字以后可以调整，但语义必须区分。

例如：

```text
A. RULE_CANDIDATE
   规则候选

B. RATIONALE
   规则理由

C. EXAMPLE
   示例

D. ANTI_PATTERN
   错误模式 / 反例

E. FACT
   技术事实

F. APPLICABILITY
   适用条件

G. EXCEPTION
   例外条件

H. VERSION_CONSTRAINT
   版本限制

I. TERMINOLOGY
   术语解释

J. DEPRECATION
   废弃 / 替代信息

K. REFERENCE_ONLY
   参考信息

L. UNCERTAIN
   当前无法可靠判断
```

这样 AI 就不会看到什么都喊：

> “这是一条规则！”

---

# 五、举个组件规范物资的例子

假设一份官方文档写：

> 某组件在新版中不再支持属性 X。建议迁移到属性 Y。对于复杂筛选场景，可以使用方案 Z。下面给出示例……

盘点以后可能得到：

### 技术事实

```text
属性 X 在某版本已经移除
```

### 迁移规则候选

```text
满足版本条件时，不得继续使用 X，
应迁移到 Y。
```

### 可选方案

```text
复杂筛选场景可以考虑 Z。
```

### 示例

```text
一段代码
```

所以不是：

> 整段文档 = 一条规则。

也不是：

> 每一句话 = 一条规则。

---

# 六、第二步：Rule Qualification Gate
## 什么东西才有资格成为规则

我建议一条知识要形成 Rule Entry Candidate（规则条目候选），至少通过下面这些判断。

### 1. 它必须解决一个明确的工程问题

例如：

> “父级 Grid 已经决定子项尺寸时，不要再给每个子项写截图测量宽度。”

很明确。

---

### 2. 它具有复用价值

如果只是在讲：

> “2026 年 9 月这个项目某页面临时写了 42px。”

通常不是公共规则。

可能只是项目证据。

---

### 3. 它必须能够指导一次实际选择

例如：

```text
应该怎样做
不应该怎样做
什么条件下这样做
```

而不是纯科普。

---

### 4. 它有一个相对完整的责任边界

不能：

```text
颜色不要乱用
```

这么模糊。

也不要：

```text
padding-left 16px
```

这么碎。

---

### 5. 它的适用范围至少基本可判断

例如：

```text
所有 Web 页面？

只有移动端？

只有特定组件体系？

只有某个版本？

只有表格场景？
```

完全无法判断时，先保持 Candidate / Unknown。

---

### 6. 它不能只是另外一条规则的解释

理由和示例应该挂在已有规则下面。

---

### 7. 它不能和已有规则纯语义重复

要先对账。

---

# 七、第三步：Semantic Clustering
## 语义聚类，防止垃圾规则

这是 D02-04 最重要的“压缩层”。

例如物资里有 17 个句子：

```text
不要抄截图坐标
不要全部 absolute
不要机械写 left/top
页面结构要使用真实布局
Flex 应表达关系
Grid 应表达轨道
截图位置只是当前结果
……
```

AI 不应该形成 17 条。

要先判断：

> 哪些其实属于同一完整原则？

可能最终形成：

```text
RULE-A
布局实现关系，而不是抄截图坐标。

RULE-B
Absolute 只应用于真正的脱离文档流关系。

RULE-C
Rendered Geometry 不自动等于固定尺寸。
```

17 句话压成 3 条完整规则。

这就是：

> **Rule Compression（规则语义压缩）。**

不是“删信息”，而是把：

```text
规则正文
理由
示例
错误模式
来源证据
```

放回正确的位置。

---

# 八、非常重要：压缩不能丢信息

比如 17 个片段最后只形成 3 条 Rule Entry。

其余 14 个片段不能：

> “没成为独立规则，所以删了。”

应该成为：

```text
Rule A
├── source 1
├── source 2
├── rationale
├── examples
└── anti-patterns
```

或者保留为相关 Supporting Knowledge（辅助知识）。

也就是说：

> **减少 Rule 数量 ≠ 减少有价值信息。**

这和你一直强调的：

> **本期有价值但暂时不能确定的内容绝不能丢**

完全一致。

---

# 九、第四步：和已有 Rule Entry 做语义对账

形成 Rule Candidate 后不能直接：

```text
append 到模块尾部
```

必须找已有规则。

例如候选：

> “父级 Grid 决定卡片宽度时不要给 Card 固定宽度。”

已有规则：

> “Parent-driven Sizing（父级驱动尺寸）：父容器决定子项尺寸时，子项应优先 stretch/fill，而不是重复声明截图宽度。”

显然是同一条。

所以结果应该：

```text
ENRICH_EXISTING
增强已有规则
```

而不是新建 Rule ID。

---

# 十、我建议对账结果至少能表达这些语义

具体枚举名以后可以定，但逻辑必须存在：

```text
NEW
新的独立规则

DUPLICATE
语义重复

ENRICH
补充理由 / 示例 / 来源

REFINE
把已有规则表达得更准确

SCOPE_REFINEMENT
补充或收窄适用范围

APPLICABILITY_REFINEMENT
补充适用条件

STRENGTH_CHANGE
规则强度发生变化

REVISION
规则语义发生有效修订

SUPERSESSION
新规则正式替代旧规则

CONFLICT
同范围内真正互相矛盾

NON_RULE
有价值，但不属于规则

DEFERRED
有价值但暂时无法可靠归纳
```

---

# 十一、怎么判断“同一条规则”

这个必须有语义标准，不能只做文字相似度。

判断重点应该看：

```text
解决的是不是同一个问题
+
要求的工程结果是不是同一个
+
适用条件是不是兼容
+
Scope 是否兼容
```

例如：

### 物资 A

> 卡片容器采用 Grid 时，卡片宽度由轨道控制。

### 物资 B

> Grid 下不要再给每个 Card 写当前截图测出的 width。

文字不一样。

但语义是高度一致的。

应该：

```text
同一 Rule Entry
```

---

# 十二、仅仅换措辞不创建新 ID

比如：

```text
旧：
不要把测量宽度直接固定。

新：
Rendered Geometry 不能自动推断为 Fixed Sizing。
```

如果核心语义没变化：

> Rule ID 继续保持。

只是正文可能得到更准确表达。

---

# 十三、增加示例，也不是新规则

旧规则：

```text
二维重复布局优先根据结构判断 Grid。
```

新物资补了一段：

```css
grid-template-columns:
  repeat(auto-fit, minmax(240px, 1fr));
```

结果：

```text
ENRICH
补充 Example
```

不是：

```text
NEW RULE
```

---

# 十四、增加“为什么”，也不是新规则

例如新资料解释：

> 这样可以减少断点数量，让卡片自然重排。

应该：

```text
Rationale += ...
```

而不是重新产生：

> “减少断点是一条规则。”

除非它自己确实构成另一个完整工程约束。

---

# 十五、Scope 变了要谨慎

例如旧规则：

> Web 后台卡片墙推荐 Grid。

新物资说：

> 所有前端页面都必须 Grid。

这就不是普通补充。

它扩大了：

```text
Scope
```

同时可能改变：

```text
Strength
```

这种必须标：

```text
SCOPE_CHANGE
+
STRENGTH_CHANGE
```

不能自动当“新版表述更完整”直接覆盖。

---

# 十六、真正冲突是什么

物资 A：

> 同类卡片宽度必须由父级 Grid 决定。

物资 B：

> 当前组件在某版本必须使用固定宽度才能正常虚拟滚动。

这不一定立刻是冲突。

因为可能：

```text
Scope 不同
条件不同
技术版本不同
```

系统要先看看能否变成：

```text
通用规则
+
特定条件例外
```

只有当两条都是：

```text
同一 Scope
同一适用条件
同一问题
但要求相反
```

才是真正：

```text
CONFLICT
```

---

# 十七、冲突不能靠“新文档覆盖旧文档”

我们已经冻结：

```text
Latest != Current Effective
最新 ≠ 当前有效
```

所以你以后投：

> 《前端开发规范 v8.pdf》

不能：

```text
v8 新
↓
把以前全部覆盖
```

仍然必须逐条做：

```text
ADD
KEEP
REFINE
SUPERSEDE
CONFLICT
```

而不是文件级 `latest wins`。

---

# 十八、第五步：形成 Reconciled Rule Delta
## 规则最小变化集

一批物资盘完以后，不重新生成整个 Module。

应该得到：

```text
Reconciled Rule Delta
规则对账变化集
```

例如：

```text
Module A

新增：
3 条

增强已有：
7 条

补充示例：
11 条

补充适用范围：
2 条

重复：
14 条

替代候选：
1 条

真实冲突：
1 条

Deferred：
2 条
```

然后只处理变化部分。

这和 F5 已冻结的：

> Reconciliation-first，并产生 smallest valid delta（最小有效变化）

是同一个思想。fileciteturn94file26L7-L24

---

# 十九、100 页文档实际可能是什么效果

假设你投：

```text
《某前端工程最佳实践》
100 页
```

里面有：

```text
328 个段落
104 个代码片段
61 个注意事项
```

最后不应该得到：

```text
493 条规则
```

有可能最终结果只是：

```text
15 条真正新 Rule Entry

21 条增强已有规则

38 个新增 Example

16 个新增 Anti-pattern

9 个版本限制

4 个废弃关系

2 个冲突

17 个有价值但非 Rule 的知识片段

1 个 Carry-Forward
```

这个结果才健康。

# 二十、Rule Entry 正文应该是什么形态

现在不冻结具体 YAML，但逻辑上一条规则应该能回答：

```text
1. 这条规则解决什么问题？

2. 正式规则正文是什么？

3. 什么情况下适用？

4. 什么情况下不适用？

5. 强度是什么？

6. 为什么这样做？

7. 有什么正确示例？

8. 有什么错误模式？

9. 来自哪些物资和具体证据？

10. 是否关联其它 Rule？

11. 是否存在例外 / 版本限制？

12. 当前版本 / 状态是什么？
```

但不是说每条规则都强制写满 12 大段。

仍然遵循：

> **Schema 可以完整，实际 Rule Entry 保持必要最小信息。**

---

# 二十一、规则正文和例子一定分开

这是一个硬边界。

例如：

```text
Rule Body：
规则二维内容优先根据布局关系采用二维布局策略。

Example：
4 列 Grid。
```

后续 AI 不能理解为：

> “所有场景必须 4 列。”

所以：

```text
Rule
≠ Example
```

同样：

```text
Rule
≠ Rationale
```

---

# 二十二、来源追踪必须做到“能反查”

以后看到：

```text
FE-RULE-017
```

必须能够知道：

```text
最初来源于哪一个项目

哪一批 Material

哪几个文件

哪些内容片段

后来又被哪些物资补充

哪一次改变了 Scope

哪一次改变了 Strength

谁决定过冲突
```

这样以后规则有问题，不用猜：

> “这是谁总结出来的？”

---

# 二十三、一份物资可以产生多条 Rule Entry

例如《移动端开发规范》可以同时产生：

```text
安全区 Rule
触摸目标 Rule
键盘避让 Rule
底部导航 Rule
滚动 Rule
```

所以：

```text
Material → many Rules
```

很正常。

---

# 二十四、多份物资也可以共同支持同一条规则

例如：

```text
Material A
Material B
Material C
```

全部都在表达：

> 同一个 Parent-driven Sizing 原则。

那么：

```text
A ─┐
B ─┼→ RULE-017
C ─┘
```

而不是三个重复 Rule。

这叫：

> **Many Sources → One Rule。**

---

# 二十五、有价值但不是规则的内容怎么办

这个是 No-Loss（无损）必须重点解决的。

比如物资里发现：

> “某浏览器版本存在特殊渲染 Bug。”

它可能不是长期前端 Rule。

但它有价值。

可以：

```text
保留为 Supporting Knowledge / Evidence
辅助知识 / 证据
```

以后：

```text
某个兼容性模块出现
```

再重新盘点。

---

# 二十六、有价值但暂时不知道怎么归类

例如：

> “这部分似乎是一种重要前端原则，但目前只有一份资料，作用范围也不明确。”

不能：

```text
不生成 Rule
↓
直接丢掉
```

必须：

```text
DEFERRED
↓
Carry-Forward
```

以后相关物资进来自动重新盘。

这继承 F5 对 Deferred 的要求：延期项不能因为不阻塞当前工作就消失，必须保留 lineage（来源演进）和 revisit capability（重新访问能力）。fileciteturn94file26L34-L45

---

# 二十七、`.banyan` 里应该承载这整个提取工作区

按照我们上一轮已经调整好的边界：

```text
当前项目/.banyan/
```

逻辑上可以持有：

```text
Material
↓
Knowledge Fragment
↓
Rule Candidate
↓
Reconciliation Result
↓
Conflict Buffer
↓
Carry-Forward
```

这些都是当前项目在加工物资过程中产生的治理状态。

---

# 二十八、但 Candidate 不等于共享规则正文

例如：

```text
Project A/.banyan
↓
RULE-CANDIDATE-037
```

如果未来确认：

> 这是 Project A 专属规则。

它进入项目工程规范。

如果确认：

> 这是跨项目通用前端规则。

则：

```text
Reusable Candidate
↓
Governed Promotion
受治理晋升
↓
Shared Frontend Rule System
```

不能说：

> 因为在 A 项目里 AI 抽出来了，所以全世界项目立刻生效。

---

# 二十九、哪些事情可以 AI 自动做

为了使用体验和速度，我建议自动化：

```text
物资切片
知识片段分类
明显重复检测
语义聚类
同义合并候选
Example / Rationale 识别
明显模块匹配
已有 Rule 查找
来源 Trace
普通新增 Candidate
批次摘要
```

这些是治理成本。

应该由 Banyan 承担。

---

# 三十、哪些事情不能 AI 静默决定

下面这些需要升级治理：

```text
把推荐规则改成 REQUIRED
把允许改成 FORBIDDEN

把项目规则扩大成共享规则

大幅扩大 Scope

正式替代一个 Current Effective Rule

废弃一个被大量项目使用的 Rule

同 Scope 的规则真正冲突

从一份模糊材料推导新的强制工程原则

无法确认版本适用性但影响关键施工
```

这些应该：

```text
Candidate
↓
Impact
↓
Decision / Buffer
```

而不是 AI 自己拍板。

# 三十一、用户最终看到什么

绝对不应该给你看：

> “本批提取 182 个 Fragment，请逐项确认。”

正确应该是：

> **本批前端规则物资盘点完成。**

例如：

```text
读取：6 份物资

涉及已有模块：2 个

提取有价值知识：73 项

归纳后：

新增规则候选：8 条
增强已有规则：11 条
新增示例：17 项
重复内容：29 项
版本限制：3 项
Deferred：4 项
真正需要你决定：1 项
```

然后只展开：

> **需要你决定的 1 项是什么。**

这才符合我们一直要的：

> **便捷但可靠。**

# 三十二、Rule Extraction 也必须按“受影响范围”工作

例如你说：

> “这是某个已有模块的第 4 批补充规范。”

系统已经大概率知道 Scope。

不应该每次：

```text
读取所有 300 个模块
读取所有 5 万条规则
```

而应该：

```text
本批 Theme
+
Material 内容
+
Module Index
↓
先找相关模块
↓
只读取相关 Module Canonical Rules
↓
必要时扩展查询
```

这保证速度。

# 三十三、但是速度不能牺牲查重质量

不能因为只看 Module A：

> 结果相同规则其实已经在 Module B 中存在。

所以需要：

```text
先轻量全局索引查语义候选
↓
再精准读取少量 Canonical Rule Body
```

也就是：

> **索引负责找，正式文件负责判断。**

仍然对应：

> **文件存真相，SQLite 存地图。**

# 三十五、F6-D02-04 候选不变量

我建议这一轮形成下面这些候选规则：

```text
RE-01
Material 中的句子、段落、标题、代码片段
都不自动等于 Rule Entry。
```

```text
RE-02
Material 必须先提取 Knowledge Fragment，
区分规则候选、理由、示例、反例、事实、
版本条件、例外、术语和未知等语义。
```

```text
RE-03
只有通过 Rule Qualification 的知识
才能成为 Rule Entry Candidate。
```

```text
RE-04
Rule Entry 粒度遵循最小完整工程规则边界，
不得“一句话一规则”，也不得万能大规则。
```

```text
RE-05
在创建新 Rule 前必须进行语义聚类、
去重以及 Existing Rule Reconciliation。
```

```text
RE-06
文字不同但工程问题、目标语义和适用范围兼容时，
优先视为同一 Rule，不因措辞变化创建新 ID。
```

```text
RE-07
Reason、Example、Anti-pattern、
Source Evidence 等优先增强现有 Rule，
不得机械生成新的 Rule Entry。
```

```text
RE-08
Scope、Applicability、Strength 的实质变化
必须被显式识别，不得伪装成普通文字更新。
```

```text
RE-09
真正同 Scope、同条件但工程要求相反时
才形成 Rule Conflict；
版本差异和条件例外应优先结构化处理。
```

```text
RE-10
每批物资默认只产生 Reconciled Rule Delta，
不得整模块重生成。
```

```text
RE-11
一份 Material 可支持多个 Rule；
多个 Material 也可共同支持同一 Rule。
```

```text
RE-12
每个 Rule 必须可反向追踪到来源 Material /
Batch / Evidence。
```

```text
RE-13
有价值但不适合成为 Rule 的信息不得丢弃；
按 Evidence / Supporting Knowledge /
Deferred 等方式保留。
```

```text
RE-14
有价值但当前无法可靠归纳的内容必须进入
Carry-Forward，未来相关物资进入时重新盘点。
```

```text
RE-15
AI 可自动执行提取、分类、聚类、去重、
普通候选形成和 Trace；
高影响 Strength / Scope / Supersession /
Shared Promotion / Conflict 不得静默决定。
```

```text
RE-16
Rule Extraction Workspace 属于当前项目
.banyan Project Instance，
Candidate / Fragment / Reconciliation Result
均为 NON-CANONICAL，不能冒充正式共享规则。
```

# 三十六、用一句最直白的话总结 D02-04

> **你以后可以把一整批 Markdown、PDF、官网规范、自己的总结直接投进 `.banyan` 的统一物资入口，不需要自己一条一条整理。Banyan 先完整盘点，把规则、解释、示例、事实、版本限制等拆开，再把表达同一工程原则的内容重新合并，对照已有规则，最后只形成真正有独立价值的一笔一笔规则。重复的不重复建，例子只挂例子，理由只挂理由，冲突进入缓冲区，暂时搞不清但有价值的进入 Carry-Forward，绝不因为“没形成规则”就把有价值内容扔掉。**

这套机制基本能把你最担心的两个问题同时解决：

```text
一份大规范 → 几百条垃圾规则
```

和：

```text
为了不制造规则 → 有价值内容被漏掉
```

都避免掉。

下一步最自然的是 **F6-D02-05：Module Index + Rule Association Index（模块索引与规则语义对照索引）**，正式解决你前面最看重的：

> **PRD / Design Package / Current Code 识别出“气泡选中、三角、表格、搜索、移动端”等语义后，系统到底怎样快速、准确地自动找到对应模块和具体 Rule Entry，而且不依赖大模型每次从头猜。**
