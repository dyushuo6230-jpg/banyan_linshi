好，按这个方向继续。

你刚才关于 **“歧义时允许 AI 结合当前项目 + 可靠现代实践进行有边界自主裁决”** 的提议，我先正式放进跨阶段承接清单，避免后面丢掉：

```text
CROSS-STAGE-AUTONOMY-01
Bounded Autonomous Resolution
有边界的自主裁决

Direction = HUMAN_CONFIRMED
Implementation = NOT_AUTHORIZED
```

后续 Owner 已明确：

```text
F6  → 定义领域歧义、规则候选和调用接口
F8  → Project Autonomy Profile / 当前项目允许 AI 自主到什么程度
F9  → Context / Freshness / External Evidence / 市场与官方实践
F10 → Permission / 是否真正允许自动执行
F11 → 自动裁决记录、解释、查看与人工覆盖
F12 → Legacy 迁移时复用
```

所以后面到这些阶段我会主动把它重新拉出来，不会靠“记得以后再说”。

---

# 继续：F6-D02-06
## Frontend Profile × Effective Rule Set
### 项目前端规则配置 × 当前任务有效规则集

这一项是把 D02-01～D02-05 真正串起来。

我们前面已经有：

```text
Rule Module
模块

↓
Rule Entry
规则条目

↓
Module Index
模块索引

↓
Rule Association Index
规则关联索引
```

但真正开发一个项目时，还缺：

> **这个项目到底采用哪些规则模块？采用哪个版本？项目自己的规则放哪里？任务开始后怎样只给 AI 最少但足够的一组规则？**

这就是 D02-06。

---

# 一、先给核心结论

我建议正式区分两个对象：

```text
Frontend Profile
项目前端规则配置
```

和：

```text
Effective Frontend Rule Set
当前任务有效前端规则集
```

二者完全不同。

大白话：

> **Profile 说“这个项目平时采用哪些规则体系”。**

> **Effective Rule Set 说“做眼前这个任务时真正要执行哪些规则”。**

---

# 二、Frontend Profile 是项目长期配置

例如这里只举例，不冻结正式模块名称：

```text
Project A

Frontend Profile
│
├── 某通用 Web 模块
├── 某框架模块
├── 某组件体系模块
├── 某项目专属模块
└── 某专项质量模块
```

这表示：

> Project A 平时从这些知识范围里选择前端规则。

但不意味着：

> 每次开发都把这些模块所有规则全部读一遍。

---

# 三、Effective Rule Set 是一次任务的派生结果

例如当前任务：

> “用户管理页面增加状态筛选，并按设计图修复选中气泡样式。”

系统可能最终只需要：

```text
RULE-017
RULE-038
RULE-102
RULE-155
RULE-PROJECT-009
```

那么当前任务就是：

```text
Effective Frontend Rule Set
= 这 5 条
```

其余数百条规则不进入 Coding Context。

所以：

```text
Profile
≠ Effective Rule Set
```

---

# 四、这样直接满足你要求的“速度快”

错误方式：

```text
Frontend Profile 有 9 个 Module
↓
9 个 Module 全读
↓
900 条 Rule 全塞给 AI
```

正确：

```text
Frontend Profile
↓
限制可用 Module
↓
当前任务语义
↓
Module Index
↓
Rule Association Index
↓
Scope / Applicability
↓
Consistency Check
↓
最终 8 条规则
```

因此 Profile 负责：

> **先缩小世界。**

Rule Index 负责：

> **再精准定位。**

---

# 五、Profile 不复制规则正文

这个继续作为硬边界。

Profile 只能记录：

```text
采用什么 Module / Rule Pack
采用哪个版本或版本策略
适用于什么 Scope
有哪些合法 Project Override
项目专属规则在哪
```

不能：

```text
把 Module A 的 200 条正文复制一遍
把 Module B 的 300 条正文再复制一遍
```

否则将来一定形成双真源。

---

# 六、Profile 也不能只是一张“模块开关表”

这点要优化。

如果只有：

```text
Module A = ON
Module B = ON
Module C = OFF
```

还不够。

因为项目可能说：

> Module A 只用于 admin；
> Module B 只用于 mobile；
> Module C 某版本暂时禁用；
> Module D 只有特定页面使用。

所以 Profile 逻辑上至少需要表达：

```text
Binding
绑定什么

Scope
在哪生效

Version
采用哪个版本

Conditions
什么条件下适用

Override / Exception
有什么项目级覆盖

Status
当前是否有效
```

具体 YAML 字段以后实现冻结再定。

---

# 七、模块版本必须由 Profile 控制

这是可靠性很重要的一点。

例如共享模块：

```text
Module A v1
↓
v2
↓
v3
```

Project A 当前经过验证的是：

```text
v2
```

公共库更新到 v3 后：

> Project A 不能第二天突然被改成 v3。

应该：

```text
Shared Module Current = v3

Project A Profile
= pinned / compatible policy → v2
```

然后后续：

```text
发现 v3
↓
Impact Analysis
↓
Compatibility Check
↓
Profile Upgrade Candidate
```

确认适合再切。

---

# 八、“最新”仍然不能等于“项目当前有效”

所以必须保持：

```text
Latest Module
≠
Current Effective Module
```

同理：

```text
Latest Rule
≠
Current Effective Rule
```

这个原则不能因为我们现在做 Profile 就破坏掉。

---

# 九、项目自己的规则怎么进入 Profile

比如公共模块说：

> 表格操作过多时建议折叠。

Project A 有正式约束：

> 本项目后台默认最多展示 2 个直接操作。

那么：

```text
Shared Module
+
Project-specific Rule Module
```

同时进入 Profile。

项目规则不用复制公共规则。

只负责表达：

> Project A 真正不同的地方。

---

# 十、项目规则也不能随便“覆盖所有共享规则”

仍然复用 D02-02：

```text
Strength
Authority
Scope
Applicability
Override Policy
```

例如：

```text
Shared REQUIRED + non-overridable
```

项目不能因为自己定义了一条：

```text
Project OPTIONAL
```

就把它顶掉。

所以：

> **Profile 只负责组合；Profile 本身没有权力发明新的覆盖优先级。**

这条非常重要。

---

# 十一、Profile 不重新定义 Rule Priority

这是我们新增全局“条款不要打架”的直接要求。

D02-02 已经负责：

```text
Strength / Authority / Scope / Applicability / Override
```

D02-06 就不能再说：

> “Profile 中排在下面的 Module 优先。”

禁止这种设计。

因此：

```text
Profile Ordering
≠ Rule Priority
```

就算文件里：

```text
Module A
Module B
Module C
```

也不能：

> “C 最后加载，所以 C 赢。”

---

# 十二、禁止 CSS 那种“last one wins”思维进入规则治理

以后尤其要防止 AI误判：

```text
后加载规则覆盖先加载规则
后写 Rule 覆盖前写 Rule
Profile 最后一项优先
文件夹后一个优先
```

全部禁止。

真正冲突仍然走 D02-02 + D02-05。

---

# 十三、Profile 最好支持“组合”，而不是继承大树

我不建议设计成：

```text
GlobalProfile
  ↓
WebProfile
    ↓
AdminProfile
      ↓
ReactProfile
        ↓
AntProfile
          ↓
ProjectProfile
```

继承六七层。

虽然看起来整齐，但以后非常难知道：

> 一条规则到底从哪继承来的。

更好的设计是：

```text
Project Frontend Profile
       │
       ├── binds Module A
       ├── binds Module B
       ├── binds Module C
       └── binds Project Module P
```

即：

> **Composition over deep inheritance**
> 以组合为主，避免深层继承。

---

# 十四、模块自身也不要偷偷激活大量其它模块

比如：

```text
用了 React Module
↓
自动激活 Web + Ant + Tailwind + Mobile
```

这是危险的。

Module 之间可以存在必要依赖：

```text
depends_on
```

但：

> 项目采用哪些主要 Module，应该由 Profile 可见地决定。

避免隐藏规则链。

---

# 十五、Effective Rule Set 如何生成

我建议架构流程正式定成：

```text
Task Intent / Goal
        ↓
Project Frontend Profile
        ↓
Current Effective Modules
        ↓
PRD Semantic
Design Package Semantic
Current Code Semantic
Project Context
        ↓
Module Index
        ↓
Rule Association Index
        ↓
Scope Filter
        ↓
Applicability Filter
        ↓
Version Filter
        ↓
Strength / Authority / Override Resolution
        ↓
Cross-Rule Consistency Check
        ↓
Effective Frontend Rule Set
```

这是当前 D02 最完整的一条链。

---

# 十六、Effective Rule Set 必须是“最小充分集”

这条建议成为硬原则：

> **Minimum Sufficient Rule Context（最小充分规则上下文）**

不能：

> 越多越保险。

过多规则反而容易让 AI：

```text
混淆
误关联
注意力分散
产生伪冲突
浪费 Token
```

所以目标是：

```text
少，但不能漏关键规则
```

而不是：

```text
多，就一定可靠
```

---

# 十七、但“最小”不能为了省 Token 漏强制规则

所以还要配一条：

```text
Token Efficiency
不得降低 Governance Fidelity
```

例如当前任务只看起来是：

> “调一个按钮样式。”

但如果该按钮：

```text
是危险删除操作
```

相关安全/交互强制规则仍必须加载。

不能因为：

> “这次只是 CSS 任务”

就漏掉。

---

# 十八、因此 Effective Rule Set 可以有两类来源

我建议逻辑上分：

### A. Semantic-Matched Rules
任务语义匹配出来的规则

例如：

```text
table
selected
scroll
modal
```

---

### B. Mandatory Context Rules
无论是否被关键词直接命中都必须带上的规则

例如可能包括：

```text
项目不可绕过规范
安全类约束
必须的 Accessibility
当前项目强制框架约束
```

具体哪些以后由规则本身和 Profile 决定。

最终：

```text
Effective Rule Set
=
Semantic Matched
+
Mandatory Context
```

这样既快，又不漏治理底线。

---

# 十九、Effective Rule Set 不应该成为新的长期 Authority

这个继续保持：

```text
Effective Rule Set
= Derived / Rebuildable
```

它只是：

> 某一任务、某一时间、某一 Project Profile 下算出来的结果。

如果：

```text
Profile 变了
Rule Version 变了
Design Package 变了
PRD 变了
```

它应该：

```text
STALE
→ regenerate
```

而不是手工继续编辑旧的 Effective Set。

---

# 二十、但是为了可追踪，要保存“当时实际用了哪些规则”

例如半年以后出现 Bug。

应该能查：

```text
TASK-017
当时使用：

RULE-A v2.1
RULE-B v4.0
RULE-P-009 v1.2
```

而不是只看：

> 今天最新规则是什么。

所以这里要区分：

```text
Effective Rule Resolution
当前计算结果
```

和：

```text
Execution Rule Snapshot / Trace
当时执行证据
```

前者可重建。

后者是审计证据。

---

# 二十一、这对“规则升级后旧代码是否要改”非常重要

例如：

```text
2026-09
页面 A 用 RULE-017 v2

2026-12
RULE-017 升 v3
```

不能：

> v3 一出就认为页面 A 错了。

要先判断：

```text
v3 是否适用于已存在代码？
是不是仅新代码适用？
是不是 breaking？
是不是应重新验证？
```

这会后续进入 F9 Impact。

---

# 二十二、Profile 需要支持 Coverage Gap
## 规则覆盖缺口

假设当前任务：

> 开发一种从未处理过的新设备端。

Profile 中完全没有对应模块。

系统不能：

```text
无规则
↓
AI 自由发挥
```

应该产生：

```text
RULE_COVERAGE_GAP
```

然后：

```text
共享库有候选 Module？
    ↓
YES → Profile Extension Candidate

NO
↓
External Evidence / Material / Rule Candidate
```

这里未来可以接我们刚定的：

```text
Bounded Autonomous Resolution
```

但不能绕过 Profile。

---

# 二十三、Profile Extension 也分低风险和高风险

例如只是：

> 当前任务明确需要一个已经存在、兼容性确定、无冲突的低风险前端规范模块。

未来可以允许：

```text
AUTO_PROPOSE
甚至在项目 Autonomy Policy 允许时
AUTO_BIND
```

但：

> 新组件体系、新 Framework、大型规则体系、Breaking Module

显然不能随便自动加入。

这个具体自主级别留给：

```text
F8 + CROSS-STAGE-AUTONOMY-01
```

D02-06 这里只留接口。

---

# 二十四、这个地方不要提前把“市场最佳方案”塞进 Profile

Profile 应该表达：

> **项目已经采用什么。**

外部市场最佳实践属于：

```text
Evidence
```

不是 Profile 本身。

所以正确：

```text
Profile 覆盖不足
↓
F9 外部证据
↓
Autonomous Resolution / Recommendation
↓
Profile Change Candidate
```

而不是：

```text
网上流行
↓
自动写 Profile
```

职责很干净。

---

# 二十五、项目现有代码惯例是什么位置

也不能直接变成 Profile Authority。

比如：

```text
项目里 80% 页面都用了 margin
```

不能推出：

> “项目 Profile 正式要求 margin。”

现有代码是：

```text
Implementation Evidence
```

它可以帮助判断：

```text
当前项目习惯
迁移成本
兼容性
```

但不能静默变成正式 Rule。

---

# 二十六、Frontend Profile 最好是“声明式”的

不要让它变成：

```text
if page is xxx then ...
else if ...
else if ...
```

塞大量业务逻辑。

Profile 最好只声明：

```text
我采用什么
在哪适用
采用哪个版本
有哪些项目补充
```

复杂 Rule Resolution 交给 Resolver。

这样 Profile 才长期可维护。

---

# 二十七、以后前端 Agent 的体验应该非常简单

例如你说：

> “按设计图修商品分类页。”

内部：

```text
识别 Project
↓
读取 Frontend Profile
↓
解析任务语义
↓
获得 Effective Rule Set
↓
生成 Implementation Guidance
↓
Coding
```

用户不需要说：

> “请加载 PC 模块 2.3、组件模块 5.1……”

全部内部完成。

---

# 二十八、开发时 Agent 也不能越过 Effective Rule Set 自己去“翻公共规则库”

这条我建议非常明确。

正常情况下 Coding Agent 收到：

```text
Effective Rule Set
```

就按它施工。

不能因为：

> “我感觉还有个更好的 Rule”

自己偷偷去全局共享库拿一条没经过 Profile/Resolution 的规则。

如果发现缺失：

```text
Rule Coverage Gap
```

返回 Resolver。

不能自行扩大 Authority。

---

# 二十九、这会形成非常清楚的职责分层

```text
Shared Rule System
负责：
有哪些可复用知识

Project Frontend Profile
负责：
当前项目采用哪些知识

Rule Resolver
负责：
当前任务哪些规则真正适用

Effective Rule Set
负责：
把这次任务需要的规则交给执行方

Coding Agent
负责：
按照有效规则实施
```

非常干净。

---

# 三十、与 Bounded Autonomous Resolution 怎么连接

建议接口放在：

```text
Rule Resolution
↓
存在无法正常解析的歧义？
```

如果没有：

```text
Effective Rule Set
```

如果有：

```text
Ambiguity
↓
CROSS-STAGE-AUTONOMY-01
```

然后可能：

```text
AUTO_RESOLVED
↓
重新生成 Effective Rule Set
```

或者：

```text
RECOMMENDATION_REQUIRED
```

或者：

```text
HUMAN_DECISION_REQUIRED
```

所以 Autonomy 不取代规则系统。

它只处理：

> **规则系统正常解析以后剩下的合法歧义。**

这是很重要的定位。

---

# 三十一、这样防止一个很危险的 AI 错误

错误：

```text
规则冲突
↓
AI 说“我查了最新最佳实践”
↓
选一条
```

正确：

```text
规则冲突
↓
先判断是不是已有 Authority / Strength /
Scope / Override 可以解决
↓
无法解决
↓
判断是否属于 Eligible Autonomous Ambiguity
↓
允许才调用外部证据
```

不能拿“先进实践”绕过已有 Authority。

---

# 三十二、本轮再做一次跨条款一致性检查

按照你新增的全局要求：

### 与 D02-02

不冲突。

D02-02：

> 规则本身怎么判 Strength / Authority / Scope / Override。

D02-06：

> 项目采用哪些规则、任务怎样生成有效集合。

---

### 与 D02-03

不冲突。

D02-03：

> Module 如何形成、拆、合。

D02-06：

> 已存在 Module 如何被项目选择。

---

### 与 D02-04

不冲突。

D02-04：

> 物资怎样产生 Rule。

D02-06：

> 正式 Rule 怎样进入项目使用范围。

---

### 与 D02-05

不冲突。

D02-05：

> 怎样根据语义找到候选 Rule。

D02-06：

> 怎样从候选 Rule 形成项目当前真正有效 Rule Set。

---

### 与 CROSS-STAGE-AUTONOMY-01

不冲突。

D02-06 不自己定义 AI 可以自动决定什么，只把未解决歧义交给跨阶段自主裁决能力。

这样不会产生两套 Autonomy 规则。

---

# 三十三、F6-D02-06 候选不变量

我建议本轮形成这些：

```text
FP-01
Frontend Profile 是当前 Project Instance
采用哪些 Frontend Rule Modules / Rule Sets
及其 Scope / Version / Binding 的声明式配置。
```

```text
FP-02
Frontend Profile != Rule Body；
Profile 通过引用组合规则，
不得复制共享规则正文形成第二真源。
```

```text
FP-03
Profile 主要采用组合模型，
避免深层继承和隐式规则链。
```

```text
FP-04
Profile 中的文件顺序、加载顺序、声明顺序
均不得成为 Rule Priority。
```

```text
FP-05
共享 Module 发布新版本
不自动改变项目 Current Effective Version。
```

```text
FP-06
Project-specific Rule Module 可以与 Shared Modules
组合，但其覆盖能力仍由 D02-02 决定，
Profile 不创造第二套 Override 规则。
```

```text
FP-07
Effective Frontend Rule Set
由 Project Profile + Task Context + Semantic Match +
Scope + Applicability + Version + Rule Resolution
派生形成。
```

```text
FP-08
Effective Rule Set 遵循
Minimum Sufficient Rule Context，
只加载当前任务必要规则。
```

```text
FP-09
最小上下文不得省略 Mandatory Context Rules；
Token 效率不得降低 Governance Fidelity。
```

```text
FP-10
Effective Rule Set 是 Derived / Rebuildable，
不得成为 Frontend Rule Authority。
```

```text
FP-11
任务实际使用的 Rule ID / Version /
Resolution Evidence 必须可追踪，
以支持未来审计与 Impact Analysis。
```

```text
FP-12
```
