可以。提升以后，**F6-D02-08 已经不能只叫“UI Design Profile + Effective Design Rule Set”**，它应该完整升级成一套：

# F6-D02-08 — UI Design Profile × Rule Resolution × Design Context Compilation
## 项目设计规则配置 × 规则解析 × 有效设计上下文编译方案

当前先记为：

```text
Status = HUMAN_REVIEW
Implementation = NOT_AUTHORIZED
```

这套方案的最终目标不是“让 AI 找到很多规则”，而是：

> **把 PRD、用户明确设计约束、Shared Foundation、设计证据、当前项目配置、有效设计规则、已经做出的设计决策以及剩余未知项，经过确定性的治理解析后，快速编译成一份最小、准确、可靠、可追踪的 Effective Design Context（当前有效设计上下文），让 Design Agent 可以直接工作，而不是每次自己重新理解所有历史资料。**

这也是我认为目前 Banyan 更合理的一步提升。

---

# 一、先明确 D02-08 最终解决什么问题

以前我们解决的是：

```text
有哪些 UI Design Rules？
```

现在要进一步解决：

```text
这个项目
这个页面
这次任务
这个时间点

到底应该给 AI 哪些设计事实、
哪些规则、
哪些约束、
哪些决定、
哪些未知？
```

所以 D02-08 的最终产物，不应该只有：

```text
Effective Design Rule Set
```

而应该是：

```text
Effective Design Context
```

其中 Rule Set 只是 Context 的一部分。

# 三、先把四个核心对象彻底分开

## 1. UI Design Profile

回答：

> **这个项目允许使用哪些设计规则体系？**

属于长期 Project Configuration。

例如：

```text
Project A
└── UI Design Profile
    ├── Shared Module A
    ├── Shared Module D
    ├── Accessibility Module
    └── Project-specific Module P
```

它不是具体页面设计。

---

## 2. Effective Design Rule Set

回答：

> **这次设计任务真正适用哪些设计规则？**

例如：

```text
DR-017
DR-026
DR-081
DR-P-009
```

它是任务级派生结果。

---

## 3. Effective Design Context

回答：

> **这次 Design Agent 工作之前，真正需要知道的全部有效上下文是什么？**

它除了 Rules，还包含：

```text
PRD Facts
UDC
Foundation
Design Evidence
Resolved Decisions
Forbidden Constraints
Unknowns
Trace
```

---

## 4. Effective UI Contract

回答：

> **当前开发 Batch 最终锁定使用哪一版已批准 UI_SPEC。**

已有规划已经把 `Effective UI Contract` 定位为 Batch UI Snapshot。fileciteturn106file0L5610-L5632

因此必须永久保持：

```text
Effective Design Rule Set
≠ Effective Design Context
≠ Effective UI Contract
```

这是防止未来 AI 混淆的硬边界。

---

# 四、所谓“优先级”，正式改成 Resolution Matrix
## 多维解析矩阵

你的理解没错，它确实带有“矩阵思想”。

但不要设计成：

```text
Rule A priority = 100
Rule B priority = 80
所以 A 赢
```

这种方案虽然简单，但是以后一定误判。

真正应该判断的是：

| 维度 | 负责回答 |
|---|---|
| Semantic Owner | 这个事实到底归谁拥有 |
| Authority | 这个来源有没有决定权 |
| Scope | 管哪个项目/应用/页面/组件 |
| Applicability | 当前任务是否适用 |
| Strength | REQUIRED / FORBIDDEN / RECOMMENDED / OPTIONAL |
| Specificity | 一般规则还是具体规则 |
| Override Policy | 是否允许覆盖 |
| Version | 项目绑定哪个版本 |
| Freshness | 信息是不是仍然当前有效 |
| Relation | COMPOSE / SPECIALIZE / ALTERNATIVE / CONFLICT |
| Evidence Status | FACT / INFERENCE / RECOMMENDATION / UNKNOWN |
| Autonomy Eligibility | 剩余歧义 AI 是否允许自己处理 |

所以：

> **不是规则“谁分数高谁赢”，而是先解析它们是不是在争夺同一个语义事实。**

---

# 五、第一层：Semantic Owner 先裁掉大量伪冲突

比如：

```text
PRD：
必须支持新增、导入、导出。

Design Rule：
数据密集页面应减少视觉噪声。
```

看起来可能冲突。

实际上没有。

因为：

```text
PRD owns Product Capability
Design Rule owns Design Guidance
```

因此正确结果：

```text
不能删除导入导出
但可以折叠到更多菜单
```

所以第一判断永远应该是：

> **两条内容是不是属于同一个 Semantic Owner。**

不是同一个 Owner：

> 不进入“谁优先谁覆盖”的比赛。

这是防误判非常重要的一步。

---

# 六、建议形成稳定的设计语义来源层

概念上可以理解：

```text
Product Semantics
       ↓
PRD / Approved Change

Human Design Constraint
       ↓
UDC

Project Design Facts
       ↓
Shared Foundation

Current Concrete Design
       ↓
Design Package / Current-effective UI_SPEC

General Design Knowledge
       ↓
Applicable UI Design Rules

Evidence
       ↓
Design Sources / Existing UI / External Evidence
```

但注意：

> 这不是简单“上面永远压下面”的排行榜。

是：

> **各自拥有不同的事实。**

只有两个对象试图修改同一个语义事实时，才进入 Authority / Override / Conflict Resolution。

---

# 七、UI Design Profile 的完整职责

UI Design Profile 应该只负责四件事：

```text
选择哪些 Rule Module
限定它们适用于哪里
绑定哪个版本
声明项目级 Binding /合法 Override Reference
```

不能负责：

```text
重写 Rule Body
定义第二套 Rule Priority
存 Shared Foundation
存 UI_SPEC
存具体页面设计
```

---

# 八、Profile 必须声明式，不做程序脚本

正确：

```text
项目采用：
Module A
Module C
Project Module P

Module A:
scope = admin

Module C:
scope = mobile
```

不建议变成：

```text
if page == xxx:
  if device == ...
    then ...
```

复杂解析属于 Resolver。

否则 Profile 会变成第二套程序语言。

---

# 九、Profile 使用组合，不使用深层继承

建议：

```text
Project UI Design Profile

bind:
- Module A
- Module C
- Module F
- Project Module P
```

而不是：

```text
Global
  ↓
Web
  ↓
Enterprise
  ↓
Admin
  ↓
Project
  ↓
Page
```

继承五六层。

因为深层继承以后非常难判断：

> 一条规则为什么生效。

---

# 十、Profile 顺序不能是优先级

必须冻结：

```text
Profile Order
≠ Authority
≠ Strength
≠ Rule Priority
```

禁止：

```text
最后加载覆盖前面
最后声明优先
文件排后面的赢
```

这些都属于执行 AI 的高风险误判源。

真正冲突依旧由 D02-02：

```text
Strength
Authority
Scope
Applicability
Override
```

解决。

---

# 十一、共享规则版本不能自动升级项目

例如：

```text
Shared Module A
v2 → v3
```

Project A 当前使用：

```text
v2
```

不能因为 v3 发布：

```text
所有 Project 自动变 v3
```

应该：

```text
New Version Available
↓
Compatibility
↓
Impact
↓
Profile Upgrade Candidate
↓
Governed Adoption
```

继续坚持：

```text
Latest != Current Effective
```

---

# 十二、任务进入后先做 Semantic Normalization

例如用户说：

> “把左边一级分类、横向二级分类和下面圆图标三级分类重新设计成目标图那种感觉。”

系统不能直接拿这句话全文搜规则。

应先归一成：

```text
component:category_navigation

hierarchy:
level_1
level_2
level_3

state:selected

visual_shape:capsule

indicator:triangle

overflow:horizontal_scroll

effect:edge_fade

relationship:shared_background_surface
```

然后再进入索引。

---

# 十三、规则查找应该采用三级检索

这是速度快的关键。

## 第一级：Profile Filter

例如：

```text
platform-admin
Web PC
```

先排除：

```text
Mobile-only
Mini-program-only
unbound module
```

---

## 第二级：Semantic Index

只根据：

```text
category-navigation
selected-state
capsule
triangle
horizontal-scroll
fade-mask
```

找候选规则。

---

## 第三级：Targeted Canonical Read

索引只告诉：

```text
可能是 DR-017
DR-026
DR-081
```

真正判断时再去读取这几条 Canonical Rule Body。

因此未来即使：

```text
设计规则库 = 20,000 条
```

也不意味着每次读 20,000 条。

---

# 十四、SQLite / Embedding 只负责“找”

继续硬边界：

```text
Search Score
Embedding Similarity
FTS Rank
Keyword Match

≠
Authority
≠
Applicability
≠
Rule Priority
```

所以：

```text
Similarity = 0.97
```

只能说明：

> 可能相关。

不能说明：

> 这条规则一定应该执行。

---

# 十五、形成 Candidate Rule Set 以后进入 Resolution Matrix

例如候选：

```text
DR-A
DR-B
DR-C
DR-D
```

依次判断：

```text
Profile enabled?
↓
Version valid?
↓
Scope matches?
↓
Applicability matches?
↓
Current effective?
↓
Superseded?
↓
Strength?
↓
Override allowed?
↓
Relation with others?
```

最后可能：

```text
DR-A → EFFECTIVE
DR-B → NOT_APPLICABLE
DR-C → SPECIALIZES A
DR-D → ALTERNATIVE
```

---

# 十六、Rule Relation 必须先解析

一批规则同时命中，不代表：

> 全部执行。

它们可能是：

```text
COMPOSE
可以共同执行

SPECIALIZE
一条是另一条更具体版本

DEPEND_ON
需要一起考虑

ALTERNATIVE
多个合法设计方案

OVERRIDE
条件满足时允许覆盖

EXCLUDE
当前条件下排除另一条

CONFLICT
真正冲突
```

如果关系没有被治理清楚：

```text
UNRESOLVED_RELATION
```

不能让 Design Agent 自己猜。

---

# 十七、跨来源一致性检查必须在 Context 生成前做

不仅检查 Rule vs Rule。

还要检查：

```text
PRD vs UDC
UDC vs Foundation
Foundation vs Rule
Rule vs Design Evidence
Rule vs Current UI_SPEC
Design Decision vs PRD
Autonomous Decision vs UDC
```

最后生成：

```text
Resolved
Compatible
Alternative
Conflict
Unknown
```

---

# 十八、只有“剩余合法歧义”才交给 Autonomous Resolution

顺序必须是：

```text
正常 Authority / Scope / Rule Resolution
           ↓
还能剩下多个合法方案？
           ↓
才进入 Autonomy
```

而不是：

```text
规则冲突
↓
AI 上网找最先进方案
↓
自己决定
```

这是错误的。

---

# 十九、Autonomy 的资格条件

AI 自主设计至少要同时满足：

```text
不改变 Product Semantics
不违反 UDC
不违反 Shared Foundation
不违反 Current Effective UI_SPEC
不违反 non-overridable mandatory rule
属于当前授权 Scope
低风险
可逆
可验证
有足够 Context
能够解释选择理由
```

否则进入：

```text
RECOMMEND
```

或：

```text
DECISION_REQUIRED
```

---

# 二十、外部“先进设计方案”是 Evidence，不是 Authority

以后设计歧义可能需要查：

```text
Apple HIG
Material Design
Ant Design Guidelines
成熟设计系统
可靠行业研究
```

但结果只能进入：

```text
External Design Evidence
```

然后帮助：

```text
Best-Fit Resolution
```

不能：

```text
网上现在流行什么
↓
直接覆盖当前项目设计
```

---

# 二十一、Effective Design Rule Set 的定位

经过解析后形成：

```text
Effective Design Rule Set
```

例如：

```text
MANDATORY
- DR-017
- DR-021

RECOMMENDED
- DR-044

OPTIONAL
- DR-071

FORBIDDEN
- DR-102
```

同时还要知道：

```text
为什么命中
适用 Scope
版本
来源 Profile
Relation
Resolution Result
```

它本身：

```text
Derived
Rebuildable
Task-scoped
```

不是新的 Canonical Rule Truth。

---

# 二十二、然后进入真正核心：Design Context Compiler

这是提升以后最重要的能力。

它的职责：

> **不是简单把 Rule Set 拼成 Prompt。**

而是：

> **把已经治理和解析过的所有当前有效设计信息重新组织为 Design Agent 可以直接消费的工作上下文。**

---

# 二十三、Compiler 主要做“编译”，不是重新决策

Resolver 已经确定：

```text
哪些事实有效
哪些规则适用
哪些被排除
哪些已经解决
哪些仍是 Unknown
```

Compiler 不应该重新：

> “我再猜一下谁优先。”

所以职责必须分开：

```text
Resolver
= 判

Compiler
= 组装
```

这是避免第二套 AI 判断逻辑的重要边界。

---

# 二十四、Effective Design Context 的建议结构

逻辑结构建议至少包含：

```text
Effective Design Context
│
├── A. Task Identity
│
├── B. Goal / Scope
│
├── C. Product Facts
│
├── D. Human Design Constraints
│
├── E. Shared Foundation
│
├── F. Confirmed Design Evidence
│
├── G. Effective Design Rules
│
├── H. Mandatory Constraints
│
├── I. Forbidden Constraints
│
├── J. Resolved Design Decisions
│
├── K. Allowed Alternatives
│
├── L. Autonomous Decisions
│
├── M. Unknown / Gap
│
├── N. Conflict / Blocker
│
├── O. Validation Requirements
│
└── P. Trace / Provenance
```

---

# 二十五、A. Task Identity

告诉 AI：

```text
当前在做什么
哪个项目
哪个应用
哪个页面
什么版本
哪个任务
```

防止规则作用错地方。

---

# 二十六、B. Goal / Scope

例如：

```text
Goal:
重建设计商品分类导航区域

Scope:
platform-admin
商品分类页
一级/二级/三级分类区域

Out of Scope:
商品列表
后端分类 API
权限模型
```

这会极大减少 AI 越界。

---

# 二十七、C. Product Facts

只放当前任务相关 PRD 事实。

例如：

```text
必须存在三级分类
三级分类之间存在父子关系
选择一级分类会影响下游分类内容
```

而不是把完整 300 页 PRD 全塞进 Context。

Stage 08 已经明确主链从 PRD / Approved Change 到 UI Contract，而且设计图、AnyDesign、Figma 等只能作为 Evidence，不能成为 Canonical Product Requirement。fileciteturn106file4L213-L233

---

# 二十八、D. Human Design Constraints

例如你明确要求：

```text
一级、二级、三级公用一个底板

一级顶部收窄

一级选中上下需要三角效果

二级气泡需要底部三角

横向隐藏区域要渐隐遮罩
```

这类内容不能和一般 Design Rule 混在一起。

因为它们是：

```text
Human Constraint
```

---

# 二十九、E. Shared Foundation

只放当前项目真正相关的公共事实，例如：

```text
品牌色
统一视觉密度
项目圆角语言
后台基础视觉体系
公共导航风格
```

---

# 三十、F. Design Evidence

例如：

```text
目标图确认的布局关系
现有页面实际状态
Design Source 中可观察到的视觉事实
```

并保留：

```text
FACT
INFERENCE
UNKNOWN
```

不能混。

---

# 三十一、G. Effective Design Rules

这里放已经解析过的 Rule。

不是简单复制 50 页规则全文。

应该给：

```text
Rule ID
Resolved Rule Meaning
Applicability
Strength
必要理由
```

必要时可按需回查 Canonical Body。

---

# 三十二、H / I. Mandatory 与 Forbidden 单独提升

这是减少 AI 误判非常有价值的一步。

不要让 AI 在 30 条规则中自己寻找：

> 哪条是不能违反的？

直接编译成：

```text
MUST
- 一级/二级/三级结构不得删除
- Human UDC 必须保持
- ...

MUST NOT
- 不得因组件库方便修改 Design Target
- 不得将截图宽度直接当固定 CSS
- ...
```

这样执行可靠性会明显提高。

---

# 三十三、J. Resolved Design Decisions

例如已经确定：

```text
一级分类采用左侧纵向
三级分类采用圆形图标表现
选中态包含指示器
```

这些不用 Agent 重新决策。

---

# 三十四、K. Allowed Alternatives

有时仍然有多种都合法，例如：

```text
三角指示器的视觉大小允许轻微调整
阴影强度存在两个合法方案
```

明确写成：

```text
Allowed Alternatives
```

而不是 Unknown。

---

# 三十五、L. Autonomous Decisions

比如 AI 已在治理边界内决定：

```text
左右渐隐遮罩使用相同视觉逻辑
```

应记录：

```text
Decision
Reason
Evidence
Risk
Reversible
Validation
```

---

# 三十六、M. Unknown / Gap

例如：

```text
Hover 状态没有设计证据
窄屏断点尚未确定
```

保持 UNKNOWN。

不要为了 Context 看起来完整：

> AI 自己补全。

---

# 三十七、N. Conflict / Blocker

如果还有：

```text
Foundation 与 UDC 真冲突
Mandatory Rule 冲突
PRD 与设计冲突
```

Context 不应该标记：

```text
READY
```

---

# 三十八、O. Validation Requirements

Context 最好直接告诉后续：

```text
视觉上需要验证什么
哪些 State 必须截图
哪些 viewport 必须检查
哪些规则需要 test
```

这样上下游闭环。

---

# 三十九、P. Trace / Provenance

每个关键结论应该能反查：

```text
来自哪条 PRD
哪个 UDC
哪个 Foundation
哪张设计图
哪条 Rule
哪个 Human Decision
哪个 Autonomous Resolution
```

但平时不用全部展示给用户。

---

# 四十、Context 的核心优化：不是“信息越多越好”

正式采用：

```text
Minimum Sufficient Design Context
最小充分设计上下文
```

要求：

> 足以完成任务，但不加载无关信息。

因为 Context 太大也会导致：

```text
注意力稀释
语义冲突
错误关联
Token 浪费
响应变慢
```

---

# 四十一、但“最小”不能漏治理底线

所以：

```text

≠ Minimal at any cost
```

必须自动加入：

```text
Mandatory Context
```

即使关键词没命中。

例如：

```text

Human UDC
```

# 四十二、Design Context Validation Gate

Effective Context 出来前必须校验。

至少检查：

```text
Product Facts 是否完整到当前任务？

Human Constraint 是否全部进入？

Foundation 是否被错误覆盖？

Mandatory Rule 是否遗漏？

是否引用 Superseded Rule？

Version 是否正确？

是否把 INFERENCE 写成 FACT？

是否存在 REQUIRED vs FORBIDDEN？

是否还有 UNRESOLVED_RELATION？

Autonomous Decision 是否越权？

Context 是否引用 stale input？
```

# 四十三、Context Readiness 不使用一个百分比分数

不建议：

```text
Context Quality = 91%
```

因为：

> 99 个小项正确 + 1 个关键 Authority 冲突，也不能 READY。

建议：

```text
Product Coverage        READY
Human Constraint        READY
Foundation              READY
Design Rule Coverage    READY
Design Evidence         PARTIAL
Mandatory Conflict      NONE
Critical Unknown        NONE
Authority Conflict      NONE

Overall:
CONTEXT_READY
```

这叫：

```text
Typed Readiness
```

# 四十四、建议设计四类主要 Context 状态

```text
存在有意义的设计取舍
```

# 四十六、变化后做局部重算


于是：

```text

C → RECHECK
B → KEEP
```

不是：

```text

```

# 四十七、Foundation 变化与 Rule 变化不能同等处理

例如：

```text

改了一个表述
```

可能几乎没有影响。

```text

项目主色改变
```

可能影响整个 Project。

所以 Impact 必须保留 Change Type。

不能：

```text

→ rebuild everything
```

# 四十八、Design Rule 更新也不能自动推翻旧 Design Package

```text

```

> 自动变成错误页面。

```text

mandatory?
new-design-only?
```
