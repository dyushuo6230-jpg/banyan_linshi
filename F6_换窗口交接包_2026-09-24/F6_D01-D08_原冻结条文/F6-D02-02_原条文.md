好，继续进入 **F6-D02 的第二个核心问题**。这一轮讨论的是前端开发规则真正开始“可执行”前必须解决的事情：

# F6-D02-02 — Rule Strength × Authority × Scope × Conflict Resolution  
## 规则强度、权威、适用范围与冲突裁决

当前仍然只是 `HUMAN_REVIEW（人工评审）`，不施工、不冻结。

这一项非常关键。因为我们上一轮已经有了：

```text
Frontend Development Rule System
前端开发规则体系

    ↓

Rule Module
规则模块

    ↓

Rule Entry
一笔一笔规则

    ↓

Module Index
模块索引

    ↓

Rule Association Index
规则关联索引
```

但现在还有一个问题：

> **找到了 6 条相关规则以后，到底哪些必须执行？哪些只是建议？如果两条规则打架怎么办？用户当前明确说的话又怎么算？**

这一轮就是解决这个。

---

# 一、先定一个最重要的原则：不能只设计“规则优先级”

最容易犯的错误是给所有规则简单编号：

```text
等级 1
等级 2
等级 3
等级 4
```

然后：

> 数字大的永远压数字小的。

这样不够。

因为一条规则最终能不能生效，其实至少取决于四件不同的事情：

```text
Rule Strength
规则强度

+

Authority
规则当前有没有正式权威

+

Scope
适用于哪里

+

Applicability
当前场景到底适不适用
```

这四个必须分开。

一句大白话：

> **一条规则“很强”，不代表它“管得到这里”；一条规则“管得到这里”，也不代表它已经成为当前项目正式规则。**

---

# 二、Rule Strength：这条规则有多硬

我建议规则条目至少能表达四种基本强度，名字以后可以微调。

| 强度 | 大白话意思 | 例子 |
|---|---|---|
| `REQUIRED（必须）` | 符合适用条件时必须执行 | 父级已经决定子项尺寸时，不应再给每个子项写无依据固定宽度 |
| `FORBIDDEN（禁止）` | 明确不能这样做 | 不得把截图坐标机械转换成整页 absolute |
| `RECOMMENDED（推荐）` | 通常这样更好，但有合理理由可以不同 | 一维按钮组优先 Flex + Gap |
| `OPTIONAL（可选）` | 是一种可用办法，不要求默认采用 | 某复杂视觉效果可以使用伪元素实现 |

这里有一个很重要的区别。

比如：

```text
“表格一般优先复用现有组件”
```

可以是推荐。

但是：

```text
“不得因为设计图测出 1180px，
就直接把动态 Main 写死为 1180px”
```

可能是禁止型规则。

两者不能一个力度。

---

# 三、但是“规则强度”不等于“规则权威”

比如你投了一份网上找到的：

> 《优秀后台设计实践》

里面写：

> 表格操作超过 3 个全部折叠。

这份文档自己写得再肯定：

```text
“必须这样！”
```

也不能因为作者用了“必须”两个字，就自动成为你当前项目的强制规则。

它首先只是：

```text
Material
物资

↓

Rule Candidate
规则候选
```

经过治理以后，才可能成为：

```text
Shared Rule
共享规则
```

再通过当前项目的：

```text
Frontend Profile
项目规则配置
```

成为：

```text
Project Effective Rule
当前项目有效规则
```

所以：

> **Strength（规则强度）描述规则本身有多硬；Authority（权威）描述它现在有没有资格约束这个项目。**

这两个绝不能混。

---

# 四、共享规则也不能一创建就自动约束所有项目

假设公共前端规则体系里已经有：

```text
MODULE-A
通用 Web 规则

MODULE-B
某类移动设备规则

MODULE-C
某组件体系规则
```

Project A 可能使用：

```text
MODULE-A
MODULE-C
```

Project B 可能使用：

```text
MODULE-A
MODULE-B
```

因此：

```text
存在于 Shared Rule Catalog
共享规则库

≠

当前项目必须执行
```

项目必须通过：

```text
Profile / Binding
配置 / 绑定
```

明确当前有效组合。

这也符合我们之前已经确定的思想：公共 Engineering Standards（工程规范）可以复用，但不能自动成为每个项目的正式项目规则。

---

# 五、Scope：这条规则到底管多大范围

Scope（适用范围）不是简单的“全局/局部”两个等级。

它可以同时表达多个维度。

例如某条规则可能是：

```text
项目：
Project A

应用：
tenant-admin

平台：
Web PC

技术：
React

组件体系：
某组件体系

问题领域：
Table

页面：
不限
```

另一条可能只有：

```text
页面：
商品分类页

视觉语义：
selected capsule
```

所以 Scope 本质上回答：

> **“这条规则管谁？”**

而不是回答：

> “谁的级别更高？”

---

# 六、Applicability：当前任务到底是否匹配

这个是保证**速度快**的关键。

比如有一个移动端规则模块：

```text
Mobile Module
```

当前开发：

```text
PC 后台
```

那它连冲突判断都不需要进入。

直接：

```text
NOT_APPLICABLE
不适用
```

同理，某组件体系模块：

```text
某组件体系规则
```

如果当前项目根本没采用它：

```text
不加载
```

所以实际查规则时不是：

```text
读取所有规则
↓
再一个一个判断
```

而应该：

```text
当前 Project Profile
        ↓
先缩小 Module 范围
        ↓
任务语义
        ↓
Module Index
        ↓
Rule Association Index
        ↓
Scope / Applicability 过滤
        ↓
只剩真正相关规则
```

这非常符合我们要求的：

> **速度快，但不能为了速度降低可靠性。**

---

# 七、我建议产生一个“当前任务有效规则集”

这个概念很有价值。

可以暂时叫：

`Effective Frontend Rule Set（当前有效前端规则集）`

注意：

> **它不是新的正式真源。**

它只是当前任务把规则算完以后得到的派生结果。

例如：

```text
Project Profile
+
当前技术栈
+
当前设备
+
当前页面
+
PRD Semantic
+
Design Package Semantic
+
Rule Index
        ↓
Effective Frontend Rule Set
```

最终可能只有：

```text
FE-RULE-003
FE-RULE-018
FE-RULE-026
FE-RULE-091
```

Coding Agent 只需要读这几条。

而不是整个前端规则库。

---

# 八、它非常适合放到 `.banyan` 的派生工作区

按照我们刚才调整好的存储边界：

```text
.banyan
= 当前 Project Instance 工作空间
```

那么这种：

```text
Effective Rule Set
规则解析结果

Module Match
模块匹配结果

Association Result
语义关联结果
```

就很适合属于：

```text
.banyan
```

因为它是：

> 当前项目 + 当前任务算出来的东西。

但共享 Frontend Rule 正文仍然不需要复制进当前项目。

可以理解成：

```text
Shared Frontend Rules
公共规则正文
          ↓ reference
.banyan Project Profile
          ↓
当前任务规则解析
          ↓
Effective Rule Set
派生结果
```

这和我们“文件存正式语义、索引/派生结果可重建”的整体思想也是一致的。

---

# 九、Scope 要支持“继承 + 更具体覆盖”

这是你以后实际使用特别重要的能力。

例如有一个通用规则：

```text
通用表格规则：

操作项较多时，
应避免所有按钮长期平铺。
```

当前 Project A 有一个项目规则：

```text
Project A：

后台表格默认最多直接显示两个操作，
其余放入更多。
```

那么 Project A 的规则比公共规则更具体。

不是说公共规则错了。

而是：

```text
General Rule
通用规则

↓

Project Rule
项目具体化
```

---

# 十、再往下还可以有页面局部覆盖

比如商品审核页因为业务特殊：

> 审核、驳回、查看三个操作必须一直直接显示。

那么可以存在：

```text
Project Rule：
默认最多 2 个

↓

Page Override：
商品审核页允许 3 个
```

但这里要加一个非常重要的条件：

> **只有允许 Override（覆盖）的规则才能这样做。**

---

# 十一、因此 Rule Entry 还需要“是否允许覆盖”的语义

不能所有规则都能：

> “页面特殊，所以算了。”

比如：

```text
推荐型布局规则
```

通常可以覆盖。

但是某些：

```text
安全规则
无障碍强制规则
项目硬性规范
明确禁止项
```

可能：

```text
不可局部覆盖
```

所以 Rule Entry 逻辑上应该知道：

```text
Override Policy
覆盖策略
```

大白话：

> **别人能不能在更小范围内说“这个地方例外”？**

---

# 十二、用户当前明确说的话怎么处理

这是最容易出问题的地方。

假设当前项目规则：

> 表格默认只显示两个操作。

你对 AI 说：

> “这个页面三个操作全部直接显示。”

不能简单：

```text
用户说了
↓
立刻无条件覆盖所有规则
```

也不能反过来：

```text
规范最大
↓
不听用户
```

正确流程应该先判断：

```text
这条 Project Rule 是否允许局部 Override？
```

如果允许：

```text
用户明确要求
↓
形成 Local Design / Implementation Constraint
局部约束
↓
只对当前页面覆盖
```

不用把公共规则改掉。

---

# 十三、如果规则明确“不允许覆盖”怎么办

例如存在一个真正强制的规则：

> 当前项目所有危险删除操作必须具备明确防误触机制。

用户说：

> “这个页面删除点一下直接执行，不需要任何防误触。”

系统不能默默执行。

而应该发现：

```text
Human Request
人工要求

vs

Non-overridable Effective Rule
不可覆盖的当前有效规则
```

这时候：

```text
Conflict
冲突
↓
Material / Decision Buffer
↓
让人知道影响
↓
做正式决策
```

也就是说：

> **用户仍然能改变规则，但需要改变正式规则本身，而不是让 Coding Agent 偷偷绕过去。**

这才既方便又可靠。

---

# 十四、规则冲突不能靠“来源名字听起来更厉害”

比如：

```text
官方组件文档
项目规则
用户自然语言
旧规范
最新规范
```

不能简单说：

```text
官方 > 项目 > 用户
```

这种总排序是不合理的。

例如：

组件官方文档说：

> 推荐使用某种实现。

项目自己的工程标准说：

> 为了兼容现有封装，本项目统一使用内部 Wrapper（包装组件）。

那项目规则完全可以不同。

反过来，如果官方文档说明：

> 某 API 已被删除。

这是一条技术事实。

项目规则不能说：

> 我偏要调用已经不存在的 API。

所以：

> **事实约束、工程规则、设计建议、用户偏好不是同一种 Authority。**

---

# 十五、我建议冲突裁决采用“逐层过滤”，而不是一张固定排名表

完整过程可以这样：

```text
找到相关 Rule Entries
        ↓
1. 当前 Profile 是否启用这个 Module？
        ↓
2. 当前 Platform / Framework /
   Component System / Version 是否适用？
        ↓
3. 当前语义是否匹配？
        ↓
4. 当前 Scope 是否覆盖任务？
        ↓
5. 是否存在更具体规则？
        ↓
6. 是否允许 Override？
        ↓
7. Strength 是否冲突？
        ↓
8. 是否有明确 Human Constraint？
        ↓
9. 能自动确定？
   ├─ YES → Effective Rule Set
   └─ NO  → Buffer
```

这比：

> “数字大的赢”

稳很多。

---

# 十六、一个完整例子：气泡选中效果

Design Package 得到：

```text
selected_state
bubble
bottom_triangle
horizontal_scroll
```

然后索引找到：

```text
通用布局 Module
视觉效果 Module
某组件体系 Module
```

过滤后得到：

```text
Rule A
选中态应与未选中态有明确视觉区分
REQUIRED

Rule B
气泡/胶囊效果应避免使用页面绝对坐标
FORBIDDEN 某种错误方式

Rule C
三角指示器通常跟随选中容器
RECOMMENDED

Rule D
当前组件体系提供某种实现模式
OPTIONAL
```

那么 Coding Agent 就知道：

> A 必须满足，B 不能违反，C 一般应该采用，但如果当前结构有合理方式可以不同，D 只是可用实现之一。

这比给 AI 一份“大规范文档”靠谱得多。

---

# 十七、另一个例子：通用规则与项目规则

假设共享规则说：

```text
RECOMMENDED：
表格操作过多时收进更多菜单。
```

Project A 的正式规则说：

```text
REQUIRED：
后台列表直接操作最多 2 个。
```

当前用户管理页没有特殊要求。

最终：

```text
Project Rule
成为当前有效规则
```

因为它：

```text
已经被 Project Profile 采用
+
Scope 更具体
+
Strength 更明确
```

# 十八、如果用户这次说“三个都要显示”

先查：

```text
Project Rule
允许 Page Override 吗？
```

如果：

```text
YES
```

那：

```text
Local Override
只作用这个页面
```

如果：

```text
NO
```

那：

```text
Conflict
↓
需要正式决定：
A. 修改项目规则
B. 为此类页面建立允许例外的正式规则
C. 保持项目规则
```

系统不能自己选。

---

# 十九、Module 本身和 Rule Entry 的强度不要混

我建议：

```text
Module
```

主要负责：

> 一类知识的组织、适用边界、依赖和默认上下文。

真正：

```text
REQUIRED
FORBIDDEN
RECOMMENDED
OPTIONAL
```

放在：

```text
Rule Entry
```

上。

否则：

> “某 Module 是 REQUIRED”

语义很怪。

不是整个模块每一条都一样硬。

---

# 二十、Module 可以提供默认 Scope，但 Rule Entry 可以更具体

比如某个模块经过治理以后属于：

```text
Web / PC
```

那模块内的规则默认：

```text
platform = Web PC
```

不用每条重复写。

但其中一条规则可能只针对：

```text
data-table
```

那么：

```text
Module Default Scope
+
Rule Entry Narrow Scope
```

这样又减少重复，又保持精准。

---

# 二十一、Version 也必须进入适用判断

以后非常实际。

比如某组件体系：

```text
Module Version A
```

里面某条规则只适用：

```text
v5.x
```

项目升级：

```text
v6.x
```

不能继续无脑使用。

所以：

```text
Technology Version
Component Version
```

属于 Applicability（适用条件）。

如果无法确认：

```text
UNKNOWN
```

可以进入 Gap / Buffer，而不能假装兼容。

---

# 二十二、Rule Entry 的逻辑身份证现在基本出来了

现在还不冻结 YAML 字段，但逻辑上每一笔规则至少需要表达这些东西：

| 逻辑信息 | 大白话 |
|---|---|
| Rule ID | 我是谁 |
| Module | 我属于哪类知识 |
| Problem / Intent | 我解决什么问题 |
| Rule Body | 规则正文 |
| Strength | 必须、禁止、推荐还是可选 |
| Scope | 我管哪里 |
| Applicability | 什么情况下才适用 |
| Override Policy | 能不能有更具体的例外 |
| Provenance | 我从哪里来的 |
| Version / Status | 我现在是哪一版、什么状态 |
| Supersession | 有没有被新规则替代 |
| Semantic Triggers | 什么 PRD / Design / Code 语义会找到我 |
| References | 我依赖或关联什么 |
| Rationale | 为什么这样做 |
| Examples | 示例，辅助理解 |

这里最后两项：

```text
Rationale / Examples
理由 / 示例
```

我认为应该保留。

因为 AI Coding 时只看到一句：

> “不准这样。”

有时并不知道为什么。

知道原因以后，遇到新情况会更容易正确泛化。

---

# 二十三、但 Example 不能变成新的规则真源

例如规则正文是：

> 二维重复布局优先根据结构使用 Grid。

示例写：

```css
grid-template-columns: repeat(4, 1fr)
```

不能因为示例是 4 列，AI 就理解：

> 所有 Grid 必须 4 列。

所以：

```text
Rule Body
= 正式规则

Example
= 解释
```

必须区分。

然后只把这 12 条规则放进 Coding Context（编码上下文）。

这会非常高效。

# 二十五、这样也解决“大模型上下文越积越大”的问题

不是：

```text
所有历史物资
+
所有前端规范
+
所有设计规范
+
所有模块
+
所有规则
↓
全部喂给 AI
```

而是：

```text
SQLite / Index
负责找

↓

Module Index
缩小范围

↓

Rule Association Index
精准选择

↓

Context Builder
只读取 Canonical Rule Bodies
正式规则正文
```

这正好和我们已经冻结的：

> **文件存真相，SQLite 存地图**

一致。

# 二十六、我建议 D02-02 暂时形成以下候选不变量

这轮先不正式批准，但方向可以压缩成下面这些：

```text
RS-01
Rule Strength、Authority、Scope、Applicability
是四个不同维度，不得压成单一优先级数字。

RS-02
Rule Entry 才拥有具体规则强度；
Module 不统一继承一个规则强度。

RS-03
共享 Rule 存在不等于项目自动采用；
Project Profile / Binding 决定项目有效规则。

RS-04
Rule Strength 至少要能表达：
必须、禁止、推荐、可选。

RS-05
Scope 支持从公共到项目、应用、平台、
模块、页面、组件等更具体范围，
但不要求固定死成单一层级树。

RS-06
Applicability 必须支持技术栈、
组件体系、版本、平台、语义场景等条件。

RS-07
更具体规则只有在 Override Policy 允许时，
才能覆盖更广规则。

RS-08
明确 Human Constraint 可以形成局部 Override
或触发正式规则修改，
但不能静默绕过不可覆盖的有效强制规则。

RS-09
规则冲突不能使用 latest wins、
majority wins、file order wins 等简单策略。

RS-10
无法自动可靠裁决的规则冲突进入 Buffer，

RS-11
当前任务通过 Profile + Context + Semantic Index
生成 Effective Frontend Rule Set；
该结果是派生视图，不是第二真源。

RS-12
Rule Example 只是解释和示范，
不得反向升级成正式规则语义。
```

# 二十七、从你的六项设计要求检查这一版

这一版仍然符合你要求的：

**灵活**：Scope、Profile、Override 都不是写死的一条全局规则。

**有条理**：Module 管类别，Rule Entry 管正文，Profile 管项目选择，Effective Rule Set 管当前任务。

**可扩展**：以后新增框架、端、组件体系、Rule Module，不需要重做系统。

**速度快**：先 Profile → Module → Entry，不全库加载。

**符合逻辑**：先判断是否适用，再判断强度和冲突，不靠一个粗暴数字。

**便捷但可靠**：普通情况自动算规则；真正无法裁决的冲突才找你。
