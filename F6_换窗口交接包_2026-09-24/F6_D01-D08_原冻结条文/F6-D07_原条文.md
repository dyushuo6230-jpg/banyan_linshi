# F6-D07 — Design Package × UI_SPEC Governance
## 设计包 × UI_SPEC 治理 × 当前有效 UI 契约

```text
Status = HUMAN_REVIEW
Implementation = NOT_AUTHORIZED
```

这一项非常关键，因为前面 D03～D06 已经把设计相关的信息拆清楚了：

```text
D03 → Static Design Truth / Scene / Semantic
D04 → Visual Property / Token / Foundation
D05 → Behavior / State / Interaction
D06 → UI Data Semantics / Fixture
```

D07 要解决的是：

> **这些东西最终如何汇聚成一个可审阅的 Design Package；Design Package 又如何经过治理形成 UI_SPEC；UI_SPEC 批准之后谁才是前端施工真正应该遵守的 UI Contract；以后设计修改了，旧 UI_SPEC 怎么变 stale，而不是出现 Design Package、UI_SPEC、设计图、代码四个真源互相打架。**

现有 Stage 08 已经明确冻结了主链：

```text
PRD / Approved Change
↓
UI Scope
↓
Design Evidence
↓
Draft UI Contract
↓
Human / Workflow Gate
↓
Approved UI_SPEC
↓
Implementation Readiness
```

同时设计图、AnyDesign、Figma、截图、原型都只是 Evidence / Design Source。fileciteturn130file0L1-L37

---

# 一、先把 5 个东西彻底区分

D07 建议正式区分：

```text
Design Source
设计证据来源

Design Package
具体页面/界面的设计目标包

Draft UI Contract
待治理的 UI 契约候选

UI_SPEC
已批准的 UI 施工契约

Effective UI Contract
当前开发批次真正锁定使用的 UI 契约快照
```

它们不是同一个东西。

---

# 二、Design Package 的正式定义

建议定义：

> **Design Package = 针对一个明确 UI Scope，将当前设计目标所需的静态设计事实、视觉语义、动态行为、数据语义、来源、未知项和验证目标组织起来的结构化设计目标包。**

它回答：

> **“这个页面/组件最终应该设计成什么样。”**

逻辑上可以包含：

```text
Design Package
├── Scope / Identity
├── Design Truth Model
├── Layout / Structural Target
├── Visual Properties
├── Token / Foundation refs
├── Component Semantics
├── Behavior Model
├── UI Data Semantics
├── Fixture refs
├── Evidence refs
├── Decisions / Origins
├── Unknown / Conflict
├── Responsive / State coverage
└── Validation intent
```

注意：

> 这是逻辑结构，不是现在就冻结一个巨大 JSON Schema。

---

# 三、Design Package 是具体设计目标 Owner

前面已经确认：

```text
Design Truth Model
= Design Package 的结构化语义部分
```

所以正式关系是：

```text
Design Package
OWNS:
page-specific / component-specific Design Target
```

而不是：

```text
design-truth.json
design.md
state-map.json
tokens.json
```

每个文件各自成为一份可独立编辑的 Design Truth。

这些如果未来存在，只能是：

```text
Projection / Structured View
```

不能形成多个 Canonical Owner。

---

# 四、Design Package 不拥有 Product Authority

例如 Design Package 里出现：

```text
按钮：
删除账户
```

如果 PRD 没有：

```text
Delete Account Capability
```

不能因为设计完整就认为产品需求成立。

正确：

```text
Design Package
↓
Product Semantic Conflict / Gap
↓
F5 Product Governance
```

所以：

```text
Design Package
≠ PRD
```

---

# 五、Design Package 也不是 UI_SPEC

这是 D07 最大的核心边界。

```text
Design Package
= Design Target

UI_SPEC
= Approved Construction UI Contract
```

举例：

你让 Banyan 根据设计图、UDC、Foundation、Rules 生成了一版很完整的页面设计。

此时：

```text
Design Package = READY_FOR_UI_REVIEW
```

但还不能说：

```text
UI_SPEC = APPROVED
```

中间仍然需要：

```text
UI Governance
```

---

# 六、为什么必须有这层区别

因为 Design Package 可能包含：

```text
INFERENCE
Rule-derived Decision
Autonomous low-risk Decision
UNKNOWN
Reference Evidence
```

而施工 Contract 应该明确：

```text
哪些已经接受
哪些是当前有效
哪些仍然未知
哪些禁止施工时自行改变
```

所以：

> **Design Package 负责表达设计目标。UI_SPEC 负责表达已批准施工约束。**

---

# 七、Draft UI Contract 的作用

我建议 D07 保留一个逻辑阶段：

```text
Design Package
↓
Contract Projection
↓
Draft UI Contract
```

Draft UI Contract 的作用不是建立第二 Truth。

而是：

> 把 Design Package 中真正需要成为施工约束的内容整理成“待批准 UI Contract”。

例如 Design Package 可能有很多：

```text
Evidence
Rationale
Provider metadata
Confidence
Source lineage
```

这些都不一定需要全部进入 Coding Contract。

Draft UI Contract 只提炼：

```text
Construction-relevant UI semantics
```

---

# 八、Draft UI Contract 是 Derived Candidate

所以：

```text
Draft UI Contract
= Derived / Reviewable Candidate
```

不是：

```text
Current Effective UI Truth
```

它允许被：

```text
Review
Reconcile
Reject
Revise
```

---

# 九、UI_SPEC 的正式定义

现有 Stage 08 已明确：

```text
UI_SPEC = APPROVED_UI_CONTRACT_PROJECTION
```

fileciteturn130file1L1-L31

我建议在 Banyan F6 里进一步解释：

> **UI_SPEC = 针对明确 Application / Surface / Scope，经治理批准后生效的当前 UI 施工契约。**

它回答：

> **“开发这个 UI 时，哪些设计语义已经正式批准并必须被实现。”**

---

# 十、UI_SPEC 不应该复制整个 Design Package

例如 Design Package 里可能包含：

```text
Raw Source refs
Provider details
Confidence
Alternative candidates
Discarded evidence
Design rationale
```

UI_SPEC 不必全部复制。

应该：

```text
UI_SPEC
references:
Design Package
Design Decisions
Evidence when required
```

并只承载：

```text
Approved Construction Contract
```

---

# 十一、UI_SPEC 与 PRD 的边界

继续正式冻结：

```text
PRD
= Business/Product Truth

UI_SPEC
= UI Construction Truth
```

现有总纲也明确：

```text
PRD = Business Truth
UI_SPEC = UI Truth
Design Source = Evidence
Implementation Pack = UI施工图
Effective UI Contract = Batch UI Snapshot
```

fileciteturn130file2L1-L26

所以遇到冲突：

### 涉及业务

例如：

```text
权限
金额
产品状态
业务流程
字段业务含义
```

PRD / Approved Product Change 拥有上游 Authority。

### 纯 UI

例如：

```text
颜色
布局
状态视觉
间距
圆角
交互表现
```

Current Effective UI_SPEC 拥有施工 Authority。

---

# 十二、UI_SPEC 不能反向修改 PRD

例如 UI_SPEC 想写：

```text
点击删除无需确认且永久删除所有资源
```

如果这实际上改变 Product Behavior：

> 不允许只作为 UI_SPEC 修改。

必须：

```text
UI/Product semantic change
↓
Product Change / Decision
↓
PRD update if approved
↓
UI_SCOPE / Design update
↓
UI_SPEC refresh
```

---

# 十三、PRD 改变也不能静默让 UI_SPEC继续生效

现有 Stage 08 已明确要求 UI_SPEC 跟踪：

```text
derived_from_prd
derived_from_change
design_evidence_refs
coverage
freshness
supersedes
```

而相关 PRD 改变时：

```text
UI_SPEC → STALE / REVIEW_REQUIRED
```

不能静默视为仍有效。fileciteturn130file0L13-L37

这条正式进入 D07。

---

# 十四、Design Package 改变也不代表 UI_SPEC 自动改变

例如：

```text
Design Package D3
```

比当前：

```text
UI_SPEC 1.2
```

新。

不能：

```text
D3 exists
→ UI_SPEC automatically follows
```

正确：

```text
New Design Revision
↓
Semantic Diff
↓
UI Impact Classification
↓
UI_SPEC Review / Revision if needed
```

所以继续：

```text
Latest Design
≠ Current Effective UI Contract
```

---

# 十五、设计版本和 UI_SPEC 版本必须独立

已有架构明确禁止：

```text
Design v5
=
UI_SPEC v5
```

而应该是两个独立版本轴：

```text
Design:
D1 → D2 → D3 → D4

UI_SPEC:
1.0 → 1.1 → 1.1.1 → 2.0
```

fileciteturn130file26

原因很简单：

> 一次 Design Source 修订不一定真正改变施工 Contract。

---

# 十六、Source-only Change 不需要升级 UI_SPEC

例如：

设计图重新导出：

```text
PNG 压缩变化
metadata 变化
无视觉语义变化
```

这只是：

```text
SOURCE_ONLY_CHANGE
```

不需要：

```text
UI_SPEC +1
```

否则版本会疯狂膨胀。

---

# 十七、Design Change 必须做 Semantic Diff

不能只比较：

```text
文件 checksum changed?
```

而应该判断：

```text
Structure changed?
Layout changed?
Behavior changed?
Token changed?
Data semantics changed?
Responsive changed?
Asset changed?
Validation target changed?
```

再决定：

```text
NO_UI_SPEC_CHANGE
UI_SPEC_PATCH
UI_SPEC_MINOR
UI_SPEC_MAJOR
```

具体 SemVer 规则可以继承既有规划，但是否最终采用精确 `MAJOR/MINOR/PATCH` 字符串，可留到 Implementation Freeze。

---

# 十八、UI_SPEC Version 不能代替 Freshness

例如：

```text
UI_SPEC 2.0
```

数字很新。

但如果基于：

```text
PRD v3
```

而现在：

```text
PRD v5
```

已经改变相关页面：

```text
UI_SPEC 2.0
```

仍可能：

```text
STALE
```

所以：

```text
Version
≠ Freshness
```

---

# 十九、Approved 也不等于 Current Effective

例如：

```text
UI_SPEC 1.2 = APPROVED
UI_SPEC 2.0 = APPROVED
```

某个开发 Batch 可能仍锁定：

```text
1.2
```

那么该 Batch 当前有效的是：

```text
1.2
```

不是：

```text
Latest approved 2.0
```

所以：

```text
Approved
≠ Current Effective
```

这和 F5-D09 / D02-10 的全局语义完全一致。

---

# 二十、Effective UI Contract 的正式定位

现有架构里：

```text
Effective UI Contract
= Batch UI Snapshot
```

fileciteturn130file2L1-L26

我建议 D07 正式定义：

> **Effective UI Contract = 某个具体开发/实现 Scope 在某个时间点锁定消费的 Current Effective UI_SPEC 及其必要依赖版本快照。**

它不是新的 UI Truth。

而是：

```text
Derived execution snapshot
```

---

# 二十一、Effective UI Contract 为什么必要

因为开发一个页面可能持续：

```text
3 天
1 周
2 周
```

期间 UI_SPEC 更新。

如果 Coding Agent 每次都拿 latest：

```text
Monday → 1.2
Tuesday → 1.3
Friday → 2.0
```

它会边开发边换施工图。

所以：

```text
Batch / Task
↓
lock Effective UI Contract
```

稳定施工。

---

# 二十二、新 UI_SPEC 出现时，不自动污染当前 Batch

现有规划已经明确：

```text
NEWER_UI_AVAILABLE
```

先产生提示，再进行 Impact Analysis；正在开发的 Batch 不自动追随 latest。fileciteturn130file4

因此：

```text
New UI_SPEC
≠ Active Batch Auto-upgrade
```

这是 D07 必须冻结的硬规则。

---

# 二十三、Batch Upgrade 应该是显式行为

例如当前：

```text
Batch B12
UI_SPEC = 1.3
```

出现：

```text
UI_SPEC = 1.4
```

B12 可以：

```text
KEEP 1.3
```

或者：

```text
UPGRADE → 1.4
```

但必须基于：

```text
Impact
Compatibility
Rework
Acceptance baseline
```

而不是 latest wins。

---

# 二十四、Design Package Coverage 与 UI_SPEC Coverage 要分离

例如一个页面 Design Package 已经覆盖：

```text
Desktop
Tablet
Mobile
```

但当前 UI_SPEC 只批准：

```text
Desktop
```

那么：

```text
Design Package Coverage = broader
UI_SPEC Coverage = Desktop
```

不能因为设计包有 Mobile：

> Coding Agent 自动实现 Mobile。

只有 Current Effective UI Contract 覆盖的才是施工契约。

---

# 二十五、Partial UI_SPEC 必须合法

可能：

```text
Page A = Approved
Page B = Draft
Page C = Not enabled
```

不应该为了形式完整：

```text
全应用全部 Approved
```

现有 Stage 08 本来就支持 application-level enablement / partial coverage。

所以：

> UI_SPEC Coverage 必须显式。

---

# 二十六、UI_SPEC Approval 与 Design Approval 不能混

用户说：

> “这个设计效果可以。”

可能表示：

```text
Design Target accepted
```

不必自动表示：

```text
整个 UI_SPEC Construction Contract approved
```

反过来，用户确认：

> “按这一版 UI_SPEC 开发。”

则可能已经构成 UI Contract Approval Evidence。

具体沟通仍复用：

```text
CROSS-STAGE-DECISION-01
```

避免反复确认同一个根决定。

---

# 二十七、一个根决定只确认一次

如果用户说：

> “整个资源管理页面主色改成橙色。”

它可能影响：

```text
Shared Foundation
Design Package
UI_SPEC
Implementation
Visual Baseline
```

不能每同步一份 Artifact 就问一次。

应该：

```text
Root Human Decision
↓
Governed Apply
↓
propagate to affected artifacts
```

已有总纲同样明确：根决策只确认一次，文件同步不构成新的用户决策。fileciteturn130file26

---

# 二十八、UI_SPEC Draft 不能静默成为 Approved

无论 AI 多有信心：

```text
Draft
```

都不能因为：

```text
confidence = 0.99
```

变：

```text
APPROVED
```

必须符合：

```text
Authority
Approval Evidence
Workflow/Governance
```

所以：

```text
AI confidence
≠ UI approval authority
```

---

# 二十九、Design Package 的 Unknown 不一定阻塞整个 UI_SPEC

例如：

```text
Page:
大部分已明确

一个低影响 tooltip delay = UNKNOWN
```

不一定阻塞整个页面。

应该：

```text
Localized blocker
```

然后根据 Gap 分类：

```text
Safe auto-complete
Assumption
Decision Required
Deferrable
Blocking
```

继续复用 F5-G02。

---

# 三十、但是高影响 UNKNOWN 必须阻塞相关 Scope

例如：

```text
删除操作是否永久不可恢复？
支付确认流程？
权限不足是隐藏还是禁用？
```

这些不能：

```text
UI_SPEC Approved with guessed semantics
```

应该：

```text
affected scope = BLOCKED / REVIEW_REQUIRED
```

但其他不相关区域可以继续。

---

# 三十一、UI_SPEC 应保留 Origin / Trace，而不是复制所有 Evidence

例如：

```text
Selected state triangle
```

UI_SPEC 可以保留：

```text
design_ref
decision_ref
origin
```

而不是把：

```text
原始 PNG
Scene
Semantic Tree
Rule text
Human chat
```

全复制进去。

所以：

```text
Trace by reference
> duplicate truth
```

---

# 三十二、UI_SPEC 与 Shared Foundation 的关系

如果 UI_SPEC 使用：

```text
brand.primary
```

最好：

```text
reference Shared Foundation / Token version
```

而不是复制：

```text
brand.primary = #1677FF
```

成第二 Truth。

但为了 Batch 稳定，可以：

```text
Effective UI Contract
```

记录解析时使用的：

```text
Foundation/Token version / resolved snapshot fingerprint
```

它仍然只是执行快照。

---

# 三十三、UI_SPEC 与 Behavior / Data 同理

例如：

```text
UI_SPEC
```

可以引用：

```text
approved Behavior Model
approved UI Data Semantics
```

但不能把：

```text
Product state
API schema
```

重新定义一份。

所以 D07 是：

> **UI construction contract aggregator**

不是：

> **Everything Truth File**

---

# 三十四、UI_SPEC 不应该无限变成巨型文档

这是可维护性重点。

长期不能：

```text
所有颜色
所有规则
所有接口
所有状态
所有设计历史
全部复制进 UI_SPEC
```

那最后 UI_SPEC 会变成另一个超级提示词。

正确：

```text
UI_SPEC
= minimal sufficient approved construction contract
+ stable references
```

这符合我们一直强调的：

```text
Minimum Sufficient Context
```

---

# 三十五、Current Effective UI_SPEC 是 Coding Authority

进入真正编码时：

```text
Current Effective PRD
+
Current Effective UI_SPEC
+
Effective Frontend Rules
+
Technical Context
```

形成 D02-09 的：

```text
Effective Implementation Context
```

Coding Agent 不应该重新从：

```text
raw image
old Design Package
chat history
AnyDesign output
```

重建 UI Authority。

---

# 三十六、Design Package 仍然可以作为支持输入

例如 Coding / Validation 需要：

```text
视觉基准
Source refs
结构细节
截图
```

可以通过 UI_SPEC Reference 获取 Design Package。

但：

```text
Design Package
cannot override Current Effective UI_SPEC
```

冲突时：

```text
Freshness / Reconciliation
```

而不是看谁更新。

---

# 三十七、Implementation Pack 不拥有 UI Truth

已有架构明确：

```text
Implementation Pack
= UI施工图
```

它是：

```text
HOW
```

而 UI_SPEC 是：

```text
Approved UI WHAT / Contract
```

所以：

```text
Implementation Pack
≠ UI Truth
```

如果 Implementation Pack 和 UI_SPEC 冲突：

```text
Implementation Pack must be regenerated/reconciled
```

不能让 HOW 反向覆盖 WHAT。

---

# 三十八、UI Change Classification 必须显式

我建议至少逻辑上区分：

```text
SOURCE_ONLY
PURE_UI_CHANGE
BUSINESS_AFFECTING_UI_CHANGE
IMPLEMENTATION_ONLY
```

例如：

### SOURCE_ONLY

PNG 重新压缩，没有语义变化。

### PURE_UI_CHANGE

圆角 8 → 12。

### BUSINESS_AFFECTING_UI_CHANGE

加入：

```text
“永久删除账户”
```

改变了产品行为。

### IMPLEMENTATION_ONLY

```text
flex → grid
```

但 UI Contract 完全没变。

这四类不能走同一个 Change 路径。

---

# 三十九、PURE_UI_CHANGE 不一定改 PRD

比如：

```text
按钮圆角 8 → 12
```

通常：

```text
PRD unchanged
UI_SPEC revision
```

不能为了“所有文档同步”去修改 PRD。

---

# 四十、BUSINESS_AFFECTING_UI_CHANGE 必须先回 Product

例如设计图新增：

```text
退款
永久删除
自动续费
```

这已经不是纯 UI。

必须：

```text
UI Change Candidate
↓
Product Governance
↓
Approved Product Change
↓
Design Refresh
↓
UI_SPEC Refresh
```

不能 UI_SPEC 单独批准。

---

# 四十一、IMPLEMENTATION_ONLY 不应升级 UI_SPEC

例如：

```text
原来：
Flex

改为：
Grid
```

如果：

```text
visual / behavior / contract unchanged
```

这是：

```text
Implementation Change
```

UI_SPEC 不应该因此升版本。

这能避免 UI Governance 被代码细节污染。

---

# 四十二、UI_SPEC Lifecycle 与 Freshness

建议逻辑上支持：

```text
Draft
Review
Approved
Current Effective
Stale
Superseded
Deprecated / Retired
```

但精确 enum 不在 Architecture Freeze 写死。

重点是：

```text
Lifecycle
Freshness
Current Effective
```

三个维度继续分开。

---

# 四十三、Approved UI_SPEC 被新版本替代后不能直接删除

例如：

```text
1.3
→ superseded by 2.0
```

1.3 可能仍被：

```text
old batch
historical validation
old release
```

引用。

所以继续：

```text
Supersede / Retire
> Delete
```

物理删除后面 F12。

---

# 四十四、Design Package Revision 也必须保持 lineage

例如：

```text
DP-17 rev1
↓
rev2
↓
rev3
```

要知道：

```text
derived from
supersedes
decision refs
source refs
```

但是 Design Package revision 和 UI_SPEC revision：

```text
不是 1:1
```

---

# 四十五、UI_SPEC Freshness 至少关注四类依赖

逻辑上至少：

```text
Product dependency
Design Package dependency
Shared Foundation dependency
Behavior/Data dependency
```

例如：

```text
PRD changed unrelated module
```

不应该：

```text
所有 UI_SPEC stale
```

必须做：

```text
scope-aware impact
```

具体 Freshness 计算 F9。

# 四十七、UI_SPEC Approval 不能授权 Implementation

```text
≠ Runtime Permission
```


# 四十八、Effective UI Contract READY 也不是 Coding Authorization


不要把 Readiness 和 Authorization 混起来。

# 五十三、建议正式冻结 UC-01 ～ UC-32

```text
UC-01
Design Source、Design Package、Draft UI Contract、
Approved UI_SPEC、Effective UI Contract
必须保持不同语义。

UC-02
Design Package 是具体 UI Scope 的
page/component-specific Design Target Owner。

UC-03
Design Truth、Token、Behavior、UI Data Semantics
作为 Design Package 的组成/关联语义，
不得各自形成 competing canonical UI truths。

UC-04
Design Package 不得取得 Product Authority；
Design/Product conflict 必须回 Product Governance。

UC-05
Design Package != UI_SPEC。
Design Target 完整不代表 Construction Contract 已批准。

UC-06
Draft UI Contract 是从 Design Package 投影出的
reviewable construction-contract candidate，
属于 Derived Candidate，不是 Current Effective Truth。

UC-07
UI_SPEC 是经过 UI Governance 批准的
Application/Surface/Scope-specific UI Construction Contract。

UC-08
UI_SPEC 应保持 Minimum Sufficient Contract，
通过 stable references 引用证据/设计包，
不得复制全部历史和 Provider metadata。

UC-09
PRD = Product/Business Truth；
UI_SPEC = Approved UI Construction Truth；
二者不得互相越权。

UC-10
Business-affecting UI semantics
不得仅通过 UI_SPEC 改写 Product Semantics。

UC-11
相关 PRD / Approved Product Change 更新时，
受影响 UI_SPEC 必须进入
STALE / REVIEW_REQUIRED 或等价 freshness 状态，
不得静默继续生效。

UC-12
Design Package Revision 不得自动改变 UI_SPEC；
必须经过 Semantic Diff / Impact / Review。

UC-13
Design Revision 与 UI_SPEC Version
必须保持独立版本轴，不得 1:1 绑定。

UC-14
Source-only Change 在无 UI semantic change 时
不得强制产生 UI_SPEC Revision。

UC-15
UI Change Impact 必须比较
Structure / Layout / Behavior / Token /
Data Semantics / Responsive / Asset /
Validation Target 等相关语义，
不得只看文件 checksum。

UC-16
Version、Lifecycle、Approval、
Freshness、Current Effective
必须继续保持不同维度。

UC-17
Approved != Current Effective。
多个 Approved UI_SPEC 可以存在，
具体 Task/Batch 只消费其锁定版本。

UC-18
Effective UI Contract 是
Task/Batch-scoped derived execution snapshot，
不得成为第二 UI Canonical Truth。

UC-19
Active Task/Batch 不得自动追随
newest/latest UI_SPEC。

UC-20
Newer UI_SPEC / Design Revision
默认只产生 NEWER_UI_AVAILABLE 或等价信号，
是否升级必须根据 Impact / Compatibility 决定。

UC-21
Design Package Coverage 与 UI_SPEC Coverage
必须分别治理；
未批准 Scope 不得因为 Design Package 已存在而自动进入施工。

UC-22
Partial UI_SPEC / Partial Coverage 是合法状态；
不得为了形式完整伪造批准范围。

UC-23
Design Acceptance 与 UI Contract Approval
必须保持不同语义；
但同一根 Human Decision 不得因传播到多份 Artifact 被重复确认。

UC-24
AI Confidence、Provider Result、
Design Completeness 不得自动产生 UI Approval。

UC-25
低影响 Unknown 可以局部 Deferred / Auto-resolve；
高影响 Product/Authority/Safety/Irreversible Unknown
必须阻塞对应 Scope。

UC-26
UI_SPEC 通过 stable refs 保留
Design Package / Decision / Evidence / Foundation lineage；
禁止通过全文复制建立双真源。

UC-27
Shared Foundation / Token /
Behavior / Data Semantics 的更新
必须通过 scope-aware impact 判断 UI_SPEC freshness，
不得默认全部 UI_SPEC 失效。

UC-28
Implementation Pack / Guidance 是 HOW，
不得覆盖 Current Effective UI_SPEC 的 WHAT。

UC-29
Coding Agent 默认消费
Current Effective PRD +
Current Effective UI_SPEC +
Effective Frontend Rules +
Technical Context，
不得从 Raw Design Source 重新构建平行 UI Authority。

UC-30
UI_SPEC Approved / Effective UI Contract Ready
不得等同于 Implementation Authorization、
Runtime Permission 或 Write Permission。

UC-31
Design Package / UI_SPEC Contract
必须保持 Provider-neutral、可版本化、可替换、
可局部失效和可追踪；
不得绑定 AnyDesign/Figma/某框架为 Core Authority。

UC-32
UI_SPEC Freshness / dependency /
impact / effective-snapshot runtime mechanics
留 F9/F8 实现；
Canonical Apply 留 F7；
D07 只冻结 UI Governance Semantic Contract。
```
