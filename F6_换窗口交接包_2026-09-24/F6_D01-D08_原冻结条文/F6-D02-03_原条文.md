好，继续进入 **F6-D02-03**。

你上一轮说“F6-D02-02 的大方向就按这套继续”，我把它记为：

```text
F6-D02-02
Direction = HUMAN_CONFIRMED
详细字段 / Schema = DEFERRED
Implementation = NOT_AUTHORIZED
```

现在这一轮专门解决：

# F6-D02-03 — Frontend Rule Module Governance
## 前端规则模块的建立、归纳、拆分、合并与演进

核心问题就是你以后真实会遇到的：

> **我按“某一类前端规则”分批投物资以后，Banyan 到底怎么判断是在补一个已有模块，还是应该新建模块、拆模块、合并模块？以后继续投第 2 批、第 10 批又怎么增量维护？**

这一轮仍然是 `HUMAN_REVIEW（人工评审）`，不施工。

---

# 一、先把最核心结构定清楚

我们现在讨论的正式逻辑应该是：

```text
Frontend Development Rule System
前端开发规则体系
│
├── Rule Module A
│   规则模块 A
│   ├── Rule Entry 001
│   ├── Rule Entry 002
│   └── ...
│
├── Rule Module B
│   ├── Rule Entry 001
│   └── ...
│
└── Rule Module ...
```

所以：

> **Module（模块）是“一类相对完整的前端开发知识集合”。**

而：

> **Rule Entry（规则条目）是模块内部一笔一笔、可以独立引用和匹配的规则。**

---

# 二、模块到底按什么标准建立

我建议不要用：

> 一个文件夹名字 = 一个模块。

也不要：

> 一批物资 = 一定新建一个模块。

而使用：

## “最小完整知识责任边界”

大白话就是：

> **这一批规则是不是在共同解决一类稳定、可以独立维护、可以独立被项目采用的前端工程问题？**

如果是，就适合作为一个 Module。

这个思想与前面 F4 / F5 已经冻结的“最小完整语义边界”和“不要机械一条一句拆对象”的原则一致。F5 也已经明确新输入要先 Reconcile（对账），AI 可以自动 extract / normalize / split / merge / dedup，再形成候选，而不能直接把文件结构当最终语义。fileciteturn94file26

---

# 三、用你举的例子理解

以下全部只是例子，不是正式模块名单。

比如未来真的形成：

```text
某类 PC 前端开发模块
```

它可能负责：

> PC / Web 页面的一整套通用工程实现问题。

里面有：

```text
布局
尺寸
滚动
表格
表单
Sticky
响应式
文本溢出
图片约束
...
```

也可能盘点后发现范围太大，需要拆。

---

再比如：

```text
某组件体系开发模块
```

负责：

> 当前组件体系自身的使用模式、限制、适配和最佳实践。

内部再是一笔一笔：

```text
Table 相关规则
Form 相关规则
Modal 相关规则
Select 相关规则
...
```

---

也可能未来有：

```text
某类移动设备开发模块
```

负责：

```text
触摸
安全区
窄屏布局
软键盘
移动导航
手势
...
```

但再次强调：

> **正式有哪些模块，要由你后续投的真实物资盘点后形成。**

---

# 四、你以后投物资时，可以直接声明“本批主题”

例如：

> “这是我整理的第 3 批移动端前端规则。”

系统收到：

```text
MAT-BATCH-037

user_intent:
这批主要用于移动端前端开发规则
```

这个说明非常有价值。

它是：

> **Module Intent（模块意图）**

系统优先按你指定的方向去对账。

---

# 五、但用户说的模块主题不是强制分类结果

比如你认为这一批全部是“移动端”。

实际盘点发现：

```text
20 条是移动端特有
8 条其实 Web / Mobile 都适用
3 条属于通用可访问性
2 条与已有通用布局规则重复
1 条和已有规则冲突
```

Banyan 不能为了服从文件夹名字，把全部 34 条硬塞进“移动端”。

应该告诉你：

> 这一批总体属于移动端主题，但其中部分内容属于已有通用模块，我已经避免重复收录；另有一项真实冲突需要处理。

所以：

```text
User Batch Theme
用户投放主题

≠

Final Module Ownership
最终模块归属
```

---

# 六、不过不要因此频繁打扰你

这里继续遵守：

> **用户表达意图，榕树承担治理成本。**

例如上面的：

```text
20 条移动端
8 条通用
3 条可访问性
2 条重复
```

只要没有重要语义冲突：

> **AI 可以自动分类。**

没必要问你：

> “第 1 条放移动端还是通用？”
>
> “第 2 条呢？”
>
> “第 3 条呢？”

这种交互完全违背我们的低打扰原则。F5 已经冻结：普通分类、ID、Trace、Routine bookkeeping 等由系统处理，主要在真实歧义、语义冲突、高影响和关键缺失时打断 Human。fileciteturn94file28

---

# 七、一批物资盘完以后，应该得到什么

比如：

```text
MAT-BATCH-037
```

盘点完成以后，不直接改规则库，而先得到类似：

```text
Module Reconciliation Result
模块对账结果
```

大白话展示：

```text
本批共提取 41 个规则语义

已有模块补充：
- 模块 A：新增 8 条
- 模块 B：补充 5 条

已有规则重复：
- 14 条

已有规则内容增强：
- 7 条

疑似替代旧规则：
- 3 条

跨模块规则：
- 2 条

真实冲突：
- 1 条

新模块候选：
- 1 个
```

这才是你真正需要看的盘点。

---

# 八、什么情况下直接补已有模块

如果新规则：

```text
解决的问题相同
适用范围相同
模块职责相同
```

那就补已有模块。

例如已有模块负责：

> “某组件体系前端开发”。

你新投一份该组件体系 Modal 的使用规范。

显然：

```text
Existing Module
↓
新增 Rule Entry
```

没必要新建：

```text
“Modal 模块”
```

---

# 九、什么情况下应该形成新模块候选

不能因为出现一个新术语就新建 Module。

应该至少满足：

```text
形成了一类稳定的工程问题
+
具有多个可复用规则
+
适用范围明显不同
+
可以独立维护
+
可以独立被 Profile 采用
```

再考虑：

```text
New Module Candidate
新模块候选
```

---

## 举例

假设目前只有：

```text
通用 Web 模块
```

后面连续几批物资出现大量：

```text
Safe Area
Touch Target
Soft Keyboard
Gesture
Bottom Navigation
Mobile Drawer
```

而且这些规则：

> PC 根本不需要。

那：

```text
新模块候选
```

就比较合理。

---

# 十、什么情况下不能新建模块

比如只发现：

> “上传进度条的圆圈怎么实现。”

不能因此建立：

```text
上传进度圆圈模块
```

这只是：

```text
现有某个模块中的一个 Rule Entry
```

甚至可能属于现有：

```text
反馈 / 上传 / 复杂视觉
```

某一个条目。

否则模块很快爆炸。

---

# 十一、模块粒度要防两个极端

### 极端 A：God Module（万能大模块）

```text
Frontend Rules
```

一个模块里：

```text
Web
Mobile
React
Vue
组件库
CSS
Accessibility
Performance
全部塞进去
```

结果：

> 不能精准加载，不能独立采用，也很难维护。

---

### 极端 B：模块爆炸

```text
Flex Module
Grid Module
Margin Module
Tag Module
Button Module
Triangle Module
...
```

最后几百个模块。

同样难用。

---

正确原则：

> **一个模块 = 一类具有稳定共同上下文的完整工程知识。**

---

# 十二、一个模块内部的 Rule Entry 也要保持“最小完整规则”

例如：

```text
不要把所有截图宽度写死
```

是一条相对完整的规则。

可以包含：

```text
问题
原则
适用条件
错误模式
正确思路
示例
理由
```

而不是拆：

```text
RULE-001：不要写 width 280
RULE-002：不要写 width 320
RULE-003：不要写 width 400
```

那是数据，不是规则。

---

# 十三、Module 要有稳定 ID

即使以后改名字：

```text
“通用后台开发”
↓
“Web Desktop Development”
```

它仍然可能是同一个 Module。

所以：

```text
Module ID
≠ Module Name
```

名字可以改。

ID 保持稳定。

---

# 十四、什么时候保留同一个 Module ID

如果模块：

> 核心责任仍然是同一类知识。

即使：

```text
新增规则
删掉过时规则
修改名称
扩充说明
版本升级
```

都不需要换 Module ID。

---

# 十五、什么时候不能再用旧 Module ID

假设原来：

```text
MODULE-A
```

混了：

```text
移动端
+
PC
+
组件体系
```

后来发现这是错误结构，必须正式拆成：

```text
MODULE-B
MODULE-C
MODULE-D
```

那不能偷偷让 `MODULE-A` 的意思变了。

应该：

```text
MODULE-A
SUPERSEDED
被替代

→ MODULE-B
→ MODULE-C
→ MODULE-D
```

保留 Lineage（演进关系）。

F5 已经明确历史版本、替代关系必须可追踪，Stable ID 不能重新绑定无关语义。fileciteturn94file25

---

# 十六、模块拆分怎么处理

例如：

```text
MODULE-A
通用前端
```

长期越来越大。

盘点发现：

```text
其中一部分属于布局
一部分属于组件体系
一部分属于移动端
```

可以提出：

```text
Module Split Candidate
模块拆分候选
```

但拆分不能只看：

> “文件太长了。”

要看：

> **语义职责是否真正已经变成几个可以独立采用的知识域。**

---

# 十七、模块合并怎么处理

反过来，如果：

```text
MODULE-A
MODULE-B
```

长期：

```text
Scope 几乎一样
规则高度重叠
项目总是同时加载
维护时一直一起变
```

说明模块可能拆得过细。

可以形成：

```text
Module Merge Candidate
模块合并候选
```

---

# 十八、AI 可以自动拆分 / 合并模块吗？

我的建议：

### 普通内部分类

可以自动。

例如：

> 这 3 条应该从本批移动端主题归入已有通用模块。

自动做。

---

### 正式模块结构变化

例如：

```text
新建共享 Module
拆 Module
合并 Module
废弃 Module
大规模移动 Rule Entry
改变 Profile 依赖
```

不能 AI 静默完成。

因为会影响：

```text
Rule IDs
Project Profiles
Association Index
已有引用
Context Loading
多个项目
```

属于更高影响变化。

应该：

```text
Candidate
↓
Impact Analysis
影响分析
↓
必要时 Human Decision
↓
Governed Apply
```

---

# 十九、但不意味着每加一条规则都要审批

这点要特别强调。

例如已经确认：

```text
模块 A 的职责很明确
```

你投第 7 批物资。

系统识别：

```text
新增 5 条
都是明显属于 A
无冲突
无权威问题
```

这种应该低打扰。

如果规则本身不涉及强制高影响变化，可以自动形成正常 Candidate / Draft 流程，不需要把“模块归属”再问你一遍。

---

# 二十、模块必须允许跨 Module Reference

一条规则有时候不是孤立的。

例如某组件体系规则可能说：

> “布局仍然遵循通用 Web Layout Rules。”

不应该把那 20 条通用规则复制过来。

应该：

```text
Component Module
    ↓ reference
Common Web Module
```

这就是：

> **复用，不复制。**

---

# 二十一、但要防止 Module Dependency（模块依赖）变成复杂蜘蛛网

模块可以：

```text
reference
depends-on
extends
```

但不能随便互相依赖。

否则：

```text
A → B
B → C
C → D
D → A
```

上下文加载会越来越慢。

所以我建议：

> **模块间依赖保持显式、最小、可解析，避免循环依赖。**

---

# 二十二、Profile 才负责组合模块

不要用模块自己去决定：

> “只要用了 A，就必须使用 B、C、D、E。”

真正项目采用什么，主要还是：

```text
Frontend Profile
```

负责。

例如：

```text
Project A

Frontend Profile
├── Module A
├── Module C
└── Module F
```

Module 依赖只表达：

> 语义上确实必须依赖的基础。

不能替代 Profile。

---

# 二十三、项目规则模块与共享规则模块也要分开

假设当前项目有：

> “我们的租户后台所有表格操作统一这样做。”

它可能形成：

```text
Project-specific Module
项目专属模块
```

属于当前 `.banyan` Project Instance。

---

但如果你后来发现：

> 这套规则其实所有项目都能用。

不能直接：

```text
project module
↓
搬到 shared
```

而是：

```text
Project Rule
↓
Reusable Candidate
跨项目复用候选
↓
对账
↓
Shared Module / Rule
```

并继续保留它最初来自哪个项目、哪批物资的来源。

---

# 二十四、共享模块晋升之后，原项目怎么处理

比如 Project A 产生：

```text
RULE-A-017
```

后来被治理成公共规则：

```text
SHARED-RULE-031
```

项目 A 不应该继续维护：

```text
一份项目规则
+
一份公共规则
```

两个可编辑真源。

而应该：

```text
Project A Profile
↓
引用 SHARED-RULE-031
```

原来的项目条目保留历史 lineage（演进关系），但不再形成双真源。

---

# 二十五、模块更新时还必须做 Impact（影响）分析

比如共享模块升级：

```text
v3 → v4
```

某条：

```text
RECOMMENDED
```

变成：

```text
REQUIRED
```

这不是小修改。

系统必须知道：

```text
哪些 Project Profile 使用这个模块？
哪些页面 / Implementation Guidance 会受影响？
现有代码要不要重新检查？
```

所以 Module / Rule 的版本变化需要和 F9 后面的 Impact Index（影响索引）衔接。

---

# 二十六、但是“规则库更新”不应该把所有项目立刻自动升级

例如公共 Module：

```text
v1
↓
v2
```

不能：

> 今天一更新，100 个项目全部自动切 v2。

Project Profile 需要能够：

```text
Pin
固定某个版本

或

Follow compatible version
跟随兼容版本
```

具体版本策略以后再定。

但架构原则现在就应该保留：

> **共享规则更新 ≠ 所有项目立即生效。**

否则很危险。

---

# 二十七、用户按模块投物资的完整流程现在可以闭环了

未来你的实际工作方式：

```text
你：
“这一批是某类前端开发规范。”
        ↓
.banyan Material Intake
        ↓
MAT-BATCH-N
        ↓
Banyan 自动盘点
        ↓
提取 Rule Candidates
        ↓
Module Reconciliation
模块对账
        ↓
        ├─ Existing Module Update
        │  补已有模块
        │
        ├─ Cross-Module Routing
        │  分流到其它已有模块
        │
        ├─ Duplicate
        │  重复
        │
        ├─ Rule Revision
        │  规则修订
        │
        ├─ Conflict
        │       ↓
        │     Buffer
        │
        └─ New Module Candidate
               ↓
          模块候选
```

这就是完整的“按模块持续投物资”。

---

# 二十八、第二批、第三批以后不用重新生成模块

例如：

```text
第一批
→ 建立 MODULE-A
→ 30 条规则
```

第二批：

```text
→ 与 MODULE-A 对账
→ 新增 8
→ 修订 3
→ 重复 11
→ 冲突 1
```

第三批：

```text
→ 再增量对账
```

永远遵循：

> **Incremental Reconciliation（增量对账）**

而不是：

> 每次把整个规则模块重新生成一遍。

这与 F5 已冻结的“Reconciliation-first + smallest valid delta（对账优先，只生成最小有效变化）”是一致的。fileciteturn94file3

---

# 二十九、如果有价值但这批不能确定，继续执行 No-Loss

比如第 6 批发现：

> 这 20 条可能足以形成新的跨端公共模块，但资料还不够。

不要：

```text
不建模块
↓
就忘了
```

而是：

```text
New Module Candidate
Status:
DEFERRABLE_UNCERTAINTY

↓

Carry-Forward
```

未来再投相关物资时自动重新拿出来。

F5 已冻结 Deferred 必须保留 origin / lineage，并具备重新访问和后续转化能力。fileciteturn94file1

---

# 三十、Module 本身建议具备哪些逻辑信息

现在只定逻辑，不定 YAML 字段。

一个 Module 至少应该能回答：

```text
我是谁？
解决哪一类问题？

适用哪里？
不适用哪里？

包含哪些 Rule Entry？

当前是什么版本？

来源于哪些物资 / 批次？

属于共享还是项目专属？

依赖 / 引用哪些其它模块？

哪些 Project Profile 在使用我？

有没有被拆分 / 合并 / 替代？

当前是否有效？
```

---

# 三十一、Rule Entry 的位置也不能和 ID 绑定死

例如：

```text
RULE-123
```

原来在 Module A。

以后治理发现：

> 更合理归 Module B。

如果规则语义本身没变：

```text
Rule ID
```

可以继续保持。

改变的是：

```text
Module Membership
模块归属
```

而不是：

> 一移动文件夹就创建新 Rule ID。

这样追踪才稳定。

---

# 三十二、同样，物理目录不能决定模块语义

以后可能有：

```text
frontend-rules/module-a/...
```

但：

> **目录是实现，不是 Authority（权威）。**

Module Identity（模块身份）由稳定语义 ID 决定。

这和我们前面“Stable ID 独立于 Path”的原则一致。fileciteturn94file3

---

# 三十三、规则模块也不能被“最新文件”静默重写

比如你投入：

```text
某规范-v5.pdf
```

不能：

> v5 最大，所以旧规则全部直接覆盖。

仍然要：

```text
新 Material
↓
```

# 三十四、这一套如何满足你一直强调的 6 个原则

### 灵活

模块不是 Core 写死，可以根据实际知识演进。

### 有条理

```text
Module
→ Rule Entry
→ Module Index
→ Rule Index
→ Profile
```

清楚。

### 可扩展

新增一整类前端知识只增加模块，不推翻系统。

### 速度快

任务先选模块，再选条目，不读整个知识库。

### 符合逻辑

模块按知识责任形成，而不是按“文件叫什么”形成。

### 便捷但可靠

你只负责：

> “这是这一类规则的第 N 批物资。”

分类、去重、版本、关联、索引由 Banyan 完成；真正拆模块、合并模块、重大冲突时才找你。

# 三十五、F6-D02-03 候选不变量

我建议这一轮先形成下面这些：

```text
RM-01
Frontend Rule Module 是一类稳定、可复用、
可独立维护的前端工程知识集合。

RM-02
Module 内包含多个 Rule Entry；
一条 Rule Entry 不等于一个 Module。

RM-03
正式 Module 分类不由 Core 预先写死，
由实际物资和持续治理形成。

RM-04
用户可按知识主题分批投放物资；
用户声明的主题是强路由提示，
但不强制所有规则最终归属同一 Module。

RM-05
每批物资必须先 Reconcile，
再判断新增、重复、修订、冲突、
跨模块分流、新模块候选等结果。

RM-06
已有 Module 的普通确定性补充应低打扰增量处理，
不得每批重新生成整个 Module。

RM-07
New Module 必须满足相对稳定、
可独立维护、可独立采用的完整知识责任边界，
不得因为出现少量新规则就制造模块爆炸。

RM-08
Module Split / Merge / Retirement /
大规模 Rule Relocation 属于受治理结构变化，
不得 AI 静默执行。

RM-09
Module ID 和 Rule ID 均独立于文件名和物理路径。

RM-10
语义未改变的 Rule 即使调整 Module Membership，
原则上继续保持 Stable Rule ID。

RM-11
Module / Rule 的历史版本、拆分、合并、
替代、来源和 lineage 必须可追踪。

RM-12
共享 Module 更新不等于所有 Project Profile
立即自动升级。

RM-13
Module 可以最小化引用其它 Module，
但不得形成不可解析的依赖蜘蛛网或循环依赖。

RM-14
Project-specific Rule Module 可以产生
Reusable Candidate，但跨项目晋升必须经过治理，
不得直接把项目规则当公共真源。

RM-15
有价值但当前不足以决定 Module 结构的内容，
必须进入 Carry-Forward，不得丢失。
```
