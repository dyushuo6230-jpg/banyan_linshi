# 1. 决策目的

F6-D01 要解决的不是“AnyDesign 应该输出几个文件”这么小的问题。

它要解决的是整个榕树 AI 的：

> **设计相关信息到底怎样进入、怎样被理解、怎样被对账、怎样被长期保存，以及怎样形成可靠的 Design Package（设计包）。**

最终目标：

```text
用户投放各种物资
        ↓
榕树 AI 自动登记、分类、盘点、对账
        ↓
业务语义 → PRD
UI 明确要求 → User Design Constraint（用户设计约束）
设计证据 → Design Evidence（设计证据）
通用设计思想 → UI Design Rule Candidate（UI 设计规则候选）
        ↓
形成 / 更新 Design Package（设计包）
        ↓
后续 F6 再进入 UI_SPEC 定稿
        ↓
前端施工
        ↓
视觉验证与修复
```

用户主要负责：

> **“给资料、说需求、做真正需要人的决定。”**

榕树 AI 负责内部分类、ID、关系、版本、追踪、普通对账和状态维护。

这继承 F5 已冻结的原则：

> **用户表达意图，榕树承担治理成本；人的注意力只用于真正需要人决定的事情。** fileciteturn81file38L25-L71

# 2. 上游已冻结约束

F6-D01 不重新推翻 F1～F5。

## 2.1 PRD 与 UI 的权威边界

已经冻结：

```text
PRD
= 产品 / 业务需求正式真源

UI_SPEC
= 经批准的 UI 合同

Design Source
= 设计证据
```

设计图、UI、代码和运行结果可以发现冲突，但不能静默改写 PRD。fileciteturn72file9L1-L37

因此：

> **设计图不是产品真源。AnyDesign 也不是产品真源。**

---

## 2.2 一个语义事实不能有两份正式真源

已经冻结：

> Same semantic fact has one Canonical Write Target  
> **同一语义事实只有一个正式写入位置。**

Requirement（需求项）可以拥有独立 ID，但不意味着每条需求必须单独一个文件；SQLite 也不能保存另一份可编辑的产品正文。fileciteturn73file8L1-L25

F6-D01 继承这一原则。

---

## 2.3 文件与 SQLite 已有边界

已冻结：

```text
受治理文件
= Canonical Semantic Truth
  正式语义真源

SQLite
= Derived / Rebuildable / Query Layer
  派生、可重建的索引和查询层
```

不能建立一个“万能数据库”取代所有正式文件。fileciteturn79file5L10-L17

# 5. Unified Material System — 统一物资体系

## 5.1 所有外部输入统一视为 Material（物资）

以后 Banyan 不再为 PRD、UI、技术各造一套互不兼容的“资料系统”。

统一使用：

```text
Material
物资
│
├── Requirement Material
│   需求物资
│
├── Design Material
│   设计物资
│
├── Standard Material
│   规范 / 标准物资
│
├── Technical Material
│   技术物资
│
├── Legacy Material
│   历史物资
│
└── Change Material
    变更物资
```

用户不需要先自己分类。

---

## 5.2 物资统一投放，但可以有领域视图

例如一个 PDF 同时包含：

```text
需求说明
+
UI 草图
+
设计规范
```

物理上只保存一份。

系统可以同时把它显示在：

```text
Requirement Material View
需求物资视图

Design Material View
设计物资视图
```

**不得为了分类重复复制原始文件。**

# 6. Material Intake — 统一物资投放

所有物资从统一的 Material Intake（物资投放入口）进入。

逻辑模型：

```text
Material Intake
    ↓
MAT-BATCH-001
MAT-BATCH-002
MAT-BATCH-003
...
```

物理目录可以后续确定，但架构上必须：

> **按批次接收。**

---

# 7. Batch — 批次模型

Batch（批次）表达：

> **哪些文件和哪些用户说明，是在同一次投放中一起进入系统的。**

例如：

```text
MAT-BATCH-018

├── 新版需求.docx
├── 用户管理.png
├── 后台设计原则.pdf
└── 用户说明：
    “搜索区域沿用当前后台；
     操作列按新图；
     删除按钮不要常显。”
```

这些信息属于同一投放上下文。

---

## 7.1 Batch 不等于正式版本

必须冻结：

```text
Material Batch
≠ PRD Revision

Material Batch
≠ Design Revision

Material Batch
≠ UI_SPEC Revision
```

一次物资投放可能：

- 修改 PRD；
- 只修改 Design Package；
- 什么正式产物都不修改；
- 同时影响多个对象。

---

# 8. 原始物资保护

用户投入的原始资料原则上保持原样。

```text
用户提交文件
= Source Evidence
= 原始来源证据
```

AI 不得：

```text
覆盖原图片
重写原 Word
把 AI 总结替换原 PDF
用新版静默覆盖旧版
```

新版本应作为新的 Material / Revision 纳入。

v3.1 已有素材版本、来源、文件哈希、适用范围、替代关系以及“新版本不得静默覆盖旧版本”等规则，本决策继续保留这些语义。fileciteturn74file3L31-L61

# 9. Material Reconciliation — 物资盘点与对账

物资进入以后，不直接生成真相。

先：

```text
登记
↓
完整性检查
↓
去重
↓
分类
↓
判断新旧关系
↓
识别适用范围
↓
提取语义
↓
与当前正式状态对账
↓
识别新增 / 修改 / 保留 / 冲突 / 未知
```

这叫：

`Material Reconciliation（物资对账）`

---

# 10. 对账结果必须分类

物资盘点产生的问题，不是一律“问用户”。

应至少区分为：

```text
SAFE_AUTO_COMPLETE
可安全自动处理

WORKING_ASSUMPTION
工作假设

DEFERRABLE_UNCERTAINTY
可延期的不确定项

DECISION_REQUIRED
需要人工决定

BLOCKING_GAP
阻断缺口
```

其中：

### 可安全自动处理

例如重复文件、明确版本关系、普通格式归一。

系统自动处理。

### 工作假设

必须：

```text
低风险
可逆
有范围
明确不是批准结论
```

### 可延期未知

例如：

> 没有移动端设计。

可以写：

```text
UNKNOWN
```

不一定阻止桌面端工作。

### 需要决策

例如：

> 新设计和当前公共规范明显冲突。

才真正询问用户。

### 阻断缺口

只阻断受影响范围。

不能一个局部问题拖死整个批次。

---

# 11. Material Reconciliation Buffer — 物资对账缓冲区

无法可靠处理、且真正需要人的问题，进入：

> **Material Reconciliation Buffer（物资对账缓冲区）**

缓冲区保存的不是原文件，而是：

> **“哪些对账问题还没有解决。”**

例如：

```text
BUFFER-017

来源：
MAT-BATCH-021

问题：
新版页面搜索按钮为橙色，
当前公共 Search 为黑色。

无法判断：
A. 当前页面局部特例
B. 公共 Search 升级

如果升级公共设计：
可能影响 12 个页面

状态：
DECISION_REQUIRED
```

---

## 11.1 Buffer 不是正式真源

冻结：

```text
Buffer
≠ PRD

Buffer
≠ Current Design Package

Buffer
≠ Shared Foundation

Buffer
≠ UI_SPEC
```

它属于：

`NON-CANONICAL（非正式真源）`

---

## 11.2 决策后不能直接“把 Buffer 改名为正式文件”

必须：

```text
Buffer
↓
Human Decision
人工决定
↓
Reconcile
重新对账
↓
形成正式 Delta（变化）
↓
进入后续 Canonical Apply
正式应用
```

Canonical Apply（正式应用）的执行机制属于 F7。

---

# 12. 局部阻塞原则

假设一批物资发现：

```text
10 个确定项
1 个公共设计冲突
1 个移动端 UNKNOWN
```

不能：

> 整批全部停住。

应该：

```text
10 个确定项 → 正常继续

公共冲突 → Buffer

移动端未知 → UNKNOWN
```

这继承 F5 的渐进式闭合和低打扰治理原则。fileciteturn81file38L25-L71

# 13. No-Loss Carry-Forward — 无损承接

这是 F6-D01 新增的重要硬规则。

> **任何已经发现“有价值”，但本期不能确定、暂时不应决定或属于后续阶段的问题，都不得丢失。**

必须进入：

`Carry-Forward Register（后续承接清单）`

---

## 13.1 Carry-Forward 至少要表达

逻辑上必须能知道：

```text
事项是什么
来源是什么
为什么有价值
为什么本期不确定
当前已经确定到什么程度
关联哪些对象
未来应该由哪个阶段继续处理
重新盘点的触发条件
当前状态
```

---

## 13.2 进入后续阶段时必须回收

例如进入 F6-D02：

系统必须先检查：

```text
target_stage = F6-D02
```

把以前留下的：

```text
UI Design Rule 格式
规则强度
规则冲突机制
跨项目复用
```

重新带回来。

---

## 13.3 四个概念不能混

```text
UNKNOWN
= 当前事实不知道

DEFERRED
= 知道问题存在，但现在不决定

DECISION_REQUIRED
= 现在就需要人做决定

CARRY_FORWARD
= 有价值，必须保证未来继续处理
```

---

# 14. Requirement × UI 语义拆分

用户自然语言不能按“整句话归哪个文档”处理。

必须按 Semantic Ownership（语义归属）拆分。

例如：

> “增加收藏功能，收藏按钮放购物车左边，收藏后黄色实心。”

系统自动拆：

```text
增加收藏功能
→ Product Semantics
→ PRD

购物车左边
→ UI Design Semantics
→ User Design Constraint

黄色实心
→ UI State Constraint
→ User Design Constraint
```

用户不需要自己重新写两遍。

---

# 15. User Design Constraint — 用户设计约束

正式定义：

> **User Design Constraint 是用户明确表达的、作用于 UI 目标设计的自然语言约束。**

它可以来源于：

```text
需求描述
物资投放说明
设计图补充说明
后续修改要求
Design Review 决策
```

例如：

```text
顶部保持旧版
这个模块不要
按钮放购物车左边
公共 Search 使用黑底白字
分类主体按新版设计
```

---

# 16. User Design Constraint 的存储身份

User Design Constraint：

> **逻辑上独立于 PRD。**

PRD 可以引用：

```text
REQ-USER-001
→ UIC-USER-001
```

但 PRD 不重复复制完整 UI 细节。

---

## 16.1 User Design Constraint 不要求一条一个文件

继承 F5：

> Addressable Semantic Entity ≠ Independent Artifact File  
> **可寻址语义对象不等于每条都必须一个文件。** fileciteturn73file8L1-L25

例如：

```text
UIC-001
UIC-002
UIC-003
```

可以集中存在同一个受治理对象中。

精确存储格式后续确定。

---

# 17. UI 约束不能静默覆盖 PRD

例如 PRD 明确：

> 未登录用户可以查看商品价格。

用户后来写：

> 未登录时隐藏价格。

这不是普通视觉变化。

它影响 Product Behavior（产品行为）。

因此：

```text
发现 Product Semantic Conflict
↓
进入产品变更 / 决策流程
↓
必要时修改 PRD
↓
再更新 UI
```

不能：

```text
User Design Constraint > PRD
```

直接覆盖。

# 20. UI Design Rule 与 Shared Foundation 分离

## UI Design Rule

回答：

> **通常应该怎样设计。**

例如：

```text
高频操作应该容易发现
危险操作应该明确反馈
低频工具可以降低视觉干扰
```

## Shared Foundation

回答：

> **当前这个项目具体采用什么公共设计语言。**

例如：

```text
主色黄色
黑色胶囊 Search
白色大圆角卡片
当前字体体系
```

冻结：

```text
UI Design Rule
≠ Shared Foundation
```

# 21. Design Package — 正式定位

Design Package（设计包）回答：

> **“这个页面 / 这套页面当前目标设计是什么样、由什么组成、元素之间是什么关系。”**

它负责：

```text
结构
图层
视觉
状态
复杂效果
滚动
裁剪
遮罩
关键细节
来源
人工约束
继承
局部覆盖
未知项
```

它不负责：

```text
React 怎么写
Vue 怎么写
Flex / Grid 最终怎么实现
伪元素怎么写
Ant Design API 怎么调用
CSS 具体写法
```

---

# 22. Design Package 不是 UI_SPEC

冻结：

```text
Design Package
= 结构化设计表达 / UI_SPEC 输入

UI_SPEC
= Approved UI Contract
  经批准的正式 UI 合同
```

Design Package 不得自动宣布自己是 Approved UI_SPEC。

---

# 23. Design Package 不依赖设计图

必须支持四类输入方式：

```text
IMAGE-DRIVEN
设计图驱动

DESCRIPTION-DRIVEN
文字描述驱动

INHERITANCE-DRIVEN
继承已有设计驱动

MIXED
混合驱动
```

具体枚举名后续可以调整。

---

# 24. 无图设计模式

例如用户说：

> “新增后台用户管理，姓名/手机号搜索，状态筛选，操作列放右边，新增按钮右上，整体沿用当前后台规范。”

即使没有图：

```text
PRD
+
User Design Constraint
+
Shared Foundation
+
适用 UI Design Rules
↓
F0 Design Package
```

仍然可以继续工作。

v3.1 已经支持无图 F0 和 Partial（部分覆盖）思路，并明确 AnyDesign 产物不能直接成为 Approved UI_SPEC。fileciteturn74file6L1-L8

# 52. Design Package × UI Design Rules × Frontend Rules × UI_SPEC

四者正式分工：

```text

= 这个页面具体应该是什么样

= 这种东西通常应该怎样设计

= 工程上通常怎样实现
```

# 60. F6-D01 Core Invariants — 核心不变量

为方便以后施工和验收，本决策汇总冻结以下规则。

### DP-01
Design Package 不混入普通实现技术和前端代码。

### DP-02
Rendered Geometry（呈现几何）不等于 CSS 固定尺寸。

### DP-03
复杂视觉细节不得静默消失；无法确认时必须 UNKNOWN。

### DP-04
先理解结构、父子、图层、滚动、遮罩，再处理微观样式。

### DP-05
状态必须表达完整可见差异。

### DP-06
静态图片不能被用于凭空发明交互、动画或业务行为。

### DP-07
视觉 Demo 数据不得成为业务真数据。

### DP-08
`design-review.md` 是派生审核视图，不拥有设计 Authority（权威）。

### DP-09
Design Package 必须 Provider-neutral（不绑定具体设计工具）。

### DP-10
Schema 可以完整，实例必须保持轻量；无关字段不强制制造空数据。

### DP-11
多页面必须支持公共 Foundation 提取。

### DP-12
公共冲突禁止投票、随机选择或静默采用第一份材料。

### DP-13
页面局部差异不得被过度“统一化”。

### DP-14
多个需要用户处理的问题优先集中呈现，而不是逐条高频打断。

### DP-15
公共设计采用继承；页面记录局部差异。

### DP-16
同页面多状态、多视口、重复图应先归组再建包。

### DP-17
Design Package 支持持续增量演进。

### DP-18
旧页面重新提交优先识别为 Revision。

### DP-19
新批次页面可以扩展 Partial Design Set。

### DP-20
每批新增材料都重新检查是否影响 Shared Foundation。

### DP-21
已确认 Shared Foundation 不得被后续页面证据静默覆盖。

### DP-22
局部变化默认保持局部，不能无治理地升级为公共规则。

### DP-23
Material / Reconciliation Workspace（物资/对账工作区）不是 Design Truth。

### DP-24
人工注意力只用于真正重要的冲突、歧义和高影响设计变化。

### DP-25
设计物资投放可以同时携带自然语言 User Design Constraint。

### DP-26
UI 范围内明确人工约束高于冲突的 AI 推断。

### DP-27
人工约束可以改变目标设计，但不能篡改历史设计证据。
