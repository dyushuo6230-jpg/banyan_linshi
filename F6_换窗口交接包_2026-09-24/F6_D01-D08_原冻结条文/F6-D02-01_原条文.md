# 一、调整后的前端开发规则体系

新的结构是：

```text
Frontend Development Rule System
前端开发规则体系
│
├── Rule Module
│   规则模块
│   │
│   ├── Rule Entry
│   │   一笔规则
│   ├── Rule Entry

│   └── ...
│

│   │
│   ├── Rule Entry

│
```

核心原则：

> **先有“模块”，模块里面才是一笔一笔的规则。**

不是一条规则一个模块。

# 二、模块不是预先写死的

你举的：

```text
移动端开发
Ant Design 组件开发
通用 PC 开发
```

目前都只是例子。

**不会在 F6-D02 里直接冻结成正式模块名称。**

正式模块要经过：

```text
你按主题投放一批物资
↓
Banyan 盘点
↓
提取知识
↓
与已有模块对账
↓
判断：
- 归入已有模块
- 拆到多个已有模块
- 形成新模块候选
↓
必要时你审批
```

也就是说：

> **模块结构来自物资长期盘点，不来自 AI 事先拍脑袋。**

# 三、你以后怎么投前端规范物资

例如你说：

> “这一批是我整理的移动端前端开发资料。”

进入统一物资入口：

```text
Material Intake
统一物资入口
        ↓
MAT-BATCH-N
        ↓
用户说明：
“这批主要是移动端前端开发资料”
        ↓
附件若干
```

然后 Banyan 自动：

```text
登记
↓
盘点
↓
提取 Rule Candidate
规则候选
↓
去重
↓
同义合并
↓
与已有规则对账
↓
识别归属模块
↓
冲突检查
```

最终可能出现：

```text
已有模块 A：
新增 6 条

已有模块 B：
补充 3 条

重复：
5 条

疑似替代旧规则：
2 条

冲突：
1 条 → Buffer

新模块候选：
1 个
```

你不需要自己把每份文档手工拆成规则。

# 四、模块内部才是一笔一笔的 Rule Entry

比如某个模块以后正式形成后，内部可能是：

```text
MODULE-XXX

├── RULE-001
├── RULE-002
├── RULE-003
├── RULE-004
└── ...
```

一条 Rule Entry 应该解决一个：

> **完整、可复用、可解释的工程问题。**

不能太大：

> “前端所有布局规则”一条。

也不能太碎：

```text
padding-top 一条
padding-bottom 一条
```

要保持“最小完整责任边界”。

# 五、增加 Module Index + Rule Association Index

为了速度和自动关联，我建议保留我们刚才讨论的“两级索引”。

## 第一级：Module Index
### 模块索引

回答：

> **这个问题应该先去哪些模块里找？**

例如识别到：

```text
table
selected-state
horizontal-scroll
```

模块索引先缩小范围。

---

## 第二级：Rule Association Index
### 规则关联索引

回答：

> **这些模块内部具体需要加载哪几笔规则？**

所以最终：

```text
PRD / Design Package / Code Semantic
语义
        ↓
Module Index
模块定位
        ↓
Rule Association Index
具体规则定位
        ↓
加载少量相关 Rule Entry
```

这比全库搜索更快，也更稳定。

# 六、设计图里的气泡效果怎么关联

例如 Design Package 已经识别：

```text
selected_state
capsule_or_bubble
bottom_triangle
horizontal_scroll
fade_mask
```

注意：

> 到这里仅仅是在描述“它是什么”。

然后：

```text
这些标准语义
↓
Module Index
↓
找到相关前端开发模块
↓
Rule Association Index
↓
找到具体规则条目
```

最终才形成：

```text
Implementation Guidance
施工指导
```

所以：

> **前端规则不会反过来影响 Design Package 对设计事实的判断。**

# 十七、调整后依然符合你要求的整体设计原则

### 灵活

模块不是写死的，可以持续增加、拆分、合并。

### 有条理

```text
物资
→ 模块
→ Rule Entry
→ 索引
→ Profile
→ 施工
```

层次明确。

### 可扩展

未来任何新的端、框架、组件体系、开发方法都能增加模块，不改 Core。

### 速度快

先匹配模块，再匹配 Rule Entry，只读取当前任务需要的内容。

### 符合逻辑

设计/需求先产生语义，再找工程规则，不让工程知识污染设计事实。

### 使用方便

你只需要：

> “这一批是某类前端规范资料。”

Banyan 负责整理。

### 可靠

有：

```text
来源
版本
模块身份
Rule ID
冲突
Buffer
Trace
Profile
```

不会变成 AI 凭记忆临场写代码。
