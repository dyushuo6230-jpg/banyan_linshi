# F6-D08 — Implementation Guidance × Implementation IR × Implementation Pack
## 实现指导 × 实现中间语义 × 前端施工包

```text
Status = HUMAN_REVIEW
Implementation = NOT_AUTHORIZED
```

这一项解决的是：

> **当 PRD、UI_SPEC、Design Package、Behavior、Data 都已经明确以后，Banyan 怎样把“页面应该是什么”转换成“前端应该怎样实现”，同时又不直接绑定 React / Vue / Ant Design / Element Plus，不把截图坐标抄成 absolute，不把设计测量值直接写成固定宽高，也不让 Implementation HOW 反过来改写 UI Truth。**

现有 Implementation 规则已经把这层定位为 **Design → Implementation IR**，目标是生成 Framework-neutral Implementation Pack，而不是直接生成 React/Vue 代码。fileciteturn131file0  
总纲也已经把最终 UI 链冻结为：`Design Truth → Behavior + Data → Frontend Layout Guidance → Implementation IR → Framework Adapter → React/Vue/Other`。fileciteturn132file0

---

# 一、D08 先把 5 个概念彻底分开

建议正式区分：

```text
Implementation Semantic Need
实现需求语义

Implementation Guidance
实现指导

Implementation IR
框架无关实现中间语义

Implementation Pack
任务级前端施工包

Framework Adapter Output
具体技术栈施工表达
```

它们不是一个东西。

---

# 二、Implementation Semantic Need 从 D02-09 继承

D02-09 已经冻结：

```text
Design Target
↓
Implementation Semantic Need
↓
Frontend Rule Resolution
↓
Implementation Context
```

所以 D08 不再发明第二个“设计到实现桥”。

D08 从这里接着往下：

```text
Effective Implementation Context
        ↓
Implementation Guidance
        ↓
Implementation IR
        ↓
Implementation Pack
        ↓
Framework Adapter
```

关系是：

```text
D02-09 OWNS semantic bridge/context
D08 OWNS implementation representation/pack
```

---

# 三、Implementation Guidance 的正式定位

建议定义：

> **Implementation Guidance = 针对当前 UI Contract，在当前项目约束和 Frontend Rules 下，对“应该采用什么工程实现策略”的结构化指导。**

例如：

```text
设计目标：
一排 4 个卡片等宽排列

Implementation Guidance:
- 采用二维规则布局
- 子项由父容器控制宽度
- 间距使用容器 gap
- 卡片宽度应可伸缩
- 避免根据截图逐项写固定 width
```

这里已经是 HOW。

但还没有变成：

```css
display: grid;
grid-template-columns: repeat(4, minmax(0, 1fr));
```

---

# 四、Implementation Guidance 和 Frontend Rule 不能混

Frontend Rule 是：

> 通用工程规范。

例如：

```text
规则：
规则二维重复布局优先使用 Grid；
不应逐项 hardcode card width。
```

Implementation Guidance 是：

> 这个具体页面怎么应用这些规则。

例如：

```text
ResourceGrid
→ Grid layout
→ 4 columns at current approved desktop state
→ child stretch
→ gap = current approved spacing
```

所以：

```text
Frontend Rule
= reusable HOW rule

Implementation Guidance
= project/task-specific application of HOW
```

---

# 五、Implementation Guidance 不是 UI Truth

例如：

```text
Design:
4 个等宽卡片
```

可以有两种合法实现：

```text
Grid
Flex-wrap
```

只要都满足 UI Contract。

所以：

```text
Design Target
≠ implementation strategy
```

UI_SPEC 不应该写死：

```text
必须 CSS Grid
```

除非这本身就是工程约束。

---

# 六、Implementation IR 的正式定义

建议：

> **Implementation IR = 将 Implementation Guidance 编译成稳定、可验证、Framework-neutral 的机器可读实现语义。**

它应该回答：

```text
怎么布局？
谁控制尺寸？
如何伸缩？
如何换行？
如何溢出？
哪些约束必须满足？
如何响应式转换？
引用哪些 Behavior / Data？
允许哪些实现替代？
```

但不回答：

```text
具体 Vue template 怎么写
React JSX 怎么写
AntD prop 叫什么
Tailwind class 是什么
```

---

# 七、Implementation IR 必须 Framework-neutral

已有规则明确要求 Implementation Core 禁止出现：

```text
React JSX
Vue SFC / Vue Template
AntD API
Element Plus API
Tailwind class
```

具体写法只进入 Framework Adapter。fileciteturn131file23

所以：

```text
Core:
layout.strategy = grid

Adapter:
React/CSS → display:grid
Tailwind → grid
某组件库 → 对应 Grid/Flex 组件
```

---

# 八、Implementation Pack 的正式定义

建议：

> **Implementation Pack = 针对一个明确 Task / Page / Component，将当前有效 UI Contract、Implementation IR、Frontend Rules 应用结果、技术约束、必要引用和验证要求编译成可直接供 Coding Agent 使用的施工包。**

它不是：

```text
全项目永久 Truth
```

而是：

```text
Task-scoped
Derived
Rebuildable
Version-aware
```

---

# 九、Implementation Pack 与 Effective Implementation Context 的区别

这两个非常容易混。

```text
Effective Implementation Context
= Coding Agent 当前做判断需要知道什么

Implementation Pack
= 当前 UI 具体应该怎样施工
```

可以理解：

```text
Context
= 决策输入

Pack
= 编译后的施工图
```

Coding Agent 可以同时消费二者。

---

# 十、Implementation Pack 不能成为第二 UI_SPEC

这条必须硬冻结。

错误：

```text
UI_SPEC:
Sidebar = 240 target

Implementation Pack:
Sidebar = 220

然后 Implementation Pack 继续施工
```

正确：

```text
Conflict / Deviation
↓
reconcile
```

因为：

```text
UI_SPEC owns approved UI WHAT
Implementation Pack owns HOW
```

Implementation Pack 不能改 WHAT。

---

# 十一、Scene / Design / Implementation 三层必须继续分开

现有规则明确要求：

```text
Scene
= 设计观察事实

Implementation
= 根据设计事实生成的实现指导
```

例如：

```text
Scene:
rectangle width = 1200

Semantic:
main-content

Implementation:
width.mode = fill
layout = flex/grid
```

三者不能混。fileciteturn131file0

这也是 D08 的根原则。

---

# 十二、Geometry 不能自动变 Fixed

这是 D08 最重要的实现规则之一。

例如设计图测到：

```text
Main width = 1180px
```

不能：

```text
width = fixed 1180
```

因为真实布局可能是：

```text
Sidebar fixed
Main fill
```

现有 v1.1 已明确：

> Main 即使测得 1180px，也不应因此 fixed。fileciteturn132file3

所以：

```text
Rendered Geometry
≠ Sizing Strategy
```

---

# 十三、Sizing 必须表达“尺寸关系”

建议至少逻辑支持：

```text
fixed
fill
intrinsic/content
stretch
fraction
minmax
fit-content
parent-controlled
```

但 Architecture Freeze 不把最终 enum 写死。

核心原则：

> **实现尺寸时优先恢复布局关系，而不是复制截图尺寸。**

---

# 十四、Parent-driven Sizing 必须是一等能力

例如：

```text
Grid
├── Card
├── Card
├── Card
└── Card
```

如果父级 Grid 决定列宽：

```text
Child width
= controlled by parent
```

就不应该再：

```text
Card width = 248px
```

现有 Design Pack 示例也明确：`rendered width=248` 不应自动变成 `fixed width=248`。fileciteturn132file16

---

# 十五、Layout Strategy 关注关系，不关注截图坐标

现有总纲已经明确最终原则：

> **布局实现关系，不抄截图坐标。** fileciteturn132file0

所以：

```text
视觉上：
四个卡片横向规则排列
```

优先思考：

```text
Grid
Flex
Gap
Stretch
Wrap
```

而不是：

```text
left: 124px
top: 88px
width: 248px
```

---

# 十六、Absolute Position 不是禁用，而是要有语义依据

不能粗暴变成：

```text
absolute 永远禁止
```

有些 UI 本来就适合：

```text
badge
attached triangle
floating decoration
overlay
tooltip arrow
popover
```

可以使用 absolute。

正确规则：

```text
Absolute allowed
only when positional relationship itself is intentional
```

而不是：

```text
因为截图里 x/y 明确，所以 absolute
```

---

# 十七、Flex / Grid 不是视觉真相

例如：

```text
4-column layout
```

Design Truth 是：

```text
规则 4 列关系
```

Implementation IR 可以选择：

```text
Grid
```

但 Grid 属于：

```text
Implementation Recommendation / Decision
```

不是：

```text
Design Fact
```

现有 Implementation 示例本身就给 `layout.strategy=flex` 标记了 `origin=RECOMMENDATION`。fileciteturn131file3

---

# 十八、重要 Implementation Decision 必须保留 Origin

例如：

```text
layout.strategy = grid
```

要知道它是：

```text
Frontend Rule derived
Technical constraint derived
Existing project convention
Authorized autonomy
Human decision
```

而不能只留下：

```text
grid
```

否则以后没人知道为什么用了 Grid。

---

# 十九、Confidence 仍然不等于 Authority

例如：

```text
grid
confidence = 0.94
```

只代表：

> 系统觉得 Grid 很适合。

不代表：

```text
必须 Grid
```

现有 Implementation 规则已经要求重要推断保留 `INFERRED + confidence + reason`。fileciteturn131file5

---

# 二十、Implementation IR 里的状态必须区分

我建议至少允许：

```text
FACT_REFERENCE
CONSTRAINT
RESOLVED_DECISION
RECOMMENDATION
ALTERNATIVE
UNKNOWN
DEVIATION
```

精确 enum 后面定。

目的不是再造 D03 的 FACT 系统。

而是让 Coding Agent知道：

```text
哪些必须遵守
哪些只是实现建议
哪些可以替换
哪些根本还没决定
```

---

# 二十一、Implementation IR 不复制 Behavior / Data Truth

现有规则已经明确：

> Implementation 对 State / Interaction / Data 应使用引用方式，避免多个文件形成冲突。fileciteturn131file23

所以：

```text
Implementation IR
→ behaviorRef
→ dataRef
→ fixtureRef
```

而不是复制：

```text
完整 interaction
完整 business state
完整 fixture
```

---

# 二十二、Implementation IR 也不复制 Token Truth

同样：

```text
Implementation IR
→ tokenRef
```

然后 Adapter：

```text
tokenRef
→ CSS Variable / Theme Token / JS Theme
```

不能在 IR 里复制一套：

```text
#1677FF
8px
16px
```

形成第二 Token Truth。

---

# 二十三、Component Mapping 的正确定位

Design Semantic：

```text
ResourceCard
```

Implementation 需要：

```text
复用已有组件？
组合已有基础组件？
新建局部组件？
```

这里可以产生：

```text
Component Implementation Mapping
```

但：

```text
Semantic Component
≠ Framework Component
```

比如 Design Semantic：

```text
Modal
```

具体可能：

```text
AntD Modal
Element Plus Dialog
Custom Dialog
```

这是 Adapter / Implementation 决定。

---

# 二十四、优先复用现有项目组件，但现状不是 Authority

Coding 前应该检查：

```text
existing reusable component
existing layout primitive
existing design system adapter
```

如果符合 Current UI Contract：

```text
reuse
```

但不能：

> “项目现有 Card 就长这样，所以设计目标也改成这样。”

仍然：

```text
Existing component
= Technical Reality / Reuse Candidate
```

---

# 二十五、Existing Code Convention 可以影响 HOW

比如当前项目已经统一：

```text
CSS Modules
Flex utility
Grid wrapper
Ant Design Pro ProTable
```

这些可以影响：

```text
Implementation Strategy
```

但前提：

```text
不改变 UI Contract
不违反 Frontend Rule
```

这是 CROSS-STAGE-AUTONOMY-01 很适合处理的区域。

---

# 二十六、Responsive IR 必须表达 Transformation

已有 v1.1 明确：

> Responsive 不能只输出 breakpoint，必须描述 transformation。fileciteturn132file3

例如：

```text
Desktop:
sidebar = fixed-column

Tablet:
sidebar = compact-column

Mobile:
sidebar = drawer
```

而不是只说：

```text
768px breakpoint
```

---

# 二十七、Breakpoints 不是没有证据也能随便创造

如果 UI_SPEC 只批准：

```text
Desktop
```

不能因为“行业通常 768/1024”就自动生成：

```text
Tablet
Mobile
```

如果没有 Evidence / Rule / Decision：

```text
UNKNOWN / NOT_IN_SCOPE
```

而不是自己补齐。

---

# 二十八、Responsive Transformation 与 CSS Media Query 分离

例如：

```text
Sidebar:
fixed-column → drawer
```

这是：

```text
Implementation Semantic
```

而：

```css
@media (max-width: 768px)
```

是：

```text
Framework/technical realization
```

不要在 Core IR 里写死。

---

# 二十九、Overflow 必须显式

很多 AI 页面出问题，就是：

```text
text overflow
list overflow
horizontal overflow
image overflow
container min-width
```

没有建模。

Implementation IR 应能表达：

```text
scroll
clip
wrap
ellipsis
clamp
visible
auto
```

并且结合：

```text
dynamic content
```

判断。

---

# 三十、`min-width: 0` 这类东西属于 Implementation Knowledge

例如 Flex 子项：

```text
overflow text
```

常需要：

```css
min-width: 0;
```

这不是 Design Truth。

而是：

```text
Frontend Engineering Rule / Implementation Guidance
```

正好体现 D02 与 D08 的职责关系。

---

# 三十一、Spacing 要表达“关系来源”

例如视觉上两个按钮间距：

```text
8px
```

可能实现为：

```text
container gap
```

而不是：

```text
child margin-right
```

如果它是同级规律排列：

> 优先表达 `group spacing relationship`。

现有 Frontend Layout Guidance 同样强调 Flex/Grid + gap，而不是机械给 child 写 margin。fileciteturn132file11

---

# 三十二、Box Model 是 Implementation 层

例如：

```text
padding
border box
content box
```

属于：

```text
HOW
```

UI_SPEC 可以要求：

```text
内容区域相对边缘 24px
```

Implementation IR 决定：

```text
padding 24
```

或其它等价结构。

不能把实现细节倒灌成设计事实。

---

# 三十三、Constraint 必须是一等语义

现有 Implementation 规则已经要求支持：

```text
minWidth
maxWidth
minHeight
maxHeight
maxLines
aspectRatio
noOverflow
equalHeight
```

fileciteturn132file26

D08 建议保留为：

```text
Implementation Constraint Semantics
```

但精确字段后面定。

---

# 三十四、Constraint 的来源必须区分

例如：

```text
maxLines = 2
```

来源可能：

```text
UI_SPEC
Frontend Rule
Existing component contract
Technical platform constraint
```

不同来源的 Authority 不一样。

不能只存：

```text
maxLines=2
```

---

# 三十五、CSS Hint 永远只是建议

现有规则已经明确：

```text
CSS Hint = recommendation
```

不是 Design Fact。fileciteturn132file26

例如：

```text
preferred:
flex
gap
normal-flow

avoid:
massive absolute positioning
```

这种非常适合进入：

```text
Implementation Guidance
```

但 Coding Agent 可以在合法条件下选择等价方案。

---

# 三十六、Implementation Alternative 必须显式

例如一个底部三角：

```text
::after
DOM decorative element
SVG
```

三个方案都能满足 UI Contract。

D08 应允许：

```text
Allowed Alternatives
```

然后根据：

```text
Frontend Rules
current stack
existing component
performance
maintainability
```

由 Autonomy-01 选一个。

---

# 三十七、Alternative 与 Deviation 必须严格区分

这是 D08 关键边界。

### Alternative

```text
三种实现
最终视觉/行为相同
```

属于：

```text
legal HOW choice
```

### Deviation

```text
UI_SPEC 要有三角
实现决定不做
```

属于：

```text
WHAT changed
```

不是 Alternative。

---

# 三十八、Deviation 必须结构化

现有规则已经有：

```text
expected
actual
reason
approved
```

的 Deviation 模型，而且明确：

> 未确认偏差不得伪装成原始设计。fileciteturn131file3

D08 应正式继承。

---

# 三十九、技术限制先产生 Feasibility Issue

例如：

```text
当前组件库不支持某种 nested overlay
```

不能直接：

```text
删掉设计要求
```

应该：

```text
Technical Constraint
↓
Feasibility Issue
↓
Alternative search
↓
if still impossible
→ Deviation Candidate
```

---

# 四十、Implementation Pack 必须引用 Current Effective UI Contract

每个 Pack 都应该知道：

```text
基于哪个 PRD
基于哪个 UI_SPEC
基于哪个 Effective UI Contract
基于哪个 Frontend Profile
基于哪些 Rule Versions
基于哪个 Technical Baseline
```

这样以后 UI_SPEC 变了：

```text
Pack can become STALE
```

而不是继续默默施工。

---

# 四十一、Implementation Pack 与 UI_SPEC 必须独立版本

例如：

```text
UI_SPEC 1.2
```

可以生成：

```text
Implementation Pack 1
Implementation Pack 2
```

如果只是 HOW 优化：

```text
UI_SPEC unchanged
Pack revised
```

所以：

```text
Implementation Revision
≠ UI_SPEC Revision
```

---

# 四十二、纯 HOW 优化不污染 UI_SPEC

例如：

```text
Flex → Grid
```

只要：

```text
UI appearance unchanged
behavior unchanged
responsive contract unchanged
```

那么：

```text
Implementation Pack revision
```

即可。

不用：

```text
UI_SPEC 1.2 → 1.3
```

---

# 四十三、UI_SPEC 改了则 Pack 必须 Impact Recheck

例如：

```text
UI_SPEC:
3 columns → 4 columns
```

原 Pack：

```text
grid = 3 columns
```

当然 stale。

但如果 UI_SPEC 只是：

```text
tooltip 文案修改
```

某些布局 IR 可能完全不受影响。

所以：

```text
localized impact
```

而不是：

```text
whole pack always invalid
```

具体依赖图 F9 实现。

---

# 四十四、Implementation Pack 最小充分，而不是越大越好

不应该把：

```text
整个设计系统
全部前端规范
全部 PRD
全部源代码
全部 UI_SPEC
```

塞进去。

应该：

```text
Minimum Sufficient Implementation Pack
```

只包含当前任务施工需要的：

```text
contract refs
layout/sizing
behavior/data refs
constraints
allowed alternatives
validation requirements
```

---

# 四十五、Implementation Pack 不是 Prompt Dump

这点很重要。

它应该是：

```text
structured contract
```

而不是：

```text
一大段“请你尽量按照设计图还原”的自然语言
```

目的就是让不同 Coding Agent：

```text
Cursor
Codex
Claude
其它 Agent
```

得到相同工程语义。

---

# 四十六、Implementation Pack 必须可验证

Pack 不能只告诉 Coding Agent：

```text
“尽量像设计图”
```

它必须让后续 Validation 知道：

```text
layout expected relation
sizing relation
responsive behavior
state refs
interaction refs
fixture refs
important constraints
visual baselines
```

现有规则也已经要求 Implementation 输出最终可以被 Visual Regression 读取。fileciteturn131file2

---

# 四十七、Validation Requirements 可以进入 Pack，但 Validation 本身不在 D08

D08 可以说：

```text
必须验证：
desktop 1440
selected state
long text
empty fixture
```

但真正：

```text
截图
diff
interaction test
repair loop
```

留给 D09 / D10。

---

# 四十八、Implementation Compiler 的职责

建议逻辑上建立：

```text
Implementation Compiler
```

职责：

```text
Effective Implementation Context
↓
Implementation Guidance
↓
Implementation IR
↓
Implementation Pack
```

它不负责：

```text
批准 UI
修改 PRD
写代码
执行 Git
```

---

# 四十九、Compiler 不得重新做 Authority Resolution

这一点和 D02-08/09 一致。

```text
Resolver
= 判断什么有效

Compiler
= 把已有效结果编译成施工表达
```

Compiler 不能看到两个冲突 Rule 后：

> 自己偷偷挑一个。

如果输入 Context 还有未解决 Authority Conflict：

```text
BLOCK
```

而不是编译。

---

# 五十、Coding Agent 也不能重新开第二套 Resolver

Coding Agent 默认拿：

```text
Effective Implementation Context
+
Implementation Pack
```

就施工。

不能：

```text
自己再全仓搜规则
自己重新翻设计图
自己挑 latest 文件
自己改变 UI Contract
```

这与 D02-09 已冻结原则完全一致。

---

# 五十一、Framework Adapter 的职责继续保持窄

Adapter 负责：

```text
Framework-neutral IR
↓
Target Framework Representation
```

例如：

```text
React
Vue
Ant Design
Element Plus
Tailwind
```

但 Adapter 不负责：

```text
重新决定布局
重新决定 UI
重新决定 Product behavior
```

---

# 五十二、Adapter 可以报告 Capability Gap

例如 IR 要求：

```text
sticky nested scroll behavior
```

某 Adapter 不支持。

应该：

```text
ADAPTER_CAPABILITY_GAP
```

而不是：

```text
静默降级
```

然后回到：

```text
Alternative / Feasibility / Deviation
```

路径。

---

# 五十三、Framework Adapter 不是一个“万能模板”

例如：

```text
React Adapter
```

也可能有：

```text
React + CSS Modules
React + Tailwind
React + Ant Design
React + CSS-in-JS
```

所以未来更合理的是：

```text
Framework
+
UI Library
+
Styling Strategy
+
Project Profile
```

组合。

但 D08 当前只冻结：

```text
adapter composition must be possible
```

不提前做复杂 Adapter Matrix。

---

# 五十四、Current Project Frontend Rules 决定具体工程偏好

例如项目明确：

```text
优先 Grid/Flex
避免大面积 absolute
优先 gap
复用 AntD Form
```

这些通过：

```text
Frontend Profile
Effective Frontend Rule Set
```

进入 Context。

D08 不再复制这些规则正文。

---

# 五十五、你之前提到的“Grid / Flex + gap 不要固定宽高”正式落在 D08

例如目标图：

```text
4 个卡片
每个看起来 248px
```

错误：

```text
card {
  width:248px;
  margin-right:16px;
}
```

更合理可能：

```text
Grid:
4 equal tracks
gap:16
child: stretch
```

这正是：

> **截图中的最终像素结果，应还原成真实布局关系。**

而不是把每个测量值写进 CSS。

---

# 五十六、复杂视觉效果也要建模，而不是临时 hack

例如你前面分类页的：

```text
一级选中上下三角
二级气泡倒三角
左右 fade mask
三级共用底板
```

Implementation Pack 应该明确：

```text
Attached decoration
Shared visual surface
Edge fade behavior
Selected-state indicator
Layer/anchor relation
```

而不是 Coding Agent看到图后临时：

```text
随便加几个 div
```

---

# 五十七、但 Implementation Pack 不规定一定用什么 DOM

例如：

```text
Selected-state triangle
```

IR 描述：

```text
attached decorative indicator
anchored to selected item
```

Adapter/Coding 决定：

```text
::after
span
svg
```

只要满足 Contract 和 Frontend Rules。

# 五十八、Asset Mapping 属于 Implementation Support

```text
source
usage
type
```

这种映射。fileciteturn131file23

# 五十九、Implementation Report 是 Trace，不是 Truth

未来可以有：

```text
Implementation Report
```

记录：

```text
采用什么策略
有哪些风险
哪些 inferred
哪些 deviation
哪些 unresolved
```

但它不能反过来成为：

```text
UI_SPEC
Frontend Rule
Design Truth
```

# 六十一、D08 不做 AI 自主实现学习

当前 AI 可以：

```text

给出 alternative
```

但不：

```text

自动修改 Shared Framework
```

这些仍是 Deferred。

# 六十三、建议 D08 正式冻结 IG-01 ～ IG-32

```text
IG-01
Implementation Semantic Need、
Implementation Guidance、
Implementation IR、
Implementation Pack、
Framework Adapter Output
必须保持不同语义。

IG-02
D08 复用 D02-09 的
Design→Implementation Semantic Bridge
与 Effective Implementation Context，
不得建立第二语义桥或第二 Resolver。

IG-03
Implementation Guidance 表达
当前项目/任务应如何实现 UI Contract，
是 task-specific HOW，
不得成为 UI Truth。

IG-04
Frontend Rule 是 reusable HOW rule；
Implementation Guidance 是
该规则在当前任务上的受治理应用，
二者不得混为一个对象。

IG-05
Implementation IR 是
Framework-neutral machine-readable
implementation semantics。

IG-06
Implementation IR Core
不得绑定 React/Vue/AntD/
Element Plus/Tailwind 等具体框架 API。

IG-07
Implementation Pack 是
Task/Page/Component-scoped derived construction pack，
不得成为第二 UI_SPEC。

IG-08
Scene / Design Truth /
Implementation Guidance /
Framework Representation
必须保持分层，
不得互相反向定义。

IG-09
Rendered Geometry
不得自动转换为 Fixed Sizing。

IG-10
Sizing 必须优先表达
fixed/fill/intrinsic/stretch/fraction/
minmax/parent-controlled 等关系语义；
精确 taxonomy 后续冻结。

IG-11
Parent-driven Sizing 必须是一等语义；
父容器已决定尺寸时
不得无证据给 child 重复 hardcode width/height。

IG-12
Layout Strategy 应恢复
结构关系而非截图坐标；
不得将 Scene x/y 机械转为 absolute positioning。

IG-13
Absolute positioning 允许用于
真正具有附着/叠层/定位语义的场景，
但不得作为截图还原默认策略。

IG-14
Flex / Grid / Normal Flow 等
属于 Implementation Decision/Recommendation，
不得伪装成 Design Fact。

IG-15
关键 Implementation Decision
必须保留 Origin / Reason / Trace；
Confidence 不等于 Authority。

IG-16
Implementation IR
不得复制 Behavior、Data、Token 的第二 Truth；
应通过 stable refs 引用相关受治理语义。

IG-17
Component Semantic 与
Framework Component 必须分离；
具体组件映射属于 Implementation/Adapter 层。

IG-18
Existing Components / Code Conventions
可以作为 Reuse / Technical Evidence，
但不得反向修改 Current UI Contract。

IG-19
Responsive IR 必须表达 Transformation，
不得只记录 breakpoint。

IG-20
没有有效 Evidence / UI Contract 时
不得凭行业惯例自动创造
Mobile/Tablet/Responsive Behavior。

IG-21
Spacing、Overflow、Box Model、
Constraints 等 Implementation Semantics
必须结构化表达，
不得依赖 Coding Agent 临场猜测。

IG-22
CSS Hint / Implementation Hint
属于 Recommendation，
不得取得 Design/UI Authority。

IG-23
Legal Implementation Alternatives
必须与 Design Deviation 分离；
等价 HOW 可自主选择，
改变 WHAT 必须进入 Deviation Governance。

IG-24
Implementation Deviation 必须显式记录
Expected / Actual / Reason / Approval State，
未经治理不得伪装成 faithful implementation。

IG-25
Technical/Adapter limitation
必须先形成 Feasibility/Capability Issue；
不得直接删除或弱化 UI Requirement。

IG-26
Implementation Pack 必须引用
Current Effective PRD/UI_SPEC、
Frontend Profile/Rule versions、
Technical Baseline 等关键依赖，
以支持 Freshness / Impact。

IG-27
Implementation Revision
与 UI_SPEC Revision 必须独立；
纯 HOW 优化不得强制修改 UI_SPEC。

IG-28
UI_SPEC / Frontend Rule /
Technical Baseline 更新后，
Implementation Pack 只对真实受影响 Scope
进行 stale/recompile；
具体 dependency mechanics 留 F9。

IG-29
Implementation Compiler 只负责
把已解析的有效输入编译成 Guidance/IR/Pack，
不得重新做 Authority Resolution。

IG-30
Coding Agent 默认消费
Effective Implementation Context +
Implementation Pack，
不得自行扩展为第二全局 Resolver。

IG-31
Framework Adapter 只负责
将 Framework-neutral IR 翻译成
具体技术栈表达；
不得新增/删除 Product/UI Semantics。

IG-32
Implementation Compiler、Sizing/Layout Strategy、
Component Mapper、Framework Adapter
必须通过可替换 Contract 解耦；
当前不实现 AI Autonomous Implementation Learning /
Autonomous Pattern Promotion。
```
