记住了。现在把你新增的全局护栏一起带入 **F6-D02-05**：

> **任何条款除了自身合理，还必须检查与既有条款的兼容关系；不能把“同时命中以后到底组合、覆盖、择一还是冲突”的判断留给真正执行时的 AI 去猜。**

这会从现在开始成为后续所有决策的固定检查项。

# F6-D02-05 — Module Index + Rule Association Index
## 模块索引与规则语义关联索引

**当前状态：`HUMAN_REVIEW`**  
**Implementation：`NOT_AUTHORIZED`**

这一项专门解决你前面最看重的问题：

> PRD、Design Package（设计包）或现有代码识别出“气泡选中、三角指示器、表格、搜索、横向滚动”等内容以后，怎样**快速、准确、稳定地找到相关前端规则**，又不让 AI 每次靠大模型记忆从头猜。

---

## 一、先确定一个核心边界

索引的职责只能是：

> **“帮系统找到可能相关的规则。”**

索引绝对不能负责：

> **“决定这条规则一定要执行。”**

因此必须明确：

```text
Association Match
关联命中

≠ Rule Applicable
≠ 规则已经适用

Rule Applicable
规则适用

≠ Rule Effective
≠ 已成为当前有效规则

Rule Effective
当前有效规则

≠ Implementation Decision
≠ 最终施工选择
```

这一刀非常重要。

否则 AI 很容易：

```text
看到 selected
↓
索引命中 FE-RULE-017
↓
直接执行 FE-RULE-017
```

这是我们必须从架构上禁止的。

---

# 二、整体采用“两级索引”

保留我们已经讨论过的结构：

```text
输入语义
   ↓
Module Index
模块索引
   ↓
找到可能相关的 Rule Module
   ↓
Rule Association Index
规则关联索引
   ↓
找到模块内部可能相关的 Rule Entry
   ↓
Applicability / Scope / Profile / Version
适用性检查
   ↓
Cross-Rule Consistency Check
跨规则一致性检查
   ↓
Effective Frontend Rule Set
当前任务有效前端规则集
```

这样既快，又不会过早下结论。

---

# 三、第一级：Module Index
## 模块索引

它只回答：

> **“这个问题大概应该去哪些前端规则模块里找？”**

比如 Design Package 得到：

```text
selected_state
capsule
triangle_indicator
horizontal_scroll
fade_mask
```

Module Index 可能定位到若干候选模块。

这里只是概念举例：

```text
某通用布局模块
某视觉效果实现模块
某滚动实现模块
当前项目采用的组件体系模块
```

注意：

> **正式模块名称仍然不是 Core 写死。**

模块来自我们 D02-03 已经讨论的实际物资盘点。

---

# 四、第二级：Rule Association Index
## 规则关联索引

进入候选 Module 后，再进一步回答：

> **“这个模块里的哪几笔 Rule Entry 值得读取？”**

例如：

```text
selected_state
→ RULE-A-012

capsule
→ RULE-A-027

triangle_indicator
→ RULE-A-031

horizontal_scroll
→ RULE-B-008

fade_mask
→ RULE-B-014
```

于是原来一个模块可能有 200 条规则，最终只读取：

```text
5～10 条真正相关规则
```

这正是我们要的：

> **精准加载，而不是全量 Context。**

F5 已经冻结 Trace（追踪）应按 applicability-driven（适用性驱动）渐进建立，而不是默认把所有上下游关系一次性加载；F9 后续再负责具体查询和执行机制。fileciteturn98file0L55-L73

# 五、索引必须使用“标准语义”，不能只用自然语言关键词

这是防止 AI 误判的第一道硬防线。

如果索引只是：

```text
"气泡"
"表格"
"选中"
"按钮"
```

会非常容易错。

例如“表格”可能表示：

```text
数据表格
布局表格
Excel 式表格
设计图里的视觉表格
```

所以我们需要：

> **Typed Semantic Key（带类型的标准语义键）**

逻辑示意：

```text
state:selected

visual_shape:capsule

indicator:triangle

overflow:horizontal_scroll

effect:fade_mask

component:data_table

interaction:filter

layout:two_dimensional_repeat
```

具体最终命名和 Schema 以后再定。

但现在应该冻结：

> **语义索引不能仅依赖无类型的自由文本 Tag。**

# 六、同一个自然语言必须先 Normalize
## 先标准化再查规则

例如：

```text
“气泡”
“胶囊”
“圆角选中块”
“pill”
“capsule”
```

如果在当前上下文表达的是同类概念，可以先映射到：

```text
visual_shape:capsule
```

再检索。

也就是说：

```text
Raw Wording
原始说法
↓
Semantic Normalization
语义归一
↓
Canonical Semantic Key
标准语义键
↓
Index
```

这样不会因为用户、设计师、不同文档用词不一样就找不到规则。

# 七、但 Alias（别名）绝不能静默等同

这一条也是为了防 AI 误判。

例如：

```text
bubble
```

有时表示：

> 气泡视觉形态。

有时可能表示：

> 消息气泡组件。

所以不能建立：

```text
bubble = capsule
```

永久无条件等号。

正确应该结合：

```text
Semantic Type
上下文
父节点
状态
来源
```

才能归一。

无法可靠判断：

```text
UNKNOWN / AMBIGUOUS
```

而不是 AI 猜一个。

前端规则关联可以来自不同输入，但不能混为一种 Authority（权威）。

主要有：

```text

设计语义

Project Context
项目环境
```

比如：

```text

需要筛选
```

提供的是：

```text

interaction:filter
```

---

Design Package 说：


提供的是视觉和状态语义。

---

Current Code 识别出：

```text
现有页面已经使用某种组件
```

只是：

> **代码现状证据。**

它不能反过来说：

> “因为当前代码这样写，所以需求和设计就应该这样。”

# 九、Semantic Status 也必须进入关联判断

这是非常重要的新防误判规则。

假设 Design Package 中：

```text
selected_state
= CONFIRMED
```

可以正常检索。

但是：

```text
triangle_indicator
= INFERRED
confidence = low
```

这个低置信推断可以：

> 用来**扩大候选检索**。

但不能因为命中了一个：

```text
REQUIRED Rule
```

就直接宣布：

> “必须按三角指示器实现。”

因此要冻结：

```text
低置信推断
可以 Retrieval
可以找候选规则

但是
不能单独证明 Mandatory Applicability
不能单独触发不可逆施工结论
```

这正好符合我们已有的：

> FACT / INFERENCE / RECOMMENDATION 必须分离。

# 十、UNKNOWN 不能触发“默认猜测规则”

例如设计图根本没展示移动端。

那么：

```text

```

不能：

```text

↓
AI 猜是移动端
↓
加载移动端模块
↓
自动设计移动行为
```

正确是：

```text

↓

```

如果任务本身要求移动端：

```text
产生 Gap
↓
寻找其它证据
↓
仍无法确认再按治理处理
```

# 十一、Project Profile 必须先限制规则搜索空间

比如项目当前实际配置只采用：

```text
Module A
Module C
Module F
```

那么普通任务不能因为全局知识库里存在：

```text

```

就偷偷使用。

默认应该：

```text

当前项目有效模块集合
        ↓
Module Index
        ↓
只在允许范围内查
```

如果发现：

> 当前需求明显需要某类规则，但项目 Profile 没有对应 Module。

结果应该是：

```text
RULE_COVERAGE_GAP
规则覆盖缺口
```

或者产生 Module Candidate / Profile Change Candidate。

不是：

> AI 偷偷从公共库拉一套进来。

# 十二、但 Module Index 不能只看 Profile 名单

这里还需要一点弹性。

假设当前 Profile 没有移动端 Module。

但是用户突然说：

> “这次增加手机端。”

系统应该能发现：

```text
当前 Profile
没有足够规则覆盖
```

然后去共享规则索引检查：

> 有没有可选候选 Module。

最后形成：

```text
Profile Extension Candidate
配置扩展候选
```

所以：

```text
Profile
= 当前有效规则边界

Global Index
= 可发现候选知识
```

两者不能混。

# 十三、索引匹配以后不能直接“选最高分”

这一条建议作为硬规则。

未来 SQLite、Embedding（向量检索）、全文搜索可能给：

```text
RULE-A score 0.96
RULE-B score 0.91
```

禁止：

```text
0.96 > 0.91
↓
A 胜出
```

因为：

> **检索相似度只代表“可能相关”，不代表 Authority、Strength、Scope 或正确性。**

所以：

```text
Search Ranking
检索排序

≠ Rule Priority
规则优先级
```

必须明确。

这就是你刚增加的：

> **不能让执行 AI 因为两个条款关系不清而自己猜。**

---

# 十四、一个语义命中多条规则时，必须显式知道它们什么关系

例如：

```text
selected_state
```

命中：

```text
RULE-A
RULE-B
RULE-C
```

系统不能默认：

> “三条都执行。”

它们之间可能是不同关系。

我建议架构上至少区分这些**逻辑关系**：

| 关系 | 大白话 |
|---|---|
| `COMPOSE` | 可以组合执行 |
| `SPECIALIZE` | 一条是另一条更具体的规则 |
| `DEPEND_ON` | 执行 A 需要同时考虑 B |
| `ALTERNATIVE` | 多种可选实现，不能全部一起用 |
| `OVERRIDE` | 满足条件时允许具体规则覆盖一般规则 |
| `EXCLUDE` | 当前条件下另一条不适用 |
| `CONFLICT` | 真冲突，不能让 AI 自选 |

具体英文枚举以后可以调整。

但是：

> **“多条命中时必须能判断关系”这个原则要冻结。**

选择。

如果仍然存在真正有意义的取舍，再进入 Recommendation / Decision。

# 十六、COMPOSE 和 CONFLICT 必须彻底区分

例如：

```text
RULE-01
横向列表允许 overflow-x

RULE-02
边缘内容被遮挡时增加渐隐提示
```

这是：

```text
COMPOSE
```

可以一起执行。

---

但：

```text
RULE-03
选中指示器必须跟随滚动内容

RULE-04
选中指示器必须固定在 viewport
```

如果：

```text
Scope 相同
条件相同
```

就是：

```text
CONFLICT
```

不能交给 AI “选一个看起来合理的”。

# 十七、SPECIALIZE 也不能简单理解成“具体的永远赢”

例如：

```text
General Rule
通用规则

↓

Specific Rule
页面具体规则
```

只有：

```text
通用规则允许 Override
+
具体规则 Authority 合法
+
没有 Safety / Mandatory Constraint 阻止
```

才允许 Specific Rule 覆盖。

这和我们 D02-02 讨论的条款必须一致。

所以 D02-05 明确：

> **Index 只能表达“存在更具体关系”；能不能覆盖仍由 D02-02 的 Strength / Authority / Scope / Override Policy 决定。**

这样条款之间就不会打架。

---

# 十八、这正是新增“跨条款一致性检查”的实际应用

以后：

```text
D02-05
负责找到：
RULE-A + RULE-B
```

但：

```text
D02-05 不重新发明优先规则
```

而是调用：

```text
D02-02
Strength
Authority
Scope
Applicability
Override Policy
```

完成判断。

这就是：

> **一个条款只负责自己的职责，不和别的条款重复定义同一个规则。**

避免未来出现：

```text
D02-02 说 A 优先
D02-05 又说 B 优先
```

这种 AI 执行灾难。

# 十九、最终执行前再增加一个 Cross-Rule Consistency Check
## 跨规则一致性检查

这是你刚新增全局规则后，我认为 D02-05 必须加入的一层。

最终 Rule Set 形成前：

```text
Candidate Rules
候选规则
↓
Cross-Rule Consistency Check
```

至少检查：

```text
是否同 Scope？

是否同 Applicability？

是否存在 REQUIRED vs FORBIDDEN？

是否存在不可覆盖规则？

是否存在 SPECIALIZE？

是否存在 ALTERNATIVE？

是否存在依赖缺失？

是否有 Superseded Rule？

是否使用错误版本？

是否存在 Human Constraint？

是否和 PRD / UI_SPEC 冲突？
```

然后才能生成：

```text
Effective Frontend Rule Set
```

# 二十、如果检查不通过怎么办

绝不能：

> “AI 认为 A 更合理，所以采用 A。”

结果应分类。

例如：

```text

RESOLVED_BY_APPLICABILITY
```

核心是：

> **每一个多规则命中都要有可解释的 Resolution（解析结果）。**

# 二十六、为了速度，允许“快速直达”，但不能绕治理

```text

```

```text

↓
再扫整个 Module
```

也就是说物理索引可以做快捷路径。

> **可以优化查询路径，不能优化掉治理步骤。**

> **速度快，但可靠。**

# 二十八、索引过期也不能静默使用

```text
RULE-018
已经 Superseded
```

但旧 SQLite 还指向它。

系统不能继续施工。

应该识别：

```text
STALE_INDEX
```

然后：

```text
Refresh / Rebuild
```

精确 Freshness 机制 F9 再冻结。

现在先冻结原则：

> **Index Freshness 不可信时，索引结果不得被当作正式规则状态。**

# 二十九、规则被替代以后索引怎么办

例如：

```text
RULE-A-017
↓ superseded by
RULE-A-031
```

Association Index 需要最终指向：

```text
RULE-A-031
```

但历史 Trace 仍能：

```text
017 → 031
```

不能：

```text
直接删除 017
导致历史任务查不到以前为什么这么做
```

# 三十二、新增全局“防 AI 误判条款”在 D02-05 的具体落地

我建议从这里开始，每个重要架构条款都增加一个逻辑要求：

```text
No Implicit Execution Semantics
禁止隐式执行语义
```

大白话：

> **如果两条规则同时出现时的关系没有被定义清楚，AI 不允许自己补一个关系。**

例如没有定义：

```text
COMPOSE？
OVERRIDE？
ALTERNATIVE？
CONFLICT？
```

那么：

```text
UNRESOLVED_RELATION
```

而不是 AI：

> “我觉得应该组合。”

这个原则非常关键。

# 三十四、检查与你新增的全局原则是否打架

这次我专门做一遍。

**与 D02-02：不冲突。**  
D02-02 负责“规则本身的 Strength / Authority / Scope / Override”；D02-05 只负责找到规则，并调用 D02-02 判断，绝不再造第二套优先级。

**与 D02-03：不冲突。**  
D02-03 管 Module 怎么形成、拆、合、演进；D02-05 只消费已经存在的 Module Identity 和 Rule Membership。

**与 D02-04：不冲突。**  
D02-04 管物资怎样形成 Rule Entry；D02-05 管正式/候选 Rule 怎样被任务找到。

**与 D01：不冲突。**  
Design Package 仍只表达设计是什么；Frontend Rule Association 发生在设计语义形成之后，绝不反过来污染 Design Truth。

**与 F9：不抢职责。**  
F6 冻结逻辑索引契约；SQLite、Query、Rebuild、Freshness 的精确实现留给 F9。

所以这一版职责边界比较干净。

## 一句话总结 F6-D02-05

> **PRD、Design Package 和现有代码先被归一成有类型、有来源、有确定性的标准语义；系统先通过 Module Index 缩小知识范围，再通过 Rule Association Index 找到具体规则条目，然后结合当前项目 Profile、Scope、技术版本和适用条件过滤，并在最终施工前进行跨规则一致性检查。索引只负责“找”，不负责“判”；相似度只负责排序，不决定权威；多个规则同时命中时必须明确是组合、具体化、备选、覆盖还是冲突，关系不清就停止自动判断，绝不把歧义留给执行 AI 自己猜。**

我建议接下来进入 **F6-D02-06：Frontend Profile + Effective Rule Set（项目前端规则配置与当前任务有效规则集）**。

这一项会把前面 D02-01～D02-05 真正串起来，确定：

> **一个实际项目怎样选择哪些 Module、怎样绑定版本、共享规则和项目规则怎样组合、任务开始时怎样只生成最小必要 Rule Set，以及项目升级规则时怎样避免“公共规则一升级所有项目突然变掉”。**
