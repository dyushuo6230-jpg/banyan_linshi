# F6-D09 — UI 一致性校准会话启动与治理边界冻结条文

- **Stage**: F6
- **Decision**: F6-D09
- **Status**: HUMAN_APPROVED
- **Freeze Status**: Architecture Freeze PASS
- **Type**: UI Conformance / Validation Governance
- **Date**: 2026-09-24

## 1. UI 一致性校准会话必须显式口令启动

“UI 一致性校准会话”不得被系统、AI、工作流或运行时根据上下文自动推断启动。

启动该会话时，用户当前明确指令中必须显式包含固定关键词：

> **启动UI 一致性校准会话**

只有在同时满足以下两个条件时，才视为正式启动：

1. 用户当前指令中明确包含上述固定关键词；
2. 用户当前语义明确表达启动、执行或进入该校准会话的意图。

以下情况均不得启动 UI 一致性校准会话：

- 仅上传 UI 设计图；
- 仅要求分析 UI 差异；
- 仅讨论视觉一致性问题；
- 仅提到“一致性校准”“UI 校准”等近似词；
- 仅引用、转述、复制或在文档中出现“启动UI 一致性校准会话”；
- AI 根据上下文自行判断“现在应该进入校准流程”；
- 任何不包含固定启动关键词的隐式授权。

该规则用于防止误触发、误操作、自动进入治理流程或在用户未明确授权时扩大执行范围。

---

## 2. 一个 UI Conformance Session 必须有明确开始与结束

一次 UI 一致性校准任务对应一个明确的 **UI Conformance Session**。

Session 只能处理本次明确授权的既定 Scope，可包含该 Scope 内的多个页面、状态、组件或视觉检查项。

一个 Session 完成既定检查范围后必须结束并输出报告。

禁止形成以下自动循环：

```text
检查
→ 修复
→ 再检查
→ 再修复
→ 自动继续下一轮
```

完成一轮检查、修复或复验，不得自动创建下一 Session。

新一轮 Session 必须重新满足本条文第 1 节的显式启动条件。

---

## 3. 风险采用 Affected-Scope Blocking，而不是默认 Whole-Session Blocking

当校准过程中发现高风险问题时，风险原则上只阻塞其实际影响范围。

即：

```text
高风险 Issue
→ 标记风险
→ 冻结其 Affected Scope
→ 禁止继续触碰该受影响范围
```

与该问题不存在依赖关系的其他独立检查范围，可以继续完成。

除非已经证明某风险会污染、破坏或使整轮验证结果失去可信度，否则不得因为单个高风险项默认终止整个 Session。

---

## 4. D09 可以判断风险，但风险等级不产生修改权限

D09 的职责是判断与验证治理。

D09 可以产生或维护：

- Difference
- Drift
- Severity
- Risk
- Evidence
- Affected Scope
- Validation Result

但以下问题不属于 D09 自动授权范围：

- Can Modify?
- Who Can Modify?
- How To Modify?
- Auto Repair?
- 是否允许直接落代码？
- 是否允许修改共享组件？
- 是否允许扩大修复范围？

**Risk ≠ Authority**

即使一个问题被判断为低风险，也不能因此自动获得修改权。

修改、修复、自动修复、权限边界及修复执行治理归入 D10。

---

## 5. R0～R3 表示处理/治理风险，而不是视觉差异严重程度

R0～R3 的含义定义为：

> **处理该差异时所引入的治理、变更和影响风险。**

它不等同于“这个 UI 看起来差得有多严重”。

### R0 — 纯验证风险

仅执行：

- 截图；
- DOM / Layer / Layout 读取；
- 尺寸比较；
- 状态比较；
- 证据收集；
- 差异识别。

不进行修改。

### R1 — 局部、明确、可逆风险

目标明确，影响局部，可逆，且理论上容易验证。

但：

> **R1 仍然不等于有修改权限。**

### R2 — 共享范围 / 扩散风险

处理该差异可能影响：

- Shared Component；
- 跨页面复用组件；
- 平台后台与租户后台共用模块；
- 多业务入口；
- 共享 Token / Theme / Layout。

### R3 — 治理或契约高风险

处理该问题可能触及：

- API；
- 权限；
- 数据契约；
- 路由；
- 业务状态；
- Canonical Truth；
- Frozen Contract；
- 已冻结架构边界；
- 关键业务行为。

R0～R3 只能描述处理风险，不能自动决定是否允许修改。

---

## 6. Human Decision 必须绑定具体 Issue / Scope

一轮 D09 校准报告中的每个问题必须拥有可独立引用的 Issue 标识或明确 Scope。

例如：

```text
D09-ISSUE-001
D09-ISSUE-002
D09-ISSUE-003
```

用户后续授权必须绑定具体 Issue 或 Scope。

例如：

```text
允许处理 001、004
003 不允许修改
```

则授权范围只能覆盖：

```text
001
004
```

不得扩展到：

- 未点名 Issue；
- 同轮其他差异；
- 新发现问题；
- 相邻页面；
- 共享组件的其他调用方；
- 下一轮 Session；
- 任何推定相关范围。

授权完成后，只允许做与已授权 Issue 直接相关的必要复验。

复验完成后必须停止，不得自动开始新一轮 UI 一致性校准会话。

---

## 7. D09 / D10 冻结分界

### D09 负责

- 目标识别；
- 当前状态识别；
- 差异发现；
- Difference / Drift 判定；
- 证据充分性；
- 风险判断；
- Affected Scope；
- 功能回归识别；
- 一致性验证结果；
- Session 生命周期治理。

### D10 负责

- 是否允许修改；
- 修改权限；
- 修改主体；
- 修复方式；
- 自动修复边界；
- 人工确认边界；
- 修复执行；
- 修复后允许进行的复验与停止条件。

D09 不得越权进入 D10。

---

## 8. 冻结结论

本条文正式冻结以下原则：

1. UI 一致性校准会话采用显式固定口令启动；
2. 固定关键词为 **“启动UI 一致性校准会话”**；
3. 无显式口令不得自动启动；
4. 单次 Session 必须有明确开始和结束；
5. 不得自动续轮；
6. 风险默认只阻塞受影响范围；
7. D09 的风险判断不授予修改权限；
8. R0～R3 表示处理/治理风险；
9. Human Decision 必须绑定具体 Issue / Scope；
10. 授权不得自动扩展；
11. 必要复验结束后必须停止；
12. D09 与 D10 保持严格职责边界。
