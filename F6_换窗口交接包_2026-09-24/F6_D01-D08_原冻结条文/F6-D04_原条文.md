可以。下面我把 **F6-D04** 整理成一版完整的、可以直接确认并进入 Architecture Freeze 的正式候选稿。

```text id="f6-d04-status"
F6-D04
Visual Property × Design Token × Shared Foundation
视觉属性 × 设计令牌 × 项目共享设计基础

Status = HUMAN_REVIEW
Implementation = NOT_AUTHORIZED
```

这版 D04 的核心不是“做一个 Token 文件系统”，而是解决三个长期问题：

> **第一，设计图里看到的颜色、圆角、字体、间距，到底什么时候只是局部值，什么时候应该变成 Token。**

> **第二，Token 什么时候只是某个页面/应用自己的，什么时候真正属于项目 Shared Foundation。**

> **第三，未来换品牌、换 Design System、换 Token 标准、增加 Dark Mode、增加新 App 时，怎样改得动，又不会把所有项目和 UI_SPEC 一起搞乱。**

Legacy UI Design Pack 已经把 `Tokens / Typography / Color / Radius / Border / Shadow / Observed Spacing` 放在 Design 层，并明确不在这一层存 `display:flex`、`flex:1` 之类 Implementation 决策。fileciteturn120file0L114-L132  
AnyDesign 的 `design-tokens.json` 也已经被定位为设计材料输出，需要登记后再进入 UI_SPEC，且旧规则明确禁止把一个 C 端的 Token 随意放进 shared 污染其它产品。fileciteturn120file4L1575-L1597

# 一、D04 的正式职责

D04 只负责四件事：

```text id="d04-owner"
1. Visual Property
   视觉属性到底是什么

2. Design Token
   什么视觉语义值得 Token 化

3. Token Scope / Resolution
   Token 在哪个范围生效、怎样解析

4. Shared Foundation
   哪些设计事实已经成为项目共享基础
```

D04 **不负责**：

```text id="d04-not-owner"
- Material Intake
- Design Source 解析
- Rule System
- Product Requirement
- UI_SPEC Approval
- CSS / React / Vue 实现
- SQLite / Index / Cache
- Canonical Apply
```

对应关系：

```text id="d04-boundary"
D01 → Material / Shared Foundation 总体所有权
D02 → Rule / Profile / Context
D03 → Design Evidence / Scene / Design Truth
D04 → Visual Property / Token / Foundation 视觉语义
F7  → Canonical Apply
F8  → Project Binding
F9  → Index / Freshness / Impact Mechanics
```

---

# 二、先把 6 个对象彻底区分

这是 D04 最重要的地方。

```text id="d04-six-objects"
Observed Visual Property
观察视觉属性

Local Design Value
局部设计值

Design Token Candidate
设计令牌候选

Governed Design Token
受治理设计令牌

Token Resolution
令牌解析结果

Shared Foundation
项目共享设计基础
```

它们不是一个东西的六个名字。

---

# 三、Observed Visual Property

定义：

> **从 Design Source、Existing UI 或其它设计证据中观察、测量、提取出来的具体视觉属性。**

比如：

```text id="observed-example"
color      = #1677FF
radius     = 8
font-size  = 14
gap        = 16
shadow     = ...
border     = ...
```

它只说明：

> “在这个 Source、这个 Scope、这个 State、这个 Viewport 下，看到了这个值。”

因此：

```text id="observed-not-token"
Observed Visual Property
≠ Design Token
≠ Shared Foundation
```

---

# 四、视觉属性必须带 Observation Context

比如：

```text id="property-context"
radius = 8
```

本身信息并不完整。

至少逻辑上应该知道：

```text id="property-context-detail"
来自哪个 Source
哪个页面
哪个区域
哪个组件
哪个 State
哪个 Device
哪个 Viewport
哪个 Target / Current Reality
哪个版本
```

精确字段后面 Implementation Freeze 再定。

---

# 五、Local Design Value

很多设计值根本没必要 Token 化。

例如某个营销 Banner：

```text id="local-value-example"
border-radius = 37
```

只在这个区域出现。

它完全可以是：

```text id="local-value"
Local Design Value
```

归：

```text id="local-value-owner"
Design Package
```

而不是生成：

```text id="bad-token"
radius-special-37
```

所以：

> **Banyan 不追求“所有值都 Token 化”。**

---

# 六、什么时候才值得成为 Token Candidate

我建议至少满足下面的部分条件：

```text id="token-candidate-criteria"
具有稳定设计意义
可在多个地方复用
具有明确 Scope
不是偶然像素值
能够描述“为什么存在”
可能需要统一演进
能够被其它设计引用
```

例如：

```text id="token-candidate-example"
#1677FF
```

如果只是一个页面背景：

```text id="token-candidate-no"
Local Value
```

如果大量作为：

```text id="token-candidate-yes"
主操作
选中态
链接
强调
```

则可以产生：

```text id="token-candidate"
Design Token Candidate:
semantic = action.primary
candidate value = #1677FF
```

注意仍然只是 Candidate。

---

# 七、重复次数不能自动产生 Token

即使：

```text id="repeat"
200 个地方都是 #1677FF
```

也不能直接：

```text id="wrong-repeat"
Shared Token = #1677FF
```

因为可能：

```text id="repeat-reasons"
100 个来自旧项目历史代码
50 个来自某一个 App
30 个来自已废弃页面
20 个才是当前 Target
```

所以：

```text id="repeat-not-authority"
Frequency
≠ Authority
≠ Adoption
```

---

# 八、Design Token 正式定义

我建议：

> **Governed Design Token = 对具有稳定设计意义、明确 Scope、稳定 Identity、可复用并可被其它设计语义引用的设计值或设计语义建立的受治理引用。**

例如：

```text id="token-examples"
brand.primary
text.primary
text.secondary
surface.background
surface.elevated
border.subtle
radius.card
spacing.dense
typography.body
shadow.popup
```

重点不是名字。

重点是：

> **它表达“设计意义”，而不仅仅是一个数值。**

---

# 九、Token 必须允许“值”和“语义”分层

例如：

```text id="primitive"
color.blue.500
= #1677FF
```

这是一个基础值。

而：

```text id="semantic-token"
action.primary.background
→ color.blue.500
```

是设计语义。

这样以后品牌调整：

```text id="token-change"
#1677FF
→ #2563EB
```

不需要去改：

```text id="token-change-no"
200 个页面里的所有引用
```

只需要治理相应 Token Resolution。

---

# 十、但不把 Token Taxonomy 写死

当前 Architecture Freeze 不应该规定：

```text id="taxonomy-hardcode"
Primitive
Semantic
Component
Alias
Theme
...
```

永远只能是这几种。

我们只冻结它必须能够表达：

```text id="token-capabilities"
direct value
semantic meaning
reference / alias
contextual variant
scope
origin
version
```

具体 Token taxonomy：

> 以后根据真实项目、标准和实现再冻结。

这样更符合你的“以后容易改”。

---

# 十一、Shared Foundation 正式定义

D01 已经确定：

> **Shared Foundation 是当前项目已经确认的共享设计 WHAT。**

D04 对它进一步细化为视觉层：

```text id="shared-foundation"
Shared Foundation
│
├── Brand / Identity
├── Typography Foundation
├── Color Foundation
├── Shape / Radius Foundation
├── Spacing / Density Foundation
├── Elevation / Shadow Foundation
├── Shared Component Visual Baseline
└── Governed Shared Token References
```

也就是说：

> **Shared Foundation 比 Token 大。**

Token 是 Foundation 的一种结构化表达方式。

---

# 十二、Shared Foundation 不能退化成一个 Token 文件

错误理解：

```text id="foundation-equals-token"
Shared Foundation
= design-tokens.json
```

不对。

例如：

> “后台整体保持高信息密度。”

这属于：

```text id="foundation-non-token"
Shared Foundation Design Fact
```

它不一定能用一个 Token 表达。

而：

```text id="foundation-token"
品牌主色
基础圆角
字体字号体系
```

则非常适合 Token 化。

---

# 十三、Foundation 与 Token 绝不能形成双真源

假设：

```text id="double-truth"
foundation.md
主色 = #1677FF

tokens.json
brand.primary = #409EFF
```

两份都允许修改。

这是不可接受的。

所以正式规定：

> **同一个 Shared Design Fact 只能有一个 Canonical Semantic Owner。**

如果已经 Token 化：

```text id="canonical-token"
Foundation
→ references governed token
```

其它文档只能：

```text id="projection"
Reference / Projection
```

不能再维护一份独立值。

---

# 十四、Token 的 Owner 必须由 Scope 决定

不能有一个万能 Token Store 管全世界。

我建议逻辑上区分：

| Scope | Owner |
|---|---|
| Project-wide | Shared Foundation |
| Application-wide | Application-scoped Foundation |
| Shared Component | 对应 Shared Component Design Target / Foundation |
| Page | Design Package |
| Region / Component-local | Design Package |
| Evidence-only extracted value | Design Evidence |

所以：

```text id="scope-owner"
Page-local value
≠ Project Foundation
```

---

# 十五、值一样，不代表 Token 是同一个

例如：

```text id="same-value"
platform-admin:
primary = #1677FF

tenant-admin:
primary = #1677FF
```

不能自动合并为：

```text id="wrong-merge"
project.primary
```

因为它们可能只是：

> **碰巧现在一样。**

以后 tenant-admin 可以：

```text id="tenant-change"
#1677FF
→ #00AA66
```

不应该影响 platform-admin。

只有经过明确治理：

```text id="shared-adoption"
确认二者共同继承 Project Foundation
```

才成为同一共享设计事实。

---

# 十六、Scope 是 Token 一等语义

Token 逻辑上必须允许被：

```text id="token-scope"
Project
Application
Surface
Component
State
Device
Theme
Brand
Context
```

限制。

不知道：

```text id="scope-unknown"
UNKNOWN
```

不能靠：

```text id="scope-wrong"
路径
文件名
加载顺序
```

猜。

---

# 十七、Theme / Variant 不应该复制整套真源

例如：

```text id="theme"
Light
Dark
```

不建议：

```text id="theme-copy"
light-full-copy.json
dark-full-copy.json
```

形成两份完全独立可编辑真源。

更合理：

```text id="theme-resolution"
surface.background

LIGHT
→ #FFFFFF

DARK
→ #111111
```

即：

> 同一个 Semantic Token，根据 Context 得到不同 Resolution。

---

# 十八、State Variant 也一样

例如：

```text id="state-token"
action.primary.background
```

可以存在：

```text id="state-token-values"
default
hover
pressed
disabled
selected
```

不同 Resolution。

但：

> **D04 不定义完整 State Machine。**

完整 State / Behavior 留后续 D05。

---

# 十九、Alias / Reference 允许存在

例如：

```text id="alias-chain"
button.primary.background
→ action.primary
→ brand.primary
```

允许。

但必须满足：

```text id="alias-constraints"
Resolvable
Traceable
Acyclic
```

不能：

```text id="alias-cycle"
A → B
B → C
C → A
```

---

# 二十、Token Resolution 是派生结果

真正任务执行时，需要把：

```text id="token-resolution-input"
Token
+
Scope
+
Theme
+
State
+
Device
+
Project Binding
+
Override Policy
```

解析成：

```text id="resolved-token"
Resolved Token Value
```

所以：

```text id="resolution-derived"
Token Resolution
= Derived / Rebuildable
```

它不是新 Truth。

---

# 二十一、Token Resolution 不允许 last-file-wins

不能：

```text id="last-file"
base.yaml
project.yaml
page.yaml

page 最后加载
→ page wins
```

Banyan 不是 CSS Cascade。

必须用已经冻结的：

```text id="resolution-dimensions"
Authority
Scope
Applicability
Specificity
Override Policy
Version
Current Effective
```

解析。

---

# 二十二、更具体 Scope 不自动获胜

例如 Foundation：

```text id="foundation-radius"
card.radius = 8
```

页面：

```text id="page-radius"
card.radius = 24
```

不能简单：

> 页面更具体，所以 24 赢。

必须判断：

```text id="override-check"
Foundation 是否允许 local override？
Local Authority 是否有效？
是否属于同一 semantic fact？
```

如果允许：

```text id="specialize"
SPECIALIZE / OVERRIDE
```

如果 Foundation 是不可覆盖品牌规则：

```text id="radius-conflict"
CONFLICT
```

继续符合我们全局治理护栏。

---

# 二十三、Token Relation 不再发明第二套规则关系

D04 不新增另一套：

```text id="bad-relation"
TokenPriority
TokenLevel
TokenWeight
```

直接复用 D02 已有关系思想：

```text id="token-relations"
COMPOSE
SPECIALIZE
DEPEND_ON
ALTERNATIVE
OVERRIDE
EXCLUDE
CONFLICT
```

必要时 Token 自己还可以有：

```text id="token-reference"
REFERENCE / ALIAS
```

这种值引用关系。

但它不是 Authority Priority。

---

# 二十四、UI Design Rule 和 Token 的关系

例如 Rule：

> “主要操作应该有明确视觉强调。”

这是：

```text id="rule-should"
SHOULD / WHY
```

它不能直接：

```text id="rule-to-token-wrong"
brand.primary = blue
```

正确：

```text id="rule-to-token"
UI Design Rule
↓
Design Decision
↓
Token Candidate / Local Value
↓
Governance
↓
Token / Foundation
```

所以：

```text id="rule-no-authority"
UI Design Rule
≠ Token Authority
```

---

# 二十五、UDC 与 Token 的关系

用户说：

> “这个页面的确认按钮必须橙色。”

这是：

```text id="udc-local"
UDC
scope = page
```

正常结果：

```text id="local-orange"
Local Design Value
```

不是：

```text id="orange-global"
Project Primary Token = orange
```

如果用户说：

> “以后整个项目所有主操作统一橙色。”

这才可能：

```text id="foundation-change"
Shared Foundation Change Candidate
```

Scope 决定 Owner。

---

# 二十六、AnyDesign 提取 Token 的正式定位

AnyDesign 输出：

```text id="anydesign-output"
design-tokens.json
```

在新架构下应解释为：

```text id="anydesign-token"
Extracted Token Evidence
/
Token Candidate Projection
```

不是：

```text id="anydesign-token-not"
Project Current Effective Token Set
```

Legacy 本身已经要求 AnyDesign 输出登记为 Material 后再映射 UI_SPEC，不允许直接成为 Approved 规范。fileciteturn120file4L1575-L1597

# 二十七、Figma Variables / Design System Tokens 同理

即使 Figma 本身已经定义：

```text id="figma-variable"
Primary / 500
```

也只能先说：

> Figma Source 自己认为它是一个 Token。

进入 Banyan 后仍然要判断：

```text id="figma-check"
这是 Target 吗？
当前版本吗？
属于哪个 App？
是不是 Project Foundation？
是否已经被项目采用？
```

不能因为 Figma 文件写了 Token：

> 自动获得 Banyan Foundation Authority。

# 二十八、W3C DTCG 的定位

Legacy 已经使用 W3C DTCG 格式。

这个兼容性值得保留。

但建议：

```text id="dtcg"
Banyan Token Semantic Contract
        ↕
DTCG Adapter
```

而不是：

```text id="dtcg-hardcode"
Banyan Core
= 某一个固定版本 DTCG Schema
```

以后标准升级：

> 换 Adapter / Compatibility Layer。

不推翻 Core。

# 二十九、Existing CSS Variables 只是 Reality Evidence

例如代码：

```css id="css-vars"
--primary-color: #1677ff;
--radius-card: 8px;
```

首先属于：

```text id="css-evidence"
Current Implementation Evidence
```

不是：

```text id="css-truth"
Shared Foundation
```

因为代码可能：

```text id="css-problems"
历史遗留
局部 hack
不一致
准备废弃
```

必须经过 Reconciliation。

---

# 三十、组件库 Token 也是 External / Technical Source

例如：

```text id="antd-token"
Ant Design colorPrimary
```

不能因为选择了 Ant Design：

```text id="antd-wrong"
Project Design Truth
= Ant Design default token
```

正确关系：

```text id="antd-right"
Ant Design Token
= External / Technical Available Token Source

Project Foundation
= decides whether/how to adopt
```

# 三十一、Design Token 和 Implementation Token 必须分开

例如设计语义：

```text id="design-token"
action.primary.background
```

实现时可能变成：

```text id="implementation-mapping"
CSS Variable
Ant Design Theme Token
Tailwind Theme
JS Theme Object
Native Resource
```

所以：

```text id="design-vs-impl"
Design Token
↓
Implementation Mapping
↓
Framework-specific Token
```

不是反过来。

---

# 三十二、Implementation Convenience 不能改 Token Truth

例如组件库只支持：

```text id="impl-limit"
border radius = 6
```

而 Current Design Token 是：

```text id="design-radius"
radius.card = 8
```

Adapter 不能：

```text id="silent-change"
偷偷把 Foundation 改成 6
```

应该：

```text id="feasibility"
Implementation Constraint
↓
Deviation / Feasibility Issue
```

交回治理。

# 三十三、UI_SPEC 如何使用 Token

UI_SPEC 可以：

```text id="uispec-token"
reference:
current effective token semantics
```

也可以为了施工稳定性：

```text id="uispec-token-snapshot"
记录当次已批准的 resolved projection / version ref
```

但 UI_SPEC 不能成为：

```text id="uispec-token-not-owner"
Token Canonical Owner
```

否则 Token 修改会出现：

```text id="double-token-owner"
Foundation 一份
UI_SPEC 一份
```

双真源。

# 三十四、Design Package 如何使用 Token

Page Design Package 可以：

```text id="dp-token"
引用 Shared Token
+
声明 Local Value
+
声明合法 Local Override
```

例如：

```text id="dp-token-example"

radius.card = 8

Page:
hero.radius = 24
origin = local design decision
```

不需要为了这个页面修改 Shared Token。

# 三十五、局部值未来可以提升成 Shared Token Candidate

例如开始只是：

```text id="local-history"
Page A:
spacing = 20
```

后来：

```text id="reuse-history"
Page B
Page C
Page D
```

都发现这个值具有共同语义。

用户以后主动要求盘点时：

```text id="promotion-candidate"
Local Values
↓
Reusable Token Candidate
```

但：

> 当前没有 AI 自主学习 / 自主晋升。

继续保持：

```text id="no-learning"
Autonomous Token Learning = DEFERRED
```

# 三十六、Shared Foundation Change 必须版本化

例如：

```text id="brand-change"
brand.primary
#1677FF
→ #FF5500
```

这不是普通局部修改。

应该形成：

```text id="foundation-version"
Shared Foundation Revision
```

并保留：

```text id="foundation-version-info"
Old version
New version
Reason
Decision
Trace
Impact
```

# 三十七、Shared Token Change 不自动修改所有项目设计

即使 Token 是共享的，也不能理解成：

```text id="auto-change"
token file changed
↓
所有历史 UI_SPEC 自动改变
```

正确：

```text id="impact-flow"

↓
Dependency / Impact
↓
Affected Design Package
↓
Affected UI_SPEC
↓

```

# 三十八、Local Change 与 Shared Change 必须分级

例如：

```text id="local-impact"
Page-local spacing:
16 → 20
```

可能只是：

```text id="local-impact-result"
LOCAL_RECHECK
```

但：

```text id="shared-impact"
base typography:
14 → 16
```

可能：

```text id="shared-impact-result"
PROJECT-WIDE DESIGN REVIEW
```

所以必须保留 Scope。

# 三十九、Token 版本与其它版本必须独立

不能：

```text id="version-coupling"
Framework v3
= Token v3
= UI_SPEC v3
```

```text id="version-axes"
Framework Release
Shared Foundation Revision

```

继续遵守：

```text id="latest-not-effective"
Latest != Current Effective
```

# 四十、Reusable Token Pack

```text id="token-pack"
Enterprise Design Pack
Banyan Shared Design Pack
```

```text id="available-pack"
Available Reusable Knowledge / Source
```

```text id="adopted"
Project Adopted Foundation
```

```text id="binding"
Adoption / Binding
```

# 四十一、Design System 也不能自动覆盖 Foundation

例如用户导入：

```text id="design-system"
某 Design System
```
