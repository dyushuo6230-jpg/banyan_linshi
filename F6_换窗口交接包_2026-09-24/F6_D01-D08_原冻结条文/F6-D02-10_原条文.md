# F6-D02-10
## Rule / Module Lifecycle × Version × Freshness × Supersession × Impact
### 规则与模块生命周期、版本、有效性、替代与影响治理

```text
Status = HUMAN_REVIEW
Implementation = NOT_AUTHORIZED
```

这一项和你刚强调的“**框架以后必须非常容易修改和优化**”直接相关。

D02-10 要解决的不是“规则怎么创建”，而是：

> **Banyan 已经运行几年以后，有几百个 Module、几千条 Rule，并且一直在修改、补充、拆分、合并、升级时，怎样还能知道：哪条规则现在有效、哪个项目正在用哪版、改一条规则会影响谁、旧规则怎么退、项目怎么安全升级。**

---

# 一、先明确：Architecture Freeze 不是“以后不能改”

这一点我建议正式写进 D02-10：

```text
Architecture Freeze
=
当前版本语义已经稳定，可以作为后续工作的基线

!=
永久锁死，不允许未来优化
```

以后合法演进应该是：

```text
Current Stable Version
        ↓
Change / Revision
        ↓
Impact
        ↓
Validation
        ↓
New Version
        ↓
Project Adoption
```

而不是：

```text
直接改旧文件
↓
大家自动跟着变
```

---

# 二、先把几个很容易混淆的概念彻底分开

这是 D02-10 最核心的一步。

## 1. Identity
### 身份

回答：

> “这还是不是原来那个 Rule / Module？”

例如：

```text
Rule ID = R-017
```

即使：

- 文件移动了；
- 名称改了；
- Module 调整了；
- 描述补充了；

只要语义身份没有实质改变：

```text
ID 可以保持不变
```

所以继续坚持：

```text
Stable ID
!=
Path
!=
Display Name
!=
Version
```

---

## 2. Version
### 版本

回答：

> “同一个语义对象现在演进到了哪一版？”

例如：

```text
R-017
v1
v2
v3
```

版本变化不等于换 Identity。

---

## 3. Lifecycle Status
### 生命周期状态

回答：

> “这个对象现在处于什么治理阶段？”

逻辑上可能存在：

```text
Candidate
Current / Active
Deprecated
Superseded
Retired
```

精确 enum 后面再定。

---

## 4. Freshness
### 新鲜度 / 是否仍然适合当前上下文

回答：

> “这条 Rule 本身可能仍是合法规则，但它引用的环境、版本、证据或项目上下文是不是已经过时？”

例如：

```text
Rule = Active
但针对 React 18

Project = React 21
```

那么：

```text
Rule Status 可能仍 Active
但对于当前 Context：
Freshness / Applicability = REVIEW_REQUIRED
```

因此：

```text
Lifecycle Status
!= Freshness
```

---

## 5. Current Effective
### 当前真正生效

回答：

> “这个项目、这个 Scope、这个时间点，最终到底使用哪一个？”

它由：

```text
Rule Status
+
Project Profile / Binding
+
Version
+
Scope
+
Applicability
+
Freshness
+
Override / Supersession
```

共同决定。

因此继续保持：

```text
Latest
!= Current Effective
```

---

# 三、Rule 修改不能只有“覆盖保存”

以后修改一条 Rule，至少要判断它是哪一种变化。

我建议架构上区分：

```text
A. Editorial Change
文字 / 示例 / 拼写 /解释修正

B. Enrichment
补充 rationale / example / anti-pattern，
核心语义不变

C. Scope / Applicability Refinement
把适用边界说明得更精确

D. Compatible Semantic Revision
核心规则有改进，但旧消费者可以兼容

E. Breaking Semantic Revision
规则含义发生会改变执行结果的变化

F. Supersession
原 Rule 不再适合作为同一语义身份继续演进
```

具体名字后面可以调整。

关键是：

> **Banyan 必须知道“这次修改到底改了什么性质”。**

---

# 四、不能因为改了一句话就创建新 Rule ID

例如：

原：

> “表格区域应保持稳定扫描路径。”

修改：

> “数据密集型表格区域应保持稳定且可预测的扫描路径。”

语义基本没变。

应该：

```text
Same Rule ID
+ revision / version
```

而不是：

```text
删 R-017
新建 R-381
```

否则历史引用会非常混乱。

---

# 五、什么时候应该创建新的 Identity

例如原规则：

> “所有导航均使用顶部横向布局。”

后来发现：

> 其实后台和移动端属于完全不同的设计问题。

最后拆成：

```text
Desktop Navigation Rule
Mobile Navigation Rule
```

此时继续把旧规则强行改造成两个语义：

> 已经不再是一个 coherent semantic identity。

应：

```text
Old Rule
→ SUPERSEDED

New Rule A
New Rule B
```

并建立：

```text
superseded_by
```

关系。

---

# 六、Rule Split 要支持

例如：

```text
R-017
```

实际上混了：

```text
overflow handling
+
selected state
```

后来治理发现应该拆开。

正确：

```text
R-017
SUPERSEDED

├── R-201
└── R-202
```

历史仍能查：

> 当年哪些项目用过 R-017。

---

# 七、Rule Merge 也要支持

反过来：

```text
R-081
R-082
R-083
```

长期发现其实只是同一个规则被拆得过细。

可以：

```text
R-081 / R-082 / R-083
→ SUPERSEDED
→ R-301
```

但不能简单删除旧 Rule。

---

# 八、Module 也使用同样原则

Module 需要支持：

```text
Rename
Revision
Split
Merge
Supersede
Deprecate
Retire
```

例如：

```text
Frontend Layout Module
```

后来越来越大。

拆：

```text
Layout Composition Module
Overflow & Scroll Module
Responsive Layout Module
```

旧 Module：

```text
SUPERSEDED
```

而不是删除历史。

---

# 九、Module 拆分不等于所有 Rule 都换 ID

这是一个很重要的优化。

例如：

```text
Module A
├── R1
├── R2
└── R3
```

拆成：

```text
Module B
├── R1
└── R2

Module C
└── R3
```

如果：

```text
R1 / R2 / R3
语义本身没有变化
```

那么：

```text
Rule ID SHOULD remain stable
```

只改变：

```text
Module Membership
```

所以：

> **Identity 属于 Rule 本身，不属于目录或 Module 路径。**

---

# 十、Module Membership 也不能成为 Authority

一条 Rule 从：

```text
Module A
```

移动到：

```text
Module B
```

不能导致：

> Rule 强度突然变化。

因此：

```text
Module Membership
!= Rule Authority
!= Strength
```

除非有显式治理变更。

---

# 十一、共享 Rule 更新不等于项目自动升级

这是你“框架容易优化但项目不能乱”的核心保险。

例如：

```text
Shared Rule R-017

v2
↓
v3
```

Project A 当前：

```text
Profile binds R-017 v2
```

Shared v3 发布后：

```text
Project A
仍然可以继续使用 v2
```

直到：

```text
Compatibility
↓
Impact
↓
Upgrade Candidate
↓
Project adoption
```

所以：

```text
Shared Release
!= Project Adoption
```

---

# 十二、Framework 可以快速进化，Project 可以稳定运行

最终形成：

```text
Shared Framework
v10
v11
v12
v13
       ↓

Project A → still v10 compatible bindings

Project B → v12

Project C → v13
```

这不是问题。

反而说明：

> Framework Evolution 与 Project Stability 被正确解耦。

---

# 十三、但也不能无限 Pin 老版本

未来某个规则：

```text
v1
```

已经存在严重问题。

可以进入：

```text
Deprecated
```

甚至：

```text
Retirement Planned
```

Project 仍使用时：

```text
Upgrade Required / Warning
```

但究竟：

- 什么时候强制；
- 是否允许继续；
- 安全规则如何处理；

留给后面的 Policy / F8 / F10。

D02-10 只冻结：

> 生命周期必须能表达这种状态。

---

# 十四、Deprecated 和 Superseded 要区别

建议：

### Deprecated

表示：

> 还能识别，也可能暂时还能用，但不建议新采用。

例如：

```text
老组件库实现规则
```

---

### Superseded

表示：

> 已有明确的新语义对象替代它。

例如：

```text
R-017
→ superseded_by R-201 + R-202
```

---

### Retired

表示：

> 不再参与新的正常 Resolution。

但：

```text
历史 Trace
```

仍必须保留。

---

# 十五、删除应该是最后一步

长期治理对象默认：

```text
Retire
> Delete
```

因为 Rule / Module 可能被：

```text
old project
historical decision
audit record
validation report
```

引用。

所以物理删除不是普通生命周期步骤。

真正 Delete 要等：

```text
Reference Integrity
Migration
Retention Policy
```

确认。

这一块最终由 F7/F12 等 Owner 控制。

---

# 十六、Freshness 不能等于文件修改时间

禁止：

```text
mtime 最新
= freshest
= current effective
```

也禁止：

```text
文件名 v9
> v8
所以自动用 v9
```

Freshness 要结合：

```text
Authority
Version
Status
Supersession
Applicability
Binding
Evidence
```

之后再判。

---

# 十七、Rule 自己也可以 Fresh，但 Context 已经过时

例如：

```text
Rule v3 = CURRENT
```

但旧：

```text
Effective Design Context
```

是根据：

```text
Rule v2
```

编译的。

则：

```text
Rule = Fresh
Context = STALE / RECHECK
```

所以 Freshness 必须是：

> **相对于对象和依赖关系判断。**

不是一个全局布尔值。

---

# 十八、需要 Dependency / Impact 关系

以后修改一条 Shared Rule，Banyan 要能回答：

```text
谁在用它？
```

逻辑链可能是：

```text
Rule R-017
↓
Module M-03
↓
Profile P-07
↓
Project A
↓
Effective Context C-102
↓
Design Package DP-33
↓
UI_SPEC U-21
```

或者：

```text
Frontend Rule
↓
Effective Implementation Context
↓
Implementation Task
```

这就是为什么 Trace 很重要。

---

# 十九、但 Impact 不能等于“所有下游全部失效”

例如只是：

```text
Example typo fix
```

不需要让：

```text
100 个项目
2000 个 Context
全部重算
```

因此变化必须先分类。

---

# 二十、建议建立 Impact Class 思想

精确名称以后再定。

逻辑上至少需要区分：

```text
NO_SEMANTIC_IMPACT
没有语义影响

LOCAL_RECHECK
局部重新评估

CONTEXT_RECOMPILE
相关 Context 需要重新编译

DESIGN_REVIEW
相关 Design 需要复核

IMPLEMENTATION_REVIEW
相关实现需要复核

PROJECT_UPGRADE_REQUIRED
项目 Binding / Profile 需要升级

HIGH_IMPACT_GOVERNANCE
高影响治理变更
```

不是所有 Change 都同样处理。

---

# 二十一、Impact 必须从真实 Dependency 出发

不能：

```text
Rule 改了
→ 所有项目都影响
```

而应该：

```text
Rule changed
↓
Find bindings / references
↓
Find contexts actually consuming it
↓
Evaluate semantic change
↓
Invalidate only affected surfaces
```

也就是继续：

> **Localized Invalidation。**

---

# 二十二、上下文 Fingerprint 与 D02-10 的关系

D02-08 已冻结：

```text
Effective Design Context
```

支持 Dependency / Fingerprint。

D02-10 进一步规定：

> Rule / Module / Profile 更新后，应根据真实依赖判断 Fingerprint 是否失效。

例如：

```text
Context C1:
uses R1 v2, R2 v4

R8 v3 changes
```

C1 根本没用 R8：

```text
C1 stays valid
```

---

# 二十三、Rule Strength 改变属于高价值 Impact

例如：

```text
RECOMMENDED
↓
REQUIRED
```

这绝对不是普通文字修改。

可能意味着：

```text
过去合法实现
现在需要复核
```

因此 Strength Change 必须触发：

```text
Impact Analysis
```

---

# 二十四、Scope 改变也可能很危险

例如：

原：

```text
Scope = mobile only
```

改：

```text
Scope = all platforms
```

即使 Rule Body 一个字没变：

> 实际影响可能非常大。

所以：

```text
Semantic Impact
!= Only body text diff
```

还要看：

```text
Scope
Applicability
Strength
Override Policy
Version constraints
```

变化。

---

# 二十五、Override Policy 改变同样需要 Impact

比如：

```text
Rule v2:
overridable
```

升级：

```text
Rule v3:
non-overridable
```

这可能直接影响现有 Project Override。

因此：

```text
Override Policy Change
```

属于必须分析的语义变化。

---

# 二十六、Module Dependency 改变也需要影响分析

例如 Module A 原本独立。

后来：

```text
A depends_on B
```

Project Profile 只绑定 A。

不能静默：

> 自动把 B 加进去。

应该出现：

```text
Dependency Gap
或
Profile Upgrade Candidate
```

具体自动化程度后面 F8 决定。

---

# 二十七、Profile Changes 也是版本化语义

Profile 不应该：

```text
今天 Module A
明天悄悄变 Module B
```

不留历史。

因为 Profile 变化直接决定：

> Project Current Effective Rules。

所以需要：

```text
Profile Revision
```

和历史 Trace。

---

# 二十八、Project-local Rule 也需要生命周期

不能认为只有 Shared Framework Rule 才有版本。

例如：

```text
.banyan
Project Rule PR-017
```

也可能：

```text
v1
v2
Deprecated
Superseded
```

因为一个项目自己也会长期维护。

---

# 二十九、项目 Rule 晋升 Shared 后如何处理

当前不做自主 Promotion，但未来用户主动提升时：

```text
Project Rule P-17
↓
Shared Rule S-88
```

之后：

```text
P-17
```

不应该继续和：

```text
S-88
```

形成两个长期独立可编辑 Truth。

正确：

```text
P-17
→ superseded/promoted lineage
→ S-88

Project Profile
→ reference S-88
```

必要的项目差异另写 Local Override / Project Rule。

---

# 三十、Framework Evolution 不要求“重新安装全部项目”

这也是可扩展性的重点。

以后 Framework Rule Catalog 更新：

```text
framework v5 → v6
```

Project 可以：

```text
discover update
↓
calculate impact
↓
adopt incrementally
```

不是：

```text
Framework 升级
↓
删除 .banyan
↓
重新初始化项目
```

现有基线已经明确：已有 `.banyan` 要 reconcile/upgrade，而不是删除重建。这个方向继续保持。

---

# 三十一、修改规则时需要 No-Silent-Overwrite

任何有治理意义的变化：

```text
old semantics
→ new semantics
```

都必须能够说明：

```text
ADD?
REFINE?
REVISION?
SUPERSEDE?
DEPRECATE?
CONFLICT?
```

不能：

> “新文件比较新，所以旧文件内容没了。”

---

# 三十二、AI 当前可以做什么

按照你刚修正的自主学习边界：

当前 AI 可以在用户触发或正常治理任务中：

```text
比较 old/new
识别 semantic diff
建议 change classification
找引用
计算 candidate impact
发现 duplicate
发现 possible split / merge
生成 upgrade recommendation
```

---

# 三十三、AI 当前不能做什么

现在不能因为“系统发现更优规则”就：

```text
自动修改 Shared Rule
自动拆 Module
自动提升 Project Rule
自动迁移所有 Project Profile
自动删除旧 Rule
```

这些属于：

```text
Autonomous Framework Optimization
= DEFERRED
```

---

# 三十四、但以后接 AI Learning 不需要推翻 D02-10

这就是我们现在要求可扩展性的价值。

未来 AI Learning 只需要产生：

```text
Change Candidate
Rule Candidate
Module Refactor Candidate
Promotion Candidate
```

然后继续使用：

```text
Lifecycle
Version
Impact
Validation
Canonical Apply
```

而不是让 Learning Engine 自己成为第二套 Rule Store。

```text
        ↓

        ↓

        ↓

        ↓

        ↓
```

# 四十、我建议 D02-10 候选不变量

这一轮先形成 **RL-01～RL-28**：

```text
RL-01
Architecture Freeze 表示当前版本稳定，
不代表 Rule / Module 永久不可修改。

RL-02
Rule / Module 的 Stable Identity
必须与文件路径、显示名、目录位置和版本解耦。

RL-03
Identity、Version、Lifecycle Status、
Freshness、Applicability 和 Current Effective
必须作为不同语义维度治理。

RL-04
Latest != Current Effective。
新版本发布不得自动成为所有 Project 的当前有效版本。

RL-05
Rule 修改必须区分非语义编辑、
增强、Scope/Applicability refinement、
语义 Revision、Breaking Revision 和 Supersession
等不同变化性质；精确枚举留待 Implementation Freeze。

RL-06
核心语义身份未改变时，
应优先保持 Stable Rule ID 并产生 Revision，
不得因改名或移动文件创建新 Identity。

RL-07
当一个 Rule 的语义责任已不再保持 coherent identity，
必须使用新 Identity + Supersession，
不得把多个不同语义强塞回旧 ID。

RL-08
Rule 必须支持 Split / Merge，
并保留 predecessor / successor lineage。

RL-09
Module 必须支持 Rename / Revision /
Split / Merge / Supersession /
Deprecation / Retirement。

RL-10
Module Membership 改变时，
如果 Rule semantics 未改变，
Rule ID 不应因此变化。

RL-11
Module Membership / File Order /
Physical Location 不得决定 Rule Authority / Strength。

RL-12
Deprecated、Superseded、Retired
必须具有不同治理语义；
具体状态 enum 后续实现冻结。

RL-13
Retirement 不等于 Physical Delete。
历史 Trace / Reference / Audit 必须可保留。

RL-14
Shared Rule / Module 新版本
不得自动修改 Project Profile / Binding。

RL-15
Project-local Rules 同样必须支持
Version / Revision / Supersession / Trace。

RL-16
Project Rule 晋升 Shared Rule 后，
必须保留 promotion lineage，
并避免两个长期 editable canonical truths。
```
