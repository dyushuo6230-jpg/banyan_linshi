# F6-D06 — Data Evidence × UI Data Semantics × Demo Fixture
## 数据证据 × UI 数据语义 × 演示数据边界

```text
Status = HUMAN_REVIEW
Implementation = NOT_AUTHORIZED
```

D06 解决的是一个同样很容易被 AI 搞错的问题：

> **设计图里出现了“¥39.90”“品牌主视觉.png”“上传中 72%”这些内容，到底哪些只是为了把设计图画出来的示例数据，哪些代表页面需要一个真实字段，哪些又真正来自 Product/API/Data Model。**

Legacy 已经明确过一个非常重要的边界：设计稿里的示例数据只是 Demo Fixture，不等于真实业务数据。fileciteturn123file1L130-L158

---

# 一、D06 的核心目标

完整链我建议冻结为：

```text
Design / Prototype / Existing UI / PRD / API Evidence
                    ↓
              Data Evidence
                    ↓
        UI Data Semantic Interpretation
                    ↓
       Dynamic Slot / Field Requirement
                    ↓
      Upstream Data Source Reconciliation
                    ↓
           UI Data Binding Model
                    ↓
       Deterministic Demo Fixture
                    ↓
             Design Package
                    ↓
              UI Governance
                    ↓
                UI_SPEC
                    ↓
      Implementation / Validation
```

关键点：

> **D06 不设计业务数据库。**

> **D06 不创造 API。**

> **D06 只解决 UI 为了正确设计、实现和验证，需要理解哪些数据语义。**

---

# 二、先把 7 个概念完全分开

我建议 D06 正式区分：

```text
Data Evidence
数据证据

Display Value
设计中看到的展示值

UI Data Slot
UI 动态数据槽

UI Field Semantic
UI 字段语义

Data Binding Requirement
数据绑定要求

Demo Fixture
固定演示数据

Business / API Data Contract
真实业务/API 数据契约
```

这些不能混成一个：

```text
data-map.json
```

然后让 AI 自己判断。

---

# 三、Display Value 首先只是 Evidence

例如设计图里：

```text
商品价格：¥39.90
```

首先能确认的是：

```text
这里视觉上显示了：
¥39.90
```

不能立刻推出：

```text
数据库一定有 product.price decimal(10,2)
```

也不能推出：

```text
接口字段一定叫 price
```

甚至不能直接断定：

```text
这是人民币真实价格
```

它可能只是 Designer 填的示例。

所以：

```text
Display Value
≠ Business Fact
≠ API Field
≠ Database Field
```

---

# 四、Design Demo Value 与 Real Data 必须分离

例如：

```text
¥39.90
```

更合理的结构是：

```text
UI Semantic:
CurrencyText

Business/Data reference:
product.price

Formatter:
currency(CNY)

Fixture:
39.90
```

这正是现有设计协议已经明确的方向。fileciteturn123file1L130-L158

因此我建议正式冻结：

> **设计稿中的具体值默认是 Display / Fixture Evidence，而不是业务真实值。**

除非上游 PRD、API、用户明确声明等提供更强语义。

---

# 五、UI Data Slot 是“这个位置需要动态内容”

例如你的素材管理页面：

```text
文件名
文件大小
文件类型
创建时间
缩略图
上传进度
```

D06 可以识别：

```text
ResourceItem
需要这些动态位置
```

形成：

```text
UI Data Slot
```

它回答：

> “这个 UI 区域未来需要数据。”

但暂时不回答：

> “后端接口字段具体叫什么。”

---

# 六、Dynamic Slot 必须明确是不是动态

Legacy 已经有一个非常有价值的分类：

```text
STATIC
DYNAMIC
ASYNC
USER_INPUT
SYSTEM_STATUS
```

例如上传进度列表是动态内容。fileciteturn126file0L837-L857

我建议保留这个思想，但不把精确 enum 永久写死。

架构层只要求：

```text
Static vs Dynamic
Data Origin Nature
Update Nature
```

必须能够表达。

---

# 七、UI Field Semantic 回答“这个字段在 UI 中是什么意思”

例如：

```text
resource.name
```

在 UI 中可能意味着：

```text
Field Role:
Resource Display Name

Presentation:
single/multi-line text

Overflow:
ellipsis

Fallback:
--

Validation expectation:
non-empty if available
```

所以 Field Semantic 不是简单：

```text
name: string
```

Legacy 本来就要求 UI 字段至少能够表达：

```text
name
type
source
formatter
fallback
validation
overflow
demoValue
```

fileciteturn126file0L769-L789

这部分很值得保留。

---

# 八、但 UI Field Semantic 不是 API Schema

例如：

```text
UI:
Resource Display Name
```

真正后端可能：

```text
file_name
```

也可能：

```text
displayName
```

也可能由：

```text
folder.name / asset.title
```

多个模型映射而来。

所以：

```text
UI Field Semantic
≠ API Field Name
```

---

# 九、Data Binding Requirement 是桥梁

Legacy Data Map 已经有：

```text
ResourceItem
bindings:
  name      → resource.name
  size      → resource.size
  type      → resource.type
  createdAt → resource.createdAt
  thumbnail → resource.thumbnail
```

这种结构。fileciteturn126file0L748-L768

我建议新架构里把它定义成：

> **UI Data Binding Requirement = UI 数据语义与真实可用数据语义之间的映射要求。**

重点是：

```text
Requirement
```

不是：

```text
API Authority
```

---

# 十、D06 不能自己发明后端字段

例如设计图显示：

```text
“上传人”
```

但当前 PRD/API 没有这个字段。

AI 不能为了实现 UI 自己：

```text
invent:
uploader_name
```

然后把后端也一起改了。

正确：

```text
UI Data Requirement:
Uploader Display Identity

Upstream Data Coverage:
MISSING / UNKNOWN

↓
DATA_COVERAGE_GAP
```

然后进入上游治理。

---

# 十一、UI Data Requirement 与 Product Requirement 的关系

如果 UI 需要：

```text
库存数量
```

但 PRD 完全没这个概念：

这可能不是普通数据绑定问题。

可能意味着：

```text
Design/Product Semantic Gap
```

例如：

```text
设计图：
库存：32

PRD：
完全没有库存能力
```

D06 不能直接：

```text
“那就补库存字段”
```

必须反馈给：

```text
F5 Product Governance
```

---

# 十二、UI Data Binding 和 Implementation Binding 也要分离

设计阶段可以说：

```text
ResourceName
→ needs resource display name
```

但不应该直接绑定：

```text
response.data.list[i].resource_name
```

因为那已经是：

```text
Implementation / Adapter Mapping
```

正确：

```text
UI Semantic Binding
        ↓
Implementation Context
        ↓
API / OpenAPI / Code Reality
        ↓
Concrete Binding
```

---

# 十三、OpenAPI / Existing API 是技术事实来源

如果项目已经有 OpenAPI：

```text
GET /resources
```

并定义：

```text
name
size
type
createdAt
thumbnail
```

D06 可以将其作为：

```text
Technical / Data Contract Evidence
```

然后判断：

```text
UI Requirement
↔ API Coverage
```

但不能修改它的 Authority。

也不能因为：

> API 里有一个字段

就自动决定 UI 必须展示它。

---

# 十四、Current Code 同样只是 Data Reality Evidence

例如旧页面写：

```text
item.fileName
```

它可以说明：

> 现有实现里曾使用这个字段。

但是：

```text
Current Code Field
≠ Current Product Data Truth
```

可能 API 已经变了。

所以仍然需要 Freshness / Current Effective 检查。

---

# 十五、Demo Fixture 的正式定义

我建议：

> **Demo Fixture = 为设计、实现、视觉回归和交互验证提供稳定、可重复的数据场景。**

它不是：

```text
业务数据库 Seed
```

也不是：

```text
生产数据快照
```

---

# 十六、Fixture 必须 Deterministic

Legacy 已经明确：

> 设计演示必须使用固定 Fixture，不允许直接依赖随机数据。fileciteturn126file0L802-L822

这个原则我建议正式冻结。

为什么？

例如今天截图：

```text
名字长度 = 8
```

明天随机出来：

```text
名字长度 = 38
```

Visual Diff 就失去意义。

所以：

```text
same fixture version
+ same viewport
+ same assets/fonts
→ reproducible baseline
```

---

# 十七、Fixture 必须服务“场景覆盖”，不是只让页面好看

Legacy 已明确 Fixture 应考虑：

```text
正常数据
长文本
短文本
大数字
空数据
Error
Loading
多条数据
单条数据
极端数据
```

fileciteturn126file0L822-L842

我建议保留这个理念。

但修正一个边界：

> 不是所有页面必须机械包含全部这些场景。

应该是：

```text
Applicable Data Scenario Coverage
```

和 D05 一样：

```text
Applicable?
Required?
Covered?
Unknown?
Not Applicable?
```

---

# 十八、Fixture Scenario 与 Product State 不同

例如：

```text
Fixture:
empty resource list
```

可以用于验证：

```text
Empty UI
```

但不能自动说明：

> 产品业务中这个页面允许永久为空。

它只是：

```text
Validation Scenario
```

---

# 十九、Fixture 里的 status 不是业务真源

例如：

```json
{
  "status": "ready"
}
```

只是 Fixture 为页面提供的场景值。

不能反向定义：

```text
正式业务状态机包含 READY
```

除非 F5 / API Contract 已经确认。

---

# 二十、Fixture 可以派生于真实 Schema，但不能冒充真实数据

例如 OpenAPI 已定义：

```text
Resource:
id
name
size
type
createdAt
```

可以据此构造：

```text
Fixture Resource
```

但：

```text
Fixture instance
≠ Production instance
```

Schema Evidence 与 Demo Data 必须分离。

---

# 二十一、Fixture 与 Test Data 也要区分

以后可能存在：

```text
Design Fixture
Interaction Test Fixture
API Test Fixture
Integration Test Fixture
Production Seed
```

D06 不应该把这些都合成一个万能 fixture。

当前 D06 只拥有：

```text
UI Design / Visual / Interaction Validation Fixture Semantics
```

更广的 Test Data 留测试体系 Owner。

---

# 二十二、UI Data Scenario 与 D05 Behavior State 怎么衔接

例如：

```text
Data Scenario:
loading
```

D06 表达：

```text
数据目前处于等待结果场景
```

D05 表达：

```text
UI 在这种场景下如何显示 Loading State
```

所以：

```text
D06 Data Scenario
        ↓
D05 UI State
```

而不是同一对象。

---

# 二十三、Empty / Error / Loading 不要重复定义

这是 D05 和 D06 最容易重叠的地方。

我建议正式明确：

```text
D06 owns:
Data Scenario / Data Availability Semantics

D05 owns:
UI State / Interaction Response
```

例如：

```text
D06:
resource collection = EMPTY

D05:
ResourceGrid UI state = EMPTY

Design:
show EmptyState illustration
```

这样没有双 Owner。

---

# 二十四、Formatter 属于 UI Data Semantics

例如：

```text
price = 39.9
```

UI 可能需要：

```text
¥39.90
```

因此：

```text
Formatter
```

是 D06 的设计语义。

但：

```text
currency = CNY
```

如果涉及业务币种：

> 必须来自 Product/Data Authority。

不能设计 AI 自己决定币种。

---

# 二十五、Fallback 也要区分 UI 与业务

例如：

```text
createdAt = null
```

UI 可以显示：

```text
--
```

这是：

```text
Presentation Fallback
```

但不能把：

```text
null → 1970-01-01
```

这种业务数据修复规则塞到 D06。

---

# 二十六、Overflow 是 Presentation Contract，不是数据变更

例如：

```text
文件名很长
```

UI 可以：

```text
ellipsis
two-line clamp
wrap
tooltip
```

这些属于：

```text
Presentation Semantics
```

不能：

```text
truncate actual business data
```

UI 截断显示：

```text
≠ 数据被截断保存
```

---

# 二十七、Validation 也要分层

UI Field Validation 可能指：

```text
Input presentation / client interaction constraint
```

但业务 Validation：

```text
用户名唯一
金额不能超过账户余额
```

属于 Product/Business。

所以 D06 不允许把：

```text
UI validation
```

扩大成：

```text
Business Rule Authority
```

---

# 二十八、USER_INPUT 是特殊 Data Slot

例如：

```text
搜索关键字
表单内容
文件名称编辑
```

它们是：

```text
User Input Data
```

D06 可以描述：

```text
field semantic
display/input format
local validation expectation
```

但真实：

```text
提交规则
业务校验
持久化
权限
```

仍属于上游 Product / API。

---

# 二十九、SYSTEM_STATUS 同样只表达 UI 消费语义

例如：

```text
上传中 72%
```

D06 可以定义：

```text
progress percentage slot
```

但：

> 百分比如何由上传任务计算、如何重试、切片怎么合并

这些属于系统实现逻辑。

D06 不拥有。

---

# 三十、Data Source Role 必须显式

同一个 UI Slot 可能来自：

```text
Product Data
API Data
Local UI State
Derived Presentation Value
User Input
System Runtime Status
Fixture
```

不能混为一个：

```text
source = data
```

我建议 D06 要求保留：

```text
Data Origin Role
```

但精确枚举后面再定。

---

# 三十一、Derived UI Value 是合法的

例如：

```text
firstName = 张
lastName = 三
```

UI 显示：

```text
张三
```

或者：

```text
1024000 bytes
→ 1000 KB / 0.98 MB
```

这是：

```text
Derived Presentation Value
```

可以存在。

但必须知道：

```text
source facts
+
formatter/derivation
```

而不是伪造一个新业务字段。

---

# 三十二、UI Data Model 不应该成为第二 Domain Model

这是 D06 的核心硬规则之一。

不能因为 UI 为了方便建立：

```text
ResourceViewData
```

最后让它成为：

> “全项目真正的数据模型”。

它只是：

```text
UI-facing projection / requirement
```

业务数据真相仍在对应 Product/Data/API Authority。

---

# 三十三、Design Package 只持有页面所需的数据语义

例如 Resource Manager Design Package 可以包含：

```text
需要：
name
type
size
thumbnail
createdAt
duration?
resolution?
```

但不需要：

```text
整个 Resource 数据库模型
所有后台内部字段
审计字段
数据库索引
```

继续遵守：

```text
Minimum Sufficient Context
```

---

# 三十四、UI Data Contract 必须允许 Partial

例如当前只有设计图：

```text
名称
大小
时间
```

API 还没设计。

那么：

```text
UI Data Semantics = KNOWN

Concrete Source Binding = UNKNOWN
```

这是合法状态。

不能为了“完整”：

```text
AI invent API endpoint
```

---

# 三十五、Data Coverage Gap 需要显式

例如 UI Target 需要：

```text
视频 duration
```

当前 API 没有。

形成：

```text
DATA_COVERAGE_GAP
```

然后分类：

```text
UI can derive locally?
Existing source exists elsewhere?
Product/Data change required?
Unknown?
```

不能静默：

```text
hardcode “02:14”
```

---

# 三十六、低风险 Derived Presentation 可以 Autonomy

比如已有：

```text
sizeBytes
```

需要显示：

```text
1.0 MB
```

项目规则允许某个标准 Formatter。

这属于：

```text
low-risk reversible presentation decision
```

可以在 AUTONOMY-01 范围内处理。

---

# 三十七、Autonomy 不能创造业务数据

不能自主：

```text
增加库存字段
虚构余额
创造权限字段
生成订单状态
把 demoValue 当真实值
```

这都是越权。

---

# 三十八、Design Fixture 必须与视觉基线绑定版本

以后 Visual Validation：

```text
Baseline Screenshot
```

必须知道它对应：

```text
Fixture version
Design Package version
Viewport
Assets/fonts
State
```

否则：

> 数据变了导致截图不同，

会被误判成 UI Drift。

具体 Fingerprint F9 实现。

D06 只冻结这个依赖语义。

---

# 三十九、Fixture 修改可能导致 Baseline Stale

例如：

```text
Fixture v1:
3 个资源

Fixture v2:
20 个资源
```

即使设计没变：

```text
截图结构也可能改变
```

因此：

```text
Fixture Revision
→ Validation Baseline Impact
```

不能把它当无意义测试文件修改。

---

# 四十、Fixture 不应该随着每次运行自动随机生成

这再次强化：

```text
Deterministic
Versioned
Traceable
```

但不代表所有 Fixture 都要长期 Canonical。

它可以是：

```text
Design Package-owned / validation-owned governed support artifact
```

具体物理归属后面定。

---

# 四十一、设计图里的敏感/真实数据不应被当 Fixture 长期复制

这里我建议增加一个安全边界：

如果 Existing UI 截图里出现：

```text
真实手机号
邮箱
订单号
用户姓名
敏感业务数据
```

不能因为要做 Fixture 就直接复制长期使用。

应该：

```text
sanitize / synthesize
```

同时保留：

```text
数据形态
长度
格式
极端场景
```

而不是保留真实敏感值。

这一条是 D06 的设计安全要求，不改变数据 Authority。

---

# 四十二、D06 不绑定具体数据技术

Core 不能写死：

```text
REST
GraphQL
MySQL
Go struct
TypeScript interface
React Query
Pinia
Redux
```

这些属于：

```text
Implementation / Technical Adapter
```

D06 只认识：

```text
UI data semantics
source role
binding requirement
fixture
scenario
```

---

# 四十三、以后换数据源不推翻 UI Design

例如今天：

```text
REST
```

以后：

```text
GraphQL
```

如果提供的 Data Semantics 一样：

```text
UI Design Package
不需要跟着重做
```

只改变：

```text
Implementation Binding
```

这正好符合你要求的可修改性。

```text
品牌主视觉.png
1920×1080
1.2 MB
2026-09-24
```

D06 不应该得到：

```text
真实数据库里一定存在：

width
height
size
created_at
```

而应该先得到：

```text
UI Data Semantics

Resource Display Name
Image Dimensions

```

再去对账：

```text
PRD / API / Current Code / Data Contract
```

---


```text

圆环进度
```

