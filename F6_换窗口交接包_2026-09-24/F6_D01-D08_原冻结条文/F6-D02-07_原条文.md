# F6-D02-07 — UI Design Rule System
## UI 设计规则体系治理、边界、形成与使用原则

## 1. 决策目标

F6-D02-07 要解决的不是：

> “具体某个页面怎么画。”

而是解决：

> **Banyan 如何长期管理可复用的 UI 设计知识，使其能够参与有设计图、无设计图、部分设计图、继承已有项目设计等不同场景，同时不污染 PRD、不冒充 Design Truth、不和 Frontend Development Rules 混淆。**

目标结构：

```text
UI Design Material
设计规范物资
        ↓
Material Reconciliation
物资对账
        ↓
UI Design Rule Candidate
设计规则候选
        ↓
UI Design Rule Module
        ↓
UI Design Rule Entry
        ↓
后续由 UI Design Profile / Resolver
按任务选择适用规则
        ↓
Design Candidate / Design Decision
        ↓
Design Package
        ↓
UI_SPEC
```

---

# 2. 已有上游边界，本轮不能推翻

## 2.1 Engineering Standards 已经是独立治理语义域

F4 已冻结：

> Engineering Standards（工程规范）是独立治理语义域，并且没有新增 `StandardDefinition`。fileciteturn104file0L154-L170

因此本轮建议：

```text
UI Design Rules
Frontend Development Rules
```

都使用既有 Engineering Standards 治理能力。

但：

```text
共享治理能力
≠ 共用一套规则正文
```

---

## 2.2 Design Intelligence 必须保持 FACT / INFERENCE / RECOMMENDATION 分离

现有 Stage 09 已明确：

```text
Design Source = Evidence
Normalized Scene = Provider-neutral
Semantic = Inference
Implementation Suggestion = Recommendation
```

并且禁止把 `INFERENCE / RECOMMENDATION` 冒充 `FACT`。fileciteturn104file5L58-L96

因此 UI Design Rule 只能：

> 帮助形成设计判断。

不能：

> 把设计原则伪装成“设计图里本来就是这样”。

---

## 2.3 Legacy 已经证明 UI 不只存在“有设计图”一种模式

Legacy 支持：

```text
NONE
DESIGN_SYSTEM_ONLY
EXISTING_BASELINE_ONLY
STYLE_REFERENCE
STRUCTURE_REFERENCE
HYBRID
HIGH_FIDELITY
```

即 UI 约束来源可能是 Design System、现有项目基线、风格参考、结构参考、设计图或混合来源，而不是只有图片。fileciteturn88file1L395-L417

因此：

> **UI Design Rule System 必须同时服务“有图”和“无图”设计。**

---

# 3. UI Design Rule 的正式定位

定义：

> **UI Design Rule = 可复用、可治理、具有明确适用条件的 UI 设计知识，用来描述“一般情况下 UI 应该怎样设计，以及为什么”。**

主要回答：

```text
WHAT kind of design is appropriate?
什么样的设计通常合理？

WHY?
为什么？
```

而不是：

```text
HOW to code it?
具体怎么写 CSS / React / Vue？
```

---

# 4. UI Design Rule 与 Frontend Rule 必须独立

这是本轮最重要边界之一。

```text
UI Design Rule System
UI 设计规则体系

≠

Frontend Development Rule System
前端开发规则体系
```

例如：

### UI Design Rule

> 主操作应与次操作形成可识别的视觉层级。

这是设计原则。

### Frontend Rule

> 当前组件体系中主操作使用 Primary 类型组件。

这是工程实现规则。

再例如：

### UI Design Rule

> 当前选中项应该与未选中项形成清楚、稳定的状态差异。

### Frontend Rule

> 胶囊底部三角可通过伪元素实现。

两者不能进入同一个 Rule Entry。

---

# 5. UI Design Rule System 使用 Module → Entry

正式逻辑结构：

```text
UI Design Rule System
│
├── UI Design Rule Module
│   │
│   ├── Design Rule Entry
│   ├── Design Rule Entry
│   └── ...
│
├── UI Design Rule Module
│   └── ...
│
└── ...
```

基本原则：

> **先是一类完整设计知识 Module，Module 内才是一笔一笔 Rule Entry。**

---

# 6. Module 分类不能被 Core 写死

当前不要冻结：

```text
按钮模块
表格模块
移动端模块
后台模块
导航模块
```

为固定系统分类。

这些都只能作为未来例子。

正式 Module 必须通过：

```text
真实设计物资
↓
长期盘点
↓
规则提取
↓
聚类
↓
职责边界判断
↓
Module Candidate
```

逐步形成。

---

# 7. Module 粒度继续遵循“最小完整知识责任边界”

禁止两个极端。

### 极端 A

```text
UI Design Rules
```

一个超级 Module 什么都装。

### 极端 B

```text
Button Color Module
Button Radius Module
Button Padding Module
Triangle Module
Shadow Module
```

产生模块爆炸。

正确原则：

> **一个 Module 应代表一类稳定、相对完整、可以独立维护和选择使用的设计知识。**

---

# 8. Design Rule Entry 也采用最小完整设计原则

例如：

> “主操作与次操作必须具备清晰且稳定的视觉层级。”

可以是一条完整规则。

其中可以包含：

```text
Rule Body
正式设计原则

Rationale
为什么

Applicability
什么情况下适用

Exception
什么情况下例外

Examples
设计示例

Anti-patterns
错误设计

Source Evidence
来源
```

但不要机械拆成：

```text
主按钮颜色一条
主按钮位置一条
主按钮字体一条
主按钮圆角一条
```

除非这些内容本身具有独立的完整设计语义。

---

# 9. Design Rule Entry 不能变成 Implementation Rule

UI Design Rule 正文中禁止把以下内容作为核心规范语义：

```text
display:flex
grid-template-columns
::after
React Hook
Vue Composition API
Ant Design API
Element Plus prop
CSS class
Tailwind class
```

这些应该路由到：

```text
Frontend Development Rule System
```

设计规则可以包含视觉示例，但：

```text
Visual Example
≠ Implementation Prescription
```

---

# 10. 同一份 Material 可以包含多种语义

这是实际最常见的情况。

例如用户投：

> 《某 UI / Component Design Guidelines》

里面可能同时包含：

```text
设计原则
组件视觉规范
设计示例
品牌规则
设计系统 Token
组件 API
CSS 实现
React 示例
版本兼容说明
```

Banyan 必须：

```text
One Physical Material
        ↓
Semantic Extraction
        ├── UI Design Rule Candidate
        ├── Frontend Rule Candidate
        ├── Shared Foundation Candidate
        ├── Project-specific Design Constraint
        ├── Example
        └── Evidence
```

不能因为一个文件属于“UI 资料”：

> 全部强制放进 Design Rule Store。

---

# 11. 原始 Material 只保存一份

继续继承 D01：

```text
One Physical Source
→ Multiple Semantic Views / Candidates
```

不能：

```text
design-rules/material-a.pdf

frontend-rules/material-a-copy.pdf

foundation/material-a-copy2.pdf
```

制造多份源物资。

语义归属通过：

```text
ID
Reference
Trace
```

表达。

---

# 12. UI Design Rule ≠ Design Evidence

例如 Rule：

> 数据密集页面通常需要清楚的信息层级和扫描路径。

不能据此声称：

> “用户上传的设计图确认顶部高度 64px。”

因此：

```text
Design Rule
≠ Evidence
```

Rule 是知识。

Evidence 是来源事实。

---

# 13. UI Design Rule ≠ Design Truth

例如：

> Tabs 通常应该有明确选中状态。

是一条一般规则。

但具体项目最终可能：

```text
Underline
Capsule
Background
Side Indicator
```

任何一种。

因此：

```text
General Design Rule
≠ Concrete Design Truth
```

---

# 14. UI Design Rule ≠ Design Package

Design Package 回答：

> **这个具体页面最终应该是什么样。**

UI Design Rule 回答：

> **一般设计原则是什么。**

关系：

```text
UI Design Rules
        ↓
帮助形成
        ↓
Design Decisions
        ↓
Design Package
```

而不是：

```text
UI Design Rules
=
Design Package
```

---

# 15. UI Design Rule ≠ UI_SPEC

UI_SPEC 是：

> **批准后的 UI Construction Contract（施工 UI 契约）。**

即使某条 UI Design Rule 很成熟：

```text
Rule exists
```

也不等于：

```text
当前页面已经采用它
```

更不等于：

```text
UI_SPEC 已批准它
```

---

# 16. UI Design Rule ≠ User Design Constraint

这是必须防 AI 误判的边界。

UDC：

> 用户明确要求的具体设计约束事实。

UI Design Rule：

> 通用、可复用设计知识。

例如：

```text
UI Rule：
一级导航通常保持稳定位置，避免无理由频繁变化。
```

用户明确：

> “这个项目一级导航必须左侧纵向。”

那么：

```text
UDC owns:
用户要求左侧纵向
```

UI Rule 不能：

> 因为通用规则推荐其他布局就自动改掉。

---

# 17. UDC 的 Canonical Fact 与最终 Design Package 仍然不同

继续保持 D01 边界：

```text
UDC
owns canonical user-expressed design constraint fact

Design Package
owns concrete page design target

UI_SPEC
owns approved construction contract
```

三者不能混为一个 Truth。

---

# 18. UI Design Rule ≠ Shared Foundation

这是另一个非常容易混淆的地方。

### Shared Foundation

表示：

> **当前项目已经确认的共享设计 WHAT。**

例如：

```text
品牌主色
项目公共视觉密度
项目统一圆角语言
项目统一页面骨架
项目导航体系
```

### UI Design Rule

表示：

> **一般情况下为什么、怎样设计更合理。**

因此：

```text
Shared Foundation
= Project-specific confirmed WHAT

UI Design Rule
= Reusable general SHOULD / WHY
```

---

# 19. UI Design Rule 不能覆盖 Shared Foundation

假设公共 UI Rule：

> 企业后台通常建议较克制的视觉色彩。

但当前品牌 Foundation 明确：

> 品牌主色是高饱和橙色。

不能：

```text
公共规则说克制
↓
AI 把品牌色改灰
```

正确：

```text
Foundation
= 当前项目明确设计事实

Design Rule
= 提供一般指导
```

如果真的出现重大冲突：

```text
Conflict / Recommendation
```

而不是自动覆盖。

---

# 20. UI Design Rule 绝不能修改 PRD Product Semantics

这是一条硬边界。

例如 UI Rule：

> 减少过多操作可以降低视觉复杂度。

PRD 要求：

```text
新增
编辑
批量删除
导入
导出
同步
```

AI 不能：

> “设计应该简洁，所以删掉导入、导出。”

因此：

```text
Design Simplification
MUST NOT
delete / change Product Capability
```

需要优化视觉，可以：

```text
分组
折叠
层级组织
More menu
```

但不能改变 Product Semantics。

---

# 21. UI Design Rule 可以参与 Design Formation

UI Design Rule 和 Frontend Rule 的一个核心不同：

Frontend Rule 通常在：

```text
设计目标已经存在
↓
帮助实现
```

UI Design Rule 可以在：

```text
设计目标还没有完全形成
↓
帮助产生合理 Design Decision
```

因此：

```text
PRD
+
UDC
+
Shared Foundation
+
Applicable UI Design Rules
↓
Design Candidate
```

是合法的。

---

# 22. 无图情况下同样可以形成高质量 Design Package

继续冻结 D01 的修正：

```text
No Image
≠ Low Quality
≠ Low Completeness
≠ Low Authority
```

只要存在充分的：

```text
PRD
UDC
Shared Foundation
Applicable UI Design Rules
Human Decisions
或 Governed Autonomous Decisions
```

完全可以产生：

> **描述 / 规则驱动的高质量 Design Package。**

Legacy 的不同 UI constraint mode 也支持这种非纯图片驱动的设计方式。fileciteturn88file1L395-L417

---

# 23. 但无图绝不能变成“AI 精确值幻觉”

例如 UI Rule：

> 页面内容需要适当留白。

不能直接变成：

```text
padding = 23px
```

然后标：

```text
FACT
```

如果具体 23px 不是来自：

```text
Design Evidence
UDC
Shared Foundation
Design System
已批准 Design Decision
```

那么必须属于：

```text
RECOMMENDATION
或者
AUTONOMOUS_DESIGN_DECISION
```

而不是“观察事实”。

---

# 24. Design Decision 必须保留 Origin

这是本轮建议新增的核心语义之一。

具体 Design Package 中的设计决定至少在逻辑上能够区分：

```text
SOURCE_EVIDENCE
来源设计证据

HUMAN_CONSTRAINT
用户明确设计约束

FOUNDATION_INHERITANCE
项目 Shared Foundation 继承

RULE_DERIVED
依据 UI Design Rule 形成

AUTONOMOUS_DESIGN_DECISION
AI 在授权边界内自主决定

UNKNOWN
当前无法确认
```

最终枚举名留到 Implementation Freeze。

但：

> **“Design Decision 必须知道来自哪里”这一原则现在冻结。**

---

# 25. Rule-derived 不能伪装成 Human Constraint

例如：

AI 根据规则决定：

> 这个页面主按钮放在右上角比较合理。

必须：

```text
origin = RULE_DERIVED
```

不能：

```text
origin = HUMAN_CONSTRAINT
```

更不能说：

> “用户要求右上角。”

---

# 26. Autonomous Design Decision 也必须独立

根据刚冻结的：

```text
CROSS-STAGE-AUTONOMY-01
Bounded Autonomous Resolution
```

如果 Design Rule 无法唯一确定方案：

```text
Underline
Capsule
Background
```

AI 可以在允许的情况下结合：

```text
当前项目 Foundation
现有页面风格
当前 Project Context
Applicable UI Rules
现代成熟设计实践
可访问性
一致性
可验证性
```

自动选择。

但是结果必须：

```text
AUTONOMOUS_DESIGN_DECISION
```

不能冒充：

```text
SOURCE_EVIDENCE
HUMAN_CONSTRAINT
```

---

# 27. 哪些设计歧义适合自动裁决

例如：

```text
多个方案都满足 PRD
不违反 UDC
不违反 Foundation
不违反 UI_SPEC
不改变产品能力
风险低
可逆
可以视觉验证

```

可以：

```text
AUTO_RESOLVE
```

# 28. 哪些设计歧义不能自动裁决

例如涉及：

```text
资金相关 UX

不可逆行为
明确 Human Constraint 冲突
```

```text
或

```

# 33. 设计物资需要先判断“这是设计规则还是设计事实”

例如：

> “本项目首页统一使用 16px 圆角。”


```text
Global UI Design Rule
```

# 34. 设计规则来源不能决定规则 Authority

例如：


```text

```

# 35. Design Rule Strength 可复用 D02-02

UI Design Rule 也允许：

```text
REQUIRED
FORBIDDEN
RECOMMENDED
OPTIONAL
```

```text

关键交互状态必须具有可识别反馈。

FORBIDDEN：
不得只靠颜色区分关键错误状态。

RECOMMENDED：
数据密集表格应保持稳定扫描路径。

OPTIONAL：
当前视觉风格可使用轻量阴影增强层次。
```

但具体规则是否适用，仍需要：

```text
Scope
Applicability
Authority
Override Policy
```

共同判断。


不能因为官方示例：

> Project A 所有 Card 都强制 12px。

除非：

```text
项目正式采用该 Design System
+
相应规则适用
+
没有 Project Override
```

---

# 41. UI Design Rule 支持 Cross-Project Reuse

规则可以：

```text
Shared Reusable Rule
```

也可以：

```text
Project-specific Design Rule
```

项目中发现高价值通用设计原则时：

```text
Project Rule
↓
Reusable Candidate
↓
Governed Reconciliation
↓
Shared UI Design Rule
```

不能静默晋升。

---

# 42. 晋升后不能形成双真源

如果 Project A 的某条规则已经正式晋升为 Shared Rule：

项目应该：

```text
reference Shared Rule
```

而不是：

```text
Project Editable Copy
+
Shared Editable Copy
```

一起维护。

# 43. UI Design Profile 的存在在 D02-07 只冻结“角色”

本轮确认：

```text
UI Design Profile
```

未来负责：

> 当前项目选择哪些 UI Design Rule Modules / Rule Sets。

但是：

```text
Profile 如何解析
怎么绑定版本
怎么生成 Effective Design Rule Set
```

放到：

```text
F6-D02-08
```

本轮不抢后续职责。

---

# 44. UI Design Profile 与 Frontend Profile 独立

硬边界：

```text
UI Design Profile
≠
Frontend Profile
```

前者参与：

```text
Design Formation
```

后者参与：

```text
Implementation Formation
```

---

# 45. 二者允许关联，但不能互相污染

例如 Project Frontend Profile 显示：

> 当前采用 Ant Design。

这可以成为：

```text
Implementation Context
```

但不能自动：

> “所以所有设计必须完全长成 Ant Design 默认样式。”

除非项目另有正式 Design Constraint。

---

# 46. Implementation Convenience 不得反向重定义 Design Truth

这是必须冻结的硬规则。

禁止：

```text
这个组件库做 A 很方便
↓
所以设计应该改成 A
```

除非：

```text
组件体系限制本身
已经被治理成明确 Design Constraint
```

否则 Implementation 只能：

```text
提出 Deviation / Recommendation
```

不能改 Design Truth。

这也与已有 Stage 09 的 `Implementation Suggestion = Recommendation` 保持一致。fileciteturn104file5L70-L96

---

# 47. Design Rule 不能制造不存在的 Interaction

例如静态设计规范只说：

> Hover 时应有反馈。

如果当前设备：

```text
Mobile Touch
```

AI 不能机械造：

```text
Hover Interaction
```

必须结合：

```text
Platform
Input Mode
Device
Context
```

Applicability 判断。

---

# 48. Design Rule 不能制造不存在的业务状态

比如 Design Rule 说：

> Error State 应明确展示。

它不能因此创建：

```text
支付失败状态
审核拒绝状态
库存冻结状态
```

这些属于产品/业务状态。

Design Rule 只能说：

> **如果业务存在 Error State，应怎样设计表达。**

---

# 49. Rule 与 Product Capability 的关系必须单向安全

正确：

```text
PRD：
存在批量删除
↓
Design Rule：
危险批量操作应该具备清晰风险表达
↓
Design Decision
```

错误：

```text
Design Rule：
危险操作应该有确认
↓
AI 自己发明一个“批量删除”功能
```

---

# 50. UNKNOWN 必须继续保持 UNKNOWN

如果某个 UI Rule 需要：

```text
目标设备
目标用户
交互模式
```

但当前材料不知道。

则：

```text
UNKNOWN
```

不能为了“设计完整”自动编。

---

# 51. Rule-derived Design 可以是高质量正式 Design Package 的组成

但要区分：

```text
Design Package
内部目标可以很明确
```

和：

```text
每个决定的来源
```

即：

> Design Package 可以最终非常完整，但内部仍能知道“这个决定是 Evidence、Human、Foundation、Rule-derived 还是 Autonomous”。

这使“高质量”和“诚实来源”可以同时成立。

# 52. Design Rule System 的用户体验

用户未来理想操作应该非常简单：

> “这是第 5 批后台 UI 设计规范。”

或者：

> “按我的现有后台风格，帮我设计这个新页面。”

```text

↓

↓
对账已有规则
↓
读取项目 Foundation / Profile
↓
选择适用规则
↓
形成设计候选
```

而不是要求用户：

> 手动选择 RULE-009、RULE-017、MODULE-03。

# 53. 用户主要只看真正有意义的问题

例如最后系统判断：

```text
支持紧凑数据密度

新 Design Rule
建议更大留白

二者都合理，
但会改变整个后台视觉密度
```

这才是：

```text
Meaningful Design Trade-off
↓
Human Decision
```

普通无冲突规则自动处理。
