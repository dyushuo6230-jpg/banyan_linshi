# F6-D05 — Behavior × State × Interaction Evidence
## 行为、状态与交互证据治理

```text
Status = HUMAN_REVIEW
Implementation = NOT_AUTHORIZED
```

这一项要解决一个非常容易让 AI“脑补”的问题：

> **静态设计图只能告诉 Banyan“某一时刻长什么样”，并不能天然告诉 Banyan“用户点了以后发生什么、有哪些状态、状态怎么变化、弹窗怎么关闭、拖拽怎么工作”。**

Legacy 本身已经明确：设计图并不天然表达全部状态、全部交互、失败处理、空数据、动画或权限逻辑。fileciteturn123file5L69-L89

---

# 一、D05 最重要的总原则

建议先冻结一句：

> **Visible State ≠ Behavior ≠ Business State Transition。**

例如目标图里：

```text
按钮 = disabled 外观
```

最多可以证明：

```text
存在一个 Disabled UI State
```

不能自动推出：

```text
库存不足时 disabled
```

更不能推出：

```text
点击按钮 → submitOrder()
```

因为后两项已经涉及：

```text
Condition
Business Rule
Product Action
```

这不是一张静态图能够证明的。

Legacy 对 AnyDesign 也明确规定：识别到一个 Button，只能证明它是按钮，不能自动推出 `click → submitOrder`；业务行为必须来自其它有效来源。fileciteturn123file4L1241-L1261

---

# 二、D05 先把 6 种东西分开

我建议完整模型至少区分：

```text
State Evidence
状态证据

State Definition
UI 状态定义

Interaction Evidence
交互证据

Interaction Definition
交互定义

Transition / Motion
状态转换与动态表现

Behavior Model
当前 Design Target 的动态行为模型
```

它们不能全部塞进一个：

```text
state-map.json
```

然后让 AI 自己理解关系。

---

# 三、UI State 和 Product State 必须彻底分开

这是 D05 最关键的一条。

例如：

```text
Selected
Hover
Focus
Disabled
Expanded
Dragging
Open
```

通常属于：

```text
UI / Interaction State
```

而：

```text
ORDER_PENDING
ORDER_PAID
ORDER_CANCELLED
REFUNDING
```

属于：

```text
Product / Business State
```

不能合成一个大 State enum。

例如：

```text
订单状态 = CANCELLED
```

可能导致：

```text
按钮 UI state = disabled
```

关系是：

```text
Business State
     ↓ condition
UI State
```

而不是：

```text
Business State == UI State
```

---

# 四、同样还要区分 Data State

例如：

```text
Loading
Empty
Error
Success
```

看起来像 UI State。

实际上经常涉及：

```text
Data / Async State
```

比如：

```text
data.loading = true
        ↓
Page Visual State = Loading
```

所以未来 D06 负责数据语义。

D05 只定义：

> UI 如何表达这个状态，以及状态之间有哪些交互关系。

不能反过来定义 API 或业务数据状态。

---

# 五、Legacy 的状态清单保留，但不能写死

原规范已经要求动态组件至少考虑：

```text
Default
Hover
Active / Pressed
Selected
Focus
Disabled
Loading
Success
Error
Empty
```

并允许：

```text
Dragging
Drop Target
Uploading
Checked
Expanded
Collapsed
Open
Closed
Partial
Readonly
```

等状态。fileciteturn123file0L152-L172

这些价值全部保留。

但是不能做成：

```text
enum State {
  Default,
  Hover,
  ...
}
```

然后认为未来世界只有这些状态。

正确是：

```text
Common State Vocabulary
+
Extensible Domain States
```

因为未来可能出现：

```text
Recording
Playing
Syncing
Mentioned
Pinned
Comparing
Previewing
AIGenerating
```

不应该修改 Core 才能加入。

---

# 六、State Definition 的正确粒度

一个 State 不应该只存：

```text
name = selected
```

逻辑上至少要能够回答：

```text
属于谁？
什么时候成立？
相对哪个默认状态？
视觉有什么不同？
交互能力有什么不同？
可以从哪里进入？
可以去哪里？
是否有证据？
来源是什么？
```

例如：

```text
SecondaryCategory
State = SELECTED

visual:
  capsule background
  bottom triangle
  highlighted text

origin:
  TARGET_DESIGN_EVIDENCE
```

这个就很明确。

---

# 七、State Evidence 和 State Definition 不能混

例如用户给：

```text
default.png
selected.png
```

这两张图提供：

```text
State Evidence
```

经过解析才能形成：

```text
Selected State Definition
```

所以：

```text
Image State Evidence
≠ State Definition automatically
```

---

# 八、一个静态图只能证明“这个状态存在过”

例如截图显示：

```text
Modal = open
```

它可以证明：

```text
OPEN state visual evidence
```

但不能证明：

```text
谁打开它？
点击什么打开？
Escape 是否关闭？
点击 Mask 是否关闭？
关闭后回到哪里？
```

这些必须有额外 Evidence。

---

# 九、Interaction Evidence 可以来自哪些 Material

可以来自：

```text
交互原型
Figma Prototype
墨刀原型
视频 / 录屏
多状态设计稿
现有运行页面
UI_SPEC
用户明确说明
产品需求
测试用例
```

但它们的 Authority 不一样。

例如：

```text
Existing UI Recording
```

默认只能证明：

```text
Current Reality Behavior
```

不能自动证明：

```text
Target Behavior
```

---

# 十、Interaction Definition 必须结构化

Legacy 已经明确，不能只写：

> “点击后打开弹窗。”

应该描述：

```text
Trigger
Target
Condition
Action
State Change
Transition
Overlay
Close Rule
Error Rule
```

fileciteturn123file0L182-L202

这个模型非常值得保留。

我建议 D05 把它提升成正式架构语义。

---

# 十一、一个完整交互可以理解成

```text
Input / Trigger
      ↓
Condition
      ↓
Target
      ↓
UI Action
      ↓
State Transition
      ↓
Visual / Motion Response
      ↓
Post-condition
```

比如：

```text
Trigger:
点击“移动到”

Target:
MoveToModal

Condition:
至少选择一个资源

Action:
open modal

State Change:
modal.closed → modal.open

Overlay:
mask visible

Close:
cancel / close icon / successful completion
```

---

# 十二、但 Business Action 必须另行引用

例如：

```text
点击“删除”
```

不能在 D05 直接定义：

```text
delete resource from database
```

D05 可以定义：

```text
UI trigger = click delete
```

然后引用：

```text
Product Capability / Command / Requirement
```

后续成功可能导致：

```text
UI refresh
Toast success
Selection reset
```

所以建议关系：

```text
UI Interaction
        ↓
Product Action Reference
        ↓
Business execution
        ↓
Result / Data State
        ↓
UI State Response
```

而不是：

```text
Interaction Model
自己拥有 Business Logic
```

---

# 十三、PRD 继续拥有业务行为

例如 PRD 说：

> 用户具有权限时可以删除资源。

那么 D05 可以设计：

```text
Delete Interaction
```

但 D05 不能自己新增：

> “支持批量彻底删除并永久清除文件。”

如果 PRD 没有这个能力：

```text
Behavior Design
≠ Product Capability Creation
```

---

# 十四、状态视觉与状态触发条件也要分开

例如：

```text
Disabled visual:
opacity 0.4
cursor ...
```

属于：

```text
UI State Visual Design
```

但：

```text
disabled when user has no permission
```

牵涉：

```text
Product / Permission Condition
```

所以一个 State 可以：

```text
拥有 visual semantics
```

但它的 Condition 可以：

```text
reference upstream product semantics
```

不能自己发明。

---

# 十五、Gesture 只是 Interaction Input 的一种

Legacy 有：

```text
gesture-map.json
```

保留价值，但不要把 Gesture 做成平行世界。

更合理：

```text
Interaction Input
├── Mouse
├── Touch
├── Keyboard
├── Pointer
├── Gesture
├── Drag
└── Future Input
```

这样：

```text
Swipe
Pinch
Long Press
```

只是不同 Input semantics。

未来增加其它设备输入不用重构 Interaction Core。

---

# 十六、Keyboard / Accessibility 不能后补

例如一个 Menu 设计：

```text
Mouse click works
```

不意味着交互完整。

如果当前 Scope 有可访问性要求，还可能需要：

```text
Focus
Tab
Enter
Space
Arrow keys
Escape
```

因此：

> Interaction 不应只围绕 Click。

Legacy 的 Interaction Regression 也明确包含 Click、Hover、Focus、Selected、Modal、Drawer、Drag、Drop、Scroll、Upload、Keyboard、Escape 等检查。fileciteturn123file4L1150-L1170

---

# 十七、Hover 必须受 Device Applicability 限制

不能：

```text
所有 Component
必须有 Hover
```

移动触屏：

```text
hover may not apply
```

所以：

```text
State / Interaction
必须有 Applicability
```

例如：

```text
Hover
platform = pointer-capable
```

继续符合 D02 的 Scope / Applicability 原则。

---

# 十八、Responsive 不是“猜媒体查询”

D03 已经规定静态单 viewport 不足以证明 Responsive 行为。

如果用户给：

```text
1440 design
1024 design
768 design
375 design
```

这些可以形成：

```text
Responsive Behavior Evidence
```

比如：

```text
Sidebar visible → collapsed → hidden
```

但仍然只能先得到：

```text
Design behavior across viewports
```

不能直接推出：

```css
@media (max-width: 768px)
```

具体实现留 Implementation。

---

# 十九、Transition 要分“状态变化”和“动画表现”

例如：

```text
Closed → Open
```

是：

```text
State Transition
```

而：

```text
180ms ease-out
```

是：

```text
Motion / Animation Design
```

二者不同。

没有动画 Evidence：

```text
Transition exists
Motion = UNKNOWN
```

不能因为现代 UI 通常有动画就自己填 180ms。

---

# 二十、Motion 值也服从 D04 Token/Foundation

例如：

```text
duration.fast
easing.standard
```

未来可以成为 Design Token / Foundation。

D05 不再造：

```text
Animation Token System
```

只是引用 D04。

---

# 二十一、Overlay 是一种 UI Behavior，不是业务对象

Modal / Drawer / Popover 等经常涉及：

```text
open
close
mask
focus trap
escape
outside click
z-order
```

这些属于 UI 行为。

但例如：

> “关闭弹窗时是否丢弃草稿”

可能涉及业务语义。

所以必须拆：

```text
Close interaction
+
Product side effect
```

---

# 二十二、Interaction 不能靠组件类型自动生成业务行为

例如识别：

```text
Button
```

只可以使用 UI Design Rules 推荐：

```text
pressed feedback
focus indication
```

但不能：

```text
Button → submit
```

因为 Button 可能：

```text
打开 Modal
切换 Tab
下载
复制
返回
确认
提交
```

组件语义不是业务动作。

---

# 二十三、Design Rule 可以补“设计行为”，不能补“产品行为”

例如 UI Design Rule：

> “可点击元素应有明确 Hover / Focus feedback。”

如果当前设备适用、没有冲突：

可以帮助形成：

```text
Rule-derived UI Design Decision
```

但规则不能：

> “这个按钮点击后跳详情页。”

因为这是产品行为。

---

# 二十四、无交互证据时允许保持 UNKNOWN

例如只有一张资源管理弹窗图。

看到了：

```text
移动到
复制
删除
下载
```

不能直接生成所有：

```text
Confirmation flow
Permission check
Error handling
Success toast
Refresh rule
```

没有来源：

```text
UNKNOWN
```

后面由：

```text
PRD
UDC
Applicable Rules
Human Decision
Authorized Autonomy
```

逐步闭合。

---

# 二十五、Autonomy 只适合低风险 UI Micro-behavior

例如：

当前 Foundation 和规则已经明确：

```text
Hover 需要轻微背景反馈
```

具体两个视觉方案都合法：

```text
A / B
```

低风险、可逆、可视觉验证。

可以：

```text
AUTONOMOUS_DESIGN_DECISION
```

---

不能自主决定：

```text
删除是否需要二次确认
付款按钮点击是否直接扣款
关闭编辑弹窗是否丢弃内容
权限不足时隐藏还是禁用
保存失败是否自动重试
```

因为这些涉及：

```text
Product Semantics
Safety
Data
Permission
Irreversibility
```

---

# 二十六、Behavior Model 的正式定位

我建议定义：

> **Behavior Model = 当前具体 Design Target 中，经过 Evidence、PRD/UDC、Design Rules 和治理决策解析后的 UI State / Interaction / Transition 动态设计模型。**

它是：

```text
Design Package
```

中的动态语义部分。

而不是独立第二真源。

---

# 二十七、不要建立 behavior.yaml 与 Design Package 两个可编辑真源

正确：

```text
Design Package
├── Static Design Truth
├── Behavior Model
├── Token refs
├── Data refs
├── Evidence refs
└── Unknowns
```

可以物理投影成：

```text
state-map
interaction-map
gesture-map
```

但这些应该是：

```text
Structured Projection
```

不能每份都独立成为可编辑 Authority。

---

# 二十八、Behavior Model 和 UI_SPEC 的关系

同 D03 一样：

```text
Behavior Model
→ Design Package
→ UI Governance
→ UI_SPEC
```

Behavior Model 完整：

```text
≠ automatically approved
```

UI_SPEC 才是施工阶段 Current Effective UI Contract。

---

# 二十九、Partial Behavior 必须合法

例如用户只提供：

```text
Default
Selected
```

那么：

```text
Hover = UNKNOWN
Disabled = UNKNOWN
Loading = UNKNOWN
```

Design Package 可以：

```text
PARTIAL
```

而不是为了“完整”强行补全所有状态。

---

# 三十、但“需要考虑状态”不等于“必须创造状态”

Legacy 说所有动态组件应考虑 Default/Hover/Disabled/Loading 等状态，正确理解应该是：

> **检查 Applicability 和 Coverage。**

不是：

> 所有组件必须拥有这些全部状态。

例如：

```text
Static Logo
```

就没必要：

```text
Loading
Selected
Dragging
```

所以未来：

```text
State Coverage Check
```

应该是：

```text
Applicable?
Evidence?
Defined?
Unknown?
Not Applicable?
```

而不是机械生成。

---

# 三十一、需要 State Coverage Gap

例如：

```text
Button is interactive
Desktop scope
```

但：

```text
Focus State = missing
```

如果项目 Accessibility Rule 要求必须定义 Focus：

应该产生：

```text
BEHAVIOR_COVERAGE_GAP
```

而不是静默继续。

---

# 三十二、Coverage Gap 继续复用已有治理

和 D02 Closure 一样：

```text
D05
发现 Behavior / State Gap
```

不再造：

```text
BehaviorMissingDecisionEngine
```

它应该进入已有：

```text
Gap / Decision Routing
```

普通低风险可自动完成。

高影响或产品语义相关：

```text
Decision Required
```

---

# 三十三、多来源 Behavior 也先按 Scope 对账

例如：

```text
Figma prototype:
mask click closes modal

User requirement:
mask click must NOT close modal
```

不能多数投票。

要看：

```text
Authority
Current Effective
Intent
Scope
Version
```

如果用户约束有效：

```text
UDC
```

则旧 Prototype 不应覆盖。

---

# 三十四、Existing UI Behavior 默认是 Current Reality Evidence

例如现在系统：

```text
删除没有确认
```

不能推出：

```text
Target Design
= 删除无需确认
```

除非：

```text
Existing baseline explicitly adopted
```

否则它只是：

```text
Current Reality
```

---

# 三十五、Behavior Drift 可以提前保留语义

以后 Implementation 出来：

```text
Target:
Escape closes modal

Reality:
Escape does nothing
```

这是：

```text
Behavior Drift
```

不是：

```text
Design Conflict
```

因为 Target 和 Reality 角色不同。

真正 Drift 检测和 Repair 在后续 D09/D10。

---

# 三十六、Interaction Validation 必须来源于 Behavior Model

后续测试不能凭 Coding Agent 自己想：

```text
我要测什么？
```

应该：

```text
Behavior Model / UI_SPEC
        ↓
Validation Requirements
        ↓
Interaction Regression
```

因此 D05 要把：

```text
Testable Expected Behavior
```

作为逻辑能力保留下来。

但具体 Test DSL 后面实现。

---

# 三十七、每个关键行为都应该能追到 Origin

例如：

```text
Escape closes modal
```

来源可能：

```text
SOURCE_EVIDENCE
HUMAN_CONSTRAINT
PRODUCT_REQUIREMENT
FOUNDATION
RULE_DERIVED
AUTONOMOUS_DESIGN_DECISION
```

必须保留。

否则以后无法判断：

> 为什么这个行为存在？

---

# 三十八、Behavior Revision 也不能静默

例如：

```text
Before:
mask click closes modal

After:
mask click does not close modal
```

这是设计行为变化。

应该：

```text
Design Package Revision
↓
Impact
↓
UI_SPEC Review
↓
Implementation Review
```

不能只改一个 `interaction-map.json`。

---

# 三十九、Behavior Model 必须保持可扩展

现在可能是：

```text
Mouse
Keyboard
Touch
Drag
Scroll
Modal
```

未来可能：

```text
Voice
Stylus
Spatial/XR input
Gamepad
AI assisted interaction
```

Core 应该认识：

```text
Interaction Input / Trigger Contract
```

而不是写死所有设备。

---

# 四十、也不能为了扩展过度抽象

当前不需要设计：

```text
Universal Human Computer Interaction Ontology
```

只需要稳定：

```text

Trigger
Condition
Target
Action
Transition
Response
Evidence
```

这些核心语义。

# 四十二、建议 D05 正式冻结 BI-01 ～ BI-30

```text
BI-01
UI State、Data State、Product/Business State、
Runtime State 必须保持不同语义域，
不得合并成一个全局 State enum。

BI-02
Static Design Source 只能证明其明确展示的
State / Visual Evidence，
不得自动证明完整 Behavior。

BI-03
State Evidence 与 State Definition 必须分离；
观察到某状态不等于已知道其 Trigger / Condition / Transition。

BI-04
Common UI State Vocabulary 可以复用，
但 State taxonomy 必须允许扩展，
Core 不得写死有限状态全集。

BI-05
State Definition 必须具有明确 Owner/Target、
Scope/Applicability，并可关联 Visual Semantics、
Conditions、Transitions、Evidence 与 Origin。

BI-06
Interaction Evidence 可以来自 Prototype、
Recording、Multi-state Design、Existing UI、
UI_SPEC、Human Input 等，
但不同 Source 的 Authority/Intent 必须保留。

BI-07
Interaction Definition 必须能够表达
Trigger、Target、Condition、Action、
State Change、Transition、Overlay、
Close/Error 等适用语义；
精确 Schema 后续冻结。

BI-08
UI Interaction 不得拥有 Product Business Logic。
涉及 Capability、Permission、Money、Data Mutation、
Business State 的 Action 必须引用上游 Product Semantics。

BI-09
识别出 Component/Button 不得自动推导其 Business Action。

BI-10
UI State Visual Semantics 与 State Activation Condition
必须分离；
视觉设计不得发明业务条件。

BI-11
Input/Gesture 是 Interaction Trigger 的一种，
不得建立与 Interaction Model 竞争的独立行为真源。

BI-12
Mouse、Touch、Keyboard、Pointer、Gesture 等
必须通过 Applicability 约束；
例如 Hover 不得默认适用于所有设备。

BI-13
Responsive Design Behavior
只有在足够多 Viewport/Device Evidence
或明确 Design Decision 下才可形成；
不得由单一静态图自动推断。

BI-14
State Transition 与 Motion/Animation
必须保持不同语义；
Transition 存在不代表动画参数已知。

BI-15
Motion Design 可以引用 D04 Token/Foundation，
D05 不建立第二 Animation Token System。

BI-16
UI Design Rule 可以补充 UI-level Behavior Design，
但不得创造 Product Behavior。

BI-17
没有 Behavior Evidence / Product Semantics /
Human Constraint 时必须允许 UNKNOWN，
不得为完整性自由脑补。

BI-18
低风险、局部、可逆、可验证的 UI Micro-behavior
可在 CROSS-STAGE-AUTONOMY-01 资格满足时
形成 Autonomous Design Decision。

BI-19
Autonomy 不得决定资金、权限、数据破坏、
不可逆操作、业务流程、产品状态或其它高风险行为。

BI-20
Behavior Model 表达当前 Design Target 的
UI State / Interaction / Transition 动态设计语义，
属于 Design Package 的组成部分。

BI-21
Behavior Model / State Map / Interaction Map /
Gesture Map 不得形成多个 competing canonical truths；
物理文件只能是同一 Design Package 语义的结构化投影。

BI-22
Behavior Model 不得自动升级为 Approved UI_SPEC；
仍须经过 UI Governance。

BI-23
Partial Behavior Definition 是合法状态；
Missing State 不得因为“完整性”伪装成 Confirmed。

BI-24
State Coverage 必须基于 Applicability 判断，
不得机械要求所有组件拥有全部 Common States。

BI-25
Applicable Mandatory Behavior/Accessibility State 缺失时
必须产生 explicit Behavior Coverage Gap，
不得静默忽略。

BI-26
Behavior Coverage Gap 必须复用现有
Gap / Missing Standard / Decision Routing，
不得创建第二 Decision Engine。

BI-27
多 Behavior Source 冲突必须按
Scope / Intent / Authority / Version /
Current Effective 进行 Reconciliation，
不得 Latest/Majority/Provider-wins。

BI-28
Existing UI Behavior 默认属于 Current Reality Evidence，
不得自动成为 Desired Target Behavior。

BI-29
Behavior Revision 必须版本化、可追踪并进入 Impact；
不得通过直接编辑 projection 静默改变 Design Target。

BI-30
Behavior Provider、Prototype Adapter、
State/Interaction Interpreter 必须保持可替换 Contract；
当前不实现 AI Autonomous Behavior Learning /
Autonomous Interaction Rule Promotion。
```
