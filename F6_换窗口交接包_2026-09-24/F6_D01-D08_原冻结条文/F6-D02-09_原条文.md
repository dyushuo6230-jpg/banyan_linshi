# F6-D02-09
## Design → Implementation Semantic Bridge × Effective Implementation Context
### 设计 → 实现语义桥 × 当前有效实现上下文

这次我把刚才“以后容易修改”的要求一起合并进去，给出一套可以确认的完整版本。

---

# 1. D02-09 到底解决什么

前面已经形成两套彼此独立的体系：

```text
设计侧

UI Design Rules
↓
UI Design Profile
↓
Effective Design Context
↓
Design Package
↓
UI_SPEC
```

以及：

```text
实现侧

Frontend Rules
↓
Frontend Profile
↓
Effective Frontend Rule Set
```

现在真正缺的是：

```text
已经批准的设计
怎么安全、准确、高效地
转换成“前端工程要解决什么”
并最终形成 Coding Agent 能直接消费的上下文？
```

所以 D02-09 不是把两套规则合并。

而是建立：

```text
Design Semantic
        ↓
Implementation Semantic Bridge
        ↓
Implementation Needs
        ↓
Frontend Rule Resolution
        ↓
Implementation Context Compilation
        ↓
Effective Implementation Context
```

---

# 2. 第一条硬边界：桥接的是“语义”，不是规则正文

禁止：

```text
Design Rule DR-017
↓
复制
↓
Frontend Rule FR-022
```

也禁止：

```text
UI Design Module
extends
Frontend Module
```

正确是：

```text
设计已经确定：
“选中项具有胶囊背景 + 底部三角”

        ↓

转换成工程需求：
“需要状态驱动视觉变化”
“需要附着式装饰指示器”
“需要稳定的父子定位关系”

        ↓

Frontend Rule Resolver 再决定：
pseudo-element？
DOM decoration？
SVG？
```

因此：

> **Bridge 只负责翻译“工程必须达到什么”，不直接决定“代码怎么写”。**

---

# 3. 建立 Implementation Semantic Need

建议增加一个逻辑对象：

```text
Implementation Semantic Need
实现需求语义
```

它不是新的 Canonical Truth。

它只是从当前有效 Design / UI Contract 派生出来的工程问题描述。

例如：

```text
Design:
横向分类两侧有渐隐遮罩

↓

Implementation Needs:
- horizontal overflow awareness
- edge content visibility hint
- left/right edge mask
- state depending on overflow position
```

注意这里仍然没有：

```text
::before
mask-image
linear-gradient
React state
```

因为这些是 HOW。

---

# 4. 正式形成四层语义边界

建议冻结：

```text
Design Target
WHAT SHOULD THE USER SEE

↓

Implementation Semantic Need
WHAT ENGINEERING MUST ACHIEVE

↓

Frontend Rule / Engineering Resolution
HOW IT SHOULD GENERALLY BE ACHIEVED

↓

Implementation Decision
HOW THIS PROJECT / TASK WILL ACTUALLY DO IT
```

这四层不能混。

# 5. Coding 阶段真正的核心 Authority

Coding Agent 正常情况下消费：

```text
Current Effective PRD
+
Current Effective UI_SPEC
+
Effective Frontend Rules
+
Technical / Code Context
```

而不是重新去读：

```text
原始聊天
全部 UDC
全部设计物资
全部设计规则
所有历史设计版本
```

Stage 08 已经明确设计图、AnyDesign、Figma、截图、原型属于 Design Evidence，不自动成为 Product Requirement。fileciteturn106file4L213-L233

因此进入施工以后：

> 上游已经治理好的设计语义，应通过 UI_SPEC / 关联 Design Package 传下来。

不能让 Coding Agent 重新建一套设计 Authority。

---

# 6. Design Package 和 UI_SPEC 的关系

这里继续区分：

```text
Design Package
= 具体设计目标的结构化表达

UI_SPEC
= 已批准的施工 UI Contract
```

Coding 可以根据 UI_SPEC 的引用读取 Design Package 中的：

```text
结构
状态
视觉细节
验证基线
```

但如果出现：

```text
Design Package A
和
Current Effective UI_SPEC B
```

不一致：

> 不能让 Coding Agent 自己选一个“看起来更新的”。

必须进入：

```text
Freshness / Conflict Resolution
```

因为 Latest 不等于 Current Effective。

---

# 7. Current Code 进入上下文，但只是 Evidence

当前代码很有价值。

它可以告诉系统：

```text
当前使用 React / Vue
当前组件库
已有项目封装组件
已有 layout pattern
已有 CSS 习惯
兼容约束
迁移成本
```

但：

```text
Current Code
≠ Frontend Rule
≠ Design Truth
≠ UI_SPEC
```

例如项目旧代码全部：

```css
position: absolute;
```

不能推出：

> Banyan Frontend Rule = “布局统一 absolute”。

代码只能作为 Reality Evidence。

# 11. 仍然坚持 Minimum Sufficient Context

例如只修：

> 分类栏选中态。

Coding Agent 不需要知道整个商城：

```text

```

应该只拿：

```text
当前 Scope

相关 Implementation Needs
相关 Frontend Rules
相关代码
必要底线规则
```

也就是：

```text
Minimum Sufficient Implementation Context
```

# 12. 但 Mandatory Context 不能被省略

比如任务表面只是：

> 改一个按钮样式。

但它是：

```text
删除按钮
```

那么危险操作相关 Mandatory Rule 必须进入 Context。

继续遵守：

```text

```

# 13. Implementation Resolver 和 Compiler 必须分开

和 D02-08 一样：

```text
Resolver
= 判

Compiler
= 组装

Coding Agent
= 写

Adapter
= 技术栈翻译
```

不能让 Compiler 再造一套 Rule Priority。

也不能让 Coding Agent自己重新解析 Authority。

# 14. Framework Adapter 继续保持窄职责

已有 Implementation 规范明确要求 Core IR 保持 Framework-neutral，不能把 JSX、Vue Template、Ant Design API、Element Plus API、Tailwind class 写进 Core IR；具体框架写法进入 Adapter。fileciteturn108file5

因此：

```text
Implementation Semantic
↓
Implementation Decision
↓
Framework Adapter
↓
React / Vue / Other
```

Adapter 负责翻译。

不负责重新设计。

---

# 15. Adapter 不得偷偷修改设计

例如：

```text
UI_SPEC：
必须有底部三角

没有直接现成组件
```

错误：

```text
那就不做三角
```

正确：

```text
自定义实现
或者
报告 Feasibility / Deviation Issue
```

Adapter 没有：

```text
Design Mutation Authority
```

# 16. Implementation Convenience 不得反向污染 Design

这是 D02-09 的重要硬规则：

```text
“这个组件库方便这样做”
≠
“所以设计应该改成这样”
```

如果实现确实困难：

```text
Implementation Constraint
↓
Feasibility Issue
↓
Deviation Candidate
↓
Design/UI Change Governance
```

而不是静默改变。

---

# 17. Deviation 必须显式

例如目标：

```text
gap = 某视觉目标
```

实际受当前组件约束只能做到另一种效果。

必须形成：

```text
Expected
Actual
Reason
Impact
Approved?
```

不能：

> 实现出来不一样，然后告诉系统“已经还原”。

已有 Implementation 规范也坚持 Scene / Implementation 分离，并要求实现偏差不能冒充设计事实。fileciteturn108file0

# 18. 哪些实现选择适合 Autonomy

```text

可逆

可验证
```

那么：

```text

→ AUTO_RESOLVE
```

非常适合。

# 23. 以后更换 Context 算法也不推翻架构

# 25. 默认归属策略：Project First

当前阶段我建议冻结：

> **新增加的、来自项目实际开发反馈的 Frontend Rule，默认先进入 Project Instance 治理范围，而不是直接进入 Shared Framework。**

理由：

```text
Project Rule 放局部
→ 以后可推广

Framework Rule 放错
→ 会污染所有项目
```

因此默认：

```text
.banyan / Project-specific Rule
```

更安全。

# 27. 什么时候可以成为 Reusable Candidate

