# Stage 00：改造安全基线与仓库保护

> 适用总纲：`榕树AI多编辑器AI软件工程框架改造总纲指导方案_v1.9.1.md`  
> 总纲状态：`FINAL_FREEZE`  
> Stage Pack 版本：`1.9.1`  
> 阶段性质：**安全基线阶段，不是迁移阶段，不是架构实现阶段**。  
> 主要执行器：Codex 可作为 `TRANSFORMATION_EXECUTOR` 读取真实 Repository 执行本 Stage。  
> 重要：Stage 18 的 `Banyan Codex Runtime Adapter` 与本次施工所用 Codex 不是同一层，不构成前置依赖。

---

# 1. 阶段唯一目标

Stage 00 只回答：

> **在任何 Banyan 改造发生之前，当前 Repository 到底处于什么真实状态；哪些东西绝不能误碰；当前未提交现场是否可以恢复；后续 Stage 可以信任哪些安全边界和 Evidence。**

本阶段必须建立并验证五类基础能力：

```text
Repository Baseline
Protected Paths
Discovery Scope Baseline
Checkpoint / Rollback Control
Bootstrap Refactor State / Trace
```

任何后续 Stage 均不得绕过 Stage 00 的真实 Acceptance。

---

# 2. 本阶段明确不做

Stage 00 **不做**：

- 不设计 Banyan Core；
- 不创建正式 Project Instance；
- 不提前创建正式 `.banyan/migrations` Canonical State；
- 不迁移 v3.1；
- 不改 Prompt / Rules / Skills；
- 不改 PRD / DEC / ADR / CR / UI_SPEC；
- 不改 Project Guide；
- 不改业务代码；
- 不改 SQL / migration；
- 不安装或接入 OpenSpec；
- 不初始化 SQLite Index；
- 不创建 Cursor / Codex / Claude Adapter；
- 不执行 AI Asset Inventory（那是 Stage 01）；
- 不清理 Legacy；
- 不整理、重命名或移动业务目录；
- 不自动 stash / commit / reset / clean；
- 不为了隐藏 Control Root 修改 `.gitignore`；
- 不修改 `git user.name / user.email`；
- 不使用 `--author` 或临时 identity 覆盖；
- 不读取、复制或回显 Secret 原值。

如果发现这些工作“顺手可以做”，也必须保持 Stage 00 边界。

# 3. 真实输入原则

本阶段不要求用户重新整理项目资料。

执行器直接从真实 Repository 发现：

```text
Repository Root
Current Branch / HEAD
Working Tree
Tracked / Untracked / Ignored State
Nested Repository / Worktree / Submodule
Sparse Checkout / LFS（若存在）
AI / Docs / Tools / Editor Roots
Governance Roots
Potential Secret Roots
Generated / Cache / Vendor Roots
```

总纲和已知项目事实只能作为 Seed。

> **真实 Repository 当前状态始终高于历史描述。**

# 4. Bootstrap Control Root

Stage 02/04 才会冻结最终 Framework Distribution / Project Instance / Source Mapping 相关物理边界，因此 Stage 00 不得把临时施工目录冒充最终架构。

统一变量：

```text
REPO_ROOT
REFRACTOR_CONTROL_ROOT
STAGE_ROOT
RUN_ID
BOOTSTRAP_TMP
```

解析顺序：

1. 若明确提供 `BANYAN_REFACTOR_CONTROL_ROOT`，优先使用；
2. 若已有明确属于本次改造且安全的 Control Root，可复用；
3. 否则默认候选：

```text
${REPO_ROOT}/.banyan-refactor/
```

但在创建 Repo 内 Control Root **之前**，必须先在 Repository 外的系统临时目录捕获 Pre-stage 状态。

推荐：

```text
${REFRACTOR_CONTROL_ROOT}/stages/00/${RUN_ID}/
```

其中：

```text
.banyan-refactor/
= bootstrap workspace
≠ Banyan Core
≠ 正式 Project Instance
≠ 正式 .banyan/migrations 真源
```

Stage 00 不修改 `.gitignore` 去隐藏它。

# 8. Protected Paths 模型

至少使用：

```text
IMMUTABLE_DURING_REFACTOR
READ_ONLY_DISCOVERY
STAGE_WRITABLE
CONDITIONAL_WRITE_LATER
SECRET_METADATA_ONLY
EXCLUDED_WITH_REASON
```

优先级：

```text
SECRET_METADATA_ONLY
>
IMMUTABLE_DURING_REFACTOR
>
READ_ONLY_DISCOVERY
>
CONDITIONAL_WRITE_LATER
>
STAGE_WRITABLE
>
EXCLUDED_WITH_REASON
```

注意：

- `EXCLUDED_WITH_REASON` 是 Discovery 决策，不等同于“可以随便改/删”；
- Stage 00 默认只允许 `REFRACTOR_CONTROL_ROOT` 为 Stage-owned writable；
- 正式 `.banyan/migrations/**` 在 Stage 00 仍属于 `CONDITIONAL_WRITE_LATER`。

---

# 9. Discovery Scope 与 Write Permission 分离

Discovery Scope 回答：

> 后续盘点为了不丢能力，哪些范围要读正文、只看 metadata、或明确排除？

Protected Paths 回答：

> 当前 Stage 是否允许写？

因此常见合法状态：

```text
SCAN = true
WRITE = false
```

这对业务代码、Canonical Docs、Legacy Governance 都很常见。

---

# 10. Hash / Integrity 原则

默认算法：

```text
SHA-256
```

至少记录：

```text
relative_path
kind
size
hash_or_redacted
tracked_state
protection_class
```

Hash 用于：

```text
Integrity
Before / After Diff
Rollback Evidence
Migration Verification
```

不用于复制项目正文形成第二真源。

规则：

- 不跟随 Repository 外 symlink target；
- Secret 只记录 metadata，不 hash 明文正文；
- vendor/node_modules/build/cache 等可排除，但必须有 reason；
- Stage 00 自己生成的 Control Artifact 不得污染 Pre-stage project baseline。

---

# 11. Dirty Working Tree 不是失败

Stage 00 不要求用户先“把仓库弄干净”。

如果 Dirty：

```text
tracked staged
tracked unstaged
renamed/deleted
binary changes
relevant untracked
ignored-but-governed
```

必须建立恢复覆盖。

正常目标：

```text
recovery.coverage = COMPLETE
```

如果：

```text
INCOMPLETE
→ BLOCK
```

`PARTIAL_APPROVED` 只有用户明确理解风险并批准时才允许继续，而且 Acceptance 必须显式记录，不得伪装为 COMPLETE。

# 12. Secret 安全

Secret / Token / Credential / Private Key：

允许记录：

```text
path
exists
classification
recovery_mode
owner_hint（若真实可知）
```

禁止：

```text
读取正文
echo
复制到普通 checkpoint
写入报告
写入 Hash manifest 的明文
```

如果重要未提交 Secret 改动没有安全恢复路径：

```text
BLOCK / NEEDS_INPUT
```

# 15. Stage 00 不自动 Rollback

Stage 00 建立：

```text
Snapshot
Hash Baseline
Checkpoint
Rollback Instructions
```

但不会为了验证“可回滚”而破坏真实工作区。

未来真正恢复前必须：

```text
生成 Restore Plan
→ 与当时最新状态比较
→ 确认不会覆盖后续用户工作
→ 获得必要确认
→ 执行最小恢复
→ 再验证
```

禁止默认：

```bash
git reset --hard
git clean -fdx
git restore .
git checkout -- .
```

# 17. Stage Handoff Contract

Stage 00 完成不能只看“文件生成了”。

必须同时满足：

```text

+
真实 ACCEPTANCE_REPORT.md
+
Bootstrap MIGRATION_REGISTER updated
+
Bootstrap BANYAN_REFACTOR_TRACE updated
+
Actual Artifact / Evidence registered
+

+

+

```

`NEXT_STAGE_HANDOFF` 至少：

```text
upstream stage / run id

unresolved risks

```

Stage 01 应优先消费 Handoff，不重新猜上游输出。

---

# 18. Stop Conditions

任一满足立即停止：

- Repository / Worktree / Submodule / nested repo 边界不可信；
- unresolved Git operation / conflict；
- 重要 Dirty 状态无法完整 checkpoint；
- 重要 binary / untracked / governed ignored 无恢复覆盖；
- Secret 只能通过明文复制才能恢复；
- Control Root 与已有关键资产冲突；
- Pack checksum/结构失败；
- 必须做破坏性 Git 操作才能继续；
- 任何业务/Canonical/Legacy 正文发生非预期 Stage 00 写入。
