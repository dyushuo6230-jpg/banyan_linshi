# Stage 02 冲突处理方案（候选）

本方案消费 Stage 01 的 31 项问题登记；不修改 Legacy、不宣布争议已裁决。完整逐项的来源、候选 Owner 与后续动作见 `CONFLICT_RISK_REGISTER.yaml`。两项 HIGH 在相应语义激活前必须解决；Stage 02 只建立可检验的处理路径。

## CON-001：知情决策题数和项目覆盖

现有通用提示词要求高影响每轮 1 项、低影响每轮最多 2 项；项目 `DEC-042` 还定义一组最多 5 题及现码可收口时自决。候选架构把“完整解释—初选—影响复述—有效确认—受控应用”作为 `DecisionSession` 的不变量，把题数、项目例外、当前决策状态放进 Project Instance Policy Overlay。这个分离不等于自动选定冲突赢家，也不允许较宽松的项目上限绕过高影响确认。

Stage 05 应提供同一批次的高/低影响、已确认/未确认、现码可收口/不可收口案例，让项目规则与通用安全底线逐条对照。存在适用性或优先级歧义时 `DECISION_REQUIRED`，停止状态变更；不靠模型偏好或文件时间戳裁决。Stage 07 用旧规则回归验证，Stage 19 证明实际问答能力无损。

## CON-002：项目入口、指南与进度真源不一致

README/AI 指南的 PRD 版本、进度和目录描述，与看板/登记现状不同。候选 `ContextRecovery` Contract 返回每条事实的来源、版本、时间、适用范围和权威状态，显式标记 `STALE_AUTHORITY`；当前进度数值的候选数据源是 `PROGRESS_REGISTER.yaml`，看板仅作为人类阅读投影。README/指南是入口和流程说明，不因较早版本而自动重写，也不能凭旧文字授权代码或状态变化。

Stage 03 应冻结 Source Role 和引用状态字段，Stage 12 以当前事实与必要证据做恢复测试，并要求对冲突事实给出人类可读差异。正式项目文档的修订须经其原有治理路径；Stage 02 不触碰这些文件。

## 其余缺口和重复

- `GAP-001`：嵌套 pre-commit 指向缺失脚本，提交校验的存在与实际生效分开；Stage 05/15 再验证，不自动安装或运行。
- `GAP-002`、`GAP-006`：真实坏链接与待判断语义 ID 分开，Stage 03 审核有效版本、主题和消费方后修复。
- `GAP-003`：AI 作者身份、生成链和可重建性未知；Stage 03/09/10 完成来源图谱之前，保留所有产物原位。
- `GAP-004`：视觉循环的进行中、叫停与回退保持原始运行语义；Stage 09 的 Runtime 映射不能伪升成功。
- `GAP-005`：16 组精确 Git Author 身份不自动合并；Stage 03/05 定义贡献身份和提交来源时保留原始历史。
- 22 组精确重复及 symlink 别名只标识关系；分别审查消费者和权威版本，没有删除或合并许可。

每项风险的激活前门禁、后续负责阶段、证据引用在 `CONFLICT_RISK_REGISTER.yaml`。本阶段“完成设计”不解除这些未裁决问题。
